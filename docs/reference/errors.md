# Error contracts and diagnostics

This page defines the public semantic and Core error families, canonical wire codec, transfer-hook classification, and local I/O diagnostics.

## Semantic error wire and SDK projection

Rust `core/foundation/c2-error` owns the canonical error registry (`ErrorCode`, `ErrorSide`, `ErrorStage`) and the versioned `C2E1` JSON wire envelope (`version`, `code`, `name`, `message`, `details`). Python and PyO3 exchange structured fields directly without an in-process `C2E1` round-trip. The Rust server callback still uses `CrmError::UserError(Vec<u8>)`, tracked with the [server callback work](../design/backlog.md). Python generates `c_two.error.ErrorCode` (`IntEnum`, matching Rust variant names) and read-only `CCError.side` / `CCError.stage` metadata directly from `_native.error_registry()`. Do not reintroduce `ERROR_Code`, `CCError.serialize()`, `CCError.deserialize()`, `_native.encode_error_wire()`, `_native.decode_error_wire_parts()`, `CoreError.error_bytes`, or `server/reply.py`.

Both Python error families (`CoreError` and `CCError`) inherit from `CCBaseError`, which exposes a read-only `transport_phase: Literal['pre_dispatch', 'dispatch_uncertain'] | None` established by Core (matching Rust `c_two::Error::transport_phase(&self) -> Option<TransportPhase>`). Outer transport facts take precedence over arbitrary peer semantic details; an error escaping a resource method that already ran (`CallStatus::Failed` over IPC, HTTP 500 from a relay, or same-process invocation) strips inner `transport_phase`, `dispatch_phase`, `fallback_eligible` and `route_withdrawal` entries. A downstream admission refusal therefore carries no outer retry or route control.

Python exposes 19 public exception classes (`CCBaseError`, `CoreError`, `CCError`, `ResourceExecutionError`, `SerializationError`, and 14 routing/admission/protocol subclasses):

- `ResourceExecutionError` (`ErrorCode.ResourceFunctionExecuting`, code 3, `side='resource'`, `stage='execute'`) reports an exception raised by a resource method, stream generator or resource cleanup. When a Python or Rust resource raises an explicit `CCError` / `Error::Semantic`, its original semantic code, message and business details are preserved (with inner dispatch phases cleared) instead of being overwritten with code 3. Server-side unknown method indices (`RouteAdmissionError::UnknownMethod`) never enter the resource and are refused as `NotExecuted` with `ProtocolViolation` (713).
- `SerializationError` accepts only the six codec and buffer-view codes (`1 ResourceInputDeserializing`, `2 ResourceOutputSerializing`, `4 ResourceInputFromBuffer`, `5 ClientInputSerializing`, `6 ClientOutputDeserializing`, `8 ClientOutputFromBuffer`) and exposes `side` (`'client'` or `'resource'`) and `stage` (`'serialize'`, `'deserialize'` or `'from_buffer'`). Transfer hooks classify by the actual failing operation rather than retention mode: opening a FastDB payload buffer (`Payload.open_copy` / borrowed view construction or invalidation) uses `from_buffer` (codes 4 and 8), while spec digest checks and Python `pickle` decoding use `deserialize` (codes 1 and 6). Client input encoding failures carry `transport_phase='pre_dispatch'`. Output decode and buffer failures occur after a response arrives and carry no transport phase, even when a codec invokes another resource. On any `from_buffer` or decode failure before a caller receives a retained value, release the native `memoryview` and buffer owner immediately so local-copy stats do not retain stale holds. Server-side pre-dispatch frame or request-storage validation failures use `ProtocolViolation` (713, `NotExecuted`), and post-execution unary response write-buffer capacity failures use `CallCapacityExceeded` (717, `Failed`), matching server streams.
- Code `7 ClientCallingResource` (`side='client'`, `stage='call'`), `705 RegistryUnavailable` and `712 RouteWatchUnavailable` remain in `ErrorCode` and project to base `CCError` rather than dedicated Python subclasses. Native `CoreError` instances without a semantic code pass through unary and stream client wrappers unchanged instead of being re-wrapped into client adapter codes. Explicitly closed `CRMProxy` handles fail every entry point locally with `ResourceClosed` (`transport_phase='pre_dispatch'`).

Relay duplicate registration returns HTTP 409 with semantic `ResourceAlreadyRegistered` (703), which Python projects with its canonical relay refusal message while keeping the native `CoreError` (and its rollback receipt) as `__cause__`. A duplicate within the same process is a local validation error. Failed relay preparation aborts the reserved local route; later registration failures retain their concrete rollback outcome. See [contracts and routing](contracts-and-routing.md#registration-mesh-resolution-and-peer-state) for the ownership rule.

Generated FastDB adapters in Rust, Python and TypeScript retain a structured external cause in the appropriate client or resource stage error. Its detail fields are `cause_owner=fastdb`, `fastdb_code`, `fastdb_symbol`, `fastdb_path`, `fastdb_message`, and `fastdb_details_json`; values come from the official FastDB error object. Generated Python `ContractClient` methods normalize FastDB input/output errors to `SerializationError` and project semantic `CoreError` causes on custom bound clients. Code generation failures retain the binding path and FastDB's code, symbol, path, message, and details JSON as separate `CodegenError::FastDb` fields. Consumers should branch on these fields rather than parse display text.

Route errors distinguish not found under the current route authority, including a route a relay has withdrawn (`ResourceNotFound`, 701), temporarily unreachable through a transport failure while the route is still current, or held only by relays that are Suspect or Dead (`ResourceUnavailable`, 702), closed (`ResourceClosed`, 707), and removed (`ResourceRemoved`, 708). A name that more than one relay holds with a live registration answers a new acquisition with `RouteConflict` (719, HTTP 409, before dispatch); `ResourceAlreadyRegistered` (703) also refuses a name that a peer holds. 702, 703 and 719 carry `registrations`, a JSON list of the holding registrations with `relay_id`, `relay_url`, `registered_at` and `relay_status`; Python raises `RouteConflict`, Rust reports `ErrorCode::RouteConflict` and generated TypeScript throws `C2RouteConflictError`. Codes 704 (`RouteStale`), 706 (`WriteConflict`) and 711 (`RouteCatalogCompacted`) are retired and are never assigned again. `ContractMismatch` (709), `IdentityMismatch` (710), `ProtocolViolation` (713) and `FallbackDenied` (714) are semantic refusals; business requests refused at a relay with `RouteWatchUnavailable` (712, HTTP 503) before upstream dispatch include `dispatch_phase=pre_dispatch`. A transport failure carries `PreDispatch` or `DispatchUncertain`; only the former is eligible for automatic fallback. An endpoint I/O failure alone does not withdraw a route. See [route bindings and fallback](contracts-and-routing.md#route-bindings-lookup-and-fallback). A call that the server refused before it entered the resource ends with the IPC 16 status NotExecuted and is pre-dispatch, with its canonical code and details kept: Rust `c2_ipc::IpcError::CallRejected`, Core and Python errors with `transport_phase == 'pre_dispatch'`, a relay HTTP response whose status follows the code (404 not found, 406 call mode mismatch, 410 removed, 413 payload over route limit, 409 contract or identity mismatch, 503 closed, unavailable, watch-unavailable or over capacity, otherwise 502) with `dispatch_phase=pre_dispatch`, including a removed, closed or other-contract route that the relay learns of while it acquires its upstream, and the generated TypeScript `C2IpcTransportError` with `transportPhase` `pre_dispatch` and `retrySafe` true. A call whose mode differs from its method's mode in the contract is refused this way with `UnsupportedCallMode` (716) and the details `call_mode` and `method_mode`. Pre-dispatch only makes a retry safe; C-Two does not retry or replay the call itself. After a pre-dispatch refusal of a missing, removed or closed route, or of another contract, the connection's next call acquires the route again by name.

`CallCancelled` (718, Python `CallCancelled` and `ErrorCode.CallCancelled`) is the outcome of a server stream whose cancellation has finished: it is reported only after the stream's cleanup has run, with status NotExecuted, and so pre-dispatch, when the stream never entered the resource, and with status Failed otherwise. A real error from a running step or from the cleanup is kept instead. When Runtime shutdown, route unregistration or the shutdown of the relay forwarding it ended the stream, the message names that cause; a client that did not cancel the stream itself and receives `CallCancelled` learns that the server or the relay ended it. A relay that is shutting down refuses a new stream call before dispatch with `CallCancelled` naming relay shutdown. When an IPC client cannot reserve a stream item because it is longer than the whole client domain memory budget, the consumer receives `CallCapacityExceeded` as a dispatch-uncertain failure, since the resource already ran. Over HTTP, a stream whose upstream call the relay lost before its CALL_END ends with a FAILURE record, which the client reports as the relay's dispatch-uncertain error, `ResourceUnavailable` (`transport_phase == 'dispatch_uncertain'`); a response body that breaks the [stream record rules](contracts-and-routing.md#server-streams-over-http) is reported as `ProtocolViolation`, and a body that ends before its terminal as a transport failure, both dispatch-uncertain.

## Public CoreError and local causes

Python Core errors are defined and typed by the public `c_two.error.CoreError` class, sharing `CCBaseError` with semantic `CCError` and retaining `RuntimeError` ancestry. When a `CoreError` carries a private immutable semantic snapshot, its read-only `semantic` property constructs a fresh, independent `CCError` instance on each access. Python and PyO3 use that snapshot even if callers edit the public diagnostic fields. PyO3 imports that same class; do not restore `_native.CoreError` or add a compatibility alias.

Local bind and connect diagnostics follow the original error chain and lifecycle watch. `IpcError::Connect` retains `EndpointIoError`; server bind failures retain `EndpointBindCause` through `ServerFailure.bind_cause`. Core exposes `LocalIoCause`, and Python projects `io_operation`, `io_kind`, `raw_os_error`, and the bind-only `endpoint_unverified_reason`. Preserve the original OS kind and code inside directory context while retaining outer policy refusals. Deadline, handshake, and contract errors must not gain fabricated local causes. These fields do not authorize retries, restart, or cleanup; do not add an error cache or infer the operation from transport phase.

The public `CoreError` category literal includes `protocol_version_mismatch`. Its `local_protocol_version` and `peer_protocol_version` are nonzero on that category and `None` on every other error. The [IPC handshake specification](ipc-handshake.md) gives the precise terminal behavior and error fields. The [local endpoint lifecycle reference](local-endpoint-lifecycle.md#public-structured-python-errors) lists all public structured fields and native cause projections.

Generated TypeScript clients read every native failure from the structured error of the [C ABI](c-abi.md), never from its message. A failure that carries a transport phase becomes `C2IpcTransportError`, whose `transportPhase` is `pre_dispatch` or `dispatch_uncertain` and whose `retrySafe` is true only before dispatch; a resource error without a phase becomes `C2CoreError`. Both keep the canonical code, name and details, and a protocol version mismatch keeps both versions. They do not read streams over HTTP yet: a stream method reached through relay HTTP forwarding fails before dispatch with `UnsupportedCallMode` (716).

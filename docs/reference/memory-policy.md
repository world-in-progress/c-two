# C-Two transport memory policy

This reference covers allocation, admission, accounting and release for C-Two-owned storage. See [configuration](configuration.md) for capacity settings, transport constants and the geometry derived from them.

## Role-domain budgets and call slots

Each Runtime has independent `client` and `server` domains. A standalone relay has one `relay` domain across all forwarding transactions and upstream connections. Every active domain has a memory budget `M`, a file spill budget `F` and an outstanding-call limit `N`. `M` accounts for native storage such as SHM backing, in-memory reassembly, server request copies and queued chunk work, and the call inputs, HTTP bodies and forwarding windows C-Two reserves. `F` accounts for temporary file-backed reassembly. Each memory or file charge follows the lifetime of its actual storage. Peer mappings, application allocations and SDK values can contribute to RSS beyond these charges.

Every remote client call, including a unary call without a deadline, holds one client slot until its real terminal. Incoming calls and same-process Python calls hold server slots. A relay forward holds one relay slot through upstream terminal and response body completion or drop. A slot is granted immediately or refused with `717 CallCapacityExceeded` and `stage=call_execution_admission` (HTTP 503 at the relay). Zero `N` closes new business admission, including calls carrying no bytes. [Execution admission](runtime-lifecycle.md#execution-admission)

A topic subscription holds one business slot of its role domain for its whole life, with no new slot configuration ([ADR 0005](../decisions/0005-publish-subscribe.md)). The reservation runs through the internal subscription guard: with `N ≥ 2` long-lived subscriptions occupy at most `N − 1` slots, keeping at least one slot free for ordinary control and unary calls once transient calls complete; `N = 1` admits one total operation; `N = 0` refuses every subscription. A refusal is the same immediate `717 CallCapacityExceeded` with `stage=call_execution_admission`. A relay's shared topic upstream is one forwarding work item for all its downstream subscribers, and the last downstream's slot stays reserved until the upstream cleanup completes, so a relay with `N = 1` can still admit a first subscription.

## When a reservation can wait

The first reservation can wait within the call's deadline for client input before serialization, a complete client stream item before sending CREDIT, a client's HTTP unary response body, or the relay's combined reservation of input and upload and download windows. An unlimited call may wait without a time bound. A reservation larger than the whole budget fails immediately. Growing an existing reservation uses `try_reserve` so that partially reserved calls cannot wait on capacity they hold themselves. Expiry while waiting reports `CallDeadlineExceeded`. Byte admission failure reports `CallCapacityExceeded` with `stage=payload_buffer_admission` on the call buffer path and preserves the transport phase.

New SHM segments, incoming reassembly, server request copies and pending chunk bytes use immediate reservations. A relay refusal before admission sends a control response without waiting for memory. If its `try_reserve` fails, it uses a bounded static control response. Client input reservations end when the transport has sent or copied the input. HTTP response owners retain their byte charge for the lifetime of the buffer, including a hold. IPC response holds retain local copies observable under `holds`.

## Lazy allocation and transport fallback

Buddy mappings are created on demand (scaling up to `4 × 64 MiB` at a `1 GiB` role budget and `16 × 64 MiB` at the `16 GiB` default). The pools start with zero prewarmed segments and may return to zero after 60 seconds idle. A new segment charges its backing once to `M`. Allocations that reuse its blocks incur no new backing charge. Idle reclamation refunds the segment. Each role domain also maintains a bounded warm local buffer pool (`RecycledBytes`, buffers `>= 256 KiB`, at most 4 buffers capped at `min(M, 2 GiB)`) that reuses receiver-side local copy buffers across calls without keeping retired domains alive (`Weak` domain reference) and evicts immediately whenever memory admission needs headroom. A dedicated segment uses `M` until its loan settles and its mapping is freed. Before creating new SHM backing, the allocator checks the mapping against 0.8 of the OS-reported available memory. Reuse remains possible under pressure. A successful sparse mapping does not guarantee that future writes can commit pages.

IPC uses inline frames for payloads up to 16 KiB. Larger payloads can use buddy or dedicated SHM. When SHM fails to allocate or cannot represent the payload, the sender uses inline where the payload fits or checked chunks of up to 128 KiB. An SHM descriptor identifies its slot, generation, offset, size, kind and loan ID. The receiver opens the exact mapping lazily, copies the bytes and releases the loan.

On Windows, named pipe session facts and the negotiated directional capabilities govern peer mappings. Across sessions, the transport uses owned bytes, inline frames or chunks when Local SHM is inaccessible. Local reassembly can still use its own budgeted storage.

SHM 4 segments carry no header: data starts at offset 0, the format comes from the handshake, and each segment's kind and generation are part of its OS name. The bitmap, live records, counters and lock stay with the owner, so a segment does not describe itself. A receiver checks a descriptor's range once against the actual OS view span with checked arithmetic. Peer mappings are read-only; only the owner maps a segment writable, and its local lock serializes allocation without waiting on a peer, application code or I/O. Logical sizes still round up to the allocation level, and trimming preserves the original release capacity. IPC 18 uses the [fixed preamble and call records](ipc-handshake.md) with SHM 4 and C/FFI ABI 10; retired handshakes, SHM layouts and ABIs are rejected.

Topic publishing reuses that single-owner discipline for 1-to-N delivery. `publish()` encodes the value once into one sealed immutable block — buddy or dedicated SHM charged once to `server.M` when the frame exceeds the inline threshold, otherwise a budgeted inline buffer — and small frames, empty frames and the SHM-unavailable fallback carry the same sealed value inline or in chunks without re-running the business serializer. Each granted local subscriber whose previous SHM loan has settled receives an independent `loan_id` on its own connection pointing at the same block; a subscription connection has at most one unsettled topic SHM loan, so the next SHM frame waits for the previous release. A borrower that has not copied, does not read its connection or blocks the release path keeps its loan exactly as the call-path rule above states, and the host reclaims the block only after its frame has left the topic's bounded history ring and every published loan has settled. Topic history never spills to `F` implicitly: a new frame that cannot be stored within budget fails `publish()` immediately with `717 CallCapacityExceeded` (`stage=topic_publish`), keeping the previous frame and consuming no sequence number.

Receiver reassembly reserves chunk storage and arrival metadata before use. It tries in-memory storage charged to `M`. If memory is unavailable or the SHM pressure check refuses the mapping, reassembly can reserve a temporary file mapping directly from `F`. The two budgets do not charge the same backing twice or require an advance reservation of `M` to use `F`. The advertised route limit on the client and the Host payload limit on the server bound each complete value. Resources receive complete values.

Before accepting an inline or single-frame `OPEN` into the active call table, the server reserves the request's local bytes against `M_server`. For a chunked request, the receive loop reserves each frame's payload plus its queue node before copying inline bytes. It refreshes the input activity timestamp and queues the frame on that request. The server schedules at most `C` blocking copies across requests in rotation. Continuations become eligible once the first chunk publishes reassembly storage. Each frame's charge ends as soon as its copy finishes.

When reassembly is complete, the server charges the request's local `Vec<u8>` to `M_server`. An exclusively owned memory mapping can return its prior charge atomically when the local copy takes over. Buddy backing and file spill charges follow their owning storage. The transport lease ends before the resource method runs. [Payload lifetimes](payload-lifetime.md#dispatch-and-transport-ownership)

A request that fails admission or reassembly before execution receives one `NotExecuted` outcome. An incomplete assembly expires 60 seconds after its last chunk enqueue or copy activity, with a 5-second scan interval. Input timeout tracking stops once all input arrives. Later frames for a closed request are discarded via the connection's [request-ID high-water mark](ipc-handshake.md#call-records-version-18), releasing any attached loans.

Rust callers free a local allocation with `MemPool::release_handle`, which consumes the move-only handle. A loaned block is freed only by its owner, when a release record or the connection's peer end settles the loan; nothing frees a block from peer coordinates. A receiver releases its reassembly storage as soon as it has copied the assembled payload. Mapped buddy segments retain their charge until idle reclamation.

Loans, release records and connection ends are described below. These paths never replay a business call.

FastDB content remains opaque at this layer. C-Two transports bytes or SHM coordinates and delegates nested payload specifications to FastDB Core.

`MemHandle` is the publicly exported low-level Rust move-only owner (with private fields) for buddy SHM, dedicated SHM and file-spill allocations. SHM authority is tied to a non-reused process-local pool identity; `PoolAllocation` and wire coordinates contain metadata, not ownership. Raw copy, free and dedicated-mapping adoption require explicit `unsafe` ownership and lifetime contracts; a raw pointer query alone grants no safe memory access. Transport callers use `alloc_shm_handle()`, which keeps `alloc()`'s GC and error behavior. A file-spill owner closes its mapping before its backing file, including Windows delete-on-close cleanup.

A received SHM descriptor is admitted once into a carrier bound to the connection's actual OS reference and mapping. The carrier copies the bytes, ends the remote read and hands its release to the connection, after which it can no longer be read; neither an SDK hold nor a borrowed input keeps it. Do not expose replaceable receive-pool slots or constructors that turn coordinates into a carrier. A sent SHM block enters the connection's loan book before its first byte is written: cancellation before that frees it locally, and afterwards the loan waits for the release record or peer end. Server callbacks receive a fixed `ResponsePool` owner; normal response preparation uses `try_prepare_shm_response`, and raw mutable pool access requires `unsafe`. Read access returns a mapped guard; an ordinary read guard can reveal its original writable lock through `RwLockReadGuard::rwlock`.

`c2-core` `LocalCopy*` accounting records metadata for the local copies kept by SDK holds and borrowed inputs, without reading payload bytes or allocating a second buffer; it has no authority over transport memory. Python export admission shares the local-copy owner boundary: `PyCoreResponse` and `PyCoreRequestBuffer` each check exports, release and tracking under their own lock. Active exports reject release before invalidation or removal, and tracking after release cannot revive a copy. View-release counter decrements remain atomic.

Each owner pool adds a fresh PID/UUID incarnation to its logical label, and only `MemPool` derives bounded OS backing names, which carry the incarnation, kind, slot and generation; SDKs must not append suffixes. The handshake exchanges only the prefix and the real directional SHM capabilities, with no segment list or announcement; a receiver opens the exact prefix, slot and generation lazily when a descriptor arrives. A `loan_id` is unique within the lending process (a checked counter that never uses 0), while loan books are kept per physical connection, so an ID from another connection is unknown here. A release frame carries loan IDs only; a zero, unknown, duplicate or already released ID is a protocol violation that deactivates the connection without undoing releases already settled. A slot is reused only after its local allocation and loan are clear; an exhausted generation retires only that slot, and when every slot has retired, transfers fall back to chunks or file backing without changing pool, prefix or connection. Dedicated indices never wrap beyond the wire's `u16` range.

Python no longer exports manual `c_two.mem.ChunkAssembler` or `MemHandle` wrappers or their `_native` names. Automatic IPC chunking remains in Rust's `ChunkRegistry` / `ChunkAssembler` / `ReassemblyBacking` chain, while Rust memory-pool APIs remain available. Do not restore Python consumed/released wrappers or aliases for the retired manual entry points.

Fallback uses the existing IPC inline/chunk and SHM paths; do not introduce a third transport stack. Capacity-limit failures propagate through the transport layer’s existing error paths; do not add a retry queue for refused allocations.

## Call outcome retention

`HostOutcomeStore` keeps a pair of Host-wide queues in settlement order. `settled_fifo` counts all settled entries against `outcome_max_entries`, including empty successes, successes with no retained response, and failures retaining only an error code. Evicting its oldest entry removes that call outcome. Pending and executing calls use business call capacity and stay out of both queues.

`retained_fifo` contains only entries with positive retained bytes. Byte-budget eviction and pressure shedding remove the oldest retained bytes while preserving terminal metadata. A successful response then reports `evicted`. A failed call retains its code and reports that its error details are unavailable. A response that exceeds `outcome_max_retained_bytes` on arrival reports `not_retained`. At a zero byte budget, metadata and successful empty responses can still be recovered or queried according to their available fields. [Host configuration](configuration.md#role-domains-and-sdk-configuration)

Inline response buffers count by their actual allocated capacity. Retained errors count by the allocated capacities of their message and detail keys and values. Both count against `server.M` and the retained byte budget. Sealed SHM counts by the allocation's actual size against the retained byte budget, with its backing already charged once to `server.M`. Original and attached callers share the immutable response or error owners, including through eviction. SHM delivery takes a separate loan for each receiving physical connection. For clients without SHM access, the writer reads the sealed response in slices for inline or chunked delivery. Delivery failures leave the recorded outcome intact.

The Host calls `shed_for_pressure` after an allocation or reservation returns a capacity shortage that shedding can relieve. The store removes retained owners in FIFO order up to the requested byte shortfall or until the queue is empty, then drops them outside the store, pool and budget locks. The affected allocation can retry at most once. Empty, oversized or unrepresentable allocations without a capacity shortage do not trigger shedding. This applies to the Host's input, reassembly, local copy and response allocations, as well as stream items and topic publication in the same role domain. Outstanding readers or loans may keep a removed owner alive, so shedding does not guarantee that the retry succeeds. [Call outcome lifecycle](runtime-lifecycle.md#keyed-unary-call-lifecycle)

## Setting budgets

Set client and server capacity independently before their roles activate. The same three fields are available on an explicit Python Runtime, and the environment variables provide defaults for roles without overrides. [Configuration](configuration.md#role-domains-and-sdk-configuration)

```python
import c_two as cc

cc.set_client(memory_budget_bytes=128 * 1024**2, max_outstanding_calls=128)
cc.set_server(
    memory_budget_bytes=256 * 1024**2,
    file_spill_budget_bytes=512 * 1024**2,
    max_outstanding_calls=256,
)
```

### Standalone relay

```bash
c3 relay --memory-budget-bytes 134217728 --file-spill-budget-bytes 268435456 --call-max-outstanding 128
```

The relay reserves its input and both windows in one admission step. The entry reservation supplies a `ReusableWindow` for the response. Each slice keeps its portion of the window until its `Bytes` owner releases it, and the next slice can reuse that space without taking a fresh reservation from the shared domain. This applies to multi-chunk unary responses and stream items. The full window reservation returns to `M` once the response and its outstanding slices release it. This allows download to progress while the forward still owns the upstream response. [Relay forwarding](contracts-and-routing.md#relay-payload-forwarding)

A relay's topic hub composes each upstream frame once into a single shared immutable frame, charged once to the relay domain's `M` and `F` regardless of how many downstream subscribers fan out from it; the upstream is one shared IPC 18 subscription with the internal `skip` policy, so a slow downstream never withholds upstream progress. Under budget pressure the hub sheds disposable history first, then skips frames no downstream has begun, and only then terminates a stalled TCP downstream singly at a record boundary. [Relay topic forwarding](contracts-and-routing.md#relay-topic-forwarding)

## Statistics and payload lifetime

`cc.observe.memory_stats()` returns `client`, `server`, `retired` and `holds`. Each role has the fields `domain_id`, `generation`, `frozen`, `closed`, `memory` and `file_spill`. Before activation, `frozen` is false and `domain_id`, `memory` and `file_spill` are `None`. Each byte cell reports `limit_bytes`, `used_bytes`, `peak_bytes`, `rejected_allocations` and `rejected_bytes`. Waiting alone does not count as a rejection. The retired entries identify their original role while a real accounting owner remains. `holds` gives `active_holds`, `total_held_bytes`, `oldest_hold_seconds` and `by_direction` for local copies kept by holds and borrowed inputs. Hold bytes are logical bytes and may describe storage already charged to a budget.

`cc.observe.call_execution_snapshot()` returns `client`, `server` and `retired`. Each role reports `max_operations`, `used_operations`, `peak_operations`, `rejected_reservations` and `closed`. An inactive role has `None` for its counters. Rust `Runtime` observes both itself and its associated Host through the same role structure. Both snapshots are read-only and perform no environment reads, domain creation or freezing.

`cc.hold(proxy.method)(args)` returns a `HeldResult` with `.value`, `.unsafe_buffer` and `.release()`. Use explicit release or a context manager; `__del__` is the fallback. For a portable method, `.value` is a FastDB `Payload` owner. A hold owns only a local copy, because the transport memory is released right after the copy. Release invalidates that owner and its checked views, then frees the local buffer. Materialize values through FastDB before keeping them beyond the hold. `unsafe_buffer` permits raw views whose exported pointers or NumPy aliases cannot be mechanically invalidated. See [Python payload usage](python-usage.md).

The FastDB invalidator is marked attempted before entry and runs at most once, including when it raises or Rust unwinds. After invalidation starts, `.value` and `.unsafe_buffer` stay inaccessible. An active export rejects release before invalidation; release the extra view and retry. A view already released during that attempt is never restored. Manually supplied `HeldResult(release_cb=...)` callbacks remain once-only user callbacks. The primary error and the cleanup cause remain in the existing exception chain on Python 3.10.

A borrower that has not copied, does not read its connection or blocks the release path keeps its loans: the owner reuses a published block only after its release record or the connection's peer end, never after a wait or timeout. Peer end means the read side's own end: EOF, or a read error reporting that the peer has closed (ECONNRESET or EPIPE on Unix, 109 or 232 on Windows); a local cancel, timeout, write failure, ordinary I/O error or DISCONNECT does not settle loans. When the read side fails without proof of an end, the remaining loans stay in the original pool until it is destroyed. A process that inherited the connection keeps it alive until its last copy closes. Copy-then-release limits loans to calls in progress and their release window, but it is not a byte limit and does not isolate one connection's traffic from another's; when the shared pool is full, allocation falls back through dedicated SHM, inline or chunked transfer and file reassembly, and returns the original capacity error without truncation when every budget is exhausted.

A prepared SHM reply becomes a loan once it enters the loan book before its first byte. A later write failure, deadline or cancellation leaves it to the release record or peer end and never frees peer-visible storage early. Fill errors, panic, cancellation while waiting for the writer and failure before the write begins free the block locally; an inline/chunk fallback cannot hide their original failure.

`cc.shutdown()` does not invalidate the local copies of SDK holds; they stay readable until released. Backing charges remain in retired domains while a real owner keeps them. A zero charge and the removal of an observation record can occur at different times; the weak observation disappears after the last actual owner is gone. Statistics do not keep pools, connections, Runtimes, callbacks or payloads alive.

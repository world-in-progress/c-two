# Runtime lifecycle

This reference owns native Runtime sessions, Python binding projections, registration, startup, connection deadlines, shutdown, and connection observations.

## Runtime authority and Python bindings

Runtime configuration is owned by Rust Core and projected into SDKs through the native session. Rust `c2-core::Runtime` owns its instance server identity, canonical `ipc://` address derivation, server IPC override storage/projection, direct IPC client acquire/release, client IPC config projection/freeze, route registration transactions, unregister/shutdown transaction outcomes, relay projection, relay-backed name resolution, explicit HTTP relay contract validation, and low-level HTTP client pool projection. Python exposes that authority through its native `RuntimeSession` projection and may expose typed override facades, but must not keep separate `_server_ipc_overrides`, `_client_config`, `_client_ipc_overrides`, `_pool_config_applied`, server-id, server-address, direct `RustClientPool` or `RustHttpClientPool` authority, `_http_pool`, `_rollback_registration`, relay control-client caches, or independent route unregister/shutdown ordering authority in `registry.py`. Python still owns Python CRM local bindings and invokes `@on_shutdown` callbacks exactly once from native structured outcomes.

Path: `sdk/python/src/c_two/transport/`

The Python transport layer is a thin orchestration shell around a Rust-native core. Python handles CRM registration, Python callback dispatch, serialization orchestration, and same-process direct-call glue. Rust handles IPC, wire framing, SHM, response allocation/transport selection, route concurrency enforcement, runtime session state, HTTP relay transport, and relay-aware route fallback. Response allocation must enforce native IPC payload limits before allocating owned fallback buffers, skip buddy SHM when buddy wire metadata cannot represent the payload, and use checked chunked fallback rather than truncating frame or chunk metadata.

| File | Purpose |
| --- | --- |
| `registry.py` | Public `cc.Runtime()` owns independent Python bindings over one native session; module-level registration, connection, shutdown and setters use the default Runtime. `cc.close(proxy)` follows the Runtime that created the proxy. |
| `wire.py` | `MethodTable` for Python resource method dispatch |
| `server/native.py` | `NativeServerBridge` exported as `Server` |
| `server/scheduler.py` | `ConcurrencyConfig` facade plus thin native route-concurrency adapter for same-process direct calls |
| `server/reply.py` | `unpack_icrm_result` and `wrap_error` |
| `client/proxy.py` | `CRMProxy` for thread-local, IPC, and HTTP modes |
| `client/util.py` | Thin native-backed `ping()` and `shutdown()` probes for direct IPC |

`registry.py` asks native `RuntimeSession.ensure_server_bridge()` for the server bridge, `RuntimeSession.acquire_ipc_client()` for direct IPC clients, `RuntimeSession.connect_explicit_relay_http()` for explicit HTTP relay clients, and `RuntimeSession.connect_via_relay()` for relay name resolution. It consumes native unregister/shutdown outcomes before mutating Python local bindings. Do not reintroduce `_relay_control_client`, `_relay_control_address`, `_relay_control_client_for()`, `_http_pool`, direct `RustHttpClientPool.instance()`, or direct construction of `RustRelayAwareHttpClient` in `registry.py`.

An explicit Python `Runtime` owns its code overrides and native session; it does not inherit the default Runtime's code overrides. Process environment and `.env` remain common resolver inputs. Instance `start()` uses the existing native readiness/PONG path, including for an empty Host. `cc.serve()` alone manages process signals for the default Runtime; explicit instances are shut down by their callers. A completed shutdown replaces that instance's native session under the existing handoff rules; old event subscriptions stay with their old source. Custom endpoint directories remain application-owned. Do not add a Runtime context manager, `Runtime.serve()`, a global instance registry, or automatic directory deletion.

Failed Host startup cleanup is observed through the concrete attempt's existing `ShutdownTransaction` receipt. NativeSession retains it under its original Host ownership lock, preferring it over an empty hostless result or an older Host outcome; pending and terminal-with-error are distinct. Release the Host lock before reattaching the Python GIL. Do not add a Python pending/closed state, a second cleanup transaction, or a scan that merges historical outcomes.

## Transport projections

Transport modes:

- Thread-local: same-process `cc.connect()` returns a zero-serialization proxy. It passes Python objects directly and may use the native route-concurrency handle through a thin Python adapter; do not route this path through Rust bytes dispatch for symmetry.
- IPC (`ipc://`): Rust `c2-local` owns local streams (Unix UDS or Windows byte-mode Named Pipes), while `c2-mem` owns POSIX SHM or Windows named mappings. `c2-config::LocalEndpoint` derives the OS endpoint from the logical address; SDKs must use that authority. Remote IPC concurrency semantics and route capacity limits belong to Rust `c2-server`; Python only projects the native handle for same-process calls. The RPC IPC handshake is version 15 and opens with the permanent fixed 25-byte version preamble (see `docs/reference/ipc-handshake.md`): native identity checks precede the preamble, un-negotiated CALL/ordinary-CTRL frames are fenced until the final metadata ACK, a complete `VersionMismatch` is a typed terminal error with no route/HTTP fallback and no retry, and older handshakes (0.10.x and earlier wheels) are incompatible with no compatibility path.
- HTTP (`http://`): relay-based cross-machine transport through Rust.

## Execution admission

An IPC server has one `max_pending_requests` semaphore shared by all accepted connections. It bounds complete remote CRM calls admitted for execution, counting active and queued work; `max_execution_workers` separately bounds callbacks actively executing across that server. Each route has its own native `max_pending` limit for active and queued calls and `max_workers` limit for active callbacks. Calls wait for execution capacity while pending capacity remains; exhaustion of pending capacity rejects a new call before its callback runs. Waiting for route or global execution capacity does not occupy a blocking callback thread.

A server stream keeps its call slot from OPEN until its cleanup ends, while each resource step and the cleanup take a route permit and an execution worker only while they run. The first step runs under the reservation OPEN made; each later step and the cleanup reserve the route again at its tail under the same admission token, so a stream waiting for demand, storage or budget holds no permit and no worker, and other calls to its route run between its steps. The setup, steps and cleanup of one stream run one at a time. A same-process Python stream steps under the route's own concurrency limits, without the IPC pending and worker pools. The [server streams](ipc-handshake.md#server-streams) section gives the wire rules.

Runtime shutdown and route unregistration end the open streams of their routes between steps, both IPC streams and same-process Python streams; they do not start a separate kill path. A step that is running finishes and the item it produced is still sent, then the cleanup runs, and the stream ends with `CallCancelled` whose message names shutdown or unregistration. The shutdown or unregistration completes only after that cleanup, and stays incomplete for as long as a step, the cleanup or the delivery of an item is stuck, for example while the consumer has stopped reading. Unary calls are unaffected: shutdown, deactivation and eviction still let calls already sent finish and reply.

On the client, a stream call holds one `max_outstanding_calls` slot from its start until its real terminal, also without a deadline. Its deadline covers encoding, admission, decoding and the whole iteration; it is not reset for each item, and its expiry ends only the caller's wait. Dropping the stream handle submits CANCEL without waiting; `close` submits CANCEL and then observes the original call record within its own budget, 30 seconds by default, unbounded with no budget and a single observation with zero, and reports whether the cleanup has finished, the real outcome and the count of complete items. A stream that the server cancelled reports `CallCancelled`, never a natural end. A stream method reached through a relay's HTTP forwarding fails before dispatch with `UnsupportedCallMode`; a route the relay resolves to local IPC streams normally.

The route's read/write policy is shared by same-process calls and remote IPC calls. Reads may run together, writes are exclusive, and scheduler reservations behind a waiting writer cannot overtake it. There is no separate per-connection write barrier; order follows from when each call reserves its route. Every IPC call reserves its route in the connection's receive loop, in frame order; a chunked request does so at its first chunk, before its chunks are copied in a separate task. Under `exclusive` and `read_parallel` a later call to the same route therefore cannot run before an earlier write, whether either call is chunked or not. Under `parallel`, calls may overlap and finish in any order, and calls to different routes have no order. The receive loop takes the route from the dispatcher under a short lock that registration never holds while it prepares a contract or does I/O, so registering or unregistering another route does not stall a connection's reservations. Relay HTTP calls are forwarded as independent requests and keep no arrival order. Same-process calls consume the route limits but not the IPC server's remote execution thread budget. Connection teardown cancels remote calls still queued before callback execution and keeps active calls and their request owners in the drain observation. Incomplete chunk assemblies are bounded by the chunk registry and `max_inflight_chunk_frames`. The first chunk takes the route's pending slot and the server-wide pending permit; execution starts only after the whole request is assembled. A refusal before execution, such as a closed route or an assembly timeout, ends the call with the IPC 16 status NotExecuted; once the call has entered the resource only its own completion ends it. On the client, the connection's single writer assigns each call's request ID when it first commits the call, and the client keeps the call's record after the caller's deadline until the reply arrives, so a late reply and any SHM loan it carries are settled on the original connection; the [call records](ipc-handshake.md#call-records-version-16) give the wire rules.

Registration reserves a route before publishing it. The native commit gate keeps a relay-dependent reservation unavailable to direct IPC lookup and callback admission until relay publication succeeds; failure aborts the reservation through the route-close transaction and returns the structured rollback outcome. These admission and close decisions belong to Rust Core and `c2-server`, including the native handle projected to Python for direct calls.

## Connection deadlines

Optional connection deadlines belong to Core. `cc.connect(..., timeout=...)` creates one native `ConnectAttempt` before SDK binding locks; the same absolute deadline covers singleton/registry/local-slot/relay override waits, pools, OS connection, handshake and live route/relay acquisition. SDKs project the attempt and never restart its budget, implement their own timer or leave a waiting thread after returning. Omitted/None retains existing phase guards; zero expires before transport. A deadline replaces the fixed five-second OS connection and handshake guards and also bounds the namespace gate or pipe wait; generated TypeScript passes its `connectTimeoutMs` through the ABI 7 connect entries. Connect expiry uses `CallDeadlineExceeded` with `operation=connect`, `transport_phase=pre_dispatch` and `stage`; it cannot execute or replay a business method. Preserve healthy shared clients on waiter expiry and isolate partial control writes.

## Startup and readiness

Startup wait configuration also belongs to Core: Python `cc.set_server(startup_timeout=...)` and native `RuntimeSession` project seconds into `RuntimeOptions.server_startup_timeout`; explicit Rust `HostOptions.with_startup_timeout` wins, then the Runtime value, then the finite five-second default. Server options freeze atomically on the first Host start attempt, including failure, and pre-use session replacement must preserve the timeout. `ServerStartupTimeout` survives the lifecycle watch and projects as `CoreError.lifecycle_kind='startup_timeout'`, with stage and configured seconds; deadline failures have no OS cause. Native shutdown cleanup retains its own budget after startup expiry. Do not reintroduce a Python timer, readiness polling, or the `config error` label on a `ServerError::Failed`.

Server lifecycle/readiness belongs to Rust. Python `NativeServerBridge` may expose `start()`, `is_started()`, and shutdown facades, but must delegate readiness to native `RustServer.start_and_wait()` and native state projection. Do not reintroduce Python socket-file polling, `os.path.exists(socket_path)` readiness checks, or Python-owned `_started` authority. Each native start attempt must be fenced in Rust before readiness waiters run: reset stale `Stopped` / `Failed` lifecycle state and the one-shot shutdown signal, then observe readiness for that attempt. A Rust `Server` may only unlink its IPC socket path after that concrete instance successfully bound the socket; failed duplicate startups must not remove another server's active socket path. Bridge shutdown must still drive the idempotent native runtime barrier through `RuntimeSession.shutdown()` so the PyO3 runtime handle drains even when native lifecycle state is already stopped by an external direct IPC shutdown signal. That native runtime barrier is a lifecycle fence: after it returns, runtime-owned server work must be terminal (`Initialized`, `Stopped`, or `Failed`) so a following start attempt does not observe stale `Stopping` state.

`NativeServerBridge` (exported as Python `Server`) is bound to one `RuntimeSession` at construction. Identity, IPC overrides and relay settings belong to that session; bridge operations cannot replace it or select a per-operation relay anchor. Keep configuration preflight at bridge construction without retaining a Python config snapshot. `start()` has no timeout argument; the actual `shutdown(timeout=...)` budget and structured completion handling remain. Independent low-level hosts must configure their session explicitly; the process registry obtains its bridge through `RuntimeSession.ensure_server_bridge()`.

## Shutdown authority

Direct IPC `shutdown("ipc://...")` under `c_two.transport.client.util` is an admin/control-plane helper for high-privilege same-host supervisors. Trusted in-process `Runtime.shutdown()` / `cc.shutdown()` retains its authority. The helper returns `'initiated'` when a valid one-byte ACK arrives, `'absent'` when the operating system reports no listener, and `'unconfirmed'` when no request was sent within the deadline, the reply lacks the ACK flags, or a possibly delivered request was not confirmed (Rust `DirectIpcShutdownOutcome::{Initiated, Absent, Unconfirmed}`). A reply with the ACK flags but a malformed payload raises a protocol error. `'initiated'` proves initiation only, without proving that active callbacks have drained or shutdown hooks are safe to run. Completion and route close outcomes must be observed through `RuntimeSession.shutdown()` / bridge barriers or a future explicit wait helper. Future name-based or HTTP/relay-propagated shutdown must be designed as an explicit authenticated admin control plane with clear route-level vs server-level scope, not as a hidden normal RPC side effect.

## Session retirement

- For the Python SDK, explicit `Runtime.shutdown()` / `cc.shutdown()` starts the Core Runtime's single permanent retirement scope, sealing its client pool and refusing new register/start/remote-connect work; pending retains the old session and slots until a later SDK shutdown consumes the completed receipt and hands off a replacement. The zero/short caller budget does not cancel its driver. Expiry before handoff is `shutdown_wait_timeout` with stage and timeout details, not pending. Python instance-lock wait remains outside the deadline; after acquisition, Native Host, Core and pool waits share one absolute deadline. The connect publication check uses the original connect deadline and never retries; normal successful client reuse is unchanged. Low-level Rust/Native Host shutdown remains restartable and seals neither the Runtime's call domain nor its outgoing clients; only explicit retirement does, and a low-level shutdown with no Host completes immediately without retiring. Core exposes `RuntimeShutdownTarget` borrowing `Host`, `FailedStartShutdownReceipt` or `ClientsOnly`, `RuntimeShutdownReceipt`, and `begin_session_retirement(..., deadline) -> Result<_, LifecycleError>`; `retirement_receipt(deadline)` observes the same scope. Keep the `FailedStartShutdownReceipt`'s concrete cleanup role, and use `Host.shutdown_outcome_until(deadline)` for bounded observation of its existing journal. Listener closure, work drain and the local copies of SDK holds are distinct; HTTP-only retirement creates no IPC pool and promises no physical closure of every HTTP keepalive socket. Shutdown error projection and hooks run outside the binding lock; hooks run after replacement, and failed replacement retains original slots/journal. These Runtime retirement semantics do not depend on the IPC, SHM or C/FFI version.

- A server closes its listener only after accepted calls and their queued replies drain. A client that stops reading keeps that drain, and the listener's address, until it reads or its connection ends; shutdown reports `completed=False` meanwhile.
- Replacing, discarding or evicting a cached IPC client, in the SDK pool or in the relay, deactivates its connection: calls already sent still receive their replies, and the connection closes once they and its loans have settled. Explicit `Runtime.shutdown()` / `cc.shutdown()` deactivates the Runtime's outgoing connections the same way while its Host drains accepted calls; nothing in shutdown fails a call already sent. A thread waiting without a call deadline on a stopped server therefore keeps waiting after shutdown, and Python waits for non-daemon threads before exiting; bound such calls with `cc.with_call_options(timeout=...)`. When a client's connection ends, its server still finishes calls already in their resource method and drops accepted calls that have not started, as 0.10.1 did.
- An SDK shutdown returning `completed=False` retains the old bridge and routes as well as the session and shutdown slots until a later SDK shutdown consumes the completed receipt and replaces the session.
- A stopped or stuck peer that still holds loans keeps its connection unconfirmed: shutdown returns `completed=False` when its budget ends, Core keeps retiring in the background, and the session is replaced only after the peer releases the loans or its connection ends. Nothing lent to that peer is freed or reused before then. In 0.10.1 a client could abort such a connection at once because the shared allocator let the server free the blocks itself. Generated TypeScript `close()` likewise resolves only after the connection's loans settle; bound it with your own timer, for example `Promise.race`, where a peer may stop.

- `RuntimeShutdownReceipt` exposes `observe_until(deadline)` and `terminal_outcome()` after `Runtime::retirement_receipt(deadline)` retrieves the existing scope.

- The `runtime_retired` lifecycle error has no I/O cause, and Python numeric strings are no longer accepted as shutdown timeout inputs.

- Retirement refusal and shutdown-begin exception projection run outside the Python binding lock; shutdown hooks run outside it only after replacement.

- A failed-start result and later retirement outcome must be retained separately. Incomplete or failed cleanup must not be hidden by the startup exception; NativeSession observes the original transaction for that concrete Server, including terminal errors.

- The historical [public Runtime acceptance record](../acceptance/2026-10-28-public-runtime-acceptance.md) covers its original acceptance scope and does not itself validate the later Runtime retirement scope.

## Connection observations

Connection observations share the existing native terminal publisher. `Runtime.connection_events()` / `c_two.observe.connection_events()` includes managed outgoing and accepted IPC connections with a client/server side; it creates no host or configuration authority. Python waits only through `ConnectionEvents.recv()`, releases the GIL, and may close that subscription from another thread. Do not restore Python `wait_closed()` or its Core blocking bridge, or add per-connection observation workers. Snapshots and the existing Rust async close barrier retain their terminal metadata and no payload/transport ownership.

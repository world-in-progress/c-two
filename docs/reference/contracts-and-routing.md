# Contracts and routing

This reference owns CRM contract identity, portable bindings, and direct IPC and relay route selection.

## CRM contracts and releases

Path: `sdk/python/src/c_two/crm/`

- CRM contracts are interface classes decorated with `@cc.crm(namespace='...', version='...')`.
- Only methods in the contract are exposed remotely.
- CRM route contracts are identified by route name plus the CRM namespace, CRM name, CRM version, ABI hash, and signature hash. Python may compute the descriptor/fingerprints from the CRM class, but Rust `c2-contract` validates the complete expected route contract at IPC and relay boundaries.
- A persistent CRM contract release is a Rust-validated `ContractReleaseRef` derived from canonical `c-two.contract.v2` content. It never contains a route name. `ExpectedRouteContract` is derived later from a validated release plus a runtime route name.
- Resource implementations are plain Python classes and are not decorated.
- Portable methods declare zero or one input and zero or one output with `@cc.transfer(input=FASTDB_SPEC, output=FASTDB_SPEC)`. Their Python parameter and return type is `fastdb4py.payload.Payload`; C-Two embeds each nested specification as an opaque JSON value and delegates it to FastDB Core.
- Python-only fallback values use pickle and must not be treated as portable descriptor or codegen inputs.
- Current source uses FastDB 0.3.0; published releases keep the FastDB version recorded in their release notes. Python FastDB payloads require the optional `c-two[fastdb]` extra, pinned to `fastdb4py==0.3.0`. Ordinary imports, CRM definitions, calls and error wrapping must not import FastDB or NumPy. The dev group selects the extra for full tests; native Core/Rust pins are independent.
- FastDB retained response owners are selected by call-site `cc.hold(...)`; server-side borrowed inputs are selected only by `cc.register(..., input_lifetime={...: 'borrowed'})`.
- CRM methods can use `@cc.read` or `@cc.write`; writes are the default.
- `@cc.topic` declares a resource-owned publish/subscribe topic on the contract: zero parameters, no access category, exactly one published output, and no resource-side implementation. See [publish-subscribe topics](#publish-subscribe-topics) below.
- `@cc.transfer(input=..., output=...)` is the only portable FastDB binding authoring surface. `@cc.transferable` and `@cc.transfer(buffer='hold')` are obsolete and must not be reintroduced as codec or lifetime selection mechanisms.
- `@on_shutdown` marks one public CRM contract method as a shutdown callback. The resource implements it normally; registration rejects implementation-only shutdown markers. It is not exposed through RPC.

## Portable contract v2 and artifact composition

The `c-two.contract.v2` descriptor has exactly `schema`, `crm`, `fingerprints`, `methods` and an optional `topics` at its root. Rust validates CRM identity, unique ordered method names, read/write access, explicit parameter and return shapes, exact binding keys, and the derived lowercase SHA-256 fingerprints. An absent input binding requires no parameters; a FastDB input binding requires one payload parameter with a missing default. An absent output binding requires a `none` return; a FastDB output binding requires a payload return. Variadic parameters are outside the portable shape. Method order fixes transport method indexes. A method may carry `"mode": "server_stream"`; unary methods omit `mode`, and any other value is rejected. A server-stream method needs a payload return, which describes one item. The mode enters the ABI and signature fingerprints only for server-stream methods, so unary contracts keep their fingerprints. Code generation supports server-stream methods for all three targets (Rust, Python and TypeScript, including ordinary and held client stream methods). Server streams travel over direct IPC, relay-selected local IPC, and (for Rust and Python clients) a relay's HTTP forwarding, see [server streams over HTTP](#server-streams-over-http); generated TypeScript clients consume streams over direct IPC and relay-selected local IPC, and refuse a stream method before dispatch with `UnsupportedCallMode` (716) when relay HTTP forwarding is selected. Rust treats each `fastdb` binding's `spec` as opaque JSON; FastDB Core validates its contents when code generation consumes it.

### Publish-subscribe topics

A descriptor may declare resource-owned topics ([ADR 0005](../decisions/0005-publish-subscribe.md)) in a root-level `"topics"` array. Each topic entry has exactly `name`, `output` and `binding`: `output` is fixed to `{"kind": "payload"}`, and `binding` is a non-null FastDB binding like a method's output binding. A topic has zero inputs and no `access` read/write category — it is not a method, resources never implement it, and publishing belongs to the registration's publisher handle. Topics must be sorted by name ascending; a duplicate topic name or a name colliding with a method is rejected, as is an explicit empty `"topics": []` — a contract with no topics omits the key. Because the key is omitted, every existing unary and server-stream contract keeps `descriptor_sha256`, `abi_hash` and `signature_hash` byte for byte, and an old parser rejects a topic-bearing descriptor as an unknown root key. Topics count toward contract admission (at most 256 topics, and their nested FastDB bytes share the cumulative nested-specification budget), and a contract with only topics and no methods is valid.

The ABI projection covers each topic's `name` and `binding`; the signature projection covers its `name` and `output`; re-declaring a contract's topic set is a contract change, not a registration parameter. Code generation supports topics for all three targets: Rust emits `subscribe_topic_{index}_{name}` client methods, a `TopicService` registration builder with per-topic capacity and initial-frame options, and `registration_topics(&Registration)` publisher accessors; Python emits `subscribe_topic_{index}_{name}` and `hold_subscribe_topic_{index}_{name}`; TypeScript emits the same pair over `TopicSubscribeOptions` and `C2TopicSubscription<T>`. Topic outputs share the digest-deduplicated payload composition with method bindings, and a topicless contract generates no topic symbols in any target. Python-private pickle topics — a `@cc.topic` member whose return annotation is not bound with `@cc.transfer(output=...)` — run only between Python peers on the language-local descriptor path and are refused by portable export with a diagnostic. See [Python usage](python-usage.md#publish-subscribe-topics) and the [relay topic forwarding](#relay-topic-forwarding) HTTP surface.

The ABI fingerprint covers CRM identity, ordered method names, and opaque input/output bindings. The signature fingerprint covers CRM identity, ordered method names, access, parameter metadata, and return metadata. JSON object key order is canonicalized for these outer hashes. FastDB's canonical specification SHA-256 remains a separate identity. Runtime choices such as hold, borrowed input, SHM coordinates and allocator policy do not enter the descriptor.

`c2-contract` bounds each externally supplied descriptor before and during parsing: 16 MiB source bytes, 1,000,000 JSON values, depth 128 with the root at depth one, 256 methods, and 16 MiB of cumulative canonical nested FastDB specification bytes. Every binding occurrence contributes to the nested total, including repeated equal specifications. `ContractError::LimitExceeded` identifies the metric, limit, observed value, and path. These control-plane limits do not cap call payloads.

`c2-codegen` delegates each nested specification to FastDB Core, retains the Core digest and structured error, verifies returned artifact hashes, and composes one deterministic tree for the selected Rust, Python, or TypeScript target. Equal FastDB specifications share a digest-named subtree. Artifact paths are relative, slash-separated ASCII with `[A-Za-z0-9._-]` segments; the composer rejects empty or traversal segments, Windows device names, case-folded duplicates, file/directory prefix collisions, and mismatched hashes. A path is limited to 1,024 bytes, a segment to 255 bytes, and each provenance owner/source field to 1,024 UTF-8 bytes. The default complete set is limited to 4,096 regular files and 256 MiB, with lexical path ordering. Publication writes and verifies a sibling staging tree and renames it to an absent destination. The destination parent must remain stable; publication promises atomic visibility, not power-loss durability or protection against hostile parent replacement.

## Core ownership and SDK parity

C-Two has a language-neutral Rust core and user-facing Rust and Python SDKs. Neither SDK is the canonical home for generic runtime mechanisms. The Rust SDK at `sdk/rust` is package `c-two`, imported as `c_two`, and is a thin facade over Core plus generated typed clients/services. The Python SDK owns Python domain logic, CRM authoring, Python resource invocation, serialization orchestration, and same-process direct-call glue. Rust `c2-core` is the single shared owner of route selection, client/host calls, retry classification, error normalization, transport lease ordering, and runtime lifecycle; the lower Core crates own memory, wire, contract, relay, and configuration mechanisms. PyO3/maturin projects that same Core into Python as `c_two._native`.

The Rust SDK may depend on the official `fastdb` Rust binding to adapt portable payloads, but `c2-core` must not depend on FastDB. Rust users continue to name `fastdb::Payload`; do not re-export it under a C-Two semantic namespace. Rust and Python must expose the same portable route, payload, error, and lifetime capabilities even when their language-level syntax differs.

## Direct IPC

Direct IPC is a complete standalone mode. `cc.connect(..., address='ipc://...')` must bypass relay discovery and remain usable when no relay is configured or a relay environment variable points at an unavailable server. Relay is only a discovery/forwarding projection above IPC; do not make relay the owner of IPC registration, scheduling, or connection establishment.

Python resource servers create an auto-generated `ipc://` address. Use `cc.server_address()` after registration only when a same-host process needs to connect directly.

## Relay discovery and forwarding

`C2_RELAY_ANCHOR_ADDRESS` sets the SDK process's relay anchor for registration and name resolution. Resolution may return a dialable `relay_url` for the route. For an iroh-only peer route, or an edge request that must go through the anchor, resolution returns `proxy_via_anchor: true`. The client uses the configured anchor base URL, preserving its scheme, port, TLS trust and reverse proxy path prefix. The anchor forwards to the route owner. The relay discloses IPC addresses and instance identity only on the control listener when the client is on loopback and its local endpoint namespace is compatible. Clients also verify that their anchor is local before selecting IPC.

The control listener (`--bind`) serves registration, administration and the local Mesh 9 peer endpoints alongside discovery and RPC. The edge listener (`--edge-bind`) serves health, route listing, resolve, probe, calls, outcomes, call cancellation and topic operations. A same-host reverse proxy uses the edge listener and receives the same discovery fields as a remote client. Both listeners share one route catalog and forwarding domain. [Relay CLI](../../cli/README.md#relay)

Relay resolution and data-plane calls are contract-scoped, not name-only. `cc.connect(CRMClass, name='...')` derives an `ExpectedRouteContract` from the CRM class and the route name. Runtime relay resolve, probe, and call paths must carry and validate the route name and complete contract identity. Do not add production APIs, fallback behavior, cache keys, or wire paths that resolve, probe, or call a CRM route by name alone. A future "find by name" or diagnostic relay-mesh lookup must be a separate discovery/admin surface that returns candidate route metadata and CRM tags; it must not be reused as the normal CRM call path.

Relay-discovered IPC fast paths must validate endpoint identity in Rust before accepting the IPC client. The relay response identity (`server_id` and `server_instance_id`) must match the identity returned by the IPC handshake, and then the requested route name must exist. Do not reintroduce Python-side or route-name-only trust decisions for relay IPC.

### Registration, mesh resolution, and peer state

The relay rejects a different process claiming a live local route name with HTTP 409 and semantic `ResourceAlreadyRegistered` (703). It probes an existing owner before replacement; a dead or route-missing owner may be replaced after the candidate passes IPC identity and route-contract attestation and a fresh final owner probe confirms the old state. Final commit fences the captured connection slot, owner generation, lease epoch, replaceability, and active-request count. Lease expiry alone does not surrender ownership, and owner freshness stays inside the owning relay rather than gossip. The relay also refuses a name that a peer holds, whether that peer is Alive or it currently sees it as Suspect or Dead, with the same `ResourceAlreadyRegistered` (703); the check runs again inside the final commit. Its details carry `registrations`, a JSON list of the holders with `relay_id`, `relay_url`, `registered_at` and `relay_status`, and the registration failure keeps them, so Python and Rust callers read them from the error. A rejected relay registration aborts or rolls back its local registration transaction. Without a relay, separate Hosts (including independent `cc.Runtime()` instances in one process) may register the same name; on the same Host a duplicate is rejected locally.

A relay keeps one control connection to each upstream server instance whose routes it serves and attests each of those routes again about every 50 ms. It withdraws a route that the server reports missing, removed or closed, or under a different contract (a route that registration has published but not yet opened counts as present), and it withdraws all of an instance's routes when a different server identity answers at that address. A transport error withdraws nothing; the relay reconnects after one second. A Host process that ends without unregistering therefore keeps its name at its relay and in the mesh. The name comes back when a restarted Host registers it again at that relay, which may replace the dead owner as described above, or when the deployer withdraws it with `POST /_admin/unregister` and a JSON body with `name` and `server_id` at that relay; the relay passes the withdrawal on to its peers, and the name can then be registered elsewhere. A route registered again on the server reaches the relay through registration, not through this check. A request the relay is still connecting upstream for when it withdraws or replaces that route reports the route fact rather than a connection failure: a withdrawn route answers `ResourceNotFound`, and for a replaced one the relay acquires the current registration once more before dispatch and answers `ResourceUnavailable` if it changed again; only while the same route is still current does a real transport failure answer `ResourceUnavailable`, and an authoritative refusal from the upstream is kept.

A route name has at most one live registration in a mesh. Resolution answers with that registration when its contract matches, and `ResourceNotFound` (701) otherwise. When more than one relay holds a live registration of the name, after a partition heals or because two relays accepted the same new name at the same time, a new acquisition fails before dispatch with `RouteConflict` (719), whose `registrations` detail lists them all; C-Two never chooses between them, and proxies that already hold one keep calling it. The deployer ends the conflict by unregistering one copy, and that copy's proxies then follow the one that remains. Each relay logs when a conflict appears in its view and when it clears, and `/_routes` (`c3 registry list-routes`) lists every registration with its relay status and marks conflicting ones. A relay that is Suspect or Dead keeps its registrations: they do not resolve, a name held only by such relays answers `ResourceUnavailable` (702), and the name cannot be registered elsewhere until that relay withdraws it after it comes back or a deployer force-leaves it; each relay judges reachability from its own view.

Mesh 9 (`PROTOCOL_VERSION = 9`) identifies a peer registration by route name, owning relay and registration time. It exchanges the relay address in joins, announcements, digests and full sync, and peers must agree on the protocol version. Loopback peers exchange Mesh 9 messages on the control listener. Across machines, the endpoints authenticate each other with a shared cluster secret over iroh before opening separate QUIC control and RPC data connections. The relay checks known membership, ownership and any claimed sender ID before applying peer updates, while keeping IPC address and server identity local to the owning relay. [ADR 0008](../decisions/0008-relay-tls-http2-and-iroh-mesh.md)

The `address` object in `/_routes` and `/_peers` includes at least one of `http_url` and `iroh`. The iroh address includes a 64-digit lowercase hexadecimal `endpoint_id` and may include the bridge origin in `bridge_url` and socket addresses in `direct_addrs`. Relays dial iroh peers behind NAT using these hints, prefer direct UDP and fall back to encrypted forwarding through the bridge. The registry CLI displays the HTTP URL when present or the iroh endpoint ID prefixed with `iroh://`. Error details continue to use their `relay_url` display string.

Because an unreachable relay keeps its names, force-leave is how a deployer releases them. A deployer can force an unreachable relay to leave the mesh with `POST /_admin/force-leave` (`c3 registry force-leave`) at any live relay. That relay accepts it only for a relay it sees as Suspect or Dead, forgets the relay together with its routes and tombstones, and sends `RelayForceLeave` to its live peers; a peer applies it only if it also sees that relay as Suspect or Dead and then passes it on. The declaration is neither retried nor remembered, so it stops where the relay can still be reached and also at a relay whose failure detection has not yet noticed the loss; the deployer repeats the operation there. A relay that has no live peer left joins a seed again and adopts the seed's view, including a force-left relay that the seed still sees alive. Force-leave is not a ban. A dead peer becomes eligible for recovery after it accepts `RelayJoin` as the expected relay over Mesh 9. The relays resume digest exchange to recover the peer’s registrations. If another relay registered the route while the peer was unreachable, new acquisitions report a route conflict. A force-left relay that restarts joins through its seeds; without seeds it starts alone, because no relay looks for it any more.

### Route bindings, lookup, and fallback

An endpoint connection is a carrier for calls to multiple routes on one server instance. A route-bound client retains its route name, complete expected contract and the way it was acquired; each acquisition verifies the server identity it reaches. Acquisition uses server `RouteLookup` authority rather than handshake data alone; calls carry `RouteCallIdentity`, the route name and contract identity, which the server checks before invoking resource code. Because the server admits a call by route name and contract identity, a route that the same server registers again under the same name and contract serves the clients that acquired it earlier. The route UID that tells registrations apart stays in the server's route catalog records and the relay's registration checks; it is not part of an IPC call, a relay request or response, or any client interface.

The server's dispatcher is the single route authority, projected by `RouteList` and exact `RouteLookup`. List improves visibility; lookup and call-time identity checks decide correctness. Route removal does not change an immutable `ContractReleaseRef` retained by a caller.

| Runtime route condition | Semantic result |
| --- | --- |
| No matching resource has been found | `ResourceNotFound` |
| A known resource is temporarily unreachable | `ResourceUnavailable` |
| An observed route was removed | `ResourceRemoved` |
| A route exists but rejects new calls | `ResourceClosed` |

Only a failure proven to occur before dispatch can trigger transport fallback or replay. A NotExecuted call end from the resource process is such proof, see [errors](errors.md); the relay treats an upstream NotExecuted for a missing, removed or closed route, or a contract or identity mismatch, as the same authoritative route fact it gets from route acquisition and withdraws the route. A failed verified local IPC acquisition may select an independent relay path; returning to the same failed local endpoint is denied. A local failure keeps the endpoint excluded; when no other route remains, acquisition reports `FallbackDenied` with that failure as its first cause. Contract, identity, and protocol mismatches are terminal. Every acquisition resolves the name at the relay; there is no shared resolution cache. When an acquisition's probe of the selected relay answers `ResourceNotFound`, the acquisition resolves the name once more. A relay-aware or explicit relay client sends each call to the relay it selected at acquisition and does not resolve per call; it keeps only that relay's URL, because the relay checks request lengths against the current registration, and it bounds response bodies by its client domain memory budget and the protocol message limit rather than by registration metadata. The relay admits a call by route name and contract identity, so a route registered again at the same relay serves the next call of an existing client.

A client follows its route name. Its views share a current target, and each call captures that target when it starts. Before a call hands its input to a transport, it acquires the route again when the captured target is known to be gone: the IPC connection ended because the peer closed or reset it, an earlier call received an authoritative pre-dispatch refusal for the route (not found, removed, closed, another contract or a route conflict returned to that call), or the client could not connect to its selected relay. Existing proxies whose own calls at their selected relay continue to succeed stay on that target even while a mesh conflict exists elsewhere; only a call explicitly refused before dispatch with `RouteConflict` (719) marks its target for re-acquisition on the next call. The acquisition repeats the original one under the calling call's own deadline, and concurrent calls share it: direct IPC returns to the same address, a relay-aware client resolves through its original anchor and may change between relay-local IPC and relay HTTP, and an explicit relay client stays on HTTP and resolves from its original relay URL; another client's acquisition never changes this client's target. A call that learns of the change only from its own refusal fails before dispatch and is safe to retry; the next call follows, since C-Two keeps no copy of the input for a possible re-send, because it would have to keep the input until the reply ([ADR 0003](../decisions/0003-server-streams.md)). Calls already sent keep their target and finish there. Identity and protocol refusals, admission denials (724), single-call metadata validation refusals (713 `stage=call_metadata_validation`), capacity limits, deadlines and resource errors do not start an acquisition, and a connection that ended on a protocol error is not reacquired. An endpoint context checks an explicitly supplied expected server identity on every acquisition; without one it accepts a new server instance at the same address. Generated TypeScript clients follow the same rules (including `ContractClient.withCallOptions({ timeoutMs?, metadata? })` views sharing the current target): each transport keeps one current target per route name and contract, shared by its clients, and acquires it again under the calling call's budget only when it is known to be gone; a relay-local target is acquired again through the relay, so the new endpoint context expects the identity that the relay reports, and a replaced endpoint stops admitting calls and closes after its calls finish. Their per-call observation reports the target that call was sent to. C-Two never automatically replays a call after possible dispatch. A call with an explicit call ID supports a separate outcome query or recovery. Transport I/O failures affect the endpoint connection and do not, by themselves, withdraw route authority.

### Relay payload forwarding

The HTTP relay validates the route, expected CRM contract, `x-c2-meta-*` call metadata headers, `Content-Length` and the upstream route's advertised `max_payload_size` before reading the request body. If the registration has changed before dispatch, it checks length against the replacement's limit. HTTP/1.1 drains an unread declared body for at most two seconds when needed to deliver a refusal. HTTP/2 sends the full error and ends the response, then resets any still-open upload with `NO_ERROR`. The bounded canonical `C2E1` error response (`<= 4 KiB`) uses an independent control error path and never waits for or borrows business domain memory `M`, so memory pressure cannot overwrite `718` or `724` with `717`. Known-length requests stream through the route-bound IPC call with checked size admission. Unknown-length requests are materialized up to the lesser of 64 KiB and the route payload limit.

Each forward takes one slot from the relay domain and reserves its input and transfer windows together. It keeps the slot until the upstream reaches its real terminal and the response body completes or is dropped. The download window stays reserved to that forward, recycling each slice's charge after the HTTP library releases the slice. The slice fits the reserved window and is at most the smaller of the fixed HTTP batch size (1 MiB) and IPC chunk size (128 KiB). An upstream SHM value keeps its read range until its final slice is copied. `c2-ipc` owns SHM allocation and release. Each anchor-to-source forward uses bounded streaming upload and download windows. It preserves a valid `Content-Length` and checks the route limit. Unknown-length uploads that exceed 64 KiB require a length and receive HTTP 411. The memory charge returns when the owner of each slice releases it. A forwarded call that may have executed is never replayed. [Relay memory policy](memory-policy.md#standalone-relay)

### Unary call outcomes over HTTP

`c3 relay` serves all data-plane calls, keyed outcomes and topic subscriptions on six unified `/_c2/*` paths, retiring the former `POST /{route}/{method}` and `POST /{route}/_topics/*` paths ([ADR 0006](../decisions/0006-post-dispatch-outcome-and-dedup.md), [ADR 0007](../decisions/0007-call-metadata-and-admission-hooks.md)). Each requires all expected contract headers (`x-c2-expected-crm-ns`, `x-c2-expected-crm-name`, `x-c2-expected-crm-ver`, `x-c2-expected-abi-hash` and `x-c2-expected-signature-hash`) and accepts optional `x-c2-meta-<key>` call metadata headers. Keyed submission, recovery and outcome query additionally require exactly one valid `x-c2-call-id` header.

| Operation | HTTP request | Body and admission |
| --- | --- | --- |
| Unary or server stream | `POST /_c2/calls/call?route=<pct>&method=<pct>` | Encoded input; `Accept: application/vnd.c-two.server-stream;version=1` selects server stream mode. |
| Keyed submission | `POST /_c2/calls/keyed?route=<pct>&method=<pct>` | Encoded input, subject to normal relay and route payload admission. |
| Recovery | `POST /_c2/calls/recover?route=<pct>&method=<pct>` | Empty body, with normal unary forwarding admission. |
| Query | `GET /_c2/calls/outcome?route=<pct>` | Independent control admission (`Q_ctrl`). On success, HTTP 200 with bounded `CallOutcome` JSON and `Cache-Control: no-store`. |
| Topic subscribe | `POST /_c2/topics/subscribe?route=<pct>&topic=<pct>` | Empty body with `Accept: application/vnd.c-two.topic-stream;version=2`. |
| Topic confirm | `POST /_c2/topics/confirm?route=<pct>&topic=<pct>` | Empty body; inter-relay `origin-only` late-join confirmation bounded by relay `Q_ctrl`. |

Call metadata `(key, value)` maps to `x-c2-meta-<key>: <value>`. The relay enumerates all headers to reject duplicate metadata keys and invalid keys, values or totals before upstream dispatch with HTTP `400` and `ProtocolViolation` (713, `stage=call_metadata_validation`, `dispatch_phase=pre_dispatch`). Generated TypeScript transports reserve the case-insensitive `x-c2-meta-` prefix for call metadata and never emit call metadata on `/_probe`, `/_resolve` or `DELETE /_calls/{token}`.

Percent-encode route, method and topic names as query values. Keeping names out of the path preserves names such as `.`, `..`, `/`, `_resolve`, `_probe` and non-ASCII names through URL normalization. For route names `.` and `..`, discovery uses `GET /_resolve?route=<pct>` with the usual contract query fields, and probing uses `GET /_probe?route=<pct>` with the expected contract headers.

For a remote route, the client contacts the relay URL selected at resolution. If it enters through the anchor, the anchor selects a single source relay and forwards with `x-c2-relay-origin-only: 1`. This applies to `/_probe`, ordinary and keyed calls, recovery, outcome queries and topic operations. The source validates the route and contract and uses IPC to reach the Host. An origin-only request for a peer route receives HTTP 502 with `ResourceUnavailable` (702) before dispatch, preventing forwarding loops. The anchor stops peer connection preparation if the downstream disconnects or the relay shuts down before dispatch; a unary call already dispatched continues to its real terminal state. A probe goes over the control connection and can cancel its dial or probe wait when the downstream disconnects. Outcome queries and topic confirmations use separate control capacity. Probes and stream cancellations do not consume business call slots. If a forwarded stream cancellation cannot be delivered, the anchor retries it against the same source and token while the original stream remains active.

The anchor preserves the source HTTP status and canonical `C2E1` error body and phase. It forwards the keyed call ID, metadata, the request body and the call's `Accept` header, and enforces the empty recovery body. Once sending to the source begins, a failure without a trustworthy terminal is `dispatch_uncertain`, and the anchor does not resend. Across all six `/_c2/*` routes, clients validate HTTP status, canonical `C2E1` error code and `dispatch_phase` together. A bare `404` or `403` without a matching canonical envelope remains `dispatch_uncertain`. [Call outcome errors](errors.md#call-outcome-errors), [admission errors](errors.md#admission-errors)

### Server streams over HTTP

A Rust or Python client calls a server-stream method through a relay with `POST /_c2/calls/call?route=<pct>&method=<pct>` and the header `Accept: application/vnd.c-two.server-stream;version=1`. The relay forwards it over IPC to its local route as a server stream and answers `200` with that media type and an `x-c2-call-token` header before any body (or a pre-200 canonical error such as `403` with `724 AdmissionDenied`). The body is a sequence of records, each a kind byte, a payload length (u64, little-endian) and the payload:

| Kind | Record | Payload |
| --- | --- | --- |
| 1 | ITEM_BEGIN | The item's total length (u64); an empty item is complete with this record |
| 4 | ITEM_DATA | The next non-empty part of the current item |
| 2 | CALL_END | Status: Success (0), Failed (1) or NotExecuted (2); Success and Failed carry the count of complete items (u64), Failed and NotExecuted a C2E1 error |
| 3 | FAILURE | A C2E1 error with `dispatch_phase=dispatch_uncertain`, sent when the relay lost the upstream call before its CALL_END |

One terminal record, CALL_END or FAILURE, ends the body. A Failed CALL_END may follow part of an item: the client discards that part, and the count covers complete items only. The HTTP codec limits terminal payloads to the CALL_END representation bound. Inline IPC errors are additionally bounded by the 1 MiB RPC frame limit. The client reads terminal payloads without waiting for a reservation of its domain memory. The client rejects an item length exceeding the stream wire representation bound (and checks each item against its client domain memory budget), ITEM_DATA beyond the announced length, an ITEM_BEGIN inside an unfinished item and a Success or NotExecuted CALL_END after part of an item, as a protocol violation reported as dispatch-uncertain (an item exceeding the client domain memory budget reports `CallCapacityExceeded`). HTTP carries no CREDIT: the relay asks its upstream for the next item only when the HTTP library asks for more body, so a reader that stops reading stops the resource only once the HTTP and TCP buffers between them are full; [Runtime lifecycle](runtime-lifecycle.md#execution-admission) gives how far a resource can run ahead.

The relay does not know a method's mode. It writes the mode the `Accept` header selects into the IPC OPEN, and the server compares it with the method's mode before the call enters the resource. A server-stream method called without the stream media type is refused with `406` and `UnsupportedCallMode` (716); a unary method called with it gets a `200` stream whose only record is a NotExecuted CALL_END with the same error. Both refusals are pre-dispatch: the resource does not run, the relay keeps its upstream connection, and the relay-aware client reports them as retry-safe.

`DELETE /_calls/{token}` submits cancellation for that one call and answers `204`; it answers `404` for an unknown token or once the relay has finished forwarding the call. The original response stays readable and ends with the real terminal and its count of complete items. The token is 128 random bits written as hexadecimal, valid only while the relay forwards the call, and gives no query, resumption or replay. A client that drops the response or closes its connection makes the relay submit the same cancellation, and that client reads no terminal; a client that only stops reading cancels nothing. Other calls on the same upstream connection are not affected. For a forwarded stream, the anchor binds its cancellation token to the selected source before sending the response headers and remembers cancellation that arrives before the source token. It sends the cancellation to that same source with `cause=consumer` or `cause=lifecycle`. HTTP 204 acknowledges submission; the original stream carries the terminal `CallCancelled` (718) with its cause and complete item count.

The Python SDK does not embed or start a relay server. Start `c3 relay` outside the SDK, through the CLI, Docker Compose, Kubernetes, or other orchestration. Do not add SDK APIs that embed, start, or manage relay-server lifecycle.

## Relay topic forwarding

Both topic operations require an empty request body. HTTP/2 checks DATA even if the request omits `Content-Length`. Nonempty DATA is refused with HTTP 400 and `ProtocolViolation` before dispatch. HTTP/2 receive flow control uses per-stream and connection windows derived from the relay memory budget. The connection window is 16 times the stream window, which starts at `M / 16` and is clamped to 16 KiB–1 MiB. Accounted payload and forwarding memory is within `M`; socket buffers, TLS and HTTP/2 frame overhead are outside it.

A relay serves topic subscriptions over HTTP with two-tier single-upstream fan-out (`Host → source relay A → anchor relay B → R clients`), removing both per-subscriber host serialization and per-subscriber cross-machine transfer amplification ([ADR 0005](../decisions/0005-publish-subscribe.md)). A Rust, Python or Node client enters through its anchor relay (in `relay_aware` mode `RelayAwareHttpClient` routes remote topics through the anchor rather than bypassing to the source relay) or an explicit relay:

- `POST /_c2/topics/subscribe?route=<pct>&topic=<pct>` with `Accept: application/vnd.c-two.topic-stream;version=2`, no request body, the topic headers `x-c2-topic-start` (`latest` or `next`) and `x-c2-topic-on-lag` (`skip` or `error`), optional `x-c2-meta-*` call metadata headers, and the same `x-c2-expected-*` contract identity headers as a call. The relay answers `200` with that media type, an `x-c2-call-token` header, `x-c2-topic-admission-required: 0|1` and `x-c2-topic-head-seq: <u64>` before any body (missing, duplicate or invalid values fail with `713`); `DELETE /_calls/{token}` cancels the subscription without metadata or admission checks, exactly as for a server stream. Ordinary client responses on both source and anchor relays expose no internal registration-association headers.
- The body is a sequence of records, each a kind byte, an 8-byte little-endian payload length and the payload: `READY(start_seq)` (kind 1), `ITEM_BEGIN(seq, total_bytes)` (kind 2), `ITEM_DATA` parts (kind 3) and one terminal record (kind 4) carrying status (`Failed` or `NotExecuted`), the count of complete items and a `C2E1` error. The subscriber computes `dropped` per item from the announced `seq` and its own expectation; the terminal carries the canonical error, including `SubscriptionLagged` (720) for a strict lagging subscriber, `AdmissionDenied` (724) for a refused subscription and `CallCancelled` (718) naming the cause.
- Hub hits never replace by-name resolution: each subscription resolves the route through the mesh view and checks conflicts (719) and unreachable holders (702) first.

For a local route, the source relay A opens exactly one upstream IPC 18 subscription per active registration and topic, driven internally with `skip` while retaining source sequence numbers, and composes each frame once into a single shared immutable frame charged once to the relay domain's memory and file budgets — every downstream receives references to that one copy. For a peer route known through the mesh, the anchor relay B opens exactly one cross-relay upstream subscription to A carrying the single-hop anti-loop header `x-c2-relay-origin-only: 1` and the hub creator's `x-c2-meta-*`, and fans out its own single budgeted copy locally to every downstream on B. A admits `x-c2-relay-origin-only: 1` only for its own local routes — refusing a peer route before dispatch with `ResourceUnavailable` (702) so a loop cannot form — and only on that inter-relay response emits `x-c2-topic-registration`, an opaque SHA-256 fingerprint over `(server_instance_id, route_uid)` that never exposes either raw identifier.

Each downstream keeps an independent cursor applying its own `start` and `on_lag` policy and computing its own `dropped`. Concurrent first subscribers merge into one upstream connection; the last downstream leaving tears the upstream down, and its forwarding slot stays reserved until upstream cleanup completes, so a relay with one forwarding slot still admits a first subscription. When the upstream Host advertises `CAP_ADMISSION_HOOK` (`requires_admission == true`), each subscriber is still admitted individually by the Host ([ADR 0007](../decisions/0007-call-metadata-and-admission-hooks.md)): the creator S1 opens the upstream with its own metadata and receives the atomic `head_seq` from IPC `READY` / `x-c2-topic-head-seq` without a second hook call; if S1 receives a private refusal (`724` or admission `717`), the hub marks `opening_abandoned`, removes itself from the hub table by `Arc::ptr_eq`, and wakes concurrent waiters to `RetryJoin` with their own metadata and original subscription slot. When `requires_admission == false`, late joiners retain the batched fast path: a merged IPC `SYNC` on A, or a merged `POST /_c2/topics/confirm?route=<pct>&topic=<pct>` from B to A. When `requires_admission == true`, each late joiner on A sends `AdmitTopic` on the hub's `IpcTopicSynchronizer`, while each late joiner on B sends `POST /_c2/topics/confirm?route=<pct>&topic=<pct>` (bounded by relay `Q_ctrl`, carrying `x-c2-relay-origin-only: 1`, `x-c2-expected-registration`, `x-c2-topic-upstream-token` set to the `x-c2-call-token` A returned for B's shared upstream, and the subscriber's `x-c2-meta-*`). A verifies the token and hub liveness before and after Host `AdmitTopic`, returning `718 CallCancelled` (`cause=route_unregistered`) for a replaced registration, `701 ResourceNotFound` for a gone route, and `707 ResourceClosed` only to B when its upstream token was revoked (never isolating A's local subscribers; `717` and `724` never isolate a shared hub). A terminal arriving from a replaced upstream cleans only its own hub instance.

Under relay budget pressure the hub sheds in order: disposable history first, then frames that no downstream has begun, and only then a stalled downstream is terminated at a record boundary or reset during a blocked frame. A mid-frame HTTP/1.1 reset aborts the connection without a chunk terminator. A mid-frame HTTP/2 reset sends `RST_STREAM(CANCEL)` immediately and keeps sibling streams open. A relay that shuts down immediately cancels its shared upstreams so the source relay and Host drain without waiting for unevicted stalled downstream readers, and ends its forwarded subscriptions with `CallCancelled` naming `relay_shutdown` after the frame selected last.

生产路径的判断如下。

1. **Body 所有权和准入发布。** [router.rs:1637](../../core/transport/c2-http/src/relay/router.rs:1637) 先让 HTTP handler 保留 Body，只把 oneshot receiver 交给既有 forwarding closure。`ForwardingDomain::spawn` 仍在同一 admission 锁内完成 reserve 和 TaskTracker 发布，失败立即丢弃 closure，成功返回后同步 `send(body)`，中间没有 await。正常 HTTP 任务取消不能插入这一同步区间；并发 close 也不会撤销已登记任务。固定依赖 tokio-util 0.7.19 的 `TaskTracker::close` 只置 closed 标志，不 abort receiver。因此两处 expect 在现有正常生命周期中有明确不变量支持；没有先 reserve 再异步发布导致 drain 漏掉任务的窗口。执行器强制销毁不属于正常 native close/drain 的完成保证。

2. **拒绝决定固定。** [router.rs:1657](../../core/transport/c2-http/src/relay/router.rs:1657) 在第一次 reserve 失败时构造完整容量 response，然后传入收尾 helper。helper 不持 RelayState、预算或 upstream client，不能再次 reserve、重新解析 route、执行 CRM 或关闭健康 IPC。原 Response 在 EOF、源错误、超长帧和超时后原样返回，仍为 HTTP 502 / 717 / envelope `pre_dispatch`。没有伪造已经收到的 SDK 错误，也没有改变 HTTP wrapper 原有 `DispatchUncertain` 或 POST 重放规则。

3. **时间、字节和公平性。** [router.rs:1678](../../core/transport/c2-http/src/relay/router.rs:1678) 只收尾已经通过原长度校验、没有 Expect 的已知长度 Body。一次 2 秒 timeout 包围整个循环；每个 frame 用 checked subtraction 扣减 remaining，第一处超额或错误立即停止，逐帧 drop，不聚合整包、不建立第二份 payload。每帧 yield 使连续 ready/空帧也让 timeout 和其他任务得到轮询，期限不会逐帧刷新。实现可在取得一个由 Body 源生成的超额 frame 后发现违规；它不承诺阻止下层源先生成那个 frame。正常 Hyper Content-Length 解码提供传输帧边界；恶意或错误自定义 Body 仍由总期限兜底。remaining 为零后继续确认 EOF，阻塞或空帧流最多占用同一收尾期限。

4. **取消、业务预算和 shutdown。** 收尾属于原 HTTP handler，没有新后台任务、线程、业务 permit 或重新准入队列；取消 helper 会直接 drop Body。已获准入的任务继续持有原 permit、input 和原生 forwarding 所有权，HTTP waiter 消失也不等于 native completion。原 [forwarding.rs:78](../../core/transport/c2-http/src/relay/forwarding.rs:78) 的锁和 task drain 语义未变，原 [server.rs:468](../../core/transport/c2-http/src/relay/server.rs:468) 仍先关闭准入、等待 forwarding，然后收尾 client 生命周期。该 drain 观察业务任务，并不证明所有 HTTP 拒绝 handler 或 OS 缓冲都已经归零。

5. **范围与性能。** 修复没有更改协议、路由能力、SDK API、错误分类、重试、内存 tier 或 ForwardingDomain 接口。成功调用新增一次小的 oneshot 所有权交接；拒绝路径新增最多 2 秒逐帧传输收尾和每帧调度让步。这是解决拒绝时 Body 被闭包提前丢弃的局部机制，未引入兼容分支或重复业务调度器。未做吞吐基准，因此不主张性能无损。每个拒绝 handler 有时间和累计输入界限，但没有新增全局拒绝连接并发上限；原 HTTP 连接并发和网络缓冲仍占用资源。

一个非阻塞表述问题：[router.rs:1693](../../core/transport/c2-http/src/relay/router.rs:1693) 的 “no allocation, decoding” 应理解为没有 C-Two 整包缓冲、payload 解码或 IPC 分配。HTTP 帧读取仍可能分配或复用传输缓冲；不能把该注释扩展为整个路径零分配的性能承诺。此项不要求扩大本轮生产修改。

测试审查没有发现删去强断言或接受错误结果来迎合实现。

- sealed 新增四组 Body 边界检查：Expect 与 unknown 禁止 poll；超额、提前 EOF 和源错误保留原 response 且释放 owner；pending 和无限 ready-empty 流受总期限限制；取消立即 drop owner。4 MiB in-process router 检查确实消费 64 个 64 KiB frame 并读取 EOF 后才回复。它证明生产 handler 的收尾行为，不单独证明 OS TCP 行为。
- 原公开 `RelayAwareHttpClient` eager case 保留：4 MiB owned input、无 Expect/Connection override、真实 resolve 和 POST、`max_attempts=3`、同 client 两个逻辑调用、每次仅一次 dispatch/POST、resolve 总计一次、完整 502/717/pre_dispatch、route 保留。仍明确不包含独立 connect-time probe。这个门禁曾在两种 Windows 上真实失败，现在仍要求 canonical response，未放宽为任何 transport failure 都算成功。
- Host 的 `DirectEagerRelease` 在 B 第一次 body poll 前确认拒绝计数 1，释放原 A permit 并观察预算归零，再完成 B；仍要求原容量 response、拒绝计数 1 和零预算。覆盖 operation 与 byte 两类满额，用相同 production router 和 ForwardingDomain；它属于进程内交错。
- Host 的 [real_http_capacity_freed_during_rejected_upload_never_dispatches](../../core/transport/c2-http/src/relay/forwarding_tests.rs:1017) 通过真实 TCP、真实 IPC server 和 production router 制造交错：A 的 target callback 已阻塞；B 无 Expect，发送 header 和 1 byte；拒绝计数为 1 后才释放 A；完整读到 A 200，观察预算归零且域仍 open，再完成 B 剩余上传。B 必须完整返回 502/717/pre_dispatch，callback 总计 `[0, 1, 0]`，拒绝计数仍 1，route 与同 Arc IPC 保留。这可识别清理期间容量释放后错误的再次业务准入。该 raw fixture 使用现有 `Connection: close`，输入为 8192 bytes；它补充真实交错，不替代上一项无 Connection override 的公开 4 MiB 客户端证明。catch_unwind 后统一释放并有界停止 fixture，没有用生产 close 提前掩盖重新准入。
- 原 Expect/100-negative、完整 chunked upload 断连、部分 frame 前缀失败、其他 RID、同 IPC incarnation、晚到 response carrier 释放及 drain/stop 检查保留。

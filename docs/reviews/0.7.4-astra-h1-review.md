## 原始失败与 Expect 改动的边界

`/tmp/c2-074-validation/e6-windows-failed.log:7467-7479` 显示 Windows 2025 的失败发生在附加容量 ping 的 response reader，实际收到 0 bytes，错误为 ConnectionAborted / 10053。没有取得完整 HTTP status 或 canonical error，不能将该结果记为容量语义拒绝。日志也不证明初始 HTTP 断连使共享 IPC 或 late response 清理失败；测试在这些后续断言完成前已于容量探针处终止。

旧 eager HTTP 请求是合法请求。其手写 fixture 顺序写 header、再写 body，携带 `Connection: close`，最后才读 response。生产 controlled HttpClient 则不设置 Expect 或 Connection，使用 reqwest 的正常并发 HTTP I/O 和 owned body；controlled builder 禁止隐藏 POST retry。两者不是同一种 I/O 调度方式。因此不能将旧失败直接宣称为“无效 fixture”，也不能把仅 Expect 路径变绿当成普通 eager SDK 已获 Windows 验证。

新的 rejection-only helper 广告完整 Content-Length 并发送 `Expect: 100-continue`，在服务器要求上传前等待最终拒绝，这符合 HTTP 对 header 可决定的提前最终响应的允许行为。[RFC 9110 §10.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.1.1) 同时，提前完全关闭 TCP 而仍有客户端数据到达确实可能令最后响应被 reset 丢失；这个风险并不使 eager 请求非法。[RFC 9112 §9.6](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.6)

本机固定依赖 Hyper 1.8.1 的 `proto/h1/dispatch.rs:204-214` 和 `conn.rs:848-863` 也表明：应用在 EOF 前丢弃 Body 后，Hyper 只尝试一次可即时完成的 drain，未完成时关闭 read 侧；Continue 状态在该清理分支跳过 100。这为旧 fixture 存在传输竞争窗口提供源码依据，但没有 Windows TCP/事件轨迹，本报告不把它写成该 10053 的完整、唯一原因。

## 没有削弱的证明

最初 output.patch 只替换了两处附加容量 ping 的发法。初始完整真实 HTTP upload、业务 callback entered 后的 socket drop、等待 native waiter detached，以及真实 8-byte IPC prefix 的另一取消场景都保留。原有断言继续验证：同一个 IPC incarnation、其它 RID 的成功响应、原 client 后续 ping、Arc identity、资源/owner 登记保持、输入 carrier 类型、late buddy/dedicated/file/chunk 的实际回收、操作/字节预算保持与最终 drain/stop。没有增加重连来遮掩 client 丢失，没有删除“不应提前释放”的检查。

`read_framed_reply` 仍要求完整、有限、无歧义的 Content-Length 或 chunked framing。新 helper 不重试；reset、EOF、超时仍失败，最终 status 必须为 502。100 的完整 interim response 被新增反例明确拒绝，不能冒充终态响应。旧读者对 1xx 的拒绝逻辑本就存在，新断言没有改变生产或放宽解析。

新增真实 TCP case 验证 operation slot 和 retained-byte 两种耗尽都返回完整 502/717/CallCapacityExceeded/pre_dispatch，且仅一次拒绝、已有容量 owner 不变、route 保留。另一个 `app.oneshot` case 的 Body 一旦被 poll 就 panic，验证生产 router 的容量拒绝发生在读取 body 之前。二者分别证明网络响应及应用处理顺序；后者不冒充真实 TCP 证据。

## 本次发现并补齐的 SDK 覆盖缺口

现有 `client/controlled_tests.rs:199-207` 的模拟 business handler 使用 `body: Bytes`，容量错误在 body 已被 extractor 读取之后才产生。其 capacity/no-replay 测试可以证明错误分类和缓存策略，无法替代生产 router 在未读 body 时返回容量错误的真实链路。生产 `router.rs:1636-1660` 则在 forwarding reservation 失败时直接返回 717 并丢弃 Body。最初 Expect patch 因而留下明确的普通 SDK proof gap。

我在 `/tmp` 的固定源码副本独立执行了两个对应探针：真实 controlled HttpClient 和公开 RelayAwareHttpClient；均以 4 MiB owned body、默认 chunk policy 调用生产 router，在实际请求 middleware 中断言没有 Expect 或 Connection header。operation 与 byte 两类耗尽都得到完整 502/717/envelope pre_dispatch，各自仅一次 dispatch。公开层使用默认 max_attempts=3，执行真实 resolve + POST；没有使用假的 HTTP capacity response。依赖版本与 Core lockfile 相同。日志分别是 `/tmp/c2-074-astra-h1-eager-probe.log`、`/tmp/c2-074-astra-h1-public-eager-probe.log`。

Host 随后把公开层门禁纳入同一测试 fixture：`controlled_eager_http_receives_production_capacity_rejection`（复核文件 `:391-394`，实现 `:501-578`）。每种容量条件下同一个 client 连续发两次逻辑调用；max_attempts=3，每次 dispatch 和真实 POST 只增加 1，resolve 总数保持 1。两次错误都保留 502、717 和 envelope pre_dispatch；route 与既有容量 owner 保持，最终完整释放并 drain 为 0。middleware 在真实入口核实没有 Expect 或 Connection。该门禁会随现有完整 c2-http relay suite 在 Windows full 执行。

这个 public case 没有单独调用 connect-time probe；它覆盖已构造公开 HTTP 客户端的 resolve/call 路径。它也没有假装完成一个成功的 IPC business call，因为提前容量拒绝正应阻止进入 upstream。原有真实共享 IPC/业务调用/late-owner 断言由原 disconnect cases 承担。

HTTP wrapper 的 `HttpCallError.phase()` 仍是既有 `DispatchUncertain`，canonical envelope 中服务端的 `dispatch_phase` 才是 `pre_dispatch`。这是原有 controlled capacity tests 和生产 error classification 的明确区别；新用例保留两者，并通过实际 POST 次数证明不重放。不能为使新测试通过而把 wrapper phase 改成另一语义。

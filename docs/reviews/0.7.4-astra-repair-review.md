## 新增清理机制的审查

`RetiredClose::claim_retry`（`pool.rs:551-561`）用 UnconfirmedIdle → Closing 的 CAS 认领重试。background settlement、普通 acquire/sweep 和 close_all 都使用该认领，单个记录的 retry barrier 不会由两方同时启动。记录在 detached client 从 cache 移除的临界区内已登记；保留 exact Arc/ticket 身份，未确认时继续可达，确认时才成为 Confirmed。没有增加按地址猜测关闭或释放 replacement 的路径。

worker 只执行 close，不继续 connect、route acquire、业务调用或 cache publish。独立的 5 秒预算属于清理工作，未重置已过期的连接预算。它只尝试一次，不自动循环；spawn 或 barrier 失败保留 UnconfirmedIdle，供后续 fresh acquire、sweep 或 drain 重试。因此长期被 native owner 阻塞时，系统仍可能保留 backing，但不会谎报已经停止或提前退款。Host 实际执行的 `connect_deadline_finite_settlement_preserves_unconfirmed_owner_for_maintenance` 覆盖 5 秒失败、重复调度排斥、保留 owner、解除阻塞后普通 sweep 收尾。

`wait_until_settled`（`:529-550`）按原绝对期限注册 record-local channel 并等待；到期无需重新取得全局 coordinator。注册后再检查状态、状态转换时取走并通知 waiter，封住完成与注册的竞态。native close 不在 global cache/coordinator 锁内运行；worker 的 prune 只 try_lock。普通 acquire 在开始新的 backing 分配前等待已有 Closing 记录，耗用同一个调用预算。新增的这一等待不进入健康 cache-hit 分支。已有维护 API 的锁获取并未被描述为硬实时承诺。

`close_retired_work` 先取得精确 client 引用，等待 native writer/receive/maintenance 等 close barrier 确认，之后移除该记录的 client Arc 并 drop 临时引用，再发布 Confirmed。这样即使 global coordinator 暂不可用，真实 backing 也能释放；残余 Confirmed 仅是待 prune 元数据。仍存活的 payload/held owners 通过自身 Arc 保持 backing 与预算，代码没有手工归零 accounting。原 epoch、domain、config freeze 和引用计数规则保持；已有 drain 在 Closing 未结算时继续报告等待/未确认。

线程成本须准确表述：这是每个成功认领的 retired 记录一个临时 OS worker，单个记录靠 CAS 去重；实现没有跨记录的固定线程数量上限。本轮确认了有期限、无自动循环、失败保留 owner 的行为，没有做高失败吞吐性能测试，也没有据此声称固定线程数或性能提升。在当前修复范围内未找到需要再扩展架构改造的阻塞依据。

新测试的目的与原缺陷一致。F3 使用真实 duplicate 和真实 rebind；ACL 用实际 chmod ACL，验证每个 grant、正例及 pinned-fd 更换；F2 除元数据/锁 seam 外还有真实 stalled handshake、真实 backing charge 和无 pool drain 的恢复。新的单位测试中“无关 cache 保留”检查的是 entry Arc/refcount/epoch，不应单独写成跨网络的 A 在途证明；已有完整 IPC/Relay 行为证据仍承担后者。未发现为了适配错误生产行为而删除关键断言。

# Live-reassembly admission and owned reservation carrier

This report records the reassembly-budget implementation slice for the accepted [memory budget contract](memory-budget-contract.md). Source base is `72b23e4` (finite owner-backing charges). This slice delivers: finite live-reassembly admission through `MemPool::budget()`, one owned reservation carrier (`ReassemblyBacking`) that survives completion, trim, queueing, and held responses until storage release is accepted, per-request first-chunk admission ordering on the server, and correlated structured errors on every chunk admission/feed failure path. A recovery repair (2026-09-26) fixed the four source defects the Host found after the original run ended plus one tautological test assertion; a second review repair on the same day fixed five server admission/ownership defects found in that first repair (stale-owner publication after abort, key-only gate removal, un-fenced capacity/duplicate refusals, leaked buddy blocks on the discard path, and unpublished work surviving cancellation). Each repair is described below and is evidence, not intent: every claim names the test that proves it and the run that executed it.

## Design

### Reservation carrier: `c2_wire::chunk::ReassemblyBacking`

One move-only RAII value owns, for the whole life of one reassembly allocation: the owner pool `Arc<RwLock<MemPool>>` (the only release authority for buddy/dedicated backing), the allocated `MemHandle` (file-spill mappings are self-owned by the handle value), and the `BudgetReservation` charging the pool's canonical reassembly cell for the full allocated capacity.

The creation seam is `ReassemblyBacking::admit(pool, total_chunks, chunk_size)`: geometry validation (zero chunk count, zero chunk size, checked `total_chunks × chunk_size` multiplication), then the reassembly budget reservation, then `alloc_handle` — all inside one pool write critical section, with the reservation guard held across the allocation so an allocation failure refunds the charge on the early-return drop. A budget rejection creates no mapping and only bumps rejection statistics; its message is the `BudgetError` text naming the cell, requested bytes, used bytes, and limit.

Release ordering is structural, not conventional: `release()` validates the handle through the pool, then asks the pool's release authority to release the allocation — `free_at` for buddy (the block returns to the allocator free list; the segment mapping is unmapped later by idle-segment GC or drop) and for dedicated (the entry is marked freed and its mapping is dropped later by `gc_dedicated`, after the peer's `read_done` or the crash-timeout fallback) — or closes the file mapping by dropping the `FileSpill` handle. Only after the authority accepts the release does the reservation refund. This is a **logical release**, not a claim that the mapped backing is physically unmapped at that instant: owner-created buddy/dedicated SHM backing stays charged in the `shm_backing` cell until the pool's segment/dedicated GC or drop actually unmaps it, while the reassembly reservation (the cell this slice adds) refunds as soon as the release is accepted. `Drop` does the same best-effort; if a drop-time release fails (corrupted coordinates), the reservation is deliberately `mem::forget`-ed — budget bytes stay charged rather than silently uncounting backing that may still be allocated. The reservation is not detachable: no accessor returns the `BudgetReservation` or a usable pool+handle pair, so callers cannot split the charge from the storage. `trim_to` shrinks only the logical length; the charge keeps covering allocated capacity, and the charge never refunds on `set_len`.

Because the carrier owns its pool `Arc`, a finished or held backing keeps the pool alive, its content readable, and its charge held after the registry, connection, or outer pool handle that produced it is dropped (proven at carrier level, see Proofs). That is the lifetime the contract requires; it is **not** a proven file-backed `HeldResponse` across an actual `Runtime` shutdown (see Deferred wiring).

### Assembler and registry

`ChunkAssembler` is rebuilt over the carrier. Its constructor takes the pool `Arc`, checks per-message limits (`max_chunks_per_request`, `max_bytes_per_request`) before any charge, then admits through `ReassemblyBacking::admit`. `feed_chunk` needs no pool argument (the carrier owns it). `finish()` returns the carrier with the logical length trimmed to `written_end`; on an incomplete assembly it returns `Err` and the dropped assembler releases storage through the pool authority and refunds the charge exactly once — fixing the previous hazard where `ChunkAssembler::finish` on an incomplete assembly (or a plain drop) leaked buddy/dedicated backing because the handle value alone never frees pool blocks. `take_handle` is removed; nothing needs it any more.

`ChunkRegistry::insert` keeps the advisory soft-limit GC sweep (warn, never reject; the hard bound is the atomic reassembly budget cell) and then constructs the assembler, so admission order is: soft-limit sweep → per-message limits → geometry → budget reservation → allocation. Duplicate keys are rejected under the shard lock and the newly admitted carrier is dropped, which releases storage and refunds once. On success `insert` returns a `ChunkAssemblyId` (key + monotonic generation) so rollback can address exactly the generation it admitted; `abort_id` removes an entry only when the stored generation matches, while key-scoped `abort` remains the connection-teardown/timeout verb. `FinishedChunk` now carries `backing: ReassemblyBacking` (plus route metadata) instead of a bare handle.

The registry counter hazard is fixed: `active_count`/`total_bytes` move with entry insertion/removal while holding the corresponding shard lock (`insert`, `finish`, `abort`, `gc_sweep`, `cleanup_connection`), and tracked assemblers are dropped outside the shard lock so backing release never nests pool locks under shard locks beyond the pre-existing shard→pool direction (never pool→shard, which is what would deadlock).

### Transport wiring and correlated errors

- `RequestData::Handle` (c2-server) and `ResponseData::Handle` (c2-ipc) now hold the carrier instead of a handle+pool pair. `RequestLease`/`ResponseLease` release Handle variants through `carrier.release()`; `ResponseLease` dropped its `reassembly_pool` field (the carrier owns the pool), so `ResponseLease::new` and `into_bytes_with_pool` are two-argument now. `HeldResponse` in c2-core needed no structural change: it already owned its `ResponseLease`, which now transitively owns the carrier.
- Server request path — admission ordering: the connection receive loop is the only wire-order point, so `chunk_frame_ordering` runs at frame dispatch. A first chunk claims a bounded per-request admission entry; a later chunk joins that entry and waits (async, per request) until the first chunk has established route permit, registry assembly, and stored route admission. This removes the earlier hazard where later chunks raced ahead of a first chunk that was still awaiting route admission and were then discarded as "no assembly" while the caller waited. The receive loop never awaits admission, control frames (PING, shutdown checks) are dispatched synchronously in the same loop, and the first chunk's route-admission await is `tokio::select!`-ed against `Connection::wait_cancelled()`, so disconnect tears the task, its chunk-processing permit, and its ordering entry down. See [Per-request first-chunk admission ordering](#per-request-first-chunk-admission-ordering).
- Server request path — errors: every malformed/feed/admission failure path answers the caller. Decode, SHM-read, zero-data, insert, duplicate route-admission, feed, and finish failures funnel through `fail_chunked_request`, which publishes the terminal admission outcome first (waking and fencing any owner still parked in route admission), then releases the assembly and the stored route admission (and therefore the route pending permit), and then writes the existing canonical structured error (`ResourceUnavailable` for capacity/admission/feed/finish, `ResourceInputDeserializing` for buddy/chunk-header/control decode failures). Route admission failures keep using the pre-existing `write_route_admission_error` canonical mapping (route-not-found/removed/closed/stale/contract-mismatch/method/acquire); if a concurrent terminal outcome already owns the reply the route-error write is skipped instead of double-answering. The receive loop's chunk-processing capacity refusal and its ordering refusal (duplicate first chunk / gate capacity) use the same terminal reasoning: they publish the abort, release any pending admission/assembly/route work for that request id, and then write the refusal. The budget rejection message keeps the cell/size detail (`chunked call reassembly admission failed: memory budget cell 'reassembly' rejected …`).
- Server request path — staged publication: the first chunk's registry assembly and stored route admission are owned by a `ChunkPublicationGuard` until the atomic admission commit succeeds. Cancellation, panic, a losing commit race, or a publish failure drops the guard, which takes the stored route admission first (while the assembly is still registered, so the key-scoped take cannot reach a successor's record) and then aborts the assembly through `ChunkRegistry::abort_id` (identity-checked, so it can never release a successor's same-key assembly). The registered assembly's `ChunkAssemblyId` is stored with the route admission, and `Server::abort_chunk_request` releases exactly that generation.
- Client response path: `recv_loop` handles control frames before data-frame dispatch (so ping keeps progressing while the client's data budget is exhausted), and every failed chunked reply now aborts the charged assembly *before* completing the exact correlated pending caller — malformed reply metadata, rejected first chunk (budget/geometry/duplicate first chunk), and any feed error (duplicate, oversized, unknown index). Capacity and the pending caller return immediately instead of waiting for assembler GC or disconnect. `finish` failure already released its entry inside the registry.
- Native FFI: `PyMemHandle` wraps the carrier; `release()` drops the carrier `Option` only after the pool authority accepted the release, so a released handle reports `len` as an error and `repr` as `MemHandle(released)` instead of looking live with length 0. On release error the carrier is preserved for retry. `PyChunkAssembler` uses the new assembler API, and the dead `PyShmBuffer::from_handle` plus its never-constructed `Handle` variant are removed (verified: no callers anywhere in Rust or Python).

### Per-request first-chunk admission ordering

`core/transport/c2-server/src/chunk_ordering.rs` holds the bounded gate. Decision point is frame dispatch in the receive loop: decode the chunk header (skipping the 15-byte buddy payload when the frame is buddy-backed), then (a) `begin` an owner entry when `chunk_idx == 0`, (b) `waiter` for a later chunk whose request entry is still pending, or (c) feed directly when no admission is pending (assembly already published, request already terminal, or a malformed header that the chunk task reports itself).

An entry has exactly one terminal outcome, published through an atomic single-winner transition (`try_publish`, built on `watch::Sender::send_if_modified`), so a refusal or abort that races the owner's commit can never be overwritten by `Admitted`, and two racing aborters cannot each believe they won. Outcomes: `Admitted` after route permit + registry insert + stored route admission; `Refused` when the owner already wrote (or is about to write) the correlated error reply; `Aborted` on disconnect cancellation, request-level abort, or owner teardown.

Every gate operation is bound to the exact entry identity. `ChunkAdmissionOwner::release`/`Drop` and `ChunkAdmissionReclaim::drop` remove only the entry they began (pointer-identity check under the gate lock), so a stale owner that was replaced or torn down can never remove a successor's same-key entry or wake its waiters. `begin` refuses while *any* entry exists for the key — pending or a terminal generation still tearing down — so a successor generation cannot start while an older generation's rollback is in flight.

An entry is a teardown fence with a small reference count: one for the owner plus one for each request-level aborter (`abort_key`) that is still releasing published state. The entry stays in the map until the last fence is released, which means a same-key successor can never begin mid-rollback and an old owner's rollback can never observe a successor's assembly or stored route admission. `cleanup_chunk_requests_for_connection` removes a closing connection's entries outright and publishes `Aborted` (no successor frame can arrive on that connection). A `Drop` guard publishes `Aborted` if the owner task disappears without a terminal outcome, so no waiter can be stranded. Waiters subscribe to a `tokio::sync::watch` value and return as soon as the outcome is terminal: `Admitted` proceeds to feed, `Refused`/`Aborted` stop silently because the admission owner already correlated the failure (or the request/connection is gone) — and release a buddy-backed frame's peer block before returning (see the review repair below).

The owner's route-admission await is fenced twice: `Connection::wait_cancelled()` for disconnect, and the admission entry's own terminal state (`terminal_waiter`), so a request-level capacity/feed/malformed refusal or a duplicate-first-chunk refusal wakes the parked owner and it publishes nothing. If a reservation nonetheless completes at the same instant, the atomic admission commit loses and the staged-publication guard rolls the generation back (below).

Bounds and backpressure: the receive loop already holds one chunk-processing permit (`max_total_chunks`, default 512) per dispatched chunk frame before it can create an entry, and an entry is removed as soon as admission is terminal and its fences are released, so live entries never exceed `max_total_chunks`; the gate also checks that capacity explicitly and answers `ResourceUnavailable` if it were ever reached. A waiting later chunk keeps its own permit, which is what bounds blocked waiters — a stalled first chunk can therefore occupy up to the configured chunk-processing capacity for its own later chunks. That is the pre-existing permit limit (the first chunk already held one under the old design), not a new unbounded queue: no task, queue, or map grows without the semaphore bound. PING/control dispatch and the frame loop itself are never blocked behind a stalled resource/route gate.

## Recovery repair (2026-09-26, first pass)

The original run ended with the Host reporting four real defects. Each was fixed narrowly, with a regression test that was then run against the unfixed source to prove it fails there (falsification log `/tmp/c2-repair-falsify.log`).

1. **Client aborts before completing the caller.** `recv_loop` previously removed the pending caller on a chunk feed error but left the charged assembly behind, and a malformed reply-chunk metadata frame was only logged and ignored, stranding both the caller and the assembly. Now malformed metadata, a rejected first chunk (including a duplicate first chunk over an in-flight assembly), and every feed error call `chunk_registry.abort(conn_id, request_id)` before completing the exact correlated caller with a useful `IpcError::Chunk` message. Falsified: with the three `abort` calls removed, `malformed_later_chunk_metadata_aborts_assembly_and_keeps_connection_usable`, `duplicate_later_chunk_aborts_assembly_and_releases_budget_once`, `duplicate_first_chunk_aborts_existing_assembly_and_releases_budget_once`, and `oversized_later_chunk_aborts_assembly_and_releases_budget_once` all fail (the pre-existing budget/control test still passes, so it does not cover these paths).
2. **Server ordering and correlated errors.** The receive loop spawned each chunk as an independent task and the first chunk awaited `reserve_route_execution` before inserting its assembly, so later chunks could feed a non-existent assembly and be discarded while the caller waited; feed/admission failures aborted state but did not answer the caller. Both are fixed as described above. Falsified: with frame-dispatch ordering bypassed (always `Direct`), `later_chunks_wait_for_stalled_first_chunk_route_admission` fails with "condition not reached within timeout: three chunk frames dispatched", proving the test observes the ordering mechanism rather than passing incidentally.
3. **`PyMemHandle` released-state contract.** `release()` used to leave `Some(released carrier)` in the wrapper, so `len()` returned 0 and `repr()` looked live (`MemHandle(len=0, type=file_spill)`); the carrier is now taken and dropped only after a successful release, and preserved on error for retry. Falsified: without the take, `TestMemHandleReleasedState::test_release_drops_carrier_and_reports_released` fails with `assert 'MemHandle(len=0, type=file_spill)' == 'MemHandle(released)'`.
4. **Report wording.** The earlier draft called dedicated `free_at` a physical free and treated the carrier-level registry/pool-Arc-drop proof as a proven file-backed `HeldResponse` across Runtime shutdown. Both claims are corrected here: release through `free_at` is logical (buddy block freed / dedicated entry marked freed), the SHM backing charge persists until the owning mapping is actually unmapped by segment/dedicated GC or drop, and the file-backed held-response-across-shutdown case remains deferred.
5. **Tautological test assertion.** `c2-wire`'s `finished_and_trimmed_backing_stays_charged` contained `assert!(reg.feed(...).unwrap() || true)`, which clippy correctly rejects as a deny-by-default logic-bug lint and which asserted nothing. It now asserts the real results (`false, false, false` for the first three of four chunks, `true` for the last). No behavior change; the test now checks what it claimed.

## Review repair (2026-09-26, second pass)

The Host reviewed artifact `bd933872` and reported five server admission/ownership defects. The client-side and native fixes above were accepted and are preserved unchanged. Falsification log: `/tmp/c2-repair2-falsify.log` (each case patches the fix out, runs the named test, fails, and restores the source byte-identically, verified with `sha256sum -c`).

1. **Post-abort publication while the owner awaited route admission.** A request-level abort or a terminal capacity/feed/malformed refusal removed the gate entry while the first-chunk task was still inside `reserve_route_execution`. That task only watched connection cancellation, so it could insert a charged assembly and stored route admission after the caller already received a terminal failure. Fixed by fencing the route wait against the entry's own terminal state (`terminal_waiter`) in addition to `Connection::wait_cancelled()`, and by making the admission commit an atomic `Pending → Admitted` transition: a reservation that completes at the same instant loses and the staged-publication guard rolls back exactly its generation. Falsified: `lost_admission_commit_rolls_back_staged_publication_exactly_once` fails (leaked charge / registered assembly) with the commit fence removed; `capacity_refusal_fences_stalled_first_admission_against_post_abort_publication` fails (parked admission never torn down, assembly later published) with the capacity-path abort removed.
2. **Key-only gate removal (ABA) and non-atomic terminal publication.** `gate.finish(key, …)` removed by key, so an old owner finishing or dropping after an abort could remove a *new* owner's same-key entry and wake its waiters; `Entry.publish` checked `Pending` separately from `send_replace`, leaving a check-then-write race. `ChunkAdmissionOwner::release`/`Drop` and `ChunkAdmissionReclaim::drop` now remove only the exact entry pointer they began, `begin` refuses while any entry (pending or tearing down) exists for the key, `abort_key` holds a teardown fence until the request teardown finishes, and `try_publish` is a single-winner compare-and-swap over `watch::Sender::send_if_modified`. Falsified: `stale_generation_release_never_removes_the_replacement_entry` fails with the pointer-identity check removed; `terminal_transition_is_a_single_winner_compare_and_swap` (8 racers × 512 rounds) fails 3/3 runs with a check-then-write `try_publish`.
3. **Un-fenced terminal refusals.** The receive loop's chunk-processing-capacity refusal wrote an error but did not abort the request, and the duplicate-first-chunk (`AlreadyPending`) ordering refusal wrote an error while leaving the pending admission and any published assembly charged. Both now call `Server::abort_chunk_request` before writing the refusal, which publishes the terminal outcome, releases the stored route admission and exactly its assembly generation, and fences the parked owner. A duplicate first chunk that arrives after admission (`begin` succeeds, registry insert rejects the duplicate) releases the already-published generation through the same path instead of stranding it. Falsified: both named tests above fail with the respective `abort_chunk_request` calls removed (the duplicate case fails by timeout: the parked admission later publishes); `duplicate_first_chunk_after_admission_aborts_the_published_assembly` fails when the publication guard takes the stored admission even though it published no assembly of its own.
4. **Leaked buddy block on the discard path.** A waiting later chunk whose outcome was `Refused`/`Aborted` returned before decoding/cleaning its buddy-backed frame, leaking the peer SHM allocation. The discard path now calls the existing `cleanup_buddy_request_block` before returning. Falsified: `discarded_waiting_buddy_chunk_returns_its_peer_block` fails (peer pool allocation count stays 1) with the cleanup removed.
5. **Unpublished work surviving cancellation.** `ChunkAdmissionOwner::drop` only tore down gate metadata, so cancellation or panic after the registry insert but before admission could leave the assembly and stored route permit charged. The first-chunk publication is now staged: a `ChunkPublicationGuard` owns the assembly + stored admission and rolls back exactly once on any non-commit exit (identity-checked `abort_id`, stored admission taken first while the assembly still blocks a same-key successor insert). No global gate lock is held across an await or mapping/I/O (the gate lock is only held for map + fence-counter updates), server route/scheduler ownership stays in `c2-server`, and no `Server ↔ gate` `Arc` cycle was introduced (the gate holds only its own entry map; `abort_key`'s reclaim borrows the gate `Arc` for the teardown and is dropped before the call returns). The registry identity (`ChunkAssemblyId`) is registry-internal bookkeeping, not route/scheduler ownership moved into `c2-wire`.

### Shared live bytes bound independent concurrent assemblies

- `chunk::registry::tests::concurrent_admissions_never_exceed_shared_live_bytes` (c2-wire): four threads race to admit one 512-byte assembly each against a shared budget capped at exactly 4 × 512 bytes and hold them at a barrier (all four must succeed; live bytes ≤ limit at every observation); with the cell fully charged, four further concurrent admissions must all be rejected naming the `'reassembly'` cell with exact rejection counters; releasing the held seats refunds to zero and the cell admits again. Deterministic barrier phases — no reliance on racing aborts to force rejections (the original slice additionally ran the full suite 8× consecutively to rule out flakiness; this repair reran the affected binaries).
- `chunk::registry::tests::shared_budget_bounds_independent_registries`: two registries over two pools sharing one `MemoryBudget`; exactly four 256-byte admissions fit across both, the fifth is rejected on either side, and releasing one admission frees room for exactly one more.

### Rejection happens before any mapping, with a useful cell/size error

- `chunk::registry::tests::admission_rejects_before_mapping_with_cell_and_size_error`: over-capacity insert returns an error naming `'reassembly'`, the requested `384`, and the limit `256`; pool stats show zero buddy/dedicated segments; only rejection statistics moved. Zero `chunk_size` / zero `total_chunks` are rejected as geometry errors without touching budget statistics.

- `chunk::registry::tests::file_backed_admission_rejection_creates_no_file_mapping`: a spill-only pool with an isolated spill directory — the rejected admission leaves the directory listing byte-for-byte unchanged (no file mapping created).

### Every failure/cancellation path returns the charge exactly once

- Duplicate insert: `duplicate_insert_rejects_and_returns_new_charge_once` (original stays charged at 128, new charge refunded, feedable original completes).
- Incomplete finish: assembler `test_finish_incomplete_fails_and_returns_charge_once` and registry `finish_error_path_returns_charge_once` (charge → 0, pool usable again).
- Abort: `abort_frees_resources_and_returns_charge_once` (idempotent double-abort safe).
- Timeout: `gc_sweep_expires_stale_and_returns_charge_once`.
- Disconnect: `disconnect_cleanup_returns_charge_once` (other connections' charges untouched).
- Invalid chunk: `invalid_chunk_feed_aborts_entry_charge_once`.
- Client receive errors (recovery repair): the four tests above assert the charge is back to 0 immediately after the caller is completed, and that a fresh assembly of the same size is admitted afterwards (exactly-once refund).

### Server first-chunk admission ordering

- `server::tests::later_chunks_wait_for_stalled_first_chunk_route_admission` (c2-server): a real `handle_connection` receive loop over a local pair, `max_total_chunks = 3`, route admission held by taking the dispatcher write lock. The first chunk plus two later chunks are written; the test proves the first chunk is parked on the held gate and that later chunks are parked on its admission with all three chunk-processing permits held, that no assembly was published or discarded, and that the receive loop still answers PING on the same connection while the gate is stalled. Releasing the gate then yields exactly one execution whose echoed bytes equal the original data, with ordering entry, registry entry, stored route admission, and all permits released and the route scheduler free.
- `server::tests::route_refusal_wakes_parked_later_chunks_and_releases_state`: a first chunk whose route is not in the catalog fails admission with a structured `RouteNotFound` reply for its own request id; the later chunk stops without feeding, and the ordering entry, assembly, permits, and route scheduler are all released.

## What this slice deliberately does not do

Budget override resolution through `c2-config`, SDK statistics projection, the Runtime shared client-cache context, and Runtime client-cache lifecycle fixes are the next integration slice (and the cache work belongs to other workers per the task split). Pools constructed by existing constructors carry private budgets from the canonical `MemoryBudgetLimits::default()` (8 GiB SHM / 16 GiB file / 8 GiB reassembly), so behavior is finite today and shared-budget wiring arrives with the Runtime slice. Wire protocol v11 is untouched — the carrier is a Rust-side ownership change only; the 15-byte BuddyPayload and C ABI are unchanged.

## Remaining limits

1. A later chunk waiting for its request's first-chunk admission holds its chunk-processing permit. That is bounded by `max_total_chunks` and by the gate's own capacity check, but a first chunk stalled behind a route/dispatcher gate can occupy up to that capacity with its own later chunks. The first chunk already held one permit before this slice; the change makes the bound cover later chunks too. PING/control frames and other requests are unaffected because the receive loop never waits on admission.
2. When admission is refused or aborted, later-chunk waiters stop silently instead of writing their own error replies, because the admission owner already wrote the correlated structured error for the request id (and after a disconnect no reply is deliverable). A waiter's own frame is not individually acknowledged in that case; a buddy-backed waiter frame still returns its peer block to the peer pool.
3. `ChunkAdmissionOwner` teardown after a panic publishes `Aborted` without a reply; the caller then relies on its own call timeout. Normal error paths always write the correlated error first. Cancellation or panic between the registry insert and the admission commit rolls the staged publication back (identity-checked), but does not by itself write a reply.
4. The first-chunk route-admission wait is cancellation-aware (`Connection::wait_cancelled` and the admission entry's terminal state), but the synchronous `Scheduler::reserve_pending` decision inside `reserve_route_execution` is not interruptible — it is a non-blocking try-acquire, so it returns promptly by construction.
5. Reassembly charge refund happens when the pool's release authority accepts the release; for buddy/dedicated SHM the underlying mapped backing may remain charged in the `shm_backing` cell until segment/dedicated GC or drop actually unmaps it. Stats must not be read as physical RSS.
6. Request-keyed teardown assumes a connection does not reuse an in-flight request id: `take_chunk_route_pending`, `sweep_stale_chunk_route_pending` (two-phase stale check), and `finish`/`feed` address a request by `(conn_id, request_id)`, and a stale frame for a reused id could target the current generation for that key. The gate fence guarantees that an *old owner's* rollback or abort teardown cannot touch a same-key successor's entry, assembly, or stored admission, but it does not re-identify an arbitrary stale frame. This is the wire/client contract (c2-ipc request ids are monotonic per connection), not a new server-side guarantee.

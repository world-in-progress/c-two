# 0.7.4 连接池 FD 回归验证

[English](0.7.4-fd-leak-regression.md)

下游交接记录了 0.6.0 空闲回收后套接字累积的问题：池移除客户端，但独立接收任务仍持有连接。当前 0.7.4 使用显式关闭及接收任务析构回收。本次补充真实连接测试，生产实现不变。

## 原探针

从提交 `46480adf7424f794482fc761a2c8ec53dd28323b` 重新构建 Python 3.13 原生模块，在私有端点目录运行原 `run.py` 的逐字节副本。阶段是 `main30 → idle62 → idle62 → bgidle70 → idle130 → main30`，耗时 341 秒，退出码 0，结果 `no growth`。

服务端和客户端每阶段各有 5 个 Unix 套接字；服务端基线是 4，客户端退出后回到 4。因此只保留一条业务连接，空闲重建没有累积旧连接。后台阶段完成 34 次调用。原交接目录的六个文件哈希不变，探针私有端点目录已删除。

## 回归门禁

`core/transport/c2-ipc/src/pool.rs` 增加四项跨平台真实 `LocalListener` 测试，验证 acquire 触发过期回收、显式 sweep、精确 discard 与替换保护、close_all 关闭活跃及空闲连接并重新建连。它们保留旧客户端 Arc，等对端实际读到 EOF；收到断开信号只应答，不能据此提前算作关闭。PING/PONG 证明保留及替换的连接仍可通信，同时检查存活连接数。

`sdk/python/tests/integration/test_client_pool_idle_cleanup.py` 使用两个独立进程，长期客户端以 `with cc.connect(...)` 调用，再空闲 62 秒，两轮均保持服务端 `baseline + 1`，退出后回到基线。Linux 使用 `/proc`，macOS 使用 `lsof`；Windows 的同机制验证使用上述 Named Pipe Rust 测试。240 秒测试 marker 覆盖 CI 的默认 30 秒超时。各用例使用自己的进程与端点，不要求整套测试串行。

本机结果：四项新增 Rust 测试通过；完整 c2-ipc 199 项以四线程并行通过；SDK 测试通过；格式和 diff 检查通过。四项真实 Named Pipe 用例也在 [Windows Native run 38014902370](https://github.com/world-in-progress/c-two/actions/runs/38014902370) 的 Windows Server 2022 和 2025 上通过，测试源码为最终提交 `dd9adecc48d215a63ff1abedd6c7d11fb4a2b688`。

## 反例验证

在独立临时源码、Cargo target 和 Python 环境中，撤回显式 retired close，并将 IpcClient Drop 置空，恢复“移除条目但接收任务仍持有连接”的机制。四项 Rust 测试均因等不到真实 EOF 失败（退出码 101）；SDK 在首次 62 秒空闲后观察到 6 个套接字，预期为 5，因数量增长失败（退出码 1）。这是机制反例，没有把修改后的 0.7.4 称为实际运行的 0.6.0。

第一次 SDK 反例构建缺少本机 C++ 标准头路径，整轮执行保留为失败。随后只为该临时构建设置当前 SDK 的 `SDKROOT` 和标准头路径，构建成功，再得到上述功能断言失败；没有把编译错误作为反例通过证据，也没有重跑已完成的正常用例。

Astra max 对固定测试补丁的源码审查无阻塞问题；[独立最终证据核验](../reviews/0.7.4-astra-fd-evidence-audit.md)接受本次有限范围的修补，没有发现问题。源码、原生模块、补丁、反例及输出哈希见 [机器记录](evidence/0.7.4-fd-leak-regression.json)。原交接目录未改动。PR #180 已合并，0.7.4 已发布；后续完整门禁与公开产物核验见 [发布记录](0.7.4-publication.zh-CN.md)。

# Wheel matrix patterns in upstream CI (2026-10-12)

Scope: primary documentation and pinned workflow source for Pydantic, Polars, uv, maturin-action, cibuildwheel, and GitHub Actions. Workflow facts below describe those repositories at the linked commits; C-Two implications are inferences, not measured speedups.

## Observed patterns

- **Group interpreter builds by target.** Pydantic's `core-build` matrix is principally OS/target; one maturin invocation passes an interpreter list (`3.10 ... 3.14t ...`) and uploads the resulting wheels as one artifact per matrix entry. Some less common targets have explicit shorter interpreter lists. The same job runs `twine check`, but its later installed-wheel tests use separate jobs. [Pydantic workflow, lines 79–203](https://github.com/pydantic/pydantic/blob/3eca5695dabc5a451ccfc0f4afa802166e61e27a/.github/workflows/ci.yml#L79-L203). This is direct evidence for grouping builds, **not** evidence of one installed-artifact test for every ABI.
- **Separate output production from consumption where needed.** Pydantic's `core-test-builds-os` waits for build jobs, downloads artifacts, installs from the artifact directory with `--no-index --no-deps --find-links`, and runs tests. Its `core-test-builds-arch` does a similar installation on selected emulated architectures. These jobs do not form an explicit per-ABI consumer matrix. [Pydantic workflow, lines 369–485](https://github.com/pydantic/pydantic/blob/3eca5695dabc5a451ccfc0f4afa802166e61e27a/.github/workflows/ci.yml#L369-L485).
- **Run broad publication builds conditionally.** Pydantic's `core-build` runs for tags, main, or PRs labelled `full build`; its ordinary PR test jobs are separate. [Pydantic workflow, lines 79–82](https://github.com/pydantic/pydantic/blob/3eca5695dabc5a451ccfc0f4afa802166e61e27a/.github/workflows/ci.yml#L79-L82). uv uses a `plan` job; its release-artifact build depends on the plan's `build-release-binaries` output, which is set for relevant changes or an explicit `build:release` label, subject to skip labels. [uv CI, lines 116–182](https://github.com/astral-sh/uv/blob/139d0914ea9563ddcd7071ed285f48d56f1ed4f4/.github/workflows/ci.yml#L116-L182), [uv plan, lines 220–245](https://github.com/astral-sh/uv/blob/139d0914ea9563ddcd7071ed285f48d56f1ed4f4/.github/workflows/plan.yml#L220-L245). These are upstream policy choices; adopting reduced PR sampling in C-Two would explicitly move the 30 ABI gate to another event and change its merge assurance.
- **Polars groups by package and platform, then smokes the built wheel in the same job.** Its dispatch-only Python release workflow has a `build-wheels` matrix over three runtime packages and eight platform configurations. The job calls maturin once, installs `dist/*.whl`, checks the reported build commit, and uploads the artifact. The in-job test excludes musl targets. [Polars workflow, lines 150–179](https://github.com/pola-rs/polars/blob/6673f6d371951b6c712d656a6851ad1d5f389863/.github/workflows/release-python.yml#L150-L179), [lines 342–374](https://github.com/pola-rs/polars/blob/6673f6d371951b6c712d656a6851ad1d5f389863/.github/workflows/release-python.yml#L342-L374). This supports a nearby platform smoke; it does not establish full per-ABI testing.
- **Official tooling permits a platform job to build several ABIs.** maturin-action documents `--find-interpreter` and explicit `-i` selection; for manylinux its container supplies supported interpreters, while macOS/Windows host interpreters must be installed. Its current README warns that installing regular and free-threaded CPython of the same minor version together with one `setup-python` step can fail on Windows and recommends separate jobs for that case. [maturin-action README](https://github.com/PyO3/maturin-action/blob/acb699e6734322acb57a0b1a5b4b62d01d68156d/README.md#free-threaded-cpython). cibuildwheel's official example uses an OS/arch matrix with one action invocation per matrix entry; its `test-command` installs and tests each built wheel from outside the source tree. [cibuildwheel FAQ](https://cibuildwheel.pypa.io/en/stable/faq/#building-linux-wheels-for-non-native-archs-using-emulation), [options](https://cibuildwheel.pypa.io/en/stable/options/#test-command).
- **`needs` is a real scheduling barrier.** GitHub specifies that a job with `needs` starts only after its dependencies complete successfully; a failed or skipped dependency skips downstream jobs unless a suitable conditional is used. [GitHub workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idneeds). Inference for C-Two: `needs: [context, cli]` on every native wheel job waits for all five CLI matrix children, even when a wheel target only needs the same target's CLI artifact or no CLI artifact. A final all-platform receipt/check job can still aggregate results after independent build jobs, as Pydantic's branch-protection check does. [Pydantic workflow, lines 1017–1030](https://github.com/pydantic/pydantic/blob/3eca5695dabc5a451ccfc0f4afa802166e61e27a/.github/workflows/ci.yml#L1017-L1030).
- **New optional in-job parallelism.** GitHub introduced `background` and `parallel` steps on 2026-06-25. The syntax runs independent steps concurrently in one job, then waits; at most 10 background steps run at once. `parallel` cannot be declared inside a composite action. [GitHub changelog](https://github.blog/changelog/2026-06-25-actions-steps-can-now-be-run-in-parallel/), [workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsparallel). Inference: a C-Two platform job could prepare FastDB once and run isolated ABI build/test steps concurrently, provided each uses separate target/output/interpreter state and the runner has enough CPU, memory, and disk. This is an option for a prototype; no current C-Two actionlint or hosted-runner validation is claimed.

## Application to C-Two

The strongest structural candidate is one native build job per platform/architecture that emits six ABI wheels, keeping the existing six-ABI-per-target Linux build arrangement as precedent. This could reduce the 18 non-Linux native ABI build jobs toward three platform jobs, while retaining an explicit **30-row installed-artifact consumer/receipt inventory** across all five targets. A job-count reduction alone does not prove elapsed-time savings: serial builds within a platform job may lengthen its critical path, and shared FastDB C++/SWIG setup, wheel repair, and runner queueing must be measured. Every consumer should install the produced wheel by exact path in an isolated interpreter, verify import and native dependency loading, bind its source and wheel hashes to the receipt, and retain the standard-user Windows smoke. Cibuildwheel's per-wheel test hook is another possible implementation, but its compatibility with C-Two's FastDB packaging and exact receipt format needs a targeted prototype.

For scheduling, let wheel jobs depend only on prerequisites that actually supply their inputs; keep the aggregate manifest/receipt gate after all artifacts. The observed all-CLI dependency is a plausible avoidable barrier, but removing it may reveal a hidden artifact or configuration dependency, so inspect each job's actual inputs before changing `needs`. The five platform smokes, all 30 ABI receipts, standard-user Windows check, and exact source/artifact hashes remain merge gates under the stated C-Two requirement. Pydantic/uv's lighter ordinary PR policy is a design alternative only if the owner deliberately authorizes a different merge gate; it should not be presented as a free optimization.

No benchmark or speedup estimate is asserted here. The supplied C-Two reference run is 49 jobs total after PR 182 (RC 41), 16m37s elapsed, 102.6 raw runner-minutes, with the longest macOS queue at 9m12s. Those figures describe one run and cannot by themselves isolate the effect of grouping or changing dependencies.

Host verification: locally installed actionlint 1.7.12 rejects a minimal workflow containing a `parallel` group as a step without `run`/`uses`. The official GitHub feature was independently verified in the documentation repository, but existing local tooling and real hosted execution still require compatibility validation. The immediate proposed experiment is two ABI groups per macOS architecture; the generic three-native-platform-jobs direction above must not override the documented Windows regular/free-threaded interpreter restriction.

# Contract Release Deferred Capabilities

Updated: 2026-10-31. Open boundaries are checked against the current [roadmap](roadmap.md), [runtime lifecycle](../reference/runtime-lifecycle.md), [Rust SDK](../../sdk/rust/README.md) and [0.10.0 release notes](../releases/0.10.0.md). The [July candidate acceptance](../acceptance/2026-07-24-rust-sdk-portable-payload-local-release-candidate.md) retains the historical baseline and exact artifacts. Closed capabilities, published FastDB dependencies, implemented Host timeout projection and completed hosted release qualification have been removed from this working record.

## Open Capabilities

| Capability | Current limitation | Why not in this slice | Impact | Owner | Exit criteria |
| --- | --- | --- | --- | --- | --- |
| Contract compatibility | Release matching is exact by descriptor digest; no semver/range acceptance exists. | Compatibility requires explicit ABI/signature evolution rules after exact identity is stable. | Consumers cannot request a compatible range and must pin one release. | C-Two | Rust-owned compatibility rules reject ambiguity and ABI-incompatible matches with structured errors and cross-language vectors. |
| Resolver and storage | C-Two defines no registry, URL, object store, or digest resolver. | Storage and distribution topology are consumer/deployment concerns. | A ref alone cannot fetch its descriptor. | Catalog/deployment owner | A consumer resolves bytes by digest, then passes them through `ContractRelease` verification without C-Two owning catalog state. |
| Signature and trust | A release digest proves integrity, not publisher identity, authorization, or revocation state. | C-Two does not own Authority identity, key distribution, policy, or revocation. | Callers must not treat a valid release as trusted by itself. | Authority/policy owner, including Toodle where applicable | A downstream signed envelope binds the C-Two ref to its Authority trust model without changing C-Two release identity. |
| C-Two official package distribution | Python C-Two 0.10.1 and c3 0.6.0 have official source-bound releases. The Rust `c-two` package and Node `@c-two/c2-mem-ffi` retain independent 0.1.0 source versions with no crates.io/npm publication. | Rust and Node distribution need their own immutable packaging and declared-platform qualification. | Ordinary registry-only Rust and Node consumers cannot yet install the complete C-Two surface. | C-Two release owner | Official Rust/Node artifacts are fetchable with source and SHA-256 provenance; isolated package, codegen, runtime and interoperability consumers pass. |
| Python portable binding shape | One portable Python method accepts zero inputs or exactly one positional `Payload`, and returns either no value or one `Payload`. It does not infer FastDB specs from annotations, synthesize domain/dataframe/GIS shapes, accept keyword-only payload parameters, or expose multiple independently encoded payload arguments. | The one-envelope shape is the language-neutral `c-two.contract.v2` boundary and prevents C-Two from becoming a second FastDB schema/type authority. Keyword-only invocation is not yet mapped consistently through thread-local direct calls, IPC dispatch, and generated non-Python clients. | Users explicitly build/adapt one FastDB payload outside the CRM method. Existing annotation-inferred domain methods must be redesigned rather than silently migrated, and Python callers may use a positional or positional-or-keyword payload parameter but not a keyword-only declaration. | C-Two for invocation ergonomics; application owners for domain adapters | Any broader invocation shape has an accepted outer-contract design, works equivalently in Rust and Python generated/runtime surfaces, preserves one Core-owned payload meaning, and passes thread/IPC/relay plus codegen interoperability tests without annotation inference. |
| Python-only pickle fallback | Ordinary Python CRM methods still use the existing pickle runtime when no explicit portable binding is present, but portable descriptor export and codegen reject those methods with a `python_only_pickle` diagnostic. | Removing the local Python fallback is a separate product compatibility decision; presenting it as portable would violate the cross-language authority contract. | Python prototypes continue to run between Python peers, but they cannot be released as `c-two.contract.v2` or consumed by generated Rust clients. | C-Two | Either the fallback remains explicitly Python-only with maintained diagnostics, or a separately accepted migration removes it and all callers; it must never become a portable fallback. |
| Per-call route receipt after relay-aware failover | `Client::observed_route()` and the Python proxy projections expose the immutable route UID/revision selected when Core acquires the client. A relay-aware HTTP client can later invalidate and resolve a different route while making a call, so the property is not a last-call route receipt. Task 8 explicit-relay rows use one resolved route and do not exercise this ambiguity. | A truthful last-call observation requires a concurrency-safe structured call outcome or observation stream shared by Rust and Python; mutating one client property would race concurrent calls and could misattribute held responses. | Callers may use the property for connect-time diagnostics and the fixed explicit-relay matrix, but must not use it as an audit assertion about the final route of an adaptive relay-aware call. | C-Two Core and SDK projections | A versioned per-call outcome or observation API binds the actual route token and transport attempt to each response/error, preserves concurrent-call identity and held-response lifetime, and passes Rust/Python relay failover tests. |
| Explicit portable-payload performance benchmark | The old annotation-inferred FastDB Kostya variants were deleted. The tracked benchmark currently retains only truthful `pickle-records` and `pickle-arrays` baselines. Task 5 now provides the public generated/runtime record and object-graph harness, but no benchmark consumes it and no explicit `Payload` throughput or retained-owner result is published. | The correctness proof intentionally does not choose workloads, warm-up, process placement, copy/direct/staged labels, or statistical reporting on behalf of a performance suite. Those choices require a separately reviewed reproducible benchmark rather than timing the integration test. | Correctness and lifecycle are proven for explicit payload IPC, but no comparative performance claim is valid yet. | C-Two | A reproducible benchmark consumes the Task 5 public harness, records copy/direct/staged and retained-owner facts accurately, reports environment and distributions, and adds guarded benchmark tests without private APIs. |
| Untrusted-peer SHM release authority | SHM 3 carries the backing generation and buddy allocation id. `c2-mem` checks the mapped span, generation, allocation level and live id under its allocator lock before freeing. Those consistency checks cover stale/replayed identities; a same-user peer with writable allocator mappings can still forge shared state. | Peer release authority belongs in the versioned memory/wire design, including the planned single-owner release protocol. | Correct-peer cleanup has checked allocation identity; hostile shared-memory writers remain outside that guarantee. | C-Two memory and wire owners | The accepted protocol and threat model define per-connection release authority and prove forged, replayed, wrong-generation and cross-process cases without SDK-local tokens. |
| Raw retained-buffer escape | Python `HeldResult` exposes raw retained bytes only through the explicitly named `unsafe_buffer`. C-Two invalidates the payload owner and releases its own memoryview/transport lease, but it cannot revoke NumPy arrays, pointers, or additional memoryviews that user code derives from that raw buffer. The former neutral `.buffer` alias is not retained. | Python's buffer protocol does not provide a general revocation mechanism for arbitrary downstream aliases. Calling the escape safe would overstate the lifetime guarantee. | Normal code should use `held.value` and FastDB checked views/materialization. Advanced raw-buffer users own alias lifetime and may prevent deterministic transport release until every export is dropped. | C-Two for naming/documentation; application owner after escape | A future checked buffer abstraction can replace this limitation only if it proves all supported derived access is revocable across Python/NumPy/native consumers; otherwise the escape remains explicitly unsafe. |
| Direct final-backing construction | The proven Rust host bounds-checks and copies `RequestData` into owned bytes before the generated FastDB adapter opens it, the Python runtime also uses an owned receive path, and response transport may copy completed FastDB binary bytes into C-Two-managed SHM. | A truthful direct claim requires a public adapter that gives FastDB the final C-Two backing during resource execution in every supported SDK. | Correctness, view, materialize, and invalidation are proven, but the integration is not described as response-SHM zero-copy. | C-Two with FastDB public backing APIs | Rust and Python resource-time builders receive the final C-Two backing, FastDB reports direct/staged execution accurately, fallback is tested, and no post-build repack occurs on the proven direct path. |
| TypeScript structured transport failure phase | Generated relay-aware TypeScript parses canonical relay errors and retries only `ResourceNotFound`, `RouteStale`, or `ResourceUnavailable` explicitly marked `pre_dispatch`; a verified local IPC call failure and an HTTP `dispatch_uncertain` failure are terminal. Public `C2HttpRelayError` and `C2IpcTransportError` still do not expose a structured `PreDispatch`/`DispatchUncertain` discriminant, and local IPC conservatively stops even when a narrower implementation might later prove no dispatch. | A truthful public phase requires one versioned error contract backed by actual transport phase tracking; inferring it from generic socket failures or adding a TypeScript-only enum would diverge from Core. This slice closes unsafe replay and proves the conservative behavior, not the broader cross-SDK error API. | Callers can rely on no hidden post-dispatch replay, but cannot uniformly branch on a typed failure phase across Rust, Python, and TypeScript. | C-Two Core, transport, and SDK projections | Core defines the stable phase contract, every supported SDK projects it structurally, IPC/HTTP tests distinguish pre-dispatch from uncertain failures, and only independently resolved pre-dispatch paths may be retried. |
| TypeScript route-revision integer precision | Relay route revisions are Core-owned positive `u64` values and the current resolve JSON emits them as JSON numbers. Generated TypeScript rejects values outside JavaScript's safe-integer range, but JSON parsing may already round an otherwise valid `u64` before that check; its route token and observation APIs therefore cover only revisions up to `Number.MAX_SAFE_INTEGER`. | Fixing this in generated code alone cannot recover digits already lost in the relay response. The relay control schema and all SDK projections need one compatible decimal-string or explicitly bounded integer contract. | Long-lived authorities whose route revision exceeds the JavaScript safe-integer range cannot be called safely by the generated TypeScript transport; rejection must not be described as full `u64` interoperability. | C-Two relay control schema, Core, and SDK projections | The versioned resolve schema preserves the complete `u64` token (for example as canonical decimal text), Rust/Python/TypeScript parse and emit identical header digits, and boundary tests cover `2^53-1`, `2^53`, and `u64::MAX` without rounding. |
| TypeScript opaque response allocators | The generated FastDB adapter accepts the default `Uint8Array`/`ArrayBuffer` responses from the retained C-Two transports and opens an owned FastDB copy. A caller-selected allocator whose returned payload is only an opaque provider object cannot be decoded because the existing transport result does not expose its writable byte view to the contract adapter; the adapter rejects that case and releases the response. | Inventing a C-Two-specific FastDB backing or reaching into provider objects would violate the public ownership boundary. A general retained-response contract must be designed with the transport and FastDB owners together. | HTTP/IPC/relay/SHM transport factories remain available, but FastDB decoding currently requires their default byte-visible response form. | C-Two with FastDB public backing APIs | A versioned byte-visible/owned response interface works across TypeScript transports and FastDB's public external-backing API, proves release and invalidation ordering, and retains provider-owned storage without private-field access. |
| Browser TypeScript runtime proof | The generated TypeScript proof runs under Node, including native Windows and Unix IPC gates. There is still no browser package, browser transport selection, browser-compatible ownership backend, or real-browser call proof. | Treating Node execution or DOM type availability as browser evidence would overclaim incompatible runtime and packaging boundaries. Browser support needs a real owner slice rather than conditional stubs in the Node candidate. | The generated contract/payload source may be reusable in a future browser client, but current documentation and receipts must not claim browser runtime support. | C-Two TypeScript/browser runtime owner | A browser-installable artifact uses supported browser transports and FastDB runtime packaging, executes no-payload/record/graph calls plus lifecycle/error cases in real browsers, records browser/platform evidence, and states unsupported browser capabilities explicitly. |
| Existing-tree artifact update | The first publisher atomically creates a complete new destination tree and refuses an existing destination. | Blind merging can retain stale artifacts, follow symlinks, or leave partial state without a prior manifest and rollback protocol. | Project generators must compose into a fresh tree and adopt it separately. | C-Two | A versioned prior-manifest protocol validates ownership, detects user edits/stale files, stages a complete replacement, rolls back on failure, and has cross-platform symlink/path tests. |
| Crash-durable or hostile-parent publication | The publisher synchronizes each regular file and performs an atomic no-replace directory rename under a pre-existing parent, but it does not synchronize every created directory and the parent after rename. It also assumes the caller-controlled parent path remains stable while publishing. | Cross-platform crash durability and adversarial path-component replacement require platform-specific directory-handle/relative-operation semantics and tests beyond the current local codegen destination contract. | Concurrent readers never observe a partial winning tree, but callers must not treat success as a power-loss durability receipt or publish inside a parent concurrently controlled by an adversary. | C-Two | A versioned publisher uses supported directory handles and relative no-follow operations, synchronizes staged directories plus the destination parent where the platform permits it, documents weaker platforms explicitly, and passes crash/fault-injection and hostile-parent race tests. |
| Non-regular artifact metadata | `ContractArtifact` carries path, semantic kind, bytes, hash, and provenance, and the publisher creates regular files only. It does not represent executable bits, ownership, extended attributes, hard links, or symbolic links. | No current C-Two/FastDB generator requires those filesystem objects, and guessing cross-platform permission/link semantics would weaken the path-safety contract. | The composer is general across regular source/metadata/binary files, but it cannot yet publish executable tooling or link-based package layouts faithfully. | C-Two | A versioned artifact metadata model defines portable modes and any supported link semantics, rejects unsupported platform mappings, and has real producer plus cross-platform publication tests. |
| C-Two C++ SDK/codegen | FastDB can generate C++ payload artifacts, but C-Two has no formal C++ route/transport SDK to compose with them. | Generating payload-only C++ under a C-Two command would falsely imply a usable C-Two C++ client. | C++ users can consume FastDB directly but not a generated C-Two contract client. | C-Two | A real C++ route-bound client/server facade exists and C-Two composes it with Core-generated C++ payload artifacts in compile/run tests. |
| Toodle consumption | This checkout retains no completed canonical downstream `CRMContractRef`/`toodle-c2` consumer acceptance. Its completion belongs to the Toodle owner and requires its own pinned official-package proof. | Toodle must consume official immutable owner artifacts through its own model/protocol and adapter boundaries; copying local packages or transport logic would create a third authority. | Upstream local readiness does not yet make Toodle Phase 0B complete or authorize Resource Service/runtime implementation against provisional local bytes. | Toodle, after FastDB/C-Two release owners | Official paired artifacts and golden evidence are immutable and pinned; Toodle delegates C-Two release verification, implements its narrow adapter without FastDB/transport duplication, and passes Rust/Python `IToodle` consumer tests. |

## Dependency Matrix

Capability names below correspond exactly to the open rows above. Dependencies identify prerequisites and collaborating owners; they do not transfer ownership into C-Two.

| Capability | Dependencies |
| --- | --- |
| Contract compatibility | Frozen v2 exact-identity semantics plus an accepted cross-language contract-evolution policy. |
| Resolver and storage | A consumer-owned catalog/deployment resolver that can return descriptor bytes by immutable identity. |
| Signature and trust | An Authority-owned identity, key-distribution, policy, and revocation model. |
| C-Two official package distribution | Authorized C-Two release channels, declared-platform hosted gates, unambiguous versions, and immutable Rust/Python/CLI/Node provenance. |
| Python portable binding shape | An accepted outer-contract invocation design and equivalent thread/IPC/relay behavior across generated SDKs. |
| Python-only pickle fallback | An explicit C-Two compatibility decision and maintained nonportable diagnostics. |
| Per-call route receipt after relay-aware failover | One concurrency-safe structured call outcome or observation stream projected equivalently through Core, Rust, and Python. |
| Explicit portable-payload performance benchmark | The public Task 5 harness plus a reviewed workload, environment, warm-up, copy/direct/staged, and statistical protocol. |
| Untrusted-peer SHM release authority | The versioned single-owner protocol, per-connection release authority, a precise shared-memory threat model and hostile-peer tests. |
| Raw retained-buffer escape | A revocable abstraction supported by every declared Python/NumPy/native buffer consumer; otherwise the Python buffer protocol remains the limiting dependency. |
| Direct final-backing construction | Public FastDB external-backing/build APIs and C-Two resource-time builder integration in both Rust and Python. |
| TypeScript structured transport failure phase | A Core-owned versioned dispatch-phase/error contract plus equivalent IPC/HTTP evidence and SDK projections. |
| TypeScript route-revision integer precision | A versioned relay-control token encoding that preserves all `u64` revisions plus equivalent parsing/header tests in every SDK. |
| TypeScript opaque response allocators | A versioned byte-visible C-Two response-owner interface plus the public FastDB external-backing contract. |
| Browser TypeScript runtime proof | Browser-compatible C-Two transports, FastDB runtime packaging, ownership/lifecycle adapters, and real-browser test infrastructure. |
| Existing-tree artifact update | A prior-manifest ownership protocol, user-edit detection, complete staging/rollback, and cross-platform path/symlink tests. |
| Crash-durable or hostile-parent publication | Platform directory-handle/no-follow operations, directory synchronization support, and fault/race test infrastructure. |
| Non-regular artifact metadata | A real producer requirement plus an accepted cross-platform mode/link representation and publication contract. |
| C-Two C++ SDK/codegen | A real C-Two C++ route/transport/lifecycle SDK that can consume FastDB's existing C++ payload artifacts. |
| Toodle consumption | Official paired FastDB/C-Two artifacts, Toodle canonical `CRMContractRef` consumption, and the narrow `toodle-c2` adapter boundary. |

## Guardrail

Do not add a JSON/pickle portable transport, a C-Two-owned FastDB parser, an unsigned `trusted` flag, a compatibility alias for call-db, an unsafe existing-tree merge, or a placeholder SDK to make these rows appear complete.

# 单一属主释放方案评估

日期：2026-10-31。输入：upstream main `606b8f13`。起因：[跨进程释放调研](../research/2026-10-31-cross-process-release-survey.md)第四节的长期方向，以及[过度防御复审](2026-10-31-over-defense-review.md)中的 R07。状态：用户已同意采用这个方向；没有改动代码；详细设计待写。另请一位审查者独立分析了属主化的问题与全双工流的安全性，其结论经 Host 对照代码核对后并入本文。

## 结论

方案更干净，建议作为协议批的核心，也作为流式 RPC 的前提。所有权与进程边界一致：每个分配器只有属主一个进程在写，"别的进程持锁时被挂起或死掉"这类失效从根上不存在。对端是否还在借用，由连接说明：借用方不在仍有借出块时关闭连接，属主只在读到对端 EOF 后回收。主要代价有三项：hold 的生命周期要和连接绑在一起，这是公开语义的调整；几条现有的强制关闭路径要改为"停用但保留连接"；以及一次横跨 Rust、Python、Node 的协议、SHM 格式与 C ABI 变更。

## 现状（Host 核对）

- 每个 Server 实例一个响应池，该实例的所有连接共用（`c2-server/src/server.rs:593-606`）；请求池每条连接一个，归客户端所有。两边都以读写方式映射对方的段（`c2-mem/src/segment/unix.rs:91,125`，`windows.rs:94,173`），只是为了直接在对方的分配器里释放：客户端释放回复走 `c2-ipc/src/client.rs:515-547` 的 `free_at`，经过段头里的跨进程分配器锁。
- 服务端在 Core 里先把请求拷进自有缓冲（`c2-core/src/host.rs:1246`），保留传输租约到 invoke 返回，再在客户端的池里直接释放。低层回调接口 `CrmCallback::invoke` 按值拿到 `RequestData`（`c2-server/src/dispatcher.rs:507-514`），实现可以把它留到回复之后。
- dedicated 段靠段头的 `read_done` 标志与崩溃超时回收（`c2-mem/src/pool.rs:494-540`）。dedicated 段与文件溢出的回收不会把同一块内存交给别的数据；会被复用的只有 buddy 块。
- held 回复能跨重连存活：每次握手换新的池容器，保留的回复留着旧容器（`c2-ipc/src/client.rs:3349`）。
- 客户端拿到 SHM 回复、还没释放就死掉时，那块 buddy 内存一直占在服务端的池里，直到服务端退出；没有按连接或按进程回收的机制。
- 仍有借出时也会关闭连接的路径有三条：
  - 服务端心跳超时（`c2-server/src/heartbeat.rs:74-87`）。本机 IPC 上，这只会发生在三种情形：对端活着但停住了、对端运行时卡死，或 fork 出的进程仍持有描述符。
  - 客户端写到一半被取消：流被标记为损坏，连接随即中止（`client.rs:2405`、`:3829`、`:4675`）。
  - Runtime 关闭时，客户端池关闭全部连接；引用计数只阻止空闲淘汰（`c2-ipc/src/pool.rs:312-320`、`:1585-1627`）。
- Python 端的 memoryview 导出仍在时，hold 拒绝释放（`sdk/python/native/src/core_ffi.rs:284-291`、`:393-404`）。
- 服务端读循环不等执行容量：pending 满时直接回错误，调用另起任务执行（`server.rs:2451-2515`）。但写这个错误回复时，读循环会等写锁、等写完（`server.rs:2456`、`:4360-4363`）。客户端发分片消息时，整段持有写锁（`client.rs:4671-4700`）。

## 方案草图

1. **释放即消息。** 借用方不再写别人的分配器，而是把释放记录交给属主：写端空闲时立即发，忙时与下一帧一起发，不设计时器。属主在自己进程里释放，并在这一处校验记录，因为记录来自另一个进程，这里是真实边界。记录队列的长度不超过这条连接上的借出数，不需要另设上限。
2. **两个方向都用释放记录。** 服务端在请求租约真正释放时发出记录，通常搭在回复帧上，不多一次写；租约留到回复之后才释放时，记录在那时单独发出。不采用"收到回复即释放"，有两个原因：低层回调可以把 `RequestData` 留到回复之后，这条规则对它不成立；两个方向用同一个机制，以后流式 RPC 也能直接沿用。
3. **连接即租约。**
   - 属主按连接记下借出的块，在发出帧之前登记；可能已完整送达的帧一律算作借出；同一块的重复归还只结算一次。
   - 属主只在读到对端 EOF 之后回收这条连接名下剩下的块。属主一方结束连接（心跳超时、协议错误）时只停止服务：取消这条连接上待处理的调用、交还许可，保留读端直到 EOF。
   - 借用方不在仍有借出块时关闭连接。写损坏、Runtime 关闭这类强制路径只停用这条连接，新调用走新连接，等它名下的 hold 都释放了再关。hold 持有它的连接。
   - dedicated 段与文件溢出不复用内存，提前回收只影响记账；严格规则只针对 buddy 块。
4. **分配器回到进程内。** 段头只留几何信息，跨进程锁字、PID、死亡观察与毒化标记随之删除；释放记录的身份校验用属主进程内的记录完成；对端改为只读映射。

## 评估要回答的五个问题

**1. 消息开销：传输层可以忽略，端到端待实测。** 本机（macOS 27）测得：Unix 流上一条 32 字节单向消息约 1.1 µs，16 条一批时每条约 50 ns，往返约 4.3 µs。SHM 只用于 4 KiB 以上的载荷；作为参照，R15 记录中 128 B 原生 RPC 的 P50 约 42 µs。这只是传输的下限，不含借出表、唤醒与峰值占用。实现后用现有基准在 Linux、macOS 与 Windows 上测端到端开销，作为验收的一部分。

**2. 请求块由谁释放：客户端，在收到服务端的释放记录时。** 见草图第 2 条。

**3. 断线时的 hold：EOF 就是归还的证明，前提是借用方不在仍有借出时关闭连接。**

- 借用方进程死亡时，内核关闭它的描述符，已经没有人会读。
- 服务端进程死亡时，客户端已映射的内存仍然有效，hold 可以继续读，释放成了空操作。
- 属主一方结束连接时，只停止服务，等对端 EOF。
- 现有的三条强制关闭路径（心跳超时、写损坏、Runtime 关闭）按草图第 3 条改。

代价有两项：停住的对端，它的套接字与借出块要一直留到它退出或恢复；hold 不再能在连接关闭后单独存活，改为"hold 未释放时连接保持打开"。

剩下的例外是：fork 出的子进程关掉了继承的描述符，却还在读继承的映射。没有发现这样的用法，不为它设防。

也考虑过每条连接一个回复池、断开时整池放弃。这样同样安全，但段数随连接数成倍增长，不采用。

**4. 协议与 ABI：一次集中变更。**

- 握手版本 15：释放记录与借出边界。
- SHM 格式 4：段头去掉跨进程字段。
- C/FFI ABI 7：Node 的释放改走连接。

这次变更并入复审第五节的协议批，Rust、Python、Node 一起改，按 AGENTS.md 用确切候选跑全平台门禁。

**5. 顺序：先定本方案，再动相关项。** 采用后，下列改造都不再需要：

- R07 的改进版
- A7 毒化标记
- A 区"持锁者已死时重复自旋"
- C2 dedicated 退休执行器
- dedicated 段的 `read_done` 与崩溃超时
- C-U1 中为了不在分配器锁上阻塞所做的那部分

A1 的位图扫描也随分配器进程内化一并消失。真缺陷批与死代码批与本方案无关，可以先做。

## 与流式 RPC 的关系

用户确认，流式 RPC 是 C-Two 必须具备的能力（路线图第 7 项）。管道本身已经是全双工的：一条连接按请求号复用多个调用，两端的读写各自独立（`server.rs:2048-2050`）。要加的是"一次调用里双方连续收发"的语义。

单一属主是流式 RPC 的前提。如果保留跨进程直接释放，流会让对端分配器上的释放次数成倍增加；改成释放消息之后，释放记录本身就是流控额度。iceoryx2 的借出与归还、HTTP/2 的窗口更新，都是这个思路。

协议批现在要做对以下几点，以后加流才不必重来：

- 释放以单个分配为单位，与调用的终态分开，两个方向都能随时发。
- 借出表按连接与池记账，不假设一个请求号只对应一个块。
- 读循环既不等写端，也不等应用；错误回复经写队列发出。
- 控制帧（释放、取消、心跳）不受业务配额限制。

协议批不加流编号、窗口协商或流式 SDK。

流式 RPC 自己的设计要回答下面这些问题，按真实发生的可能性排序：

1. **生产快于消费时的积压。** 每个方向分别限制消息数、载荷字节与未归还的借出，另有连接总量；额度随消费与释放返还，不再退到 dedicated 段或文件溢出。
2. **双方都等对方先读时的互等。** 控制帧独立推进，数据队列有界。
3. **执行线程与路由锁。** 回调现在跑在受 `max_execution_workers` 限制的阻塞线程上（`server.rs:625-630`、`:3114`）。流处理函数在等待输入或额度时不能占着执行线程，也不能在整个流期间持有路由的独占锁或读写锁（`scheduler.rs:16-23`、`:425-438`）。
4. **条目的生命周期。** 与 hold 相同：释放之前先让 FastDB 视图失效。
5. **终态与取消。** 两个方向各自的发送终态，与调用的终态分开；取消时不重放有副作用的消息。
6. **关闭。** 在关闭预算内主动取消还开着的流。
7. **大条目。** 分片消息按片交错发送，一个大条目不挡住别的流。
8. **经 relay 的端到端背压。** 最后做。

## 可删与新增

可删：

- 分配器锁的 PID 锁字、死亡观察与毒化
- R07 在 c2-mem、Core、Held 与 Python 中的保留与重试
- dedicated 段的 `read_done` 与崩溃超时回收
- C2 退休执行器
- C-U1 结算层的大部分
- 段头 v3 的跨进程字段
- 对端的读写映射

新增：

- 释放记录的编码与校验
- 属主按连接的借出表与 EOF 回收
- 两个方向的释放记录发送
- 强制关闭路径的"停用但保留"

删除量明显大于新增，具体行数在出详细方案时核算。

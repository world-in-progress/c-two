# C-Two 0.7.1：内存配置、单次调用期限与端点目录

状态：用户已于 2026-10-08 批准按本方案实施并发布。目标版本为 Python C-Two 0.7.1 / c3 0.3.1；Rust SDK/Core/TypeScript 的内部版本及未单独发布范围沿用 0.7.0 的说明。各阶段实际验证与发布状态记录于本文末尾，不能由实施授权推断已经通过或发布。

源码基线：`1207bd6f1d214c1fe6f75ad555ffcee4cb254a5e`，调查日期 2026-10-08。下文所有新增 API 名称、环境变量和错误类型均为拟议接口。

## 1. 目标与责任边界

本版处理三个问题：消除池段容量与单消息上限的不当耦合；为远程调用提供可选的单次等待期限；让 Unix 本地端点目录支持代码与环境变量覆盖。Rust Core 和底层原生 crate 继续拥有配置解析、调用状态、内存释放和端点身份，Python/Rust SDK 只提供类型化入口。

Windows 是每项设计和每阶段验收的目标平台。Core 的调用事务、deadline、预算及状态机共用；`c2-local`、`c2-local-security` 和 `c2-mem` 在现有平台后端内提供不同的 OS 操作。不新增 Windows 专属 SDK 调度器、取消机制或生命周期旁路，也不以 Unix 实现先合并、Windows 以后补齐作为阶段完成条件。

内存回退、路由契约、Persistent/OwnerBound 生命周期和端点防误删机制仍是实现前提。单次调用超时不证明资源方法停止执行；自定义目录不提供任意文件删除权限；关闭 buddy 不等于禁用 dedicated SHM。既有 [HTTP 载荷内存预算提案](../plans/2026-10-06-http-memory-budget.md) 的全量响应缓冲问题独立跟踪，本版不能据此声称 HTTP 已具有完整的字节背压。

### 1.1 共同接口与平台能力

`LocalEndpointContext` 是带平台标记的原生值，建议表示为 `UnixManaged { root, uid, layout }` 或 `WindowsNamedPipe { logon_scope_id, layout }`。路径长度、目录描述符和 inode 属于 Unix 分支；Named Pipe 名称、登录 SID、DACL 和内核监听租约属于 Windows 分支。公共缓存、Relay namespace 比较和维护 scope 使用这个类型的身份，不把所有后端都强塞进 `PathBuf`、`parent()` 或“文件存在”判断。

| 方面 | Linux / macOS | Windows | 共同契约 |
| --- | --- | --- | --- |
| 端点位置 | 可配置根目录下的私有 UDS namespace | 当前登录 SID 范围的 byte-mode Named Pipe | 逻辑地址 + 不可变平台上下文 |
| 独占监听 | gate、nonce、listener lease | 独立、非继承的内核监听租约 | 重复 bind 不得破坏已有监听器 |
| 异步传输 | Unix stream 后端 | Tokio/mio overlapped I/O、IOCP 后端 | 统一帧、事务与结果状态机 |
| SHM | POSIX backing | 当前登录域的 named mapping | generation、lease、预算与回退一致 |
| 回收 | 经身份验证的精确 unlink | 内核句柄生命周期；端点 reap 为不适用 | 等待完成、监听关闭和内存释放分开观察 |

代码、环境变量和 CLI 使用同一个 Rust resolver。Unix 目录覆盖是类型化平台能力；在 Windows 输入该选项时返回明确“不适用于此后端”，不尝试创建盘符目录、UNC 路径或网络 Named Pipe。跨平台调用期限和内存配置不能因没有 Unix root 而无法构造或被跳过。

## 3. 内存配置：拆开不同维度的上限

### 3.1 决策

删除 `pool_segment_size <= max_payload_size` 这一交叉限制，适用于 buddy 开启和关闭两种情况。一个较大的池段可以容纳多个较小的消息，池段总容量不必小于每条消息上限。只在 `pool_enabled=False` 时绕过该条件会保留同一概念错误的另一半。

保留真正约束构造和协议表示的检查：尺寸为正、索引和偏移能被线格式表示、段数有限、乘法不溢出、派生总容量正确；关闭 buddy 时显式预热必须为零。内存预算、组装容量、帧长度和每个请求/响应的实际载荷检查继续独立执行。不得通过关闭 buddy 跳过整个 `BaseIpcConfig::validate()`。

默认值和内存层级不改变。发送端继续按现有选择使用 inline、buddy 复用/扩展、dedicated SHM 和 checked chunk；接收端完整组装保留 buddy、dedicated、文件 mmap 的回退。这里的分块传输不承诺资源函数增量消费输入。请求/响应方向隔离、generation、远端完成信号、held/borrowed 失效与字节计费保持各自的真实释放时机。

### 3.2 接口与验收

无需新增开关。用户应能直接使用：

```python
cc.set_server(ipc_overrides={
    'pool_enabled': False,
    'max_payload_size': 32 * 1024 * 1024,
})
```

这一配置应通过，且不会创建 buddy 后备。dedicated SHM 仍可按需使用。启用 buddy 且池段大于消息上限的配置同样合法；实际超限请求和超限响应仍必须被拒绝，不能因池段足够大而放行。

现有 `reject_pool_segment_larger_than_payload_size` 测试要改为正确的独立维度断言，同时增加真实传输中的载荷拒绝证明，不能只把失败断言删除。覆盖 Rust resolver、Python override、环境变量、直连 IPC、relay 上游策略，以及零 SHM 预算后的既有回退。

### 3.3 Windows 映射与文件后备

Windows 的配置修正与 Unix 使用同一校验代码。关闭 buddy 后，dedicated named mapping 仍可按需建立，并继续使用当前 logon SID 的 ACL 和 `Local\` 内核命名空间；不得为了新配置转到 `Global\` 或要求管理员/全局映射权限。小的 `max_payload_size` 只限制本次消息，不能把接收方映射视图截成消息上限而丢失 allocator header 或有效段容量。

现有 [Windows ShmRegion](../../core/foundation/c2-mem/src/segment/windows.rs) 先关闭 view，再关闭 mapping handle；[SpillMapping](../../core/foundation/c2-mem/src/spill.rs) 先 unmap、再关闭 delete-on-close 文件，最后释放预算。新 deadline 的 owner 交接必须保留这个次序，不能套用 Unix 的“先 unlink 文件、稍后继续使用 mmap”步骤。调用超时、pipe 关闭和进程退出分别验证，保留中的 held/borrowed 数据不能因另一项先结束而失效。

容量校准要分别记录请求的 backing 字节、Windows 映射视图容量和实际释放状态，不将页舍入当成可读消息长度，也不以 Linux RSS 或成功 unlink 代替 Windows 证据。若后续引入局部映射，offset 必须满足系统 allocation granularity；当前完整映射方案不因本次配置修正而改成按消息长度映射。相关 OS 规则见 [MapViewOfFile](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-mapviewoffile)。

## 4. 单次调用期限：等待结束与执行结束分开

### 4.1 用户接口

新增不可变调用选项视图，推荐 Python 形式如下；以下示例是设计，不是当前可运行 API：

```python
short = cc.with_call_options(proxy, timeout=2.0)
result = short.compute(data)

with cc.hold(short.compute)(data) as held:
    consume(held.value)

unlimited = cc.with_call_options(proxy, timeout=None)
```

选项放在代理视图上，不占用 CRM 业务方法的 `timeout` 参数，不修改全局配置，不临时修改共享 client。视图与原代理共享受控连接及生命周期引用；关闭视图只释放它自己的引用，不能提前关闭原代理或同连接的其他调用。`cc.hold()` 继续使用同一原生调用事务，只改变成功响应的保留方式。

Rust 使用 `Client::with_call_options(CallOptions)` 返回同类不可变视图，生成客户端继续通过 Core `EncodedClient` 调用。优先保持现有 trait 方法签名，通过 Client 内的选项视图投影到原生事务，避免为新配置改写业务 CRM、契约哈希和已生成方法签名。

`CallTimeout` 有三种明确状态：未覆盖时 `Inherit`，从路径默认策略解析；`Unlimited` 显式关闭该调用的总等待期限；`After(Duration)` 给本次调用总预算。Python 省略 `timeout` 对应继承，显式 `None` 对应无限，`0` 表示立即到期且不得派发。负值、NaN、无穷和无法表示的时间在入口拒绝。IPC 默认仍为无限；HTTP 默认仍从 `C2_RELAY_CALL_TIMEOUT` 取得 300 秒，环境值 0 对应无限。HTTP 的计时范围拟从单个 HTTP 请求统一为一次逻辑调用，包含调用内部的路由重取；这是需要写入发布说明的语义收紧，不能宣称默认计时行为完全未变。连接池建造时的 300 秒不得额外叠加到显式 600 秒或无限调用上。

同一个视图的每次调用均创建独立 deadline。两个并发调用的 1 秒和 30 秒期限不得互相影响。`cc.connect()` 本身仍是独立操作；期限包含一次调用内部发生的重新取得路由、准入、锁/写入等待和响应接收，不追溯先前已经完成的 connect。

### 4.2 时间语义

在一次调用开始时建立单调时钟期限，后续每次允许的重试和等待只使用剩余预算，不重新计时。Python 门面只转交不透明的原生 call scope；Rust 是期限、阶段和结果竞争的唯一权威。序列化、准备载荷和复制边界检查到期状态；同步用户序列化、FFI 中不可中断的计算和操作系统调度不构成硬实时承诺。

本版远程 IPC/HTTP 的有限期限保证调用者不继续等待其结果；不承诺资源方法在同一时刻停止。对同进程同步直调，有限期限应在执行前返回明确的“不支持此执行模式”错误，用户可显式使用 IPC 获得远程等待语义。不能为了表面统一而把现有直接传对象的同步方法偷偷放到线程或字节传输中。继承和无限视图不改变直调行为。

新增原生可辨识的 `CallDeadlineExceeded`，至少携带 `pre_dispatch` 或 `dispatch_uncertain` 阶段，不能统一映射为连接丢失。过期调用不会再由框架自动重试，尤其不得重放已经可能执行的写方法。单次期限到达也不撤销 Relay 路由、不触发 OwnerBound shutdown、不影响已成功取得的 held owner。

### 4.3 原生事务和资源所有权

现有 `SendGuard::Drop` 在半帧发送时会 abort 整条流，以防下一帧被当作上一帧的后半部分。因而不能在现有调用外层直接套 `tokio::time::timeout` 并 drop future，再宣称超时不会影响并发调用。

推荐把“调用者等待者”与“原生传输事务”分离。带有限期限的调用先取得有界事务名额，再开始可能分配/派发的工作；传输事务拥有请求数据、分配释放权、request id 和状态，调用者只等待一次性结果。初始设计为每个 Runtime 最多 1024 个此类未终结事务，名额耗尽在派发前返回明确容量错误，不再创建无界等待队列或每调用 OS 线程。此上限约束新增的期限事务，不把它宣传为进程 RSS 上限或所有既有 API 的总并发限制；数值需在实施阶段通过现有负载验证。

在途数量不能替代字节边界。SHM/file/reassembly 沿用既有预算；新增传输 continuation 对自有请求副本的保留也须在接管/复制前取得有限字节 reservation，并随实际所有者释放，不因 waiter 超时退款。该 reservation 只覆盖为期限事务保留的输入，不冒称完整 HTTP 缓冲预算。Host 在实施开始时将缺省输入保留上限定为 16 GiB，与当前缺省单消息上限一致，能接管一条缺省上限的输入；它是有限准入政策，不会预分配该容量，低负载部署可显式调低。`CallExecutionLimits` 提供 max_outstanding_calls 与 retained_input_budget_bytes；代码/环境覆盖分别使用 C2_CALL_MAX_OUTSTANDING 与 C2_CALL_RETAINED_INPUT_BUDGET_BYTES，0 拒绝相应正数准入。Core/Relay 各持有自己的不可变预算域，纯计数与字节 reservation 由 c2-mem 的通用 RetentionBudget 实现，不依赖 RPC/wire 或替代 MemPool 释放权。具体负载压力验证仍是阶段 4 的验收条件。迟到 HTTP 响应的读取仍须遵守实际单消息上限，不能因为结果无人等待而省略长度/容量验证。

| 到期位置 | 调用者结果 | 原生事务责任 |
| --- | --- | --- |
| 未开始写入 | `pre_dispatch` 超时 | 与派发做原子竞争；赢家为超时时，绝不发布请求，归还本地资源 |
| 第一字节可能已写入 | `dispatch_uncertain` 超时 | 请求所有权继续由事务持有，完成必要帧/分块收尾，避免截断污染共享流 |
| 请求已发送、响应未到 | `dispatch_uncertain` 超时 | 接收并处置迟到响应，按原生释放协议结束请求所有权 |
| 成功响应与 deadline 同时发生 | 只能有一个终态 | 成功只能在期限内由原生事务确认；超时一方赢时，响应由原生回收，不交付半有效 held |

内部写入失败、真实连接关闭、无法维持帧完整性等仍按既有传输故障规则终结；“业务等待超时”本身不关闭健康共享连接。写入中或已派发的事务不能因调用者返回而提前释放对端可能使用的缓冲，也不能仅因 waiter 超时就启动 dedicated 的对端崩溃回收计时。复用现有 `RequestReleaseState`、dedicated retire permit、接收循环和 response carrier 释放权，审查每一次 owner 转移；不得另建一套与 MemPool 竞争的 free 权威。

事务名额保留到真实终结/安全交接；对端方法永久不返回时，它可以持续占用有限名额，而不能定时假装释放、复用 request id 或生成无界 orphan 表。请求 id、迟到结果与新调用必须有不可混淆的关联。shutdown、取消和 close 观察同一事务及真实租约；超时计数增加不等于 backing 计数归零。

Python native `PyCoreClient` 目前在调用期间持有客户端 mutex。实施时要改为短时取得受控引用，再在锁外执行/等待事务；close 与调用的所有权必须由 Core 统一管理，否则第二个线程可能在进入计时器之前被第一条调用无限阻塞。

### 4.4 Relay 与协议范围

0.7.1 首先提供调用方 deadline，适用于直连 IPC、Relay 发现后的本机 IPC 和 HTTP 数据面。HTTP 内部的路由取得、允许的预派发重试和 body 接收共享调用者的同一预算。期限属于 Core waiter，不能简单把它设置成 reqwest 总请求 timeout：后者会中止仍在发送的 body，使 Relay 已经开始的上游传输失去输入。有限期限到期后，有界 HTTP continuation 继续拥有请求输入及必要的上传/回收流程；真正的网络故障按传输错误处理。移除连接池级隐含总 timeout，由 Core 解析出的调用政策控制等待；独立的连接建立/网络故障策略不能冒充业务执行取消。

本版不新增“远程强制停止资源函数”语义，也不要求升级 IPC 帧版本或把本机 `Instant` 发送到远端。HTTP 调用方返回超时后，Relay 已发出的上游调用仍可继续；其等待者脱离时也必须通过有界原生事务保留必要所有权并回收迟到结果。直接 drop 上游 future、提前退还 SHM 预算或因容量/超时删除路由都不合格。

跨机器逐跳传播剩余预算、服务端队列取消与可协作中止资源函数属于另一份控制协议设计；不可把本版调用方期限称为这些能力。Relay 的实际转发/断连分支必须纳入本版审查和测试，即使 wire 不变也不能只测试客户端接口。

### 4.5 Windows I/O 完成与取消边界

[当前 Windows stream 后端](../../core/transport/c2-local/src/windows.rs) 的连接 abort 使用 `CancelIoEx(handle, NULL)`，会涉及该句柄上的全部待处理 I/O。因此单次调用期限绝不能调用这个连接级入口来实现“取消这一次 RPC”。即使将来精确取消某个 overlapped operation，也不证明整个 RPC 未派发或帧仍然完整。

`CancelIoEx` 只请求取消，不等待完成；正常完成与取消可以竞争。缓冲、overlapped 状态和拥有句柄的对象必须保留到真实完成通知，不能因函数返回或 `ERROR_NOT_FOUND` 就释放或复用；后者只说明未找到可取消请求。Tokio/mio 继续作为底层句柄/缓冲 owner，Core 不越过它们重复 CloseHandle、手动注册第二个 IOCP watcher 或提前归还预算。以上是 [Microsoft CancelIoEx 文档](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex) 的要求，也是统一原生事务需要表达的状态。

Windows byte-mode pipe 使用共同的 C-Two 帧解析，不假设一次 write 对应一次完整消息。现有 `poll_flush` 通过零字节 write 等待适配器前一笔 overlapped write 完成；这不能当成业务执行 ACK。新事务不能跳过这道完成边界，也不应改用会等待对端消费的阻塞 `FlushFileBuffers` 卡住 Tokio worker。

一次调用内部的重新建连遇到 `ERROR_PIPE_BUSY` 时，异步重试使用剩余总预算；到期仍属于未派发，不能把等待重新记满或当成路由消失。`ERROR_ACCESS_DENIED` 与 busy、broken pipe 分别分类，不忙等、不自动提权或放宽 ACL。独立 `cc.connect()` 的期限与调用内重新取得连接的期限仍按第 4.1 节区分。OS 行为依据见 [Named Pipe Client](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-client)。

验收必须在真实 Windows 上控制 pending read/write、部分帧、write 完成与 timeout 的竞争，证明同 pipe 上另一调用仍可正常收发、迟到 carrier 最终释放及 shutdown 不提前宣布资源清空。仅有 Unix cancel 测试或 Windows 交叉编译不能替代这些运行证据。

## 5. 平台端点上下文与 Unix 根目录覆盖

### 5.1 配置入口与默认

增加 `C2_IPC_ROOT` 和 Python `cc.set_local_endpoint(root=...)`；Rust 提供等价的类型化 `LocalEndpointOptions` 与 Runtime 配置方法。CLI 的 `c3 relay` 和 `c3 endpoint` 增加 `--ipc-root`。优先级为显式代码/CLI 参数 > 进程环境 > `.env` > 默认。

`root` 表示承载 C-Two 私有目录的绝对根目录，默认 `/tmp`。C-Two 仍在其中创建自己的用户私有目录和版本子目录：

```text
默认：/tmp/c2-<uidhex>/v2.2/<address-hash>.sock
覆盖：<root>/c2-<uidhex>/v2.2/<address-hash>.sock
```

```python
# 拟议接口；在第一次本地 bind/connect 之前配置。
cc.set_local_endpoint(root='/run/user/1000/myapp')
```

```bash
C2_IPC_ROOT=/run/user/1000/myapp c3 relay --bind 127.0.0.1:8080
c3 endpoint inspect ipc://worker --ipc-root /run/user/1000/myapp
```

`ipc://worker` 继续表示逻辑身份。配置父目录不等于让 SDK 拼接 socket 文件名，也不重新开放旧 `endpoint_protocol` 选择器。它只调整本地端点和协调文件的落点，不移动 SHM 名称、文件 spill 后备、配置文件或所有临时文件。

Windows 继续使用当前登录 SID 的 Named Pipe。Unix `root` 选项在 Windows 被明确拒绝为不适用，不静默忽略；逻辑 IPC 名称仍然可以自定义。本版不引入可绕过 SID 隔离的任意 pipe 路径参数。

### 5.2 配置快照与端点身份

`c2-config` 解析得到不可变 `LocalEndpointContext`，根据该上下文派生 `LocalEndpoint`。Runtime 在第一次本地 bind/connect 尝试前冻结自己的上下文，失败尝试也不能留下可切换身份的半状态。冻结后设置不同 root 返回明确配置已冻结错误；修改环境变量不影响已有连接、监听器、凭据和 sweep。新 Runtime 可以选择新 root。

路径读取与维护工具也必须持有上下文快照。纯配置查询不创建目录；inspect 捕获上下文但不启动服务或冻结独立 Runtime 的客户端内存策略。scope 创建后，sweep 的每批都使用同一上下文及目录描述符，不重新读环境。旧凭据收尾以凭据绑定的上下文为准。

端点比较、直连池、Relay 上游池和维护作用域的身份包含规范化根目录/命名空间及逻辑地址，实际连接仍验证 server id、instance id 和路由契约。同一个进程可以通过不同 Runtime/上下文访问两个 root 中的同名端点；缓存不能仅凭 `ipc://name` 命中另一个 root。

所有依赖 `LocalEndpoint::from_address()` 重新派生的路径都要改为使用已有上下文：接收方记录匹配、sweep 白名单、按槽回收、inspect/reap、direct IPC ping/shutdown、FFI 和 SDK。`EndpointSweepScope::from_addresses()` 中的目标派生尤其不能退回默认目录。新参数在 Core 原生层贯通，不能只在 Python 启动前临时改 `os.environ`。

### 5.3 凭据和跨进程收尾

现有 Unix schema 2 凭据只记录逻辑地址和端点身份，不记录 root；Windows 当前输出 schema 1 的 kernel-managed 描述，不含 Unix incarnation、device、inode。默认 namespace 分别继续输出/接受各平台原有合法格式；schema 2 的 Unix 地址明确解释为历史默认 `/tmp` 上下文，不能随 `C2_IPC_ROOT` 改变含义。

Unix 非默认 root 使用新 schema 3，记录受验证的 namespace/root 描述及既有 incarnation、inode 等身份字段。schema 3 不向 Windows 凭据强加这些字段；Windows 不能解析出一个 Unix filesystem root 后开始删除文件。解析只构造原生对象，不创建目录或授予删除权限；未知字段、格式、平台或不合法 root 严格拒绝。`reap_endpoint(address, credential)` 校验地址一致后，用 credential 的已绑定上下文执行适用的原生检查；显式传入与凭据不一致的上下文应在接触目标前拒绝。它不会在当前默认 root 或其他 root 中尝试寻找同名端点。

父控制器应在 ready 后取得并保存完整凭据，确认 child 的 OS wait 结束后再回收。OwnerBound receiver 继续保持私有继承关系，不能由 root、credential 或环境变量推导出控制能力。运行器通过显式子进程环境/配置传递 root；C-Two 不假设父进程的代码配置会自动复制到 exec 后的子进程。

### 5.4 Relay 与跨根目录访问

独立 Relay 在启动时解析并冻结自己的 endpoint context；代码设置只影响当前 SDK Runtime，不能配置另一进程。0.7.1 的一个 Relay 本地上游域使用一个 root，上游资源与它采用一致配置。不同 root 可运行不同 Relay；直接跨 root 访问通过显式上下文实现。

Relay 发现不能把远端提供的原始文件路径当作本地访问指令。推荐在 resolve 请求的可选 `X-C2-Local-Namespace` 头中发送 Core 产生的 namespace 标识，并在响应中返回可选 `local_endpoint_namespace`。标识由 OS backend、用户/登录作用域、规范化 root 及内部 namespace 版本派生，不包含原始路径，不是授权凭据。新 Relay 只在请求标识与其本地上游上下文匹配时提供自定义 root 的 IPC 候选；收到没有该头的旧客户端请求时，自定义 root 路由只提供 HTTP，默认 root 则保留原有候选。严格字段、长度和支持版本均由 Rust 验证。

新客户端只在本机 anchor、namespace 匹配且握手身份/契约均匹配时接受直连。旧 Relay 响应缺少 namespace 标识时，仅历史默认 namespace 允许原有快路径；自定义 root 的新客户端使用 HTTP，不猜测路径或扫描多个目录。该能力元数据属于可选 HTTP 发现扩展，不改变 IPC wire version、CRM 契约哈希或资源方法。实际 schema 和旧新客户端/Relay 四组合必须在阶段 3 验证；当前代码尚无此判定，不能把现有身份校验失败描述为已经会自动转 HTTP。

namespace 不匹配属于路径选择条件，不是远端 route 失效证据；必须保持正常 HTTP 路由可用。注册证明、控制 watch、数据面上游和 CLI 预登记都要使用 Relay 实例的同一上下文，不能只给数据面连接加 root。

Windows 的 namespace 标识由 Windows backend、当前 logon scope 和布局版本构成，不带伪造的 root/UID。当前用户名称相同也不能推导为同一 logon scope。新旧 Relay 协商在 Windows 同样验证；不能因没有 `root` 字段而一律丢失现有本机 IPC 快路径。实际权限仍由 OS DACL、握手身份和完整路由契约检查，HTTP metadata 不能授权打开其他登录域的 pipe 或 mapping。

### 5.5 文件系统约束

根目录需要绝对路径，拒绝显式空值、NUL、相对路径和 `..`；不进行 shell 展开，不隐式读取 `TMPDIR` 改变默认。`c2-config` 与凭据解码只做纯解析，不能要求目标仍存在或创建目录；实际打开时由 `c2-local` 通过目录描述符验证对象，分清用户提供的容器目录与 C-Two 自有私有目录。自定义 root 容器由应用/部署预先创建，C-Two 只初始化其中的用户私有目录与版本目录。既有 gate pin、nonce marker、listener lease 和 incarnation 检查全部保留，目录被替换或权限不符时报告可解释的错误。

允许常见平台路径别名所需的解析必须在首次实际打开/绑定时完成，结果固定到原生对象和生成的凭据，再次操作时核对对象身份；不能在每次 unlink 前跟随一个可能已经被替换的符号链接。既有对象保持原来的目录描述符和 namespace 描述，不因后来路径别名变化重新归属。C-Two 自有的私有目录、版本目录和协调文件不能被非受控链接替换。macOS 默认 `/tmp` 与 `/private/tmp` 的系统别名必须有明确测试，不能用一条“拒绝所有路径祖先中的 symlink”规则误伤现有默认。

在创建端点之前检查最终 socket 路径字节数和 Unix `sun_path` 上限。用户提供过长 root 时明确报错，不暗中回退 `/tmp`、截断名称或改变 hash。自动建目录只创建本配置需要的私有结构，不接管旧协议目录，不递归清扫用户 root，不凭 PID、年龄或连接失败删除未知文件。

### 5.6 Windows listener、OwnerBound 与进程退出

保留现有 Windows 独立 listener lease：关闭监听器时先断开尚未被接受的 pending instance，再释放非继承的内核租约；已接受的 stream 不持有监听租约。新监听器必须能在旧 stream/held owner 尚存时重新 bind，重复 bind 的失败方不得关闭另一个监听器。不能以“所有 pipe handle 都消失”作为监听器重启条件，也不能把 Unix unlink 提升成公共生命周期完成步骤。

[OwnerBound Windows receiver](../../core/transport/c2-local/src/owner/windows.rs) 对一个 handle 只建立一次 IOCP watcher；取消一次 wait 后复用该 watcher，已观察 EOF 后的重复 wait 返回同一终态。新调用 deadline 不取消这个 owner watcher，不关闭控制器 keepalive。子进程继续只继承显式授予的 receiver；监听、mapping 和 keepalive 句柄不能泄漏到无关子进程。代码配置和 Python 进程状态不能假定像 Unix fork 那样自动出现在 Windows 新进程中。

Windows `inspect/reap/sweep` 保留 kernel-managed / not-applicable 的真实含义：它不是“已验证进程退出”，也不是清理失败。`kill()` 后必须等待实际进程退出；owner 缓冲、对端 view、overlapped I/O 和 endpoint listener 各自观察完成。Windows 普通用户运行不需要提权；缺少当前 logon SID 的服务账户场景返回现有明确错误，不因 0.7.1 扩展 root 或 timeout 而偷偷采用更宽 ACL。

## 6. 发布与兼容性边界

目标是保留 0.7.0 默认端点、业务契约、现有调用入口和 IPC wire version 11。新调用选项属于本地策略；新目录属于显式 opt-in。HTTP 默认超时从每个请求改为逻辑调用总预算的差异按第 4 节明确记录。Core/SDK 必须同步提供能力，不能让 Python 与 Rust 形成不同默认值或第二套运行时机制。

Rust 已公开结构体不能随意增加必填字段而破坏完整 struct literal；优先增加配置方法/独立 options 对象。C FFI 优先追加 opaque context 及独立扩展函数，保留旧函数签名和数据布局；旧入口解析后也必须持有一次操作的快照。ABI 3 本身不证明新符号存在，需要明确能力检测与缺少能力时的错误。如果实现必须改变现有 ABI、强制升级 wire 或让默认通信组不再互通，就重新评估 0.7.1 的发布范围，不能把它藏进补丁版本说明。

0.7.0 的默认凭据应在新版本仍按原默认 root 生效；0.7.0 不认识非默认 root 的新凭据时应诚实拒绝。历史冻结收据保留真实 schema/ABI/源码信息，不重写成新版本证据。用户已授权本次实现、必要 PR/合并及正式发版；只有完整同源门禁通过后才发布，用户配置仍由用户选择是否覆盖。

## 7. 分阶段实施与验收计划

以下是已获授权的实施顺序。每阶段以真实 diff、固定源码、聚焦结果和 Host 审查为退出条件；Buddy 完成状态本身不构成验收。

1. **配置维度修正**：先复现错误组合，再调整交叉校验。退出条件是 buddy 两种开关、默认/小消息上限、真实请求/响应超限及既有预算回退均符合第 3 节。
2. **端点上下文基础**：同时定义并编译 UnixManaged 与 WindowsNamedPipe 上下文、resolver 和原生维护 API，再完成 Unix 目录覆盖。退出条件是两个 root 中同名端点隔离、两平台默认映射不变、Unix schema 2/Windows schema 1 含义稳定及替换目录防误删成立。
3. **端点全链路投影**：补 SDK、FFI、CLI、Relay 与 OwnerBound 子进程传参。退出条件是普通与非管理员 Windows 默认路径不回归，Unix 自定义 root 中正常关闭/异常退出/清扫可验证，Relay 跨 root 明确走 HTTP。
4. **原生期限事务**：同时设计 Unix stream 与 Windows overlapped I/O 的完成责任，建立有界准入、发送阶段和释放权，再开放 API。退出条件是两平台半帧、半分块、迟到响应、close/shutdown 竞争均安全且无重复释放、无无界遗留任务。
5. **期限 SDK 与 Relay 投影**：提供 Python/Rust 视图、HTTP 显式覆盖和错误语义。退出条件是并发不同期限、业务 `timeout` 参数、held、直调拒绝和 Relay 路径均有真实证明。
6. **集成及候选发布评估**：更新用户文档并完成受影响的原生、SDK、平台和包消费门禁。退出条件是证据关联同一源码及产物，且用户审阅发布范围。

每阶段都在 Linux/macOS 和 Windows 2022/2025 上运行该阶段受影响的检查，Windows 失败会阻止该阶段验收。阶段 1 验证 Windows resolver/实际 mapping 回退；阶段 2–3 验证默认 Named Pipe、平台凭据、CLI/FFI 和 Relay；阶段 4–5 验证真实 pending I/O、deadline、释放与 SDK。完整跨语言矩阵在集成阶段集中执行，已通过且未受修改影响的门禁不反复重跑。当前 [Windows Native workflow](../../.github/workflows/windows-native.yml) 已有两代 Windows / MSVC x64 的 local-platform 与 full 任务，实施时在现有门禁中接入必要测试，不另建一套 Windows 业务实现。本机缺少 Windows 环境时，使用对应源码的 GitHub Actions 产物与日志验收。

# Contract Release Deferred Capabilities

**Date:** 2026-07-24
**Status:** Open
**Scope:** Capabilities intentionally not provided by the route-independent `ContractRelease` and active portable-payload composition slices

## Implemented Baseline

Rust `c2-contract` now validates and canonicalizes `c-two.contract.v2`, derives and verifies its ABI/signature fingerprints, extracts ordered nested FastDB JSON values without interpreting them, constructs an immutable content-addressed `ContractRelease`, serializes a strict `c-two.contract-release-ref.v1`, verifies that reference against resolved descriptor bytes, and derives an `ExpectedRouteContract` only after a route name is supplied. The reference schema remains unchanged because its shape and route-independent meaning did not change.

Rust `c2-codegen` now delegates every opaque nested value to the official FastDB Rust projection, preserves structured Core errors, verifies Core identity and artifact hashes, deduplicates codegen by Core digest, and composes deterministic Rust/Python/TypeScript payload subtrees with C-Two-owned release metadata and target modules. Its generic composer rejects nonportable, case-colliding, duplicate, and file/directory-conflicting paths, bounds inventory/bytes, and atomically publishes a complete new regular-file tree to an absent destination. `c3` publishes that same set for all three targets; the Python native extension projects it in memory with structured errors; generated Rust compiles, generated Python imports against a locally built wheel from the audited FastDB source, and generated TypeScript type-checks while retaining C-Two's HTTP/relay/IPC/SHM transport surface.

The Python runtime now exposes only an explicit `@cc.transfer(input=..., output=...)` portable boundary whose value is `fastdb4py.payload.Payload`. FastDB Core compiles the nested value and owns its canonical identity, digest guard, binary open, views, materialization, and invalidation. C-Two transports opaque binary bytes, opens copy-backed receive owners, invalidates held outputs before releasing their response lease, invalidates borrowed resource inputs before releasing the request lease, and preserves FastDB code, symbol, path, message, and details in C-Two errors. The old call-db inference, sidecar, bridge, public exports, tests, examples, and active benchmark variants are removed. The final bidirectional runtime proof remains open until the later implementation task closes it.

## Open Capabilities

| Capability | Current limitation | Why not in this slice | Impact | Owner | Exit criteria |
| --- | --- | --- | --- | --- | --- |
| Contract compatibility | Release matching is exact by descriptor digest; no semver/range acceptance exists. | Compatibility requires explicit ABI/signature evolution rules after exact identity is stable. | Consumers cannot request a compatible range and must pin one release. | C-Two | Rust-owned compatibility rules reject ambiguity and ABI-incompatible matches with structured errors and cross-language vectors. |
| Resolver and storage | C-Two defines no registry, URL, object store, or digest resolver. | Storage and distribution topology are consumer/deployment concerns. | A ref alone cannot fetch its descriptor. | Catalog/deployment owner | A consumer resolves bytes by digest, then passes them through `ContractRelease` verification without C-Two owning catalog state. |
| Signature and trust | A release digest proves integrity, not publisher identity, authorization, or revocation state. | C-Two does not own Authority identity, key distribution, policy, or revocation. | Callers must not treat a valid release as trusted by itself. | Authority/policy owner, including Toodle where applicable | A downstream signed envelope binds the C-Two ref to its Authority trust model without changing C-Two release identity. |
| Outer descriptor admission limits | `c2-contract` validates field text and fingerprint sizes but does not yet expose caller-configurable total-source, JSON-value, or method-count limits for the outer C-Two document. FastDB Core applies its own limits only after each nested value is delegated. | One fixed C-Two byte limit could reject legitimate multi-binding contracts or become an accidental FastDB limit; the limits need an explicit outer-owner API and consistent Rust/Python/CLI projection. | Callers admitting untrusted descriptors must currently enforce a source-size limit before invoking `c2-contract`; otherwise an oversized outer document can consume memory before FastDB sees a nested value. | C-Two | A versioned `ContractLimits` API bounds total source bytes, JSON values/depth, methods, and extracted nested bytes; defaults align with transport capacity, every projection uses the same limits, and hostile boundary tests prove deterministic typed rejection. |
| Complete Rust SDK | The active codegen slice adds a real route-bound Rust IPC client plus public payload adapter functions that a host can consume, but the executable Rust host and bidirectional runtime proof remain later tasks; there is also no single ergonomic facade for every HTTP, relay, discovery, shutdown, and administration operation. | A placeholder package would hide the actual maturity of the existing core crates. The runtime slice must first prove real client and host callers. | Rust payload users can compile the generated client/adapter surface now, but must use the lower-level core server crates for a host until the recorded runtime proof and supported facade exist. | C-Two | One supported Rust SDK surface covers the proven core IPC client and host, HTTP/relay, server, lifecycle, and contract operations with runnable examples and cross-language tests. |
| FastDB Rust package distribution | FastDB now has the required official Rust projection at audited commit `6b9d0a55f27bb22fd13f867f321db821f21e777c`, but its crates remain `publish = false`, package metadata remains 0.1.22, and this goal forbids version, push, tag, publication, or release changes. C-Two therefore declares `fastdb = { path = "../../../../fastdb/bindings/rust/fastdb" }` only in `core/foundation/c2-codegen/Cargo.toml`; Cargo cannot pin a path dependency to that Git commit, so the local proof audits the sibling HEAD separately. | Publishing is an independent owner-repository release action requiring explicit authorization. | The local C-Two proof requires the sibling checkout at that relative location and audited revision; a standalone C-Two source archive cannot fetch this unreleased dependency from a registry, and a later local checkout change is not rejected by Cargo itself. | FastDB release owner | An authorized FastDB release publishes or otherwise pins the official Rust crates and C++ Core artifacts; C-Two replaces the local sibling dependency with that immutable release and reruns all gates. |
| FastDB Python/TypeScript package distribution | The official sibling sources expose `fastdb4py.payload` and `fastdb4ts/payload`, but the already-published `fastdb4py==0.1.22` wheel resolved by C-Two predates the payload package, and no authorized FastDB Python/TypeScript release is part of this goal. Python tests therefore consume a local wheel built from audited FastDB commit `6b9d0a55f27bb22fd13f867f321db821f21e777c`, while TypeScript type-checks against the sibling package source. The local wheel retains 0.1.22 metadata and is evidence only, not a registry release. | Reusing an older published version number for newer local APIs would make dependency metadata falsely claim registry availability; changing or publishing FastDB versions is explicitly out of scope. | Generated artifacts and the C-Two Python runtime are correct against the audited local implementation but are not independently installable from current registries alone. | FastDB release owner | Authorized immutable FastDB Python and TypeScript packages containing the audited payload APIs are published; C-Two pins compatible versions and repeats clean-environment import/type-check/package tests without sibling paths or locally built wheels. |
| Python portable binding shape | One portable Python method accepts zero inputs or exactly one positional `Payload`, and returns either no value or one `Payload`. It does not infer FastDB specs from annotations, synthesize domain/dataframe/GIS shapes, accept keyword-only payload parameters, or expose multiple independently encoded payload arguments. | The one-envelope shape is the language-neutral `c-two.contract.v2` boundary and prevents C-Two from becoming a second FastDB schema/type authority. Keyword-only invocation is not yet mapped consistently through thread-local direct calls, IPC dispatch, and generated non-Python clients. | Users explicitly build/adapt one FastDB payload outside the CRM method. Existing annotation-inferred domain methods must be redesigned rather than silently migrated, and Python callers may use a positional or positional-or-keyword payload parameter but not a keyword-only declaration. | C-Two for invocation ergonomics; application owners for domain adapters | Any broader invocation shape has an accepted outer-contract design, works equivalently in Rust and Python generated/runtime surfaces, preserves one Core-owned payload meaning, and passes thread/IPC/relay plus codegen interoperability tests without annotation inference. |
| Python-only pickle fallback | Ordinary Python CRM methods still use the existing pickle runtime when no explicit portable binding is present, but portable descriptor export and codegen reject those methods with a `python_only_pickle` diagnostic. | Removing the local Python fallback is a separate product compatibility decision; presenting it as portable would violate the cross-language authority contract. | Python prototypes continue to run between Python peers, but they cannot be released as `c-two.contract.v2` or consumed by generated Rust clients. | C-Two | Either the fallback remains explicitly Python-only with maintained diagnostics, or a separately accepted migration removes it and all callers; it must never become a portable fallback. |
| Explicit portable-payload performance benchmark | The old annotation-inferred FastDB Kostya variants were deleted. The tracked benchmark currently retains only truthful `pickle-records` and `pickle-arrays` baselines; it does not yet publish a new explicit `Payload` throughput or retained-owner result. | A benchmark-only schema/runtime path before the generic Task 5 interop harness would produce evidence for a special case rather than the supported public composition path. | There is currently correctness and lifecycle evidence for explicit payload IPC, but no comparative performance claim for that path. | C-Two | The Task 5 public generated/runtime harness supplies the same record/object-graph payloads to a reproducible benchmark, records copy/direct/staged and retained-owner facts accurately, and adds guarded benchmark tests without private APIs. |
| Raw retained-buffer escape | Python `HeldResult` exposes raw retained bytes only through the explicitly named `unsafe_buffer`. C-Two invalidates the FastDB owner and releases its own memoryview/transport lease, but it cannot revoke NumPy arrays, pointers, or additional memoryviews that user code derives from that raw buffer. The former neutral `.buffer` alias is not retained. | Python's buffer protocol does not provide a general revocation mechanism for arbitrary downstream aliases. Calling the escape safe would overstate the lifetime guarantee. | Normal code should use `held.value` and FastDB checked views/materialization. Advanced raw-buffer users own alias lifetime and may prevent deterministic transport release until every export is dropped. | C-Two for naming/documentation; application owner after escape | A future checked buffer abstraction can replace this limitation only if it proves all supported derived access is revocable across Python/NumPy/native consumers; otherwise the escape remains explicitly unsafe. |
| Direct final-backing construction | The initial Rust/Python receive path opens an owned copy, and response transport may copy completed FastDB binary bytes into C-Two-managed SHM. | A truthful direct claim requires a public adapter that gives FastDB the final C-Two backing during resource execution in every supported SDK. | Correctness, view, materialize, and invalidation are proven, but the integration is not described as response-SHM zero-copy. | C-Two with FastDB public backing APIs | Rust and Python resource-time builders receive the final C-Two backing, FastDB reports direct/staged execution accurately, fallback is tested, and no post-build repack occurs on the proven direct path. |
| TypeScript opaque response allocators | The generated FastDB adapter accepts the default `Uint8Array`/`ArrayBuffer` responses from the retained C-Two transports and opens an owned FastDB copy. A caller-selected allocator whose returned payload is only an opaque provider object cannot be decoded because the existing transport result does not expose its writable byte view to the contract adapter; the adapter rejects that case and releases the response. | Inventing a C-Two-specific FastDB backing or reaching into provider objects would violate the public ownership boundary. A general retained-response contract must be designed with the transport and FastDB owners together. | HTTP/IPC/relay/SHM transport factories remain available, but FastDB decoding currently requires their default byte-visible response form. | C-Two with FastDB public backing APIs | A versioned byte-visible/owned response interface works across TypeScript transports and FastDB's public external-backing API, proves release and invalidation ordering, and retains provider-owned storage without private-field access. |
| Existing-tree artifact update | The first publisher atomically creates a complete new destination tree and refuses an existing destination. | Blind merging can retain stale artifacts, follow symlinks, or leave partial state without a prior manifest and rollback protocol. | Project generators must compose into a fresh tree and adopt it separately. | C-Two | A versioned prior-manifest protocol validates ownership, detects user edits/stale files, stages a complete replacement, rolls back on failure, and has cross-platform symlink/path tests. |
| Crash-durable or hostile-parent publication | The publisher synchronizes each regular file and performs an atomic no-replace directory rename under a pre-existing parent, but it does not synchronize every created directory and the parent after rename. It also assumes the caller-controlled parent path remains stable while publishing. | Cross-platform crash durability and adversarial path-component replacement require platform-specific directory-handle/relative-operation semantics and tests beyond the current local codegen destination contract. | Concurrent readers never observe a partial winning tree, but callers must not treat success as a power-loss durability receipt or publish inside a parent concurrently controlled by an adversary. | C-Two | A versioned publisher uses supported directory handles and relative no-follow operations, synchronizes staged directories plus the destination parent where the platform permits it, documents weaker platforms explicitly, and passes crash/fault-injection and hostile-parent race tests. |
| Non-regular artifact metadata | `ContractArtifact` carries path, semantic kind, bytes, hash, and provenance, and the publisher creates regular files only. It does not represent executable bits, ownership, extended attributes, hard links, or symbolic links. | No current C-Two/FastDB generator requires those filesystem objects, and guessing cross-platform permission/link semantics would weaken the path-safety contract. | The composer is general across regular source/metadata/binary files, but it cannot yet publish executable tooling or link-based package layouts faithfully. | C-Two | A versioned artifact metadata model defines portable modes and any supported link semantics, rejects unsupported platform mappings, and has real producer plus cross-platform publication tests. |
| C-Two C++ SDK/codegen | FastDB can generate C++ payload artifacts, but C-Two has no formal C++ route/transport SDK to compose with them. | Generating payload-only C++ under a C-Two command would falsely imply a usable C-Two C++ client. | C++ users can consume FastDB directly but not a generated C-Two contract client. | C-Two | A real C++ route-bound client/server facade exists and C-Two composes it with Core-generated C++ payload artifacts in compile/run tests. |
| Bidirectional Rust/Python proof | The active implementation must still produce the final recorded runtime evidence. | Design and API presence are not substitutes for an executed cross-language path. | The row remains open until the final harness passes. | C-Two with FastDB dependency | Rust client to Python CRM, Python client to Rust CRM, and Rust-to-Rust calls pass for no-payload plus record/object-graph FastDB request/response; mismatch and invalidation fail structurally. |
| Python native strict-Clippy baseline | On Rust 1.91, `cargo clippy --manifest-path sdk/python/native/Cargo.toml --all-targets -- -D warnings` currently reports 43 diagnostics in existing transport/memory/runtime FFI modules; the new `codegen_ffi.rs` contributes none, `cargo check --all-features` passes, and the diagnostics include PyO3 functions whose argument counts mirror the current Python API as well as representation and mechanical lint findings. | Resolving the full set safely requires a separately reviewed FFI cleanup rather than broad `allow` attributes or incidental API/representation changes inside contract codegen. | Task 3 can prove its new native projection but cannot claim the repository-wide native strict-Clippy gate is green on this toolchain. | C-Two | Refactor or narrowly justify every reported site without changing Python behavior, run native tests across supported Python versions, and make the exact strict-Clippy command pass with no blanket suppression. |
| Hosted verification and release | This goal performs local verification only and explicitly forbids version bump, push, tag, publish, and release. | Hosted runners and release credentials are external actions and are not implied by local readiness. | Local evidence must not be reported as a published release or hosted pass. | Repository release owners | Hosted CI passes the frozen commits, then separately authorized version/push/tag/publish/release steps complete with immutable provenance. |

## Guardrail

Do not add a JSON/pickle portable transport, a C-Two-owned FastDB parser, an unsigned `trusted` flag, a compatibility alias for call-db, an unsafe existing-tree merge, or a placeholder SDK to make these rows appear complete.

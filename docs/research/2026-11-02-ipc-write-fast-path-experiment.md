# IPC 写路径快速通道：小调用变慢的诊断与一次不采纳的实验

日期：2026-11-02。起因：单属主释放这一批（[ADR 0001](../decisions/0001-single-owner-release.md)）让每条 IPC 连接都经过一个独立的写任务，配对基准显示小载荷调用因此变慢，超过了[设计](../design/2026-11-01-protocol-batch-design.md)第 247 行定的门槛：按每个平台至少五组配对的中位比值，candidate 的 P50 不超过 baseline 的 105%，P99 不超过 110%，吞吐不低于 95%。本文记录变慢的原因、一次"写路径快速通道"实验的做法与测量，以及不采纳它的理由，供以后再碰这条路径时参考。状态：快速通道没有合入；小调用的回退由用户于 2026-11-02 接受。baseline 是本批的实现基线 `b861f994`；配对数据来自 fork 上的 GitHub Actions 托管 runner，诊断与计数在 macOS arm64 本机做；原始收据与日志保存在本地，没有放进仓库。

## 1. 变慢在哪里

本批之前，提交调用的线程直接把帧写进连接。本批改为每条连接有一个写任务：调用先入队，写任务被唤醒后写出，释放帧也由它批量带出。CI 的配对基准（run 41394919731，candidate `26403fe5`）在 Linux 上的中位比值：1 字节调用 P50 1.25–1.27、P99 1.20–1.22、吞吐 0.78–0.83；关闭 buddy 的 64 KiB 突发 P50 1.10–1.16；走 SHM 的 64 KiB 突发基本持平；4 MiB 载荷 P50 快 6%–9%。合入本批全部修正之后的最终候选 `d646fc12`（run 41444159385，四个平台各五组）结果相近：1 字节调用 P50 在 Linux 1.18–1.20、Windows x64 1.18–1.21、Windows ARM64 1.13、macOS 1.25–1.28，吞吐 0.83–0.90；走 buddy 的 64 KiB 在 Linux 与 Windows 上为 0.97–1.06；关闭 buddy 的 64 KiB 为 1.05–1.20；4 MiB 在 Linux 与 Windows 上快 6%–14%，macOS 为 0.99–1.07。

一次只诊断的工作在 `b861f994..26403fe5` 的可构建提交之间做了性能二分（共 165 组配对）。变慢集中在 P0 到 P8b 这一段（1 字节 P50 比值 1.22），之后各段在 ±6% 以内。写任务的排队在客户端由 `643be217`、在服务端由 `d438a1c9` 引入。轻量计时探针的结果：客户端提交一次 1 字节调用中位 17.1 μs，其中入队等待 4.6 μs、唤醒 7.0 μs，baseline 直接写 1.8 μs；服务端提交 3.8 μs，baseline 2.0 μs；编码、复制与 Core 簿记各段都不到 1 μs。关闭 buddy 的 64 KiB 那一行实际走独占 SHM，每次调用还多两次释放帧的写入。

## 2. 快速通道的做法

改法是：写端空闲、前面没有排队或已预留的写时，提交调用的任务直接开始这次写，并在一个连接级的写槽里以空 waker 轮询一次；写完就结束，没写完的部分由原来的写任务用自己的 waker 接着轮询。任何时刻只有一个写者，不新增开关或第二套写法。客户端与服务端都这样做；Node 有自己的写链，没有改。

动手之前先列出单写者原本保证的性质，每条配一个快速通道下的测试：同一连接上业务帧、释放帧、续片、控制帧与 DISCONNECT 的先后，以及提交者之间的先后；释放帧的批量与前缀；写超时只停准入、继续原写；写队列背压与 `max_pending_requests` 的计数；已开始的写在调用方取消后不丢、不重放；停用、驱逐与关闭让已发出的调用做完；对端结束与帧边界失效；先释放存储再发布物理关闭；唤醒不丢；Unix 与 Windows 的部分写；DISCONNECT 的关闭原因先于 ACK 的写入记下。

一次独立审查找出两处被绕过的保证，都已复现并修正：

- 服务端写释放批时忽略了 `write_batch` 的错误，立刻重试同一批。写缓冲的分配持续失败时，这个循环不让出线程，单线程执行器会被占住；基线在这里结束写任务，设计的规定是"存储不足则报告并停用"。
- 服务端发控制回复时阻塞地拿写槽的锁，而写任务持着同一把锁轮询整帧的写入，读循环因此要等写锁。这违背了设计第 82 行"Rust 控制读取不等写锁"。修正为只在不争用时内联（`try_lock`），否则直接入队，计数改用独立的原子变量。

审查还指出几个测试比名字说得弱（没有真实的释放记录、期望值出自被测对象、pending 表为空、取消后只比同值字节），都已补实。

## 3. 测量

计数（macOS，各 720 次测量调用）：客户端 100% 的写走了快速通道，服务端 99%–100%（3 次 `try_lock` 失败）；内联的写全部在第一次轮询就写完，没有一次交给写任务继续。但客户端每次内联写完后仍无条件唤醒写任务，写任务被唤醒的次数几乎没降（616 次对 615 次）；服务端从 416 次降到 214 次。

CI 的配对基准（实验分支 `47e2dd89` = `9cb1bb63` + 实验代码；Linux 的数据最稳定，macOS 托管 runner 噪声大）：

| 比较 | 1 字节 P50 | 1 字节吞吐 | 64 KiB 突发 P50（关 buddy / 开 buddy） | 4 MiB P50 |
|---|---|---|---|---|
| 实验对集成提交 `9cb1bb63`，Linux（run 41430497366） | 0.91 | 1.08–1.09 | 0.87–1.04 / 0.93–1.01 | 0.98–1.01 |
| 实验对集成提交 `9cb1bb63`，macOS | 0.87–0.89 | 1.06–1.14 | 波动 0.71–1.20 | 0.93 |
| 实验对设计基线 `b861f994`，Linux（run 41430492288） | 1.05–1.08 | 0.94 | 1.05–1.19 / 0.84–0.99 | 0.84–0.86 |

也就是说，快速通道让严格串行的小调用快了约 9%–13%，把 1 字节调用相对设计基线的回退从约 25% 收窄到 5%–8%，仍没回到门槛以内；64 KiB 以上基本没有差别。

## 4. 不采纳的理由

- 它省下的是每次调用固定的一段排队与唤醒开销（macOS 本机约 10 μs，Linux CI runner 上约 26 μs），只在调用本身很短、而且严格串行时看得出来。写端忙的时候（并发调用、批量请求）它本来就不触发，排队的写任务反而能把多个帧合并写出。
- 收益不足以回到门槛，代价却是在核心写路径上多开一个写入口；独立审查在那里一次就找出两处被绕过的保证，说明它扩大了以后每次改动都要守的面。
- 实验分支的全量 CI（run 41430259349）还有两项失败：Windows x64 上客户端发 DISCONNECT 后断开，服务端记下的第一个关闭原因是 `IoError` 而不是 `PeerCloseMessage`；Linux 上服务端提前拒绝一次分片上传之后，生成的 TypeScript 客户端在同一连接上的下一次调用失败。当时因为不带快速通道的候选 `d646fc12` 在同样的 CI（run 41444148760）上全部通过，把这两项判为快速通道引起。这个判断不成立：2026-11-03 上游 PR 的 CI（run 41484700985）在不带快速通道的代码上出现了同一项 Linux 失败，Windows 上也出现了两处关闭时的竞态。它们是本批原有的偶发缺陷，另行修复；不采纳快速通道的理由只剩前两条与下一条。
- 需要大量小调用的场景，例如客户端逐像素读服务端的 DEM 栅格做统计，瓶颈在调用次数而不在单次开销。按最终候选那次配对在 Linux CI runner 上实测的 1 字节调用中位延迟（本批之前约 250 μs，本批约 294 μs）估算，1 亿次调用在本批之前要约 6.9 小时，本批多出约 1.2 小时，快速通道（约 9%）能收回约 0.7 小时；改成按行或按瓦片批量读，或者把统计写成资源方法在服务端就地计算，能把调用次数降三个数量级以上。

## 5. 以后再碰这条路径时

- 更有效的方向是减少调用次数：下游应用用批量读或资源方法就地计算；C-Two 可以提供批量只读的无序并发原语（已记入[待办](../design/backlog.md)）。
- 如果仍要压低单次开销，先处理快速通道实验留下的三处：内联写完后无条件唤醒写任务、服务端的提交开销、SHM 路径上的释放帧成本。共享内存归还环按设计第二节的约定，只在释放通道被证实是瓶颈时才考虑。
- 实验的最终补丁、计数探针与各轮收据保存在本地；改这条路径之前，先用配对基准在同一台机器上交替测量，CI 的 Linux runner 数据最稳定。

# 流式 RPC：流的形态、流控、取消、错误、关闭与重试的业界做法

日期：2026-11-03。起因：C-Two 要设计用户可见的流式 RPC。现在的调用都是一元的：直接 IPC 走一条按请求 id 复用调用的分帧双工连接，共享内存借出靠释放记录归还；另有 HTTP relay。本文为之后的设计收集成熟系统的一手事实，按九个问题分节：流的种类与 handler 形态、流控与背压、半关闭与取消、流中途的错误、顺序、大消息与写调度、关闭时仍开着的流、经过中间层的背压、重试与幂等。gRPC 与 HTTP/2 写得最细，QUIC、Cap'n Proto、Arrow Flight、Ray 与 Envoy 只写各自有区别的地方。关闭时在途一元调用的处理、两步 GOAWAY、透明重试在库内部的区分，已在[在途调用调研](2026-11-02-in-flight-calls-at-close-survey.md)第 1 节写过，本文只补流式的部分。状态：调研记录，只列事实，不给建议，没有改动代码。来源是规范、gRFC、官方文档与固定到标签或提交的源码；标"推论"的是本文据这些来源所做的推断。本文没有在本机运行任何程序，凡是关于运行时行为的说法都来自读文档与源码。查证都在 2026-11-03 做，版本：gRPC C core 与 Python v1.85.1、grpc-go v1.85.0、grpc-java v1.85.1（与在途调用调研相同），gRFC A6 与 A9（grpc/proposal 提交 89f34f2），grpc.io 文档（grpc/grpc.io 提交 d4b8085，网站仓库不随版本打标签），RFC 9113、RFC 9000、RFC 9114，Cap'n Proto v1.5.0，Apache Arrow 26.0.1，Ray 2.59.0，Envoy v1.40.2，CPython v3.15.2。

## 1. 流的种类、handler 形态与并发上限

结论：gRPC 定义四种方法：一元、服务端流、客户端流、双向流。handler 的形态与它占用什么资源因实现而异：Python 同步栈的 handler 在线程池里占一个线程直到整个流结束，等下一条请求、等流控额度时都占着；grpc.aio 的协程 handler 不占线程，但普通生成器 handler 仍要在线程池里占一个线程跑完；grpc-go 每个流一个 goroutine，阻塞的是 goroutine；grpc-java 是回调式，库本身不在 I/O 上阻塞。并发流数有三层上限：HTTP/2 的 SETTINGS_MAX_CONCURRENT_STREAMS（规范初始不限，C core、grpc-go、grpc-java 的服务端默认都不限，Envoy v1.40.2 默认 1024）；库的并发 RPC 上限（Python 的 `maximum_concurrent_rpcs`，默认不限）；执行资源（Python 线程池、Java 执行器）。Cap'n Proto 的流是对一个回调对象的一串调用，流式方法在服务端串行执行；Arrow Flight 是建在 gRPC 上的三个流式方法；Ray 的流是生成器任务产出的一串 ObjectRef。

**gRPC 的四种方法。** 服务端流的客户端读返回的流直到没有更多消息；客户端流的客户端写完后等服务端读完并回一个响应；双向流的两个方向独立，双方可按任意次序读写，例如服务端收齐再写，或读一条写一条；前两种写明 "gRPC guarantees message ordering within an individual RPC call"，双向流写的是每个方向内保序（[core-concepts.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/what-is-grpc/core-concepts.md?plain=1#L50-L75)）。服务端流的服务端发完全部消息后再发状态与可选的 trailing metadata，客户端收齐全部消息才算完成；客户端流的服务端"typically but not necessarily"在收齐请求后回响应（[同文件](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/what-is-grpc/core-concepts.md?plain=1#L138-L152)）。双方各自独立判断调用成败，结论可能不一致；服务端也可以在客户端发完全部请求之前就结束调用（[同文件](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/what-is-grpc/core-concepts.md?plain=1#L179-L186)）。

**Python 同步服务端。** `grpc.server(thread_pool, ..., maximum_concurrent_rpcs=None)`：handler 在传入的 `ThreadPoolExecutor` 里执行；`maximum_concurrent_rpcs` 是返回 RESOURCE_EXHAUSTED 之前服务的最大并发 RPC 数，None 表示不限（[__init__.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/__init__.py#L2194-L2228)）。实现按整个服务端计数：每交出一个 handler 计数加一，handler 结束减一，达到上限的新 RPC 以 "Concurrent RPC limit exceeded!" 拒绝（[_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L1268-L1288)、[L1059-L1120](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L1059-L1120)）。服务端流的 handler 返回响应迭代器，客户端流与双向流的 handler 收到 `request_iterator`，四种 handler 都用 `thread_pool.submit` 交给线程池，实验性的 `experimental_thread_pool` 属性可为单个方法另指定线程池（[_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L874-L978)）。请求迭代器的 `next()` 先发一个接收消息的操作，再在 `state.condition.wait()` 上等到消息到达；客户端取消时抛 `grpc.RpcError`，客户端半关闭且没有更多消息时抛 `StopIteration`（[L485-L544](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L485-L544)）。服务端流每产出一个响应，`_send_response` 发出发送操作后在同一条件变量上等到这个操作完成（[L708-L740](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L708-L740)），而 C core 的发送操作要等这条消息的字节都通过了流控才完成（第 2 节）。所以同步 handler 在整个流期间占一个线程，等下一条请求时、等流控额度时都占着（推论，据上述代码）。`ThreadPoolExecutor` 默认 `max_workers = min(32, CPU 数 + 4)`，工作队列是无界的 `SimpleQueue`（[thread.py](https://github.com/python/cpython/blob/v3.15.2/Lib/concurrent/futures/thread.py#L181-L190)）；线程全被长流占住后，新到的 RPC 已被库接受、排在队列里等线程（推论，未运行）。性能指南：Python 的流式 RPC 要为接收、可能还为发送另建线程，"much slower than unary RPCs"，建议试 asyncio（[performance.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/guides/performance.md?plain=1#L88-L97)）。客户端侧，请求迭代器由一个守护线程消费：每取一个请求发一个发送操作，等它完成再取下一个；迭代器耗尽后发半关闭（[_channel.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_channel.py#L259-L350)）。

**grpc.aio。** 流式 handler 有三种：用 `context.read()`/`context.write()` 的协程、异步生成器、普通生成器；普通生成器交给线程池，由一个线程逐项迭代到结束，每项经容量为 1 的 `asyncio.Queue` 交回事件循环（[server.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/server.pyx.pxi#L478-L545)、[common.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/common.pyx.pxi#L142-L173)）。每个 RPC 是事件循环上的一个任务（[server.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/server.pyx.pxi#L795-L807)）。`context.write()` 等发送操作完成才返回，`context.read()` 在流结束时返回 `EOF`（[L127-L148](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/server.pyx.pxi#L127-L148)、[callback_common.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/callback_common.pyx.pxi#L77-L103)）。`grpc.aio.server(migration_thread_pool=...)` 的线程池只用来执行非 asyncio 的 handler（[aio/_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/aio/_server.py#L225-L262)）。`maximum_concurrent_rpcs` 由 `_ConcurrentRpcLimiter` 计数，超出时同样回 RESOURCE_EXHAUSTED（[server.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/server.pyx.pxi#L852-L862)、[L910-L930](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/server.pyx.pxi#L910-L930)）。客户端调用的 `read()` 要由多个协程串行调用，迭代器与 read/write 两种 API 不能在一个 RPC 上混用（[_base_call.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/aio/_base_call.py#L166-L257)）。

**grpc-go。** 每个注册的 handler 在自己的 goroutine 里被调用，流式 handler 也一样（[concurrency.md](https://github.com/grpc/grpc-go/blob/v1.85.0/Documentation/concurrency.md?plain=1#L26-L32)）；实现是每个流 `go f()`，只有设了实验性的 `NumStreamWorkers` 才改用固定数目的 worker goroutine（[server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L1088-L1107)、[L626-L643](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L626-L643)）。`ServerStream.SendMsg` 阻塞到有足够的流控额度把消息交给传输、或流结束、或流断开，不等客户端收到；`RecvMsg` 阻塞到收到消息或流结束，客户端 CloseSend 之后返回 `io.EOF`；可以一个 goroutine 发、另一个收，但同一方向不能有多个 goroutine 并发调用（[stream.go](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L1687-L1731)、[concurrency.md](https://github.com/grpc/grpc-go/blob/v1.85.0/Documentation/concurrency.md?plain=1#L17-L24)）。`MaxConcurrentStreams` 默认 `math.MaxUint32`，此时服务端的 SETTINGS 里根本不带这一项（[server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L189-L191)、[L464-L474](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L464-L474)、[http2_server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_server.go#L182-L191)）；设了上限时，超出的新流被 RST_STREAM(REFUSED_STREAM) 拒绝（[http2_server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_server.go#L551-L560)）。此外，`serveStreams` 为每条传输建一个与 `MaxConcurrentStreams` 等量的阻塞信号量，分发新流之前 `acquire`，handler 返回之后才 `release`，配额用尽时 `acquire` 阻塞调用者（[server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L1088-L1107)、[L1968-L1997](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L1968-L1997)）；推论：设了上限时，限住的还有仍在运行的 handler 数，而不只是打开的流数。客户端在收到服务端的 SETTINGS 之前按 100 个并发流计（[defaults.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/defaults.go#L34)、[http2_client.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_client.go#L371-L372)）。

**grpc-java。** 回调式：应用实现 inbound 的 `StreamObserver`，库提供 outbound 的；`StreamObserver` 不要求线程安全；"gRPC guarantees it does not block on I/O in its implementation"，应用可以在回调里阻塞，但会推迟其他回调，因为这些方法不能并发调用（[StreamObserver.java](https://github.com/grpc/grpc-java/blob/v1.85.1/stub/src/main/java/io/grpc/stub/StreamObserver.java#L19-L46)）。`ServerCall.Listener` 的实现"free to block for extended periods of time"，调用方同一时刻只调用它一次；回调的先后是 contexts、消息、半关闭、完成（[ServerCall.java](https://github.com/grpc/grpc-java/blob/v1.85.1/api/src/main/java/io/grpc/ServerCall.java#L47-L55)）。服务端回调默认跑在一个静态的 cached 线程池里，文档鼓励自行指定限制线程数的执行器；`directExecutor` 直接在传输线程里跑应用代码，"must not block under any circumstances"（[ServerBuilder.java](https://github.com/grpc/grpc-java/blob/v1.85.1/api/src/main/java/io/grpc/ServerBuilder.java#L47-L77)）。性能指南同样建议按负载提供限制线程数的执行器（[performance.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/guides/performance.md?plain=1#L82-L86)）。Netty 服务端的 `maxConcurrentCallsPerConnection` 默认不限（[NettyServerBuilder.java](https://github.com/grpc/grpc-java/blob/v1.85.1/netty/src/main/java/io/grpc/netty/NettyServerBuilder.java#L409-L418)）。

**HTTP/2 与 C core 的并发流上限。** RFC 9113：SETTINGS_MAX_CONCURRENT_STREAMS 是发送方允许对方新建的流数，初始不限，建议不小于 100；处于 open 与两种 half-closed 状态的流都计数；超过上限的 HEADERS 要作为 PROTOCOL_ERROR 或 REFUSED_STREAM 流错误处理，选哪一个决定对方能否自动重试；调低上限时可以关掉多出的流，也可以让它们做完（[§5.1.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.1.2)、[§6.5.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.5.2)）。C core 的 `GRPC_ARG_MAX_CONCURRENT_STREAMS` 只对服务端有效，默认 -1（不显式限制），内部默认值为 2^32-1（[channel_arg_names.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpc/impl/channel_arg_names.h#L37-L39)、[chttp2_transport.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L512-L519)、[http2_settings.h](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/http2_settings.h#L57-L60)）。服务端对超出已确认上限的新流回 RST_STREAM(REFUSED_STREAM)，内存压力高时回 ENHANCE_YOUR_CALM（[parsing.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/parsing.cc#L705-L735)）。客户端超出对端上限的流在本地排队（[chttp2_transport.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L1469)）；性能指南把这列为长流的已知问题：连接上的活动 RPC 达到上限后，其余 RPC 在客户端排队，等活动 RPC 结束才发出，变通办法是为高负载另建通道或用通道池（[performance.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/guides/performance.md?plain=1#L30-L49)）。

**QUIC。** 流数按累计计：对方只能打开流号小于"max_streams × 4 + 该类首个流号"的流；初始值来自传输参数，之后用 MAX_STREAMS 提高，单向与双向分开计；超过上限是 STREAM_LIMIT_ERROR 连接错误（[RFC 9000 §4.6](https://www.rfc-editor.org/rfc/rfc9000.html#section-4.6)）。`initial_max_streams_bidi` 缺省或为 0 时，对方在收到 MAX_STREAMS 之前不能开双向流（[§18.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-18.2)）。流可以很长，"can last the entire duration of a connection"（[§2](https://www.rfc-editor.org/rfc/rfc9000.html#section-2)）。

**Cap'n Proto。** 0.8 的发布说明：流是一种模式而不是内置特性。服务端到客户端的流是调用方传入一个回调对象，客户端到服务端的流是服务端返回一个回调对象，每条流消息是对这个临时对象的一次调用；靠 promise pipelining，客户端不必等第一个调用返回就能开始调用回调（[0.8 发布说明](https://github.com/capnproto/capnproto/blob/v1.5.0/doc/_posts/2020-04-23-capnproto-0.8.md?plain=1#L19-L53)）。声明为 `-> stream` 的方法像返回 `()` 的方法，只是客户端库在它认为该发下一条时就让调用"返回"（[同上](https://github.com/capnproto/capnproto/blob/v1.5.0/doc/_posts/2020-04-23-capnproto-0.8.md?plain=1#L61-L75)）。服务端：流式方法执行期间，"No other calls should be permitted until this call finishes"，同一对象上的其他调用排队到它完成（[capability.h](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/capability.h#L484-L491)、[capability.c++](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/capability.c++#L604-L620)、[L829-L858](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/capability.c++#L829-L858)）。

**Arrow Flight。** `DoGet(Ticket) returns (stream FlightData)` 下载一个流；`DoPut(stream FlightData) returns (stream PutResult)` 上传；`DoExchange` 是双向的，用于把计算交给服务端（[Flight.proto](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/format/Flight.proto#L102-L127)）。C++ 的 gRPC 传输建在 gRPC C++ 同步 API 的 `ServerWriter`/`ServerReaderWriter` 上（[grpc_server.cc](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/cpp/src/arrow/flight/transport/grpc/grpc_server.cc#L482-L515)）；DoGet 的 handler 只返回一个 `FlightDataStream`，由传输层循环调用 `Next()` 并写出（[server.h](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/cpp/src/arrow/flight/server.h#L46-L60)、[transport_server.cc](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/cpp/src/arrow/flight/transport_server.cc#L298-L322)）。gRPC C++ 同步 API 的 `Read` 与 `Write` 都是"Block to ..."（[sync_stream.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpcpp/support/sync_stream.h#L91-L125)）。Arrow 的 C++ 文档写道，gRPC 会为并发客户端开到线程配额上限的线程，这些线程不一定回收（[cpp/flight.rst](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/docs/source/cpp/flight.rst?plain=1#L265-L272)）。

**Ray。** 用 `ray.remote` 装饰的生成器函数成为生成器任务，在任务结束之前把输出逐个交给调用方；返回的 `ObjectRefGenerator` 兼容同步与异步迭代；`next` 阻塞调用线程直到下一个 ObjectRef 产生；actor 的所有执行模型都支持（[ray-generator.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/ray-generator.rst?plain=1#L9-L80)）。生成器函数默认 `num_returns="streaming"`（[remote_function.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/remote_function.py#L445-L462)）。同步生成器"runs on its own execution thread"（[_raylet.pyx](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/_raylet.pyx#L1548-L1557)）。

**Envoy。** HTTP/2 的 `max_concurrent_streams` 在 v1.40.2 默认 1024，范围 1 到 2^31-1；对上游连接它也限制 Envoy 在一条连接上同时发起的流数，达到上限时排队，或在熔断限额内另建连接（[protocol.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/config/core/v3/protocol.proto#L598-L610)）。面向不可信下游的边缘配置建议设为 100（[edge.rst](https://github.com/envoyproxy/envoy/blob/v1.40.2/docs/root/configuration/best_practices/edge.rst?plain=1#L23)）。

## 2. 流控与背压

结论：HTTP/2 与 QUIC 都是接收方发放额度（credit）的两级窗口，每流一级、每连接一级，只有数据受流控；初始额度 HTTP/2 是 65,535 字节，QUIC 由传输参数给出、缺省为 0。窗口只在一跳的两端之间。慢消费者让生产者停下的方式有四种：写调用阻塞（Python 同步、grpc-go、gRPC C++ 同步 API）；挂起协程或推迟 promise（grpc.aio、Cap'n Proto）；写从不阻塞，只给 `isReady` 提示，不理会就在库内缓冲（grpc-java）；默认不停，可选按未消费的对象数暂停生成器（Ray）。C core 与 grpc-go 的接收方只在应用读消息时给流级窗口补额度，grpc-java 的文档把 `request(n)` 写成服务端施加背压的手段；grpc-go 明确让连接级窗口不依赖应用读取，以免慢流饿死同连接上的快流。

**HTTP/2。** 流控只在一跳的两端之间；基于 WINDOW_UPDATE 的额度方案；接收方可为每个流与整条连接设任意窗口，发送方必须遵守；新流与连接的初始窗口都是 65,535 字节；只有 DATA 帧受流控，"This ensures that important control frames are not blocked by flow control"；端点可以关掉自己的流控，但不能无视对方的；规范不规定接收方何时发 WINDOW_UPDATE、发多少（[§5.2.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.2.1)）。增量范围 1 到 2^31-1，窗口不得超过 2^31-1，超过就以 FLOW_CONTROL_ERROR 结束流或连接；受流控的帧都必须计入连接窗口，即使帧本身出错（[§6.9](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.9)、[§6.9.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.9.1)）。SETTINGS_INITIAL_WINDOW_SIZE 只改流级窗口，改动会按新旧差值调整所有 open 与 half-closed (remote) 流的窗口，窗口可能变成负数，此时发送方要等 WINDOW_UPDATE 把它补正；连接窗口只能用 WINDOW_UPDATE 改（[§6.9.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.9.2)）。不需要流控的部署可以通告最大窗口，并在收到数据时立即补额度，"effectively disables flow control"；"Endpoints MUST read and process HTTP/2 frames from the TCP receive buffer as soon as data is available"，否则 WINDOW_UPDATE 这类关键帧得不到处理，可能死锁（[§5.2.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.2.2)）。窗口小于对方的带宽时延积时，吞吐受流控限制（[§5.2.3](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.2.3)）。

**QUIC。** 接收方通告愿意接收的字节上限（绝对偏移），每流用 MAX_STREAM_DATA，整条连接用 MAX_DATA；流级限额"prevents a single stream from consuming the entire receive buffer for a connection"；初始值来自握手的传输参数；已通告的上限不能收回，通告更小的值无效；越限以 FLOW_CONTROL_ERROR 关闭连接；被卡住的发送方应发 STREAM_DATA_BLOCKED 或 DATA_BLOCKED，卡住超过空闲超时连接可能被关，所以要周期性地发（[§4.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-4.1)）。何时、给多少额度由实现决定；接收方不得等对方发 BLOCKED 帧才给额度，否则发送方至少被卡一个往返，甚至一直卡住（[§4.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-4.2)）。CRYPTO 帧里的数据不像流数据那样受流控（[§4](https://www.rfc-editor.org/rfc/rfc9000.html#section-4)）。发出 STOP_SENDING 之后收到的 STREAM 帧仍计入流与连接的流控（[§3.5](https://www.rfc-editor.org/rfc/rfc9000.html#section-3.5)）。传输参数缺省为 0，`initial_max_data` 与三个 `initial_max_stream_data_*` 都是如此（[§18.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-18.2)）。规范要求实现让应用写数据时能知道流控额度何时已为这些数据预留成功（[§2.4](https://www.rfc-editor.org/rfc/rfc9000.html#section-2.4)）。

**gRPC 的文档。** 流控只用于流式 RPC，与一元 RPC 无关；必要时 gRPC 让写调用等待后才返回；写调用返回不表示数据已上网，只表示已交给框架去缓冲和发送；接收方读走数据后才向发送方确认；双方都做同步读或手动流控、又都大量写而不读时可能死锁；手动流控的示例只有 Java 一种（[flow-control.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/guides/flow-control.md?plain=1#L9-L69)）。

**C core 的发送端。** 发送一条消息时，库把 5 字节前缀与消息追加到该流的待发缓冲，把本条消息末字节的偏移记为完成点（[chttp2_transport.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L1680-L1748)）。写循环为一个流写出的字节数不超过对端最大帧长、流窗口、连接窗口与本轮写目标的余量；没有窗口可用的流移进"被连接卡住"或"被流卡住"的列表，连接窗口恢复为正时，前一类流被放回可写列表（[writing.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L406-L416)、[L528-L574](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L528-L574)、[L328-L338](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L328-L338)）。普通消息的发送操作在这些字节通过流控、编成 DATA 帧放进输出缓冲之后完成；带 `GRPC_WRITE_THROUGH` 的要等写到端点之后；带 `GRPC_WRITE_BUFFER_HINT` 的完成点提前 `write_buffer_size`（`grpc.http2.write_buffer_size`，默认 65,535）（[writing.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L435-L443)、[L816-L823](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L816-L823)、[chttp2_transport.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L440-L442)、[channel_arg_names.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpc/impl/channel_arg_names.h#L156-L159)）。所以对端不读、窗口耗尽时，这条消息的发送操作一直不完成（推论）。

**C core 的接收端。** 常量：初始窗口 65,535，帧长 16,384，窗口上限 2^31-1，可通告的初始窗口上限 2^30，单次流级窗口增量上限 1 MiB，目标小于 1024 时通告 0（[flow_control.h](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/flow_control.h#L51-L59)）。BDP 探测默认开启，传输建立时就按它计算一次目标（[channel_arg_names.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpc/impl/channel_arg_names.h#L98-L100)、[chttp2_transport.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L747)、[L825-L829](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L825-L829)）。目标初始窗口随内存压力变化：压力低于 20% 时取 max(4 MiB, 2 × BDP 估计)，20% 到 50% 线性降到 2 × BDP 估计，50% 到 100% 再线性降到 0；结果向上取 2 的幂并截到 2^30（[flow_control.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/flow_control.cc#L200-L251)、[L290-L312](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/flow_control.cc#L290-L312)）。流级额度：只有该流有挂起的读、并且还需要更多字节（`min_progress_size` 大于 0）时，才把窗口增量目标设为 min(所需字节, 1 MiB) 并发 WINDOW_UPDATE；没有挂起的读时不扩大（[flow_control.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/flow_control.cc#L365-L402)、[chttp2_transport.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L2352-L2393)）。推论：内存压力低时，C core 端点让对方不经应用读取就能在每个流上先发约 4 MiB，之后要等应用读取才继续给额度。

**Python 同步栈的背压路径。** 服务端：`_send_response` 发出发送操作后等它完成，响应生成器在这期间不被推进（[_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L708-L740)、[L856-L871](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L856-L871)）。客户端：`_MultiThreadedRendezvous._next` 在每次 `next()` 时才发一个接收操作并等结果（[_channel.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_channel.py#L932-L965)）。推论：客户端停止迭代后，C core 不再为该流补额度，服务端写满窗口后，handler 线程阻塞在 `_send_response` 里。

**grpc.aio。** `await context.write()` 等批操作的 future 完成，协程在此挂起（[server.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/server.pyx.pxi#L140-L148)、[callback_common.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/callback_common.pyx.pxi#L139-L149)）。普通生成器的线程每产出一项都要等 `queue.put` 在事件循环里完成，队列容量为 1（[common.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/common.pyx.pxi#L142-L173)）。客户端的 `write()` 同样等发送操作完成（[call.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/call.pyx.pxi#L422-L428)）。

**grpc-go。** 发送端：每个流有 64 KiB 的写额度，是"number of data bytes that each stream can schedule before some of it being flushed out"；写消息之前 `wq.get` 在额度不为正时阻塞；loopy 写线程在流控检查通过、把数据写成帧时才补回额度（[defaults.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/defaults.go#L43-L46)、[flowcontrol.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/flowcontrol.go#L30-L66)、[http2_server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_server.go#L1188)、[controlbuf.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/controlbuf.go#L1070-L1071)）。接收端：流级窗口在应用读取之后补，累计未补的超过上限的四分之一才发 WINDOW_UPDATE；应用要读的消息大于窗口时一次补足整条消息（[flowcontrol.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/flowcontrol.go#L118-L211)）。连接级窗口在收到数据时就补，不等应用读取；代码注释的理由是流级流控已经会卡住发送方，连接级若也依赖应用读取，慢流或不活动的流会饿死同连接上的快流（[http2_server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_server.go#L777-L790)、[flowcontrol.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/flowcontrol.go#L81-L101)）。窗口初始 64 KiB；BDP 估计默认开启，把连接窗口与流初始窗口一起调大，上限 16 MiB；`StaticStreamWindowSize`、`StaticConnWindowSize` 与 `InitialWindowSize` 系列选项关闭动态调整，下限 64 KiB（[bdp_estimator.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/bdp_estimator.go#L26-L42)、[http2_server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_server.go#L301-L306)、[L749-L769](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_server.go#L749-L769)、[server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L280-L334)）。

**grpc-java。** 发送端：`isReady()` 表示能否不过度缓冲地再发，"just a suggestion"，不理会可能造成 observer 内部的过度缓冲；变为 true 时调用 `onReadyHandler`，可能是伪通知，要重新检查（[CallStreamObserver.java](https://github.com/grpc/grpc-java/blob/v1.85.1/stub/src/main/java/io/grpc/stub/CallStreamObserver.java#L50-L95)）。排队字节低于 32 KiB 时触发 onReady（[AbstractStream.java](https://github.com/grpc/grpc-java/blob/v1.85.1/core/src/main/java/io/grpc/internal/AbstractStream.java#L131-L137)），服务端可在初始化时用实验性的 `setOnReadyThreshold` 修改（[ServerCallStreamObserver.java](https://github.com/grpc/grpc-java/blob/v1.85.1/stub/src/main/java/io/grpc/stub/ServerCallStreamObserver.java#L70-L82)）。接收端：默认在 inbound `onNext` 返回后自动再请求一条；`disableAutoInboundFlowControl` 之后要显式调用 `request(n)`（[CallStreamObserver.java](https://github.com/grpc/grpc-java/blob/v1.85.1/stub/src/main/java/io/grpc/stub/CallStreamObserver.java#L97-L134)）；`ServerCall.request` 的文档写明服务端以此给客户端施加背压（[ServerCall.java](https://github.com/grpc/grpc-java/blob/v1.85.1/api/src/main/java/io/grpc/ServerCall.java#L127-L139)）。Netty 默认流控窗口 1 MiB，默认按 BDP 自动调整；`flowControlWindow()` 关闭自动调整（[NettyServerBuilder.java](https://github.com/grpc/grpc-java/blob/v1.85.1/netty/src/main/java/io/grpc/netty/NettyServerBuilder.java#L80)、[L110-L112](https://github.com/grpc/grpc-java/blob/v1.85.1/netty/src/main/java/io/grpc/netty/NettyServerBuilder.java#L110-L112)、[L420-L447](https://github.com/grpc/grpc-java/blob/v1.85.1/netty/src/main/java/io/grpc/netty/NettyServerBuilder.java#L420-L447)）。

**Cap'n Proto。** 流控只在客户端实现，协议没变；`-> stream` 与 `-> ()` 线上兼容；0.8 时只有 C++ 实现了流控，其他语言把它当 `-> ()`（[0.8 发布说明](https://github.com/capnproto/capnproto/blob/v1.5.0/doc/_posts/2020-04-23-capnproto-0.8.md?plain=1#L81)）。`RpcFlowController::send()` 立即发出消息，不能为了流控推迟（后面的消息可能依赖它引入的状态），返回的 promise 在"适合发下一条"时完成；确认（ack）是对方的 Return，所以包含远端应用的处理时间，远端处理慢也会形成背压（[rpc.h](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc.h#L310-L336)）。窗口实现：在途字节按消息大小计，在途少于"窗口 + 已见过的最大单条消息"时立即放行，否则挂起；多加一条最大消息是为了避免单条消息大于窗口时每条都要等一个往返（[rpc.c++](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc.c++#L3718-L3824)）。两方网络把套接字的 SO_SNDBUF 当作窗口，取不到时用默认的 64 KiB（[rpc-twoparty.c++](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc-twoparty.c++#L259-L294)、[rpc.h](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc.h#L358)）。接收端另有 `setFlowLimit(words)`：尚未返回的入站调用超过这个量，就停止读这条连接上的所有消息，包括 Return，文档警告可能因此死锁（[rpc.h](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc.h#L114-L140)）。

**Ray。** 文档：Ray 会"eagerly"把生成器任务执行完，不管调用方是否在取部分结果（[ray-generator.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/ray-generator.rst?plain=1#L86-L89)）。源码另有两个下划线开头的私有选项：每任务的 `_generator_backpressure_num_objects`（默认 -1，即关闭）与 actor 级的 `_actor_generator_backpressure_num_objects`（[remote_function.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/remote_function.py#L458-L462)、[generator_waiter.h](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/core_worker/generator_waiter.h#L70-L76)、[L122-L127](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/core_worker/generator_waiter.h#L122-L127)）；生成器文档没有提到它们。开启后，未消费的对象数达到阈值时，同步生成器的执行线程在条件变量上等待，每 1 s 醒来检查一次信号；异步生成器等一个 asyncio.Event，不占线程（[generator_waiter.cc](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/core_worker/generator_waiter.cc#L31-L61)、[_raylet.pyx](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/_raylet.pyx#L1548-L1557)）。"消费"指调用方的 `next()` 读走了对应的 ObjectRef，而不是 `ray.get` 取了值（推论，据 [object_ref_generator.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/_private/object_ref_generator.py#L259-L338) 里 `try_read_next_object_ref_stream` 的位置）。

**Arrow Flight。** Flight 的背压就是 gRPC 的。客户端另有 `write_size_limit_bytes`，是单个批次的软上限，超出时写入返回带 `FlightWriteSizeStatusDetail` 的 IOError（[client.h](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/cpp/src/arrow/flight/client.h#L110-L116)）；文档建议同时在服务端设 `GRPC_ARG_MAX_RECEIVE_MESSAGE_LENGTH`：客户端的限制可以换更小的批次重试，服务端的限制会断开连接（[cpp/flight.rst](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/docs/source/cpp/flight.rst?plain=1#L298-L308)）。

## 3. 半关闭、流结束与取消

结论：HTTP/2、QUIC 与 gRPC 都把"我不再发"（半关闭：END_STREAM 或 FIN）与"中止"（RST_STREAM、RESET_STREAM、取消）分开：半关闭后另一个方向照常，中止则让 HTTP/2 流的两个方向、或 QUIC 流的一个方向立即结束。规范与各家文档对取消之前已发出的消息都不作保证，写法是"可能送达、可能已被处理、不回滚"；C core 还会在取消后丢弃已收到但未读的消息，grpc-java 客户端的 `onError` 丢弃所有消息。取消到达 handler 有四种方式：标志或查询（Python `is_active()`、Java `isCancelled()`、Arrow `is_cancelled()`）；回调（Python `add_callback`、Java `onCancel`）；异常（Python 请求迭代器抛 `RpcError`、grpc.aio 注入 `CancelledError`、Java `onNext` 抛 CANCELLED）；context 结束（grpc-go）。gRPC 的库一般不能打断正在运行的 handler，长时间运行的 handler 要自己定期检查。

**HTTP/2 的半关闭。** 发出 END_STREAM 的一方进入 half-closed (local)，只能再发 WINDOW_UPDATE、PRIORITY 与 RST_STREAM，但要继续给对方额度才能继续收数据；收到 END_STREAM 的一方进入 half-closed (remote)，不再需要维护接收窗口，自己发送仍受对方流级窗口约束；双方都发过 END_STREAM，或任一方发出或收到 RST_STREAM，流才关闭（[§5.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.1)）。服务端可以在客户端发完请求之前就发出完整响应；此时它可以在发出 END_STREAM 之后发 RST_STREAM(NO_ERROR)，请客户端停止发送请求，客户端不得因此丢弃响应（[§8.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.1)）。

**HTTP/2 的 RST_STREAM。** 它"allows for immediate termination of a stream"，用于请求取消或报告错误；收到方不得再在该流上发帧（PRIORITY 除外），发出方要准备好接收对方在收到 RST_STREAM 之前已发出的帧（[§6.4](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.4)）；在 open 或 half-closed (local) 状态发出 RST_STREAM 后可能收到任意类型的帧，要最低限度地处理后丢弃（[§5.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.1)）。CANCEL (0x8) 表示"the stream is no longer needed"（[§7](https://www.rfc-editor.org/rfc/rfc9113.html#section-7)）。

**QUIC。** 带 FIN 的 STREAM 帧是正常结束，RESET_STREAM 是中止发送方向；接收方可以用 STOP_SENDING 请对方中止，但这"not a guarantee that incoming data will be ignored"（[§2.4](https://www.rfc-editor.org/rfc/rfc9000.html#section-2.4)、[§3.5](https://www.rfc-editor.org/rfc/rfc9000.html#section-3.5)）。双向流的一个方向被 RESET_STREAM 中止不影响另一个方向，两端要继续维护那个方向的流控状态（[§4.4](https://www.rfc-editor.org/rfc/rfc9000.html#section-4.4)）。无论流怎样结束，最终大小总是可靠地告知对方，以便两端就连接级流控的消耗达成一致（[§4.5](https://www.rfc-editor.org/rfc/rfc9000.html#section-4.5)）。

**gRPC 的结束在线上的样子。** 请求的结束是最后一个 DATA 帧上的 END_STREAM，没有数据可发时必须发一个空的 DATA 帧；响应的结束是携带 Trailers 的 HEADERS 帧上的 END_STREAM（[PROTOCOL-HTTP2.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md?plain=1#L102)、[L118-L120](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md?plain=1#L118-L120)）。RST_STREAM 的映射：客户端发出的 CANCEL 映射为调用取消，服务端发出的映射为 CANCELLED，并且服务端只应在需要取消调用而载荷字节序列不完整时这样用；REFUSED_STREAM 映射为 UNAVAILABLE，表示没有发生处理、可以重试（[L220-L236](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md?plain=1#L220-L236)）。C core 服务端发出 trailers 时，若客户端还没半关闭，紧接着发 RST_STREAM(NO_ERROR)（[writing.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L645-L660)），即 RFC 9113 §8.1 的做法。

**gRPC 对取消的定义。** 双方都可以随时取消；"A cancellation terminates the RPC immediately so that no further work is done"；警告："Changes made before a cancellation are not rolled back."（[core-concepts.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/what-is-grpc/core-concepts.md?plain=1#L188-L195)）。取消指南：截止时间到期与 I/O 错误也会触发取消；客户端不把取消原因发给服务端；库一般没有机制打断正在运行的 handler，长时间运行的 RPC 的 handler 必须定期检查是否已被取消；表中 Java、Go、C++ 写明会自动取消 handler 发出的下游 RPC，Python 一栏没有这一说明（[cancellation.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/guides/cancellation.md?plain=1#L9-L72)）。

**取消怎样到达 handler。** Python 同步：库收到"服务端关闭"事件且结果为已取消时，把 RPC 标为已取消并唤醒所有等待者（[_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L301-L311)）；之后请求迭代器抛 `grpc.RpcError`（[L500-L522](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L500-L522)），`_send_response` 返回 False，库不再从响应生成器取下一项，这段代码不调用生成器的 `close()`（[L708-L740](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L708-L740)、[L856-L871](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L856-L871)）；handler 也可以查 `context.is_active()`，或用 `add_callback` 注册在 RPC 终止时运行的回调（[__init__.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/__init__.py#L328-L369)）。grpc.aio：收到已取消的关闭事件、handler 任务还没结束、状态也还没发出时，库对任务调用 `cancel()`，在 handler 协程里注入 `CancelledError`（[server.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/server.pyx.pxi#L778-L792)）；`read()`、`write()` 先检查 RPC 是否已终止（[L127-L148](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/server.pyx.pxi#L127-L148)）；在途调用调研的本机复现表明，线程池里的普通 handler 不受这种取消影响。grpc-go：收到 RST_STREAM 时传输层关闭该流并取消它的 context，handler 经 `ServerStream.Context()` 得知（[http2_server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_server.go#L837-L850)、[L1372-L1381](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_server.go#L1372-L1381)）；客户端流要释放资源，必须关闭 ClientConn、取消 context、一直 RecvMsg 到返回非 nil 错误，或从 Header、SendMsg 得到非 EOF 错误，四者居一，否则泄漏一个 goroutine 和一个 context（[stream.go](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L227-L243)）。grpc-java：`ServerCall.Listener.onCancel` 之后不再有回调；`onHalfClose` 之后调用仍可能被取消（[ServerCall.java](https://github.com/grpc/grpc-java/blob/v1.85.1/api/src/main/java/io/grpc/ServerCall.java#L59-L88)）。stub 层设了 `onCancelHandler` 就调用它，否则把 observer 标为已取消，之后服务端流或双向流的 `onNext` 抛 CANCELLED（"call already cancelled"）；客户端还没半关闭时，请求 observer 收到 `onError(CANCELLED "client cancelled")`（[ServerCalls.java](https://github.com/grpc/grpc-java/blob/v1.85.1/stub/src/main/java/io/grpc/stub/ServerCalls.java#L276-L293)、[L359-L372](https://github.com/grpc/grpc-java/blob/v1.85.1/stub/src/main/java/io/grpc/stub/ServerCalls.java#L359-L372)）；`onCloseHandler` 与 `onCancelHandler` 恰有一个被调用（[ServerCallStreamObserver.java](https://github.com/grpc/grpc-java/blob/v1.85.1/stub/src/main/java/io/grpc/stub/ServerCallStreamObserver.java#L168-L189)）。

**取消之前发出的消息。** grpc-java `ClientCall.cancel` 之后不再发也不再收，"The server is informed of cancellations, but may not stop processing the call"（[ClientCall.java](https://github.com/grpc/grpc-java/blob/v1.85.1/api/src/main/java/io/grpc/ClientCall.java#L214-L229)）；客户端侧的 `onError()` 会取消 RPC 并丢弃所有消息（[StreamObserver.java](https://github.com/grpc/grpc-java/blob/v1.85.1/stub/src/main/java/io/grpc/stub/StreamObserver.java#L35-L39)）。服务端干净关闭时，"the client still may have not received all the messages due to network delay, client crashes, and cancellation races"（[ServerCallStreamObserver.java](https://github.com/grpc/grpc-java/blob/v1.85.1/stub/src/main/java/io/grpc/stub/ServerCallStreamObserver.java#L168-L175)、[ServerCall.java](https://github.com/grpc/grpc-java/blob/v1.85.1/api/src/main/java/io/grpc/ServerCall.java#L82-L88)）。grpc-go 的 `SendMsg` "does not wait until the message is received by the server. An untimely stream closure may result in lost messages. To ensure delivery, users should ensure the RPC completed successfully using RecvMsg."（[stream.go](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L124-L132)）。C core：流以错误关闭时（本端取消，或传输以错误关闭该流并合成非 OK 状态），只要上层已请求最终状态，已收到但应用还没读的消息字节就被丢弃（[chttp2_transport.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L2352-L2354)、[L2523-L2540](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L2523-L2540)、[L2666-L2708](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L2666-L2708)）。QUIC：发出 RESET_STREAM 意味着不能保证数据送达，但也不要求接收方不交付；接收方可以中断交付、丢弃未消费的数据，数据已全部收到时也可以不报告这次中止（[§3.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-3.2)）。

**Cap'n Proto。** Finish 消息表示调用方不再关心结果；没有别人依赖这个结果时，被调方"may wish to"立即取消并回 canceled，但实现不必支持提前取消，可以等调用做完再正常返回（[rpc.capnp](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc.capnp#L569-L581)）。

**Ray。** `ray.cancel()` 适用于生成器任务；取消后 `next(gen)` 可能返回一个包含 `TaskCancelledError` 的引用，"without any special ordering guarantee"；生成器不支持 `throw`、`send` 与 `close`（[ray-generator.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/ray-generator.rst?plain=1#L153-L159)、[L208-L215](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/ray-generator.rst?plain=1#L208-L215)）。

**Arrow Flight。** 客户端可用调用对象的 `Cancel` 或 `FlightCallOptions::stop_token` 提前结束调用；服务端要自己轮询 `ServerCallContext::is_cancelled()`（[cpp/flight.rst](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/docs/source/cpp/flight.rst?plain=1#L110-L125)、[L310-L330](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/docs/source/cpp/flight.rst?plain=1#L310-L330)）。DoGet 的传输循环在写失败（源码注释 "Connection terminated"）时直接返回 OK，这条路径不调用数据流的 `Close()`（[transport_server.cc](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/cpp/src/arrow/flight/transport_server.cc#L298-L322)）。

## 4. 流中途的错误

结论：gRPC 的响应总是"响应头、若干消息、trailers"，状态放在 trailers 里，OK 也一样；中途出错就是在已发出的消息之后跟一个非 OK 的 trailers。协议没有撤回已交付消息的机制；gRPC 只说取消前的改动不回滚，没有规定出错之前已交付的流消息是否仍有效。各实现都先把已收到的消息交给应用，再报告错误；例外是取消或本端出错（C core 丢弃未读的缓冲消息，grpc-java 客户端的 `onError` 取消 RPC 并丢弃所有消息）。Cap'n Proto 与 Ray 的规则更强：Cap'n Proto 的流式调用一旦抛错，同一对象上之后的所有调用都抛同一个错误；Ray 的应用异常按顺序排在已产出的结果之后，系统错误则不保证顺序。

**gRPC 协议。** 响应是 Response-Headers、若干 Length-Prefixed-Message 与 Trailers，或者只有 Trailers-Only；Trailers-Only 用于立即出错的调用；"Status must be sent in Trailers even if the status code is OK"（[PROTOCOL-HTTP2.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md?plain=1#L106-L120)）。应用或运行时出错时，Status 与 Status-Message 放在 Trailers 里；只有消息流的分帧可能已损坏时，运行时才用 RST_STREAM，收到方应把它当作流立即完全关闭并向应用报错（[L214-L218](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md?plain=1#L214-L218)）。客户端检测到连接故障时所有调用以 UNAVAILABLE 结束，服务端的调用以 CANCELLED 结束（[L253-L254](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md?plain=1#L253-L254)）。gRFC A6 要求服务端把 Response-Headers 推迟到第一条响应或应用主动发头时，在此之前出错就用 Trailers-Only（[A6](https://github.com/grpc/proposal/blob/89f34f2632b991776e206c97830ec3ac6f391988/A6-client-retries.md#when-retries-are-valid)）。

**错误之前的消息怎样交付。** C core 客户端：trailers 要等该流缓冲的消息字节全部被读走才交给上层，只有流以错误关闭时才先丢弃缓冲（[chttp2_transport.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L2442-L2460)）。Python 同步客户端的 `next()` 先返回已收到的响应，没有响应可返回而状态非 OK 时才抛出（[_channel.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_channel.py#L932-L965)）。grpc-go 的 `RecvMsg` 正常结束时返回 `io.EOF`，其他错误时流被中止，错误里带 RPC 状态（[stream.go](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L141-L149)）。grpc-java 的 `onError` 与 `onCompleted` 都只能调用一次，并且必须是最后一个调用（[StreamObserver.java](https://github.com/grpc/grpc-java/blob/v1.85.1/stub/src/main/java/io/grpc/stub/StreamObserver.java#L62-L88)）。

**服务端 handler 出错。** Python 同步：迭代响应时 handler 抛出异常，库以 UNKNOWN 和 "Exception iterating responses: ..." 结束 RPC；`context.abort()` 总是抛异常，以给定状态结束 RPC（[_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L646-L670)、[__init__.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/__init__.py#L1241-L1256)）。gRPC 状态码文档：服务端应用抛异常、或不以状态码结束 RPC 时是 UNKNOWN；收发的消息超过配置上限是 RESOURCE_EXHAUSTED；"Some data transmitted ... before connection breaks"在客户端是 UNAVAILABLE（[statuscodes.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/statuscodes.md?plain=1#L45-L65)）。

**前面的结果是否仍有效。** gRPC 只说了三点：取消前的改动不回滚（[core-concepts.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/what-is-grpc/core-concepts.md?plain=1#L193-L195)）；双方独立判断成败，服务端"已发出全部响应"而客户端"响应在截止时间之后才到"是可能的（[L179-L186](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/what-is-grpc/core-concepts.md?plain=1#L179-L186)）；对改变系统状态的操作，即使操作其实已成功，也可能返回 DEADLINE_EXCEEDED（[statuscodes.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/statuscodes.md?plain=1#L12)）。没有找到 gRPC 对"出错之前已交付的流消息"有效性的规定（推论：留给应用）。Arrow Flight 的 DoPut 允许服务端回带自定义元数据的消息，文档举的例子是周期性告诉客户端已提交多少行，以实现可续传的写入（[Flight.rst](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/docs/source/format/Flight.rst?plain=1#L225-L243)）。DoGet 的传输循环在 `Next()` 返回错误时把它作为调用状态返回，此前写出的批次已经发出（推论，据 [transport_server.cc](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/cpp/src/arrow/flight/transport_server.cc#L312-L319) 的 `ARROW_ASSIGN_OR_RAISE`）。

**Cap'n Proto。** 客户端可能在服务端执行之前就看到流式调用"完成"，服务端的异常传不回那次调用；规则改为：流式调用抛错之后，同一对象上之后的所有调用（流式或非流式）都抛同一个异常；调用方发完流式调用后必须调用一个非流式的 `done()` 来检查错误（[0.8 发布说明](https://github.com/capnproto/capnproto/blob/v1.5.0/doc/_posts/2020-04-23-capnproto-0.8.md?plain=1#L77)）。实现上服务端对象记下 `brokenException`，之后的调用直接以它失败（[capability.c++](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/capability.c++#L862-L897)）；客户端的流控器在某个 ack 失败后，让所有挂起的与之后的发送都失败（[rpc.c++](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc.c++#L3800-L3814)）。

**Ray。** 生成器任务失败时，`next(gen)` 返回一个包含异常的引用，`ray.get` 时抛出；应用异常的引用"in a correct order"：在第二次 yield 之后抛出，第三次 `next` 总是得到异常；系统错误（节点或 worker 进程故障）的异常引用可能在任何时候出现，没有顺序保证；有 N 次 yield 时，生成器可能产生 1 到 N+1 个引用（[ray-generator.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/ray-generator.rst?plain=1#L91-L109)、[object_ref_generator.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/_private/object_ref_generator.py#L259-L285)）。

## 5. 顺序

结论：各系统都只保证单个流或单个引用之内的顺序，不保证流与流之间的顺序。HTTP/2 在一条连接上交织不同流的帧，只要求一个头块的帧连续；QUIC 明说不保证不同流的字节之间的顺序，这正是它避开跨流队头阻塞的方式。gRPC 保证一次调用内的消息顺序，双向流的两个方向各自保序、互不约束。Cap'n Proto 的 E-order 是同一个引用上的调用按发出顺序送达，流式调用在服务端还串行执行。

**HTTP/2。** 一条连接上可以有多个并发打开的流，两端交织发送不同流的帧；帧的发送顺序有意义，接收方按收到的顺序处理，HEADERS 与 DATA 的先后在语义上重要（[§5](https://www.rfc-editor.org/rfc/rfc9113.html#section-5)）。头块必须是连续的帧序列，中间不能夹其他类型或其他流的帧（[§4.3](https://www.rfc-editor.org/rfc/rfc9113.html#section-4.3)）。

**QUIC。** 端点必须能把流数据作为有序字节流交给应用，为此要缓冲乱序到达的数据，最多到通告的流控上限；STREAM 帧的边界不保留（[§2.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-2.2)）；"QUIC does not provide any means of ensuring ordering between bytes on different streams"（[§2](https://www.rfc-editor.org/rfc/rfc9000.html#section-2)）。丢包只阻塞数据在那个包里的流；一个包装了多个流的数据时，丢了它这些流都被阻塞，所以实现被建议在不浪费包容量的前提下少把多个流放进同一个包（[§13](https://www.rfc-editor.org/rfc/rfc9000.html#section-13)）。

**gRPC。** 一次调用内保序，双向流的两个方向独立（第 1 节）。同一方向上的并发调用 API 有限制：grpc-go 每个方向只能有一个 goroutine 调用 SendMsg 或 RecvMsg（[concurrency.md](https://github.com/grpc/grpc-go/blob/v1.85.0/Documentation/concurrency.md?plain=1#L17-L24)）；gRPC C++ 同步 API 的 `Read` 不能与同一流上的另一个 `Read` 并发，"as the order of delivery will not be defined"（[sync_stream.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpcpp/support/sync_stream.h#L91-L101)）；grpc.aio 的 `read()` 要串行调用（[_base_call.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/aio/_base_call.py#L166-L178)）。没有找到对同一连接上不同调用之间顺序的说法；它们是互相独立的 HTTP/2 流（推论）。

**Cap'n Proto。** 除非另有说明，消息必须按发送应用发起的顺序交给接收应用，目标是 E-order："two calls made on the same reference must be delivered in the order which they were made"（[rpc.capnp](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc.capnp#L61-L65)）。流控器必须立即发出消息，只能靠推迟 promise 施加背压（[rpc.h](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc.h#L325-L331)）；流式方法执行期间，同一对象上的其他调用排队到它完成（第 1 节）。

**Arrow Flight。** 单个 endpoint 的数据必须按顺序返回；`FlightInfo.ordered` 为 true 时，客户端应得到与按顺序拼接各 endpoint 数据相同的结果，为 false 时不同 endpoint 的数据可以交织、并行获取（[Flight.rst](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/docs/source/format/Flight.rst?plain=1#L94-L107)）。

**Ray。** `ObjectRefGenerator` 按 yield 的顺序给出引用，错误引用的顺序见第 4 节；`ObjectRefGenerator` 不是线程安全的（[ray-generator.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/ray-generator.rst?plain=1#L70-L77)、[L204-L206](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/ray-generator.rst?plain=1#L204-L206)）。

## 6. 大消息、分帧、交织与写调度

结论：建在 HTTP/2 与 QUIC 上的系统都把大消息切成帧，在一条连接上与其他流交织，但切多大、轮转多快各不相同。HTTP/2 默认帧长 16 KiB，可协商到 16 MiB-1，规范提醒大帧会拖慢 RST_STREAM、WINDOW_UPDATE 这类时间敏感的帧。gRPC 消息带 4 字节长度前缀，DATA 帧边界与消息边界无关；C core 与 grpc-go 的收发两端、grpc-java 的服务端，默认接收上限都是 4 MiB，C core 默认发送不限，grpc-go 为 `math.MaxInt32`。写调度：grpc-go 每个流每轮最多写 16 KiB，轮转；C core 每轮把一个流写到本轮写目标（初始 128 KiB，在 32 KiB 到 16 MiB 之间自适应）为止，再放回队尾；grpc-java 用 Netty 的均匀分配器。RFC 9113 废弃了 RFC 7540 的优先级信令，QUIC 根本不交换优先级。Cap'n Proto 的 0.8 发布说明写道，排队的流式调用会挡住同一连接上的其他调用，这是它引入流控的原因之一。

**HTTP/2。** 帧载荷上限由接收方的 SETTINGS_MAX_FRAME_SIZE 决定，取值 2^14 到 2^24-1，初始 16,384；"Sending large frames can result in delays in sending time-sensitive frames (such as RST_STREAM, WINDOW_UPDATE, or PRIORITY)"（[§4.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-4.2)、[§6.5.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.5.2)）。请求与响应的发送次序、怎样避免队头阻塞由实现自己负责（[§5.2.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.2.1)）。RFC 9113 废弃了 RFC 7540 的优先级信令：那套方案复杂、实现不一致、许多服务端忽略客户端的信号，"was not successful"；需要优先级时建议改用 RFC 9218 这类替代方案；没有信号时服务端应依据其他上下文决定次序（[§5.3.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.3.1)、[§5.3.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.3.2)）。

**QUIC。** QUIC 不提供交换优先级的机制，依赖应用提供优先级信息；实现应当让应用能指定流的相对优先级（[§2.3](https://www.rfc-editor.org/rfc/rfc9000.html#section-2.3)）。

**gRPC 的消息分帧与大小上限。** Length-Prefixed-Message 是 1 字节压缩标志、4 字节大端长度与消息本身；压缩上下文不跨消息（[PROTOCOL-HTTP2.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md?plain=1#L95-L100)）；DATA 帧边界与消息边界无关（[L211-L212](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md?plain=1#L211-L212)）。C core 的接收上限默认 4 MiB，发送默认不限（-1）（[grpc_types.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpc/impl/grpc_types.h#L178-L179)、[channel_arg_names.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpc/impl/channel_arg_names.h#L40-L49)）；grpc-go 服务端与客户端的接收上限都是 4 MiB，发送是 `math.MaxInt32`（[server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L61-L62)、[clientconn.go](https://github.com/grpc/grpc-go/blob/v1.85.0/clientconn.go#L139-L140)）；grpc-java 服务端默认 4 MiB（[ServerBuilder.java](https://github.com/grpc/grpc-java/blob/v1.85.1/api/src/main/java/io/grpc/ServerBuilder.java#L375-L387)、[GrpcUtil.java](https://github.com/grpc/grpc-java/blob/v1.85.1/core/src/main/java/io/grpc/internal/GrpcUtil.java#L212)）。收发的消息超过配置上限是 RESOURCE_EXHAUSTED（[statuscodes.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/statuscodes.md?plain=1#L64)）。

**C core 的写调度。** 每个写周期从可写流列表的队头取流（新加入的放在队尾），依次刷它的 initial metadata、窗口更新、数据与 trailers；数据按帧写出，每帧不超过对端最大帧长，并受流窗口、连接窗口与本轮写目标余量的限制；输出达到本轮写目标就不再取流；流还有待发数据时重新放回队尾（[writing.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L340-L353)、[L406-L416](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L406-L416)、[L528-L574](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L528-L574)、[L700-L760](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L700-L760)、[stream_lists.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/stream_lists.cc#L56-L130)）。写目标初始 128 KiB；连续两次快于 100 ms 的写把它乘 1.5（不超过 16 MiB），连续两次慢于 1 s 的写把它除以 3（不低于 32 KiB）（[write_size_policy.h](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/write_size_policy.h#L29-L51)、[write_size_policy.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/write_size_policy.cc#L38-L58)）。trailers 要等该流的待发数据清空才写（[writing.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/writing.cc#L577-L581)）。开 BDP 探测时，C core 通告的 SETTINGS_MAX_FRAME_SIZE 随目标窗口变化，取 clamp(目标窗口, 16,384, 16,777,215)（[flow_control.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/flow_control.cc#L313-L316)、[http2_settings.h](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/http2_settings.h#L139-L141)）；`GRPC_ARG_HTTP2_MAX_FRAME_SIZE` 的说明是大帧"lower CPU usage for large messages, but more head of line blocking for small messages"（[channel_arg_names.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpc/impl/channel_arg_names.h#L92-L97)）。推论：一个带大消息的流在一个写周期内最多能占满本轮写目标，其他流排在它之后。

**grpc-go 的写调度。** loopy 写线程每次从活动流队列的队头取一个流，最多写 16 KiB 数据；还有数据且流窗口没用尽就放回队尾，流窗口用尽则转入等待额度的状态；trailers 排在该流的数据之后（[controlbuf.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/controlbuf.go#L1013-L1117)、[http_util.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http_util.go#L47)）。服务端在连接前言的 SETTINGS 里通告的最大帧长就是 16 KiB（[http2_server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_server.go#L182-L185)）。

**grpc-java 的写调度。** Netty 服务端用 `UniformStreamByteDistributor` 作为远端流控器的字节分配器（[NettyServerHandler.java](https://github.com/grpc/grpc-java/blob/v1.85.1/netty/src/main/java/io/grpc/netty/NettyServerHandler.java#L259-L265)）。分配算法属于 Netty，本文没有读它的源码。

**Cap'n Proto。** 0.8 发布说明：没有流控时，应用发得比网络快，消息就在内存里排队，"Worse, if other RPC calls were happening on the same connection concurrently, they could end up blocked behind these queued streaming calls"（[0.8 发布说明](https://github.com/capnproto/capnproto/blob/v1.5.0/doc/_posts/2020-04-23-capnproto-0.8.md?plain=1#L55)）。读消息的默认遍历上限是 8M words（64 MiB），是防恶意消息的安全限制（[message.h](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/message.h#L53-L57)）。

**Arrow Flight。** C++ 客户端与服务端都把 gRPC 的接收上限设为不限，客户端设 `GRPC_ARG_MAX_RECEIVE_MESSAGE_LENGTH = -1`，服务端调用 `SetMaxReceiveMessageSize(-1)`（[grpc_client.cc](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/cpp/src/arrow/flight/transport/grpc/grpc_client.cc#L810-L820)、[grpc_server.cc](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/cpp/src/arrow/flight/transport/grpc/grpc_server.cc#L583-L587)）；客户端可设单批次软上限（第 2 节）。

## 7. 服务端关闭与客户端关闭时仍开着的流

结论：优雅关闭在各系统里都是"停止接新流，让已有的流做完"，而且没有一家给优雅关闭里的流设默认的宽限上限：HTTP/2 的 GOAWAY 只说已接受的流"might still complete"；grpc-go 的 `GracefulStop` 阻塞到所有 RPC 结束；gRFC A9 的 `MAX_CONNECTION_AGE_GRACE` 默认无限；Envoy 的排空"never forcefully terminates active streams"。所以一条无限长的流会让优雅关闭永远不结束，gRPC 的指南为此要求另设计时器，到期调用强制关闭。自带宽限参数、到期强停的有 Python 的 `stop(grace)` 与 C++ 的 `Server::Shutdown(deadline)`（在途调用调研第 1 节）；A9 的 `MAX_CONNECTION_AGE_GRACE` 也是这种参数，但默认无限；Envoy 的 `drain_timeout` 只决定最终 GOAWAY 何时发，不终止流。强制关闭在 gRPC 里是取消所有在途调用；QUIC 的 CONNECTION_CLOSE 隐式重置所有流。

**HTTP/2 的 GOAWAY。** GOAWAY 的发送方可以保持连接打开，直到所有进行中的流完成，以此优雅关闭；last-stream-id 及以下的流"might still complete successfully"；优雅关闭建议两步 GOAWAY（[§6.8](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.8)，细节见在途调用调研第 1 节）。规范没有给进行中的流设时间上限（推论：无限流会让连接一直留着）。

**HTTP/3 与 QUIC。** HTTP/3 用 GOAWAY 帧发起优雅关闭；标识以下的请求"might have been processed"，它们的状态要等收到响应、流被单独重置、收到标识更小的 GOAWAY 或连接终止才能知道（[RFC 9114 §5.2](https://www.rfc-editor.org/rfc/rfc9114.html#section-5.2)）。QUIC 的 CONNECTION_CLOSE 让所有流立即关闭，"open streams can be assumed to be implicitly reset"；优雅关闭要由应用协议先协商好，再请 QUIC 关闭连接（[RFC 9000 §10.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-10.2)）。

**gRPC 的指南。** 优雅关闭函数立即通知客户端停止发新 RPC，之后停止接受新 RPC，在途 RPC 继续到完成或截止时间；这个函数"blocks until all currently running RPCs complete"；必须另外用计时器在预定时间后调用强制关闭函数作为安全网，"This prevents indefinite blocking"；强制关闭立即停止服务并关闭所有连接，在途 RPC 失败（[server-graceful-stop.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/guides/server-graceful-stop.md?plain=1#L16-L44)）。

**各实现怎样对待长流。** grpc-go 的 `GracefulStop` 停止接受新连接与新 RPC，阻塞到所有待处理的 RPC 结束；`Stop` 立即关闭所有连接与监听，取消服务端所有活动 RPC，客户端由连接错误得知；`Stop` 默认不等 handler 返回（[server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L1671-L1690)、[L645-L658](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L645-L658)）；中止一个太久的 `GracefulStop` 要靠并发调用 `Stop()`（在途调用调研第 1 节）。grpc-java 的 `shutdown()` 让已有调用继续、拒绝新调用，不等已有调用结束，等待要靠 `awaitTermination`；`shutdownNow()` 把已有的与新的调用都拒绝（[Server.java](https://github.com/grpc/grpc-java/blob/v1.85.1/api/src/main/java/io/grpc/Server.java#L112-L141)）。Python 的 `stop(grace)` 给了宽限就在到期时 `cancel_all_calls()`，传 None 则立即中止全部（[__init__.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/__init__.py#L1528-L1556)，在途调用调研有一元调用的本机复现）；推论：无限流在宽限到期时与一元调用一样被中止。按连接年龄关闭时，`MAX_CONNECTION_AGE_GRACE` 是留给在途 RPC 完成的时间，默认无限（[A9](https://github.com/grpc/proposal/blob/89f34f2632b991776e206c97830ec3ac6f391988/A9-server-side-conn-mgt.md#proposal)）。

**客户端关闭。** Python 的 `Channel.close()` 立即终止通道上所有活动 RPC；grpc-java 的 `ManagedChannel.shutdown()` 让在途调用继续，`shutdownNow()` 取消它们（在途调用调研第 1 节）。grpc-go 的客户端流若不按第 3 节的四个条件之一结束，会泄漏 goroutine（[stream.go](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L227-L243)）。

**Envoy 的排空。** HTTP 连接管理器在排空时给 HTTP/2 连接发 GOAWAY，请求完成后终止连接；升级（如 WebSocket）与 CONNECT 流无法被告知离开，在 HTTP/2 与 HTTP/3 连接上于排空超时后被重置；"Other requests are left to complete"（[draining.rst](https://github.com/envoyproxy/envoy/blob/v1.40.2/docs/root/intro/arch_overview/operations/draining.rst?plain=1#L42-L64)）。`drain_timeout` 是首个 GOAWAY（最大流号）与最终 GOAWAY 之间的宽限，默认 5 s；宽限之后拒绝新流，若仍有活动流，连接一直保持到它们自然结束，"The drain sequence never forcefully terminates active streams"（[timeouts.rst](https://github.com/envoyproxy/envoy/blob/v1.40.2/docs/root/faq/configuration/timeouts.rst?plain=1#L68-L80)、[http_connection_manager.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/extensions/filters/network/http_connection_manager/v3/http_connection_manager.proto#L658-L668)）。能终止长流的是另外的计时器：`max_stream_duration` 默认不设，到时间就重置流，与其他超时无关；流空闲超时见第 8 节（[protocol.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/config/core/v3/protocol.proto#L388-L390)）。

**Cap'n Proto 与 Ray。** Cap'n Proto 连接丢失时，依赖该连接的调用以 DISCONNECTED 失败（在途调用调研第 3 节）；流式调用的 ack 随之失败，之后的流式发送都得到这个异常（[rpc.h](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc.h#L321-L323)）。Ray 的几种终止方式见在途调用调研第 2 节，生成器任务被取消时的引用见本文第 3 节。

## 8. 经过中间层的端到端背压

结论：HTTP/2 的流控是逐跳的，中间层不转发 WINDOW_UPDATE，背压只能经中间层自己的缓冲上限间接传回源头。Envoy 给每个缓冲设软上限与高低水位：高水位时对数据源 `readDisable(true)`，在 HTTP/2 上就是不再消耗窗口、不再给对端 WINDOW_UPDATE，对端用完窗口自然停下；降到一半时恢复。经过 Envoy 时，一端慢下来最终会让另一端的写被窗口卡住，Envoy 里每个流积压的数据大致以流窗口（默认 16 MiB）为界，但都是软上限（推论）。Envoy 有几个默认计时器会打断流式 gRPC：路由超时默认 15 s（从请求结束算到响应结束），流空闲超时默认 5 min。

**RFC 9113。** 两级流控都是逐跳的，"Intermediaries do not forward WINDOW_UPDATE frames between dependent connections. However, throttling of data transfer by any receiver can indirectly cause the propagation of flow-control information toward the original sender."（[§6.9](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.9)）。规范用中间层举例说明流控的用途：它要在许多连接之间共享内存，上游可能慢、下游可能快（[§5.2.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.2.2)）。

**Envoy v1.40.2 的默认值。** HTTP/2 的 `initial_stream_window_size` 默认 16 MiB（范围 65,535 到 2^31-1），它同时是每个流在 HTTP/2 编解码缓冲里的软上限，达到时水位回调停止数据流入；`initial_connection_window_size` 默认 24 MiB（[protocol.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/config/core/v3/protocol.proto#L612-L631)）。QUIC 的流窗口默认 16 MiB，连接窗口默认 24 MiB（[L99-L127](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/config/core/v3/protocol.proto#L99-L127)）。监听器与集群的 `per_connection_buffer_limit_bytes` 默认 1 MiB，是连接读写缓冲的软上限（[listener.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/config/listener/v3/listener.proto#L249-L252)、[cluster.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/config/cluster/v3/cluster.proto#L905-L908)）。面向不可信下游的边缘建议：缓冲 32 KiB，HTTP/2 流窗口 64 KiB、连接窗口 1 MiB，并发流 100（[edge.rst](https://github.com/envoyproxy/envoy/blob/v1.40.2/docs/root/configuration/best_practices/edge.rst?plain=1#L14-L25)）。待写出的下游帧超过 10,000 个（PING、SETTINGS、RST_STREAM 三类超过 1,000 个）就按洪泛终止连接（[protocol.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/config/core/v3/protocol.proto#L644-L655)）。

**Envoy 的背压机制。** 每个缓冲都有上限与水位回调：超过上限时，高水位回调最终通知数据源停发，可以是立即停读套接字，也可以是逐渐停止 HTTP/2 的窗口更新，所以所有缓冲上限都是软上限；缓冲排空到低水位（一般是高水位的一半，以免来回抖动）时，低水位回调通知恢复（[flow_control.md](https://github.com/envoyproxy/envoy/blob/v1.40.2/source/docs/flow_control.md?plain=1#L1-L9)）。HTTP/2 上，过滤器、流或连接积压的最终结果都是对源流 `readDisable(true)`：该流不再消耗窗口，不再给对端 WINDOW_UPDATE，对端用完窗口就停；`readDisable(false)` 时立即消耗积压的数据，恢复窗口更新（[L45-L58](https://github.com/envoyproxy/envoy/blob/v1.40.2/source/docs/flow_control.md?plain=1#L45-L58)）。`readDisable` 计数，多个原因（例如上游 TCP 写满与单个流的 HTTP/2 窗口用尽）各自解除后才真正恢复（[L64-L79](https://github.com/envoyproxy/envoy/blob/v1.40.2/source/docs/flow_control.md?plain=1#L64-L79)）。路由过滤器与连接管理器在两个方向上传递水位事件：上游流的发送缓冲积压时，连接管理器对下游流 `readDisable`；下游流积压时，路由过滤器对上游请求 `readDisable`，若上游响应头还没到，就推迟到响应头到达时执行（[L81-L97](https://github.com/envoyproxy/envoy/blob/v1.40.2/source/docs/flow_control.md?plain=1#L81-L97)、[L242-L271](https://github.com/envoyproxy/envoy/blob/v1.40.2/source/docs/flow_control.md?plain=1#L242-L271)、[L320-L362](https://github.com/envoyproxy/envoy/blob/v1.40.2/source/docs/flow_control.md?plain=1#L320-L362)）。流被删除时，HTTP/2 连接消耗掉该流积压的窗口，以免泄漏连接级窗口（[L98-L104](https://github.com/envoyproxy/envoy/blob/v1.40.2/source/docs/flow_control.md?plain=1#L98-L104)）。"defer processing backed up streams"这份开发文档写的是当前默认关闭，并说之后才会做分块与公平性，以免一个流饿死其他流（[L107-L131](https://github.com/envoyproxy/envoy/blob/v1.40.2/source/docs/flow_control.md?plain=1#L107-L131)）。需要缓冲完整消息体的非流式过滤器超过上限时，请求方向回 413，响应方向若头已发出就中途断开，否则回 500；路由上的过滤器都是流式时，Envoy 可以转发任意大的消息体（[flow_control.rst](https://github.com/envoyproxy/envoy/blob/v1.40.2/docs/root/faq/configuration/flow_control.rst?plain=1#L6-L31)）。

**Envoy 中会打断长流的计时器。** 路由的 `timeout` 默认 15 s，从整个下游请求（end-of-stream）处理完算到上游响应处理完，0 表示关闭（[route_components.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/config/route/v3/route_components.proto#L1414-L1424)）；FAQ 明说这对流式响应"typically a problem"，要设为 0 或足够长，流式 API 一般改用 `idle_timeout`；它不会被流式请求触发，因为请求没结束就不开始计时（[timeouts.rst](https://github.com/envoyproxy/envoy/blob/v1.40.2/docs/root/faq/configuration/timeouts.rst?plain=1#L130-L152)）。连接管理器的 `request_timeout` 默认不启用，因为"not compatible with streaming requests (requests that never end)"（[L97-L104](https://github.com/envoyproxy/envoy/blob/v1.40.2/docs/root/faq/configuration/timeouts.rst?plain=1#L97-L104)）。`stream_idle_timeout` 默认 5 min：流在这段时间里上下游都没有活动就被终止，还没收到上游响应头时回 408，否则重置流；文档强烈建议所有请求都设，因为它也防住了整个响应已缓冲、对端却不开窗口的情形（[L110-L117](https://github.com/envoyproxy/envoy/blob/v1.40.2/docs/root/faq/configuration/timeouts.rst?plain=1#L110-L117)、[http_connection_manager.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/extensions/filters/network/http_connection_manager/v3/http_connection_manager.proto#L590-L623)）。`stream_flush_timeout` 默认取 `stream_idle_timeout` 的值，专管"本端数据已全部缓冲、只等对端开窗口"的情形，`max_stream_duration` 不适用于这种情形（[http_connection_manager.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/extensions/filters/network/http_connection_manager/v3/http_connection_manager.proto#L626-L640)）。

**其他。** gRPC 性能指南：流一旦开始就不能再负载均衡（[performance.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/guides/performance.md?plain=1#L21-L25)）。Cap'n Proto 用第一跳套接字的 SO_SNDBUF 作窗口，源码注释写道这在中间转发时失效：第一跳带宽远高于全路径时在瓶颈处造成缓冲膨胀，时延远低于全路径时又发不满；注释列出的改进方向，一是在协议里标出流式调用、让中间层逐跳施加背压（要改基础协议），二是由客户端测量端到端的时延与带宽（[rpc-twoparty.c++](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc-twoparty.c++#L263-L283)、[0.8 发布说明](https://github.com/capnproto/capnproto/blob/v1.5.0/doc/_posts/2020-04-23-capnproto-0.8.md?plain=1#L79)）。

## 9. 流的重试与幂等

结论：gRPC 为流式调用写明了自动重试的规则：调用一旦"提交"（收到响应头，或客户端发出的内容超过重试缓冲）就不再重试。服务端流在收到第一条响应时就提交，所以中途失败不会被自动重试；客户端流与双向流在累计发出的内容超过缓冲（C core 与 grpc-go 默认每 RPC 256 KiB，grpc-java 每 RPC 1 MiB、每通道 16 MiB）时提交。透明重试只针对服务端应用肯定没见过的调用。按 grpc.io 的支持表，hedging 只有 grpc-java 实现，C core 的通道参数说明也写未实现。Envoy 的通用重试规则同样适用于流：请求体超过缓冲上限就放弃重试，下游响应开始之后不再重试。HTTP/2 的 GOAWAY 与 REFUSED_STREAM 是仅有的两种能证明"没被处理"的信号。Arrow Flight 与 Ray 把重试交给应用或任务的重试设置。

**gRPC 的原则。** 除非明确定义，gRPC 调用不被假定为幂等："Calls that cannot be proven to have started will not be retried"；没有重复抑制机制；标为幂等的调用可能被发送多次（[PROTOCOL-HTTP2.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md?plain=1#L197-L203)）。UNAVAILABLE "not always safe to retry non-idempotent operations"；没有适用于所有应用的可重试状态码清单，应用要自己决定（[statuscodes.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/statuscodes.md?plain=1#L22)、[L76](https://github.com/grpc/grpc/blob/v1.85.1/doc/statuscodes.md?plain=1#L76)）。

**gRFC A6。** 调用在两种情形下提交：客户端收到 Response-Headers；客户端发出的内容溢出了库的缓冲。前者的理由是响应头带有服务端的初始元数据，交给应用后可能改变客户端的状态，之后出错就不能安全重试。"发出的内容"对一元与服务端流是一条消息，对客户端流与双向流是打开连接后客户端发出的整个消息流；只要整个消息流还在缓冲里就能重放（[A6](https://github.com/grpc/proposal/blob/89f34f2632b991776e206c97830ec3ac6f391988/A6-client-retries.md#when-retries-are-valid)）。缓冲上限由客户端配置，可以有每通道与每 RPC 两级；放不进缓冲的新 RPC 不可重试但照常发出；客户端流每多发一条都占用更多缓冲，越过上限时调用提交：重试策略下继续当前尝试、不再发起新尝试，即使它以可重试的状态失败；hedging 下继续"已发出最多消息"的那个尝试，立即取消其他尝试；提交后，已发出的消息立即释放，越限的那条新消息不进缓冲，等之前的消息重放完后直接发出（[A6](https://github.com/grpc/proposal/blob/89f34f2632b991776e206c97830ec3ac6f391988/A6-client-retries.md#memory-management-buffering)）。透明重试：没离开客户端的调用可以一直重试到成功或截止时间；到了服务端库但应用没见过的调用立即重试一次；HTTP/2 下由 REFUSED_STREAM 或 last-stream-id 小于该流号的 GOAWAY 判定；透明重试不计入 `maxAttempts`，也不计入重试限流（[A6](https://github.com/grpc/proposal/blob/89f34f2632b991776e206c97830ec3ac6f391988/A6-client-retries.md#transparent-retries)）。hedging 只应用于可以安全多次执行的方法；返回给应用的 listener 把调用（如 `onNext`）转发给所有未完成的 hedged 尝试；收到非错误响应时取消其余尝试（[A6](https://github.com/grpc/proposal/blob/89f34f2632b991776e206c97830ec3ac6f391988/A6-client-retries.md#hedging-policy)）。`maxAttempts` 的客户端默认上限是 5（[A6](https://github.com/grpc/proposal/blob/89f34f2632b991776e206c97830ec3ac6f391988/A6-client-retries.md#limits-on-retries-and-hedges)）。

**gRPC 的指南与实现。** 指南：即使没有配置重试策略，gRPC 也保存调用历史以备透明重试；收到响应头即提交，不再重试，调用交给应用；重试默认开启但没有默认策略，没有策略时只做透明重试（[retry.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/guides/retry.md?plain=1#L16-L44)）。hedging 的语言支持表：Java 有示例，C++ "Not yet available"，Go "Not yet supported"（[request-hedging.md](https://github.com/grpc/grpc.io/blob/d4b80855571d015e4a6df23acc4dd3692c0c7200/content/en/docs/guides/request-hedging.md?plain=1#L134-L140)）；C core 的通道参数说明 hedging 尚未实现，服务配置里的相关字段被忽略（[channel_arg_names.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpc/impl/channel_arg_names.h#L357-L375)）。C core 每 RPC 的重试缓冲默认 256 KiB，超过即提交；收到有效的初始元数据或一条有效消息时也提交（[retry_filter.h](https://github.com/grpc/grpc/blob/v1.85.1/src/core/client_channel/retry_filter.h#L76-L79)、[retry_filter_legacy_call_data.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/client_channel/retry_filter_legacy_call_data.cc#L809-L840)、[L906-L935](https://github.com/grpc/grpc/blob/v1.85.1/src/core/client_channel/retry_filter_legacy_call_data.cc#L906-L935)、[L1725-L1753](https://github.com/grpc/grpc/blob/v1.85.1/src/core/client_channel/retry_filter_legacy_call_data.cc#L1725-L1753)）。grpc-go 每 RPC 默认 256 KiB，即使关闭重试也照样缓冲以备透明重试，超出即提交；`Header()`、`RecvMsg()` 成功与调用 `Context()` 都会提交（[rpc_util.go](https://github.com/grpc/grpc-go/blob/v1.85.0/rpc_util.go#L204)、[stream.go](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L1048-L1060)、[L929-L936](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L929-L936)、[L985-L991](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L985-L991)、[L1133-L1146](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L1133-L1146)）。grpc-java 的通道级重试缓冲默认 16 MiB，每 RPC 1 MiB；收到响应头或超出缓冲时提交（[ManagedChannelImplBuilder.java](https://github.com/grpc/grpc-java/blob/v1.85.1/core/src/main/java/io/grpc/internal/ManagedChannelImplBuilder.java#L120-L121)、[RetriableStream.java](https://github.com/grpc/grpc-java/blob/v1.85.1/core/src/main/java/io/grpc/internal/RetriableStream.java#L888-L893)、[L1420-L1445](https://github.com/grpc/grpc-java/blob/v1.85.1/core/src/main/java/io/grpc/internal/RetriableStream.java#L1420-L1445)）。

**HTTP/2 与 HTTP/3。** 能向客户端保证请求没被处理的只有两个机制：GOAWAY 的 last-stream-id 与 REFUSED_STREAM；没被处理的请求"have not failed"，客户端可以自动重试，即使是非幂等方法；服务端只有在能保证时才可以这样表示，帧一旦交给应用层，就不能再对该流用 REFUSED_STREAM（[RFC 9113 §8.7](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.7)）。HTTP/3 的 GOAWAY 同样让客户端可以在另一个连接上安全重试未处理的请求（[RFC 9114 §5.2](https://www.rfc-editor.org/rfc/rfc9114.html#section-5.2)）。

**Envoy。** 重试次数、条件与预算可配置，所有重试都包含在整体请求超时之内（[http_routing.rst](https://github.com/envoyproxy/envoy/blob/v1.40.2/docs/root/intro/arch_overview/http/http_routing.rst?plain=1#L142-L168)）。路由器为可能的重试缓冲请求体，超过有效缓冲上限就放弃重试与缓冲；若此时正等着重试、没有上游请求，就回 507 "exceeded request buffer limit while retrying upstream"（[router.cc](https://github.com/envoyproxy/envoy/blob/v1.40.2/source/common/router/router.cc#L1132-L1180)）。下游响应一旦开始，就不再因上游重置而重试（[L1636-L1641](https://github.com/envoyproxy/envoy/blob/v1.40.2/source/common/router/router.cc#L1636-L1641)）。`per_try_timeout` 只在向下游发出任何响应之前有效，文档说它可用于流式端点：上游没能在时限内开始响应时重试（[timeouts.rst](https://github.com/envoyproxy/envoy/blob/v1.40.2/docs/root/faq/configuration/timeouts.rst?plain=1#L157-L163)）。缓冲上限的取法：`request_body_buffer_limit` 优先，其次是 min(`per_request_buffer_limit_bytes`, `per_connection_buffer_limit_bytes`)，都没设就用 `per_connection_buffer_limit_bytes`（[route_components.proto](https://github.com/envoyproxy/envoy/blob/v1.40.2/api/envoy/config/route/v3/route_components.proto#L218-L248)）。

**Arrow Flight。** endpoint 有 `expiration_time` 时，客户端可以在过期之前多次 DoGet 同一份数据；否则 DoGet 能否重试由应用定义（[Flight.rst](https://github.com/apache/arrow/blob/apache-arrow-26.0.1/docs/source/format/Flight.rst?plain=1#L142-L147)）。

**Ray。** 生成器任务与 actor 任务支持 `max_retries`、`retry_exceptions`、`max_restarts`、`max_task_retries` 与对象重建（[ray-generator.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/ray-generator.rst?plain=1#L144-L151)）。属主收到较早尝试的迟到上报时，把它当作过期报告丢弃（[task_manager.cc](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/core_worker/task_manager.cc#L1099-L1112)）；流按对象序号登记，`InsertToStream` 对已用过的序号返回 false，此时不再重复登记属主的引用（[L1150-L1162](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/core_worker/task_manager.cc#L1150-L1162)）。

## 未能核实的内容

- 本文没有在本机运行任何程序。Python 同步 handler 在流控上阻塞、客户端停止迭代即不再补额度、线程池被长流占满后新 RPC 排在队列里、C core 在内存压力低时通告约 4 MiB 的每流初始窗口、Arrow DoGet 出错前的批次已发出，都是读源码得出的推论，没有复现。
- C core 的连接级窗口是否独立于应用读取补充：grpc-go 有明确的代码注释，C core 只读到窗口目标的计算，没有追踪完整路径。
- C core 收到对端的 RST_STREAM 时是否走"以错误关闭流、丢弃未读缓冲"的路径：只读到 `grpc_chttp2_mark_stream_closed` 带错误时合成非 OK 状态，没有读 RST_STREAM 帧解析器的调用点。
- grpc-java：Netty 传输里应用 `request(n)` 与 WINDOW_UPDATE 的确切关系（没有读 deframer 与本地流控器的代码）、`MIN_ALLOCATED_CHUNK` 的取值、Netty `UniformStreamByteDistributor` 的算法。
- Python 同步与 aio 的 `stop(grace)` 中止长流时客户端看到的状态码：在途调用调研只复现了一元调用。
- Cap'n Proto 除 C++ 以外的实现现在是否实现了 `-> stream` 的流控：只读到 2020 年 0.8 发布说明里"只有 C++ 实现"的说法。
- Ray：生成器任务重试时，调用方已经消费过的项会怎样（新尝试重新产出的同序号对象是否替换原值、调用方能否察觉），只读到过期尝试过滤与序号去重两处代码。`_generator_backpressure_num_objects` 与 `_actor_generator_backpressure_num_objects` 有没有官方文档或稳定性承诺：生成器文档没有提，源码里以下划线开头。
- Envoy：v1.40.2 默认使用的 HTTP/2 编解码器（nghttp2 或 oghttp2）；"defer processing backed up streams"在 v1.40.2 是否仍默认关闭，只读到源码树里开发文档的说法，没有核对运行时开关的默认值；HTTP/3 路径的背压细节。
- gRPC 各实现是否发送或使用 HTTP/2 的 PRIORITY 信号：只读到写调度用 FIFO 轮转或均匀分配，没有核对优先级帧的处理。
- grpc-go 是否已实现 hedging：只读到 grpc.io 指南的支持表写 Go "Not yet supported"，没有核对 grpc-go 源码。
- Arrow Flight 只读了 C++ 实现；Java、Go 与 Python 的 Flight 是否同样把 gRPC 接收上限设为不限，没有核对。
- QUIC 实现常用的初始窗口取值：RFC 9000 只规定缺省为 0，没有推荐值；除 Envoy 的 QUIC 配置外没有查。

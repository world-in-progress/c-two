# 名字的唯一持有者：跨节点单一归属的做法与分层边界

日期：2026-11-06。起因：维护者希望路由名成为资源状态的唯一身份，Host 重启或空闲停服后重新注册，客户端不必察觉；同时希望在整个 relay 网格里，同一个路由名至多有一个活着的注册。注册表最终一致还不够：调用有状态、由调用方排序且常常不幂等，同一个路由名若有两个活着的实例，状态就会分叉。本文要回答的是：成熟系统怎样在崩溃、进程暂停、网络分区与时钟偏差下防止出现两个活着的持有者；持有者转移时，拿着引用的客户端看到什么；分层系统在哪里划界，哪些由运行时或连接层自己保证，哪些交给上层（在 C-Two 里可能是资源信任与访问层 toodle），下层是否提供可插拔的权威。另有一个将来的场景：用户把自己的机器接入计算平台，参与者不再都由一个可信的运维方运行，可能出现拜占庭式的行为。

状态：调研记录，只列事实与出处，不给建议，没有改动代码。来源是论文的正式版本或作者托管的版本、RFC 与规范、固定版本的官方文档，以及固定 tag 或提交的源码；Kleppmann 的文章是博客，只作为他本人论点的一手出处引用。网页都在 2026-11-06 读取。标“推论”的是本文据这些来源所做的推断，标“未核实”的是没能在一手来源里确认的内容。

用词：外部系统里的限时授权在本文写作 lease，不译作“租约”，因为术语表里的租约指传输对缓冲的占用；“持有者”指当前拥有一个名字、一把锁或一个 lease 的一方，是描述外部系统的普通用语，与 C-Two 的 hold 无关。术语表里还没有一个词指称“在整个 relay 网格里唯一拥有某个路由名的那次注册”。

## 1. 故障模型与不可能性结果

结论：只考虑崩溃故障时，由多数派（2f+1 个副本容忍 f 个）作出的“谁是持有者”的决定可以在任何时序下都不冲突，但在完全异步的系统里，任何确定性协议都可能永远作不出决定；容忍拜占庭故障在部分同步模型里需要 3f+1 个副本，签名只在同步模型里能降低这个数目。

Lamport、Shostak 与 Pease（[TOPLAS 4(3), 1982](https://doi.org/10.1145/357172.357176)，[作者托管版](https://lamport.azurewebsites.net/pubs/byz.pdf)）证明，只用口头消息时，拜占庭将军问题可解当且仅当超过三分之二的将军忠诚，m 个叛徒至少需要 3m+1 个将军；消息带不可伪造、人人可验证的签名时，任意数目的将军与叛徒都可解。算法假设消息缺失能被发现；论文指出用超时做到这一点，需要消息传输有固定的最长时间、双方时钟同步在固定误差之内，而在有故障处理器时保持时钟同步“is as difficult a problem as the Byzantine Generals Problem itself”。

Fischer、Lynch 与 Paterson（[JACM 32(2), 1985](https://doi.org/10.1145/3149.214121)，[作者所在组托管版](https://groups.csail.mit.edu/tds/papers/Lynch/jacm85.pdf)）证明，在完全异步的系统里，只要可能有一个进程故障，每个共识协议都存在不终止的执行；模型里没有同步时钟，无法分辨另一个进程是已经停止还是只是很慢。Dwork、Lynch 与 Stockmeyer（[JACM 35(2), 1988](https://doi.org/10.1145/42282.42283)，[托管版](https://groups.csail.mit.edu/tds/papers/Lynch/jacm88.pdf)）引入部分同步：延迟上界存在但未知，或者已知但只从某个未知的全局稳定时间（GST）起成立。此时容忍 t 个崩溃或遗漏故障需要且只需要 N ≥ 2t+1，容忍 t 个拜占庭故障不论有无签名认证都需要 N ≥ 3t+1；完全同步时，有签名的拜占庭故障可以容忍任意数目。他们把正确性拆成安全与终止：正确的处理器永不分歧，这一点不论消息系统多么异步都要满足；终止只在延迟上界最终成立时才要求。

Lamport 的 [Paxos Made Simple（2001-11-01）](https://lamport.azurewebsites.net/pubs/paxos-simple.pdf)规定值被多数接受者接受才算选定；两个提议者可以轮流用更大的编号互相压制，使任何值都选不出来；FLP 的结果意味着可靠地选出唯一提议者必须用随机化或真实时间（例如超时），但不论选举成败，安全都成立。Raft 的[扩展版论文](https://raft.github.io/raft.pdf)（[USENIX ATC 2014](https://www.usenix.org/conference/atc14/technical-sessions/presentation/ongaro) 论文的作者扩展版，2014-05-20）写道，这类算法在一切非拜占庭条件下都不返回错误结果，多数服务器运行并能互相通信即可用（五台容忍任意两台故障），不依赖时序来保证日志一致，时钟出错与极端延迟最多造成可用性问题；选主要求 broadcastTime ≪ electionTimeout ≪ MTBF。领导者回答只读请求之前必须确认自己没有被取代，Raft 先与多数派交换一轮心跳；改用心跳提供的 lease 则“would rely on timing for safety (it assumes bounded clock skew)”。领导者提交之后、回复之前崩溃时，客户端向新领导者重试会使命令执行两次，论文的办法是客户端给每条命令一个唯一序号，状态机记住每个客户端最近的序号与回复。

Castro 与 Liskov 的 PBFT（[OSDI 1999，USENIX 官方 HTML 版](https://www.usenix.org/legacy/events/osdi99/full_papers/castro/castro_html/castro.html)）用 3f+1 个副本容忍 f 个拜占庭副本，并说明这是异步系统同时提供安全与活性的最小数目；安全不依赖同步，活性要求 delay(t) 不无限期地比 t 增长得更快（[§3](https://www.usenix.org/legacy/events/osdi99/full_papers/castro/castro_html/node3.html)）。所有副本知道彼此的公钥（[§2](https://www.usenix.org/legacy/events/osdi99/full_papers/castro/castro_html/node2.html)），正常情况分 pre-prepare、prepare、commit 三个阶段（[§4](https://www.usenix.org/legacy/events/osdi99/full_papers/castro/castro_html/node4.html)），实现里只有视图变更与新视图消息用数字签名，其余用 MAC（[§5](https://www.usenix.org/legacy/events/osdi99/full_papers/castro/castro_html/node5.html)）。安全不受故障客户端数目影响，但故障客户端仍能写入垃圾数据，论文靠客户端认证与访问控制限制这种损害。论文测得基于 PBFT 的 NFS 只比不复制的标准 NFS 慢 3%。

Gilbert 与 Lynch（[SIGACT News 33(2), 2002](https://doi.org/10.1145/564585.564601)；ACM 官方版读取时返回 403，引文据[课程页托管的出版稿](https://www.cs.princeton.edu/courses/archive/spring22/cos418/papers/cap.pdf)核对）证明，在异步网络模型里，不可能实现一个在所有公平执行（包括丢消息的执行）中既可用又满足原子一致性的读写对象（定理 1）；在部分同步模型里，只要任意消息都可能丢失，结论同样成立（定理 2）。

推论：把“同一个名字至多一个活着的持有者”当作一个要达成共识的决定，上面的结果意味着，自动接管不能以“判定旧持有者已死”作为安全的前提，因为异步模型里慢与死无法区分；能做到的是让“谁是持有者”由法定人数决定、永不冲突，同时接受网络不稳定时可能暂时没有持有者，超时只用来推动活性。要在少数派一侧继续服务，就得放弃这种一致性，这正是 CAP 定理 1 所说的取舍。

## 2. lease、fencing token 与自我隔离

结论：lease 的正确性以时钟漂移有界为前提，而且持有者在 lease 失效后仍可能因暂停或延迟发出请求；各家要么让持有状态的资源检查单调递增的 fencing token 或 sequencer，要么用 lock-delay 与自我隔离缩小这个窗口，Chubby 与 Consul 都说 lock-delay 并不完备。

Gray 与 Cheriton（[SOSP 1989, pp. 202–210](https://doi.org/10.1145/74850.74870)；ACM 官方版读取时返回 403，引文据[课程页托管的副本](https://courses.cs.duke.edu/spring15/cps210/readings/leases-sosp89.pdf)核对）把 lease 定义为在限定时间内授予持有者对某项财产特定权利的约定。它在消息丢失（含分区）以及客户端、服务端崩溃时都保持一致，前提是没有包括时钟故障在内的某些拜占庭故障：服务端时钟太快，会在前一个客户端的 lease 在其本地还没到期时就允许写入；客户端时钟太慢，会继续使用服务端已认为过期的 lease；反方向的偏差只多产生流量。最低要求是时钟漂移有界。崩溃后恢复的服务端必须尊重先前发出的 lease，最简单的做法是把所有写入推迟一个发出过的最长 lease 时长。

Chubby（[Burrows, OSDI 2006](https://www.usenix.org/legacy/event/osdi06/tech/full_papers/burrows/burrows.pdf)）的一个 cell 通常有五个副本，master 要得到多数票，外加这些副本在几秒的 master lease 内不选别的 master 的承诺，所以 master lease 未过期时 master 单独回答读请求是安全的。客户端本地的 lease 超时是 master 一侧的保守近似，要求服务端时钟比客户端快不超过一个已知的常数倍；本地超时到期后会话进入 jeopardy，客户端清空并关闭缓存，再等默认 45 s 的宽限期，库向应用发 jeopardy、safe 或 expired 事件，让应用在不确定会话是否还在时先静默。论文写明锁的根本难点：持有锁 L 的进程发出请求 R 后故障，另一个进程取得 L 并动作，R 迟到时就会在没有 L 保护的情况下被执行。Chubby 的锁是建议性的，为此提供 sequencer：一个描述锁刚取得时状态的不透明字节串，含锁名、模式与锁的代次号，交给受保护的服务器，由它用 `CheckSequencer()` 或与见过的最新 sequencer 比较来拒绝过时请求。不能检查 sequencer 的服务可以依赖 lock-delay：持有者故障或失联使锁空出时，锁服务在一段时间内（客户端可设，上限一分钟）不让别人取得这把锁，论文称之为“imperfect”。最小的改法是写请求带上锁的取得次数，由文件服务器拒绝次数小于当前值的写入。Chubby 的句柄绑定文件的一次实例而不是文件名：节点在句柄创建后被删除，即使又以同名重建，经这个句柄的调用也会失败。Chubby 后来成了 Google 内部主要的名字服务。

Kleppmann 的博客文章 [How to do distributed locking（2016-02-08）](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)是他本人论点的一手出处。他把锁分为为了效率（失败只是多做一次工作）和为了正确性两类；在后一类里，持有 lease 的客户端若经历比 lease 时长还长的 GC 暂停而不自知，就可能做出不安全的修改，他说 HBase 曾有这个问题。补救是 fencing：每次取得锁时锁服务给出一个递增的数字，每个写请求都带上它，存储服务拒绝比已见过的更小的数字，这要求存储服务主动检查。他写道，用 ZooKeeper 做锁服务时，可以用 zxid 或 znode 版本号作 fencing token；Redlock 没有产生 fencing token 的手段，而且只在网络延迟、进程暂停与时钟误差都有界的同步模型下才正确。

etcd v3.6 文档的 [Notes on the usage of lock and lease](https://etcd.io/docs/v3.6/learning/why/) 说，TTL 是物理时间，服务端与客户端各用自己的时钟计时，因此会出现服务端已撤销 lease、客户端仍认为自己持有的情形；lease 机制本身不保证互斥，lock API 本身也不能用作互斥机制，叫 lock 是历史原因。etcd 对自身键的互斥靠版本号校验：Put 与 Txn 可以要求 revision 与 lease ID 满足条件，不满足就失败。文档把 Chubby 的 sequencer 对应为 revision 加 lease ID，把 fencing token 对应为 revision，并写明 etcd 的锁不能保护 etcd 之外的资源，外部资源必须自己提供版本号校验与副本一致性。Consul（[Sessions 文档](https://developer.hashicorp.com/consul/docs/automate/session)，版本选择器显示 v2.1.x）的 lock-delay 取 0 到 60 s，默认 15 s：会话失效后，它持有过的锁在这段时间内不能被重新取得，好让可能仍活着的旧 leader 察觉失效并停止处理请求；文档说这是受 Chubby 启发的安全措施，“While not a bulletproof method”。(Key, LockIndex, Session) 三元组可以当作 sequencer 传递；锁本身是纯建议性的。

Kubernetes client-go 的选主库（[leaderelection.go，v0.37.2](https://github.com/kubernetes/client-go/blob/v0.37.2/tools/leaderelection/leaderelection.go)，该包自称 alpha API）在包注释里写明“This implementation does not guarantee that only one client is acting as a leader (a.k.a. fencing).”客户端只用本地采集的时间推断选举状态，因此能容忍任意的时钟偏差，但不能容忍任意的时钟速率偏差，可容忍的速率比近似等于 LeaseDuration 与 RenewDeadline 之比。核心组件默认 LeaseDuration 15 s、RenewDeadline 10 s、RetryPeriod 2 s；非 leader 必须等满一个 LeaseDuration 且没看到记录变化才能抢占，leader 在 RenewDeadline 内续不上就放弃。Kubernetes 的 [Leases 概念页](https://kubernetes.io/docs/concepts/architecture/leases/)则说控制面组件用 Lease“to ensure only one instance of a component is running at any given time”，与源码注释的口径不同。

自我隔离的做法散见各处：Chubby 客户端在 jeopardy 期间关闭缓存、由应用静默；ZooKeeper 自身把超时设成“leaders realize they are not leaders before followers abandon them”（[Hunt et al.](https://www.usenix.org/legacy/event/atc10/tech/full_papers/Hunt.pdf)）；Orleans 的 silo 读到自己被判死后终止进程，Akka 的 Split Brain Resolver 让少数派一侧把自己下线（见第 4 节）；Curator 的 LeaderLatch 在连接 SUSPENDED 或 LOST 时立即报告自己不再是 leader（[文档](https://curator.apache.org/docs/recipes-leader-latch/)）。推论：这些做法都要求持有者自己能及时运行，被暂停的进程在恢复之前做不了任何检查，所以上述系统都另加 fencing、lock-delay 或时间余量。

## 3. 共识支撑的注册表：ZooKeeper、etcd、Consul、Chubby

结论：这四个系统对“当前谁持有”只给出一个线性一致的答案，但不保证持有者及时知道自己已失去持有，也不替受保护的资源拒绝旧持有者的迟到请求，这两件事分别交给客户端对会话事件的处理和资源一侧对 fencing 值的检查。

ZooKeeper（[Hunt et al., USENIX ATC 2010](https://www.usenix.org/legacy/event/atc10/tech/full_papers/Hunt.pdf)）保证所有更新状态的请求可串行化且尊重先后（linearizable writes），同一客户端的请求按发送顺序执行；Zab 默认用简单多数，2f+1 台服务器容忍 f 台故障。ephemeral znode 可以显式删除，也会在创建它的会话结束（主动或因故障）时被系统删除；ZooKeeper 在会话超时内收不到某会话的任何消息，就认为该客户端故障。3.9.3 的[程序员指南](https://zookeeper.apache.org/doc/r3.9.3/zookeeperProgrammers.html)写明，会话过期由集群而不是客户端决定，过期时集群删除该会话的全部 ephemeral 节点并通知观察者；被分区的客户端在重新连上集群之前收不到“session expired”通知，一直停在 disconnected 状态。`ephemeralOwner` 记录 ephemeral 节点所属的会话；每次变更有一个 zxid，zxid 给出所有变更的全序。指南特别说明 ZooKeeper 不保证“Simultaneously Consistent Cross-Client Views”，一个客户端可能在另一个客户端收到变更通知之前就完成了更新。锁库 Curator 的[文档](https://curator.apache.org/docs/recipes-shared-reentrant-lock/)要求监听连接状态：报告 SUSPENDED 时不能确定是否还持有锁，直到收到 RECONNECTED；报告 LOST 时可以确定已不再持有。

etcd v3.6 的 [API 文档](https://etcd.io/docs/v3.6/learning/api/)：store revision 是键空间每次修改都加一的集群级计数器，事务可以比较键的 `create_revision`、`mod_revision`、`version` 或值；lease 在 TTL 内收不到 keepAlive 就过期，过期或被撤销时挂在它上面的键全部删除。[并发 API](https://etcd.io/docs/v3.6/dev-guide/api_concurrency_reference_v3/) 的 Lock 返回一个只在持锁期间存在的唯一键，可以和事务一起保证对 etcd 的更新只在持锁时发生，锁持续到 Unlock 或持有者的 lease 过期；Election 的 Campaign 返回 LeaderKey，可在事务里以“仍是 leader”为条件，lease 在辞去 leader 之前过期或被撤销时，leadership 转给下一个竞选者；Observe 按顺序推送历任 leader 的公告。如第 2 节所述，这些 API 对 etcd 之外的资源不提供互斥。

Consul 的会话在节点注销、任一健康检查被注销或变为 critical、会话被显式销毁或 TTL 到期时失效；TTL 只是失效的下限，Consul 可以把过期推迟到 TTL 之后；失效时会话持有的锁按配置被释放或连键删除；只有在没有现任持有者时 acquire 才会成功（[Sessions 文档](https://developer.hashicorp.com/consul/docs/automate/session)）。Chubby 的保证与限制见第 2 节。推论：这四个系统发布的“持有者是谁”对客户端来说都只是某一时刻的观察，它们不把请求转给新持有者，持有者变化后由使用方自己重新查询或订阅通知。

## 4. 单实例运行时：Orleans、Akka、Erlang、Dapr、Ray、Kubernetes

结论：这些平台都把“一个逻辑名字至多对应一个活着的实例”做成平台功能，其中 Orleans 的默认目录、Akka 的单例与分片、Erlang global 的文档写明成员变化或分区时可能短暂出现两个实例，Kubernetes StatefulSet 则宁可让身份停在失联节点上，直到节点被确认死亡或被人工强制处理；状态的最后一道保护放在存储层的条件写、单写者日志或人工确认上。

Orleans 的技术报告（[Bernstein et al., MSR-TR-2014-41, 2014-03](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/Orleans-MSR-TR-2014-41.pdf)）说，没有故障时 Orleans 保证一个 actor 只有一个激活，有故障时只是最终保证：故障尚未传达到所有幸存者时，持有过时成员视图的发送方可能把注册请求发错目录分区，同一个 actor 可能在两个分区里各注册一个激活，成员稳定后从目录里丢掉其中一个，并通知其所在服务器撤销这个激活。作者说这是为了在成员变化时仍能推进而选择可用性、放弃一致性，“eventual single activation”对多数应用够用，不够时由应用借助外部持久存储取得更强的一致性。现行文档（[grain directory](https://learn.microsoft.com/en-us/dotnet/orleans/host/grain-directory)，页面日期 2026-10-19）一方面写“at most one activation of a grain exists at any point in time”，另一方面在实现表里写明默认的集群内目录是最终一致的分布式哈希表，“Allows occasional duplicate activations during cluster instability”；Orleans 10.0 起另有强一致的集群内目录，视图变更时用带版本的区间锁防止重复激活，目前是预览功能；也可以按 grain 类型改用 Redis、Azure Table 或 ADO.NET 的存储型目录，或注入自己的实现（3.2.0 起可插拔）。

Orleans 的[成员管理](https://learn.microsoft.com/en-us/dotnet/orleans/implementation/cluster-management)（页面日期 2026-01-22）把 `IMembershipTable` 放在可靠的持久存储里，用事务或 ETag 比较交换原子地更新成员行与版本号，默认配置下典型的故障检测时间约 15 s。一旦在表中被判死，所有 silo 都视它为死，哪怕它只是暂时分区；它自己读到这一状态后终止进程，由外部设施以新的 epoch 号重启；表不可达时 Orleans 不会误判任何 silo 死亡。状态一侧，存储提供者可以在读状态时附带 ETag，写入时发现 ETag 冲突就以 `InconsistentStateException` 使写入失败，写入失败通常作为调用异常抛回调用方（[grain persistence](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-persistence/)）。调用方拿的 grain 引用代表逻辑身份，与物理位置无关，整个系统重启后仍然有效（[grain references](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-references)）；消息默认至多投递一次，超时后返回的 Task 以超时异常结束，配置超时重试后变为至少一次、不再保证至多一次，Orleans 不持久记录哪些消息已送达（[delivery guarantees](https://learn.microsoft.com/en-us/dotnet/orleans/implementation/messaging-delivery-guarantees)）。

Akka 2.10.24 的 [Cluster Singleton](https://doc.akka.io/libraries/akka-core/2.10.24/typed/cluster-singleton.html) 确保集群里某类 actor 恰好运行一个，它在最老的节点上。最老节点崩溃或失联时，要先经 downing 把它移出集群，新的最老节点才启动新单例，没有平滑交接；文档的说法是“more than one active singletons is prevented by all reasonable means”，个别边角情况靠可配置的超时最终解决，可以再加 lease 作为额外的保险。文档列出两个单例同时运行的原因：没有合适 downing 的网络分区、部署失误造成两个独立集群、分区一侧移除成员与另一侧关停它们之间的时序问题；并警告会把集群分裂成几个独立集群的 downing 策略会让每个集群各起一个单例。调用方经单例代理发消息，单例不可用期间代理缓存消息，缓冲满时丢弃旧消息，文档说消息总可能丢失。[Cluster Sharding](https://doc.akka.io/libraries/akka-core/2.10.24/typed/cluster-sharding.html) 让调用方只用逻辑 id 与实体交互，有同样的分裂警告；配置 lease 时，shard 取不到 lease 就不初始化，消息缓存在 ShardRegion，初始化后丢失 lease 则终止该 shard；实体 passivate 期间到达的消息缓存起来，交给实体的下一次化身（new incarnation）；投递是尽力而为的至多一次（[concepts](https://doc.akka.io/libraries/akka-core/2.10.24/typed/cluster-sharding-concepts.html)）。

Akka 的 [Split Brain Resolver](https://doc.akka.io/libraries/akka-core/2.10.24/split-brain-resolver.html) 说，失败检测器能发现网络分区与机器崩溃，但区分不了两者。策略有 keep-majority（默认，保留上次已知成员中的多数一侧）、static-quorum、keep-oldest、down-all 与 lease-majority（只让取得分布式 lease 的一侧存活，lease 不可得时全部下线）。决定要等成员与可达性连续 stable-after（默认 20 s）不变才作出，迟迟不稳定时在 stable-after 加 down-all-when-unstable（默认为 stable-after 的 3/4）之后全部下线。文档解释，单例与分片的目的就是任一时刻至多一个实例，新实例必须在旧实例停止之后才能启动，持久化实例尤其如此，因为一个持久化 actor 的事件日志只能有一个活跃写者；分区两侧无法通信、作决定的时间也有先后，所以需要一段基于时间的余量（down-removal-margin，默认等于 stable-after），缩短它就增加同时运行多个实例的风险。[Coordination](https://doc.akka.io/libraries/akka-core/2.10.24/coordination.html) 把 lease 定义为分布式锁的可插拔 API，实现须保证同名 lease 在任何节点都是同一个、同一时间只有一个 owner 能取得；实现通常基于 Kubernetes API server 或 ZooKeeper，可能因与第三方通信超时而丢失 lease，`checkLease` 可在关键动作之前同步检查。heartbeat-timeout 必须大于预期的最长 JVM 暂停，否则原持有者恢复后会有一小段时间来不及关停分片或单例；追求最大安全时可以把存活期设为无限，由人工介入。

Erlang/OTP 29.1.2（kernel 11.0.4）的 [global](https://www.erlang.org/docs/29/apps/kernel/global.html) 把全局名字的副本存在每个节点的名字表里，没有中心存储，名字到 pid 的翻译在本地完成；`register_name` 完全同步，返回时名字要么在所有节点注册、要么都没有，名字已被占用时返回 `no`；进程终止或其节点宕机时名字在所有节点注销。global 维护全连接网络，OTP 25 起默认主动断开报告失联的节点以防止重叠分区；文档写明，只有 `connect_all` 与 `prevent_overlapping_partitions` 都开启时这些服务才可靠，否则 API 照常返回，结果不可靠。新节点加入或分区重新连通时若发现同名冲突，就调用注册时给的 Resolve 函数决定保留哪个 pid：默认的 `random_exit_name` 随机保留一个、杀掉另一个，`random_notify_name` 保留一个并通知另一个，`notify_all_name` 两个都注销并通知双方。`global:send/2` 发给未注册的名字时，调用方以 `{badarg, {Name, Msg}}` 退出。同一 kernel 里的 [pg](https://www.erlang.org/docs/29/apps/kernel/pg.html) 是另一种语义：一个名字对应一组进程，成员视图强最终一致，可能暂时分歧且不传递，不提供单一持有者。

Dapr v1.19 的 [Placement 服务](https://v1-19.docs.dapr.io/concepts/dapr-services/placement/)计算并分发按命名空间分组的分布式哈希表，把 actor 类型映射到 Pod 或进程；高可用模式下三副本，用 Raft 选主并把表持久化在 Raft 里（[生产部署](https://v1-19.docs.dapr.io/operations/hosting/kubernetes/kubernetes-production/)）。v1.19 起也可以改由 Scheduler 服务放置，文档说两者的保证相同：每个 sidecar 对每个 actor ID 落在哪个实例上得出同一个确定的结论，集群始终只有一个放置权威。actor 按回合访问，同一时刻只有一个线程在 actor 代码里；actor 对象闲置一段时间后被回收，以后再用同一 ID 会构造新对象，状态在状态存储里，比对象活得久；节点故障时 Dapr 把 actor 迁到健康节点（[actor 特性](https://v1-19.docs.dapr.io/developing-applications/building-blocks/actors/actors-features-concepts/)）。所读页面没有说明分区或放置表分发期间是否可能出现同一 actor 的两个激活（未核实）。

Ray 2.60.0 的[命名 actor](https://docs.ray.io/en/releases-2.60.0/ray-core/actors/named-actors.html) 在命名空间内名字唯一，集群里任一作业都能按名字取得；detached actor 用 `ray.kill` 销毁之后，名字可以重用。名字表由 [GCS](https://docs.ray.io/en/releases-2.60.0/ray-core/fault_tolerance/gcs.html) 管理，它默认只存内存、不容错，GCS 故障即整个集群故障；容错要靠外部的 HA Redis 或嵌入式 RocksDB（alpha），恢复期间不能创建、删除或重建 actor，已运行的 actor 继续存活。按 [actor 容错](https://docs.ray.io/en/releases-2.60.0/ray-core/fault_tolerance/actors.html)文档，重启的 actor 重跑构造函数重建状态；actor 任务默认至多执行一次，`RayActorError` 可能在任务其实已成功执行之后抛出；`ActorUnavailableError` 表示无法确定是否已执行，没配置重试时 Ray 保证方法不会执行两次，并建议调用方“隔离”该 actor、定期探测；配置 `max_task_retries` 后变为至少一次，同一方法可能在故障实例与重启实例上各执行一次。所读文档没有说明重启 actor 时怎样确认旧进程已经停止（未核实）。

Kubernetes v1.37 的 [StatefulSet 强制删除文档](https://kubernetes.io/docs/tasks/run-application/force-delete-stateful-set-pod/)写明，任一时刻集群里至多一个 Pod 具有某个身份（“at most one”语义）。节点失联时 Pod 不会被自动删除，只会在超时后进入 Terminating 或 Unknown；只有节点对象被删除、失联节点上的 kubelet 恢复并杀掉 Pod、或用户强制删除，它才会从 API server 移除。强制删除不等 kubelet 确认就释放名字，控制器随即可以创建同一身份的替代 Pod；旧 Pod 若仍在运行并能与其他成员通信，就违反 at most one，强制删除等于用户断言旧 Pod 再也不会与别人联系。[非优雅关机](https://kubernetes.io/docs/concepts/cluster-administration/node-shutdown/)的 out-of-service taint 同样要求先确认节点已关机或断电，而不是在重启途中。

## 5. 不依赖全局共识的命名

结论：DNS、Erlang 本地注册名与 Kubernetes 对象名都只在一个权威范围之内保证名字唯一（一个区、一个节点、一个命名空间加一个 API server），跨范围靠层级前缀区分；名字可以在删除后重用，Kubernetes 另用 UID 区分同名对象的先后出现。

[RFC 1034](https://www.rfc-editor.org/rfc/rfc1034)（1987-11）把名字空间按区切分，一个组织控制自己的区之后，可以单方面修改区内数据、增删节点，或把子区再委派出去。设计目标写着，获取信息比即时更新或一致性保证更重要，更新逐步扩散，不保证所有副本同时更新；更新因网络或主机故障不可得时，通常的做法是继续相信旧信息并继续尝试更新；TTL 限定缓存时长。

Erlang 的本地注册名（[参考手册](https://www.erlang.org/docs/29/system/ref_man_processes.html)）是一个原子，`register/2` 把它关联到本节点的一个进程，进程终止时自动注销。发往别的节点上的注册名用 `{RegName, Node}`（[erlang:send/2](https://www.erlang.org/docs/29/apps/erts/erlang.html#send/2)）；除了本地原子名未注册这一种情况，发送不会因目的地不可达而失败。名字只在一个节点之内唯一，节点名是地址的一部分。

Kubernetes 的[对象名](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/)：同一种资源同一时刻只能有一个对象使用某个名字，删除后可以新建同名对象；UID 在集群整个生命周期内各不相同，用来区分同类实体在历史上的不同出现；名字只需在[命名空间](https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/)内唯一。这种唯一性落在 API server 及其后备存储 etcd 上（[集群架构](https://kubernetes.io/docs/concepts/architecture/)）；PUT 更新必须带 resourceVersion，资源已被改过时 API server 返回 409 Conflict，以此发现丢失的更新（[API 概念](https://kubernetes.io/docs/reference/using-api/api-concepts/)）。

## 6. 参与者不再可信时

结论：容忍拜占庭参与者的复制需要 3f+1 个副本，参与者的公钥事先互相知道，或者验证者集合由应用许可；签名记录证明的是“这条记录是谁发布的”，所读规范没有规定同一名字的多个发布者之间怎样互斥；没有逻辑上集中的身份权威时，Sybil 攻击无法杜绝，只能提高成本。

PBFT 的副本数与签名、MAC 的分工见第 1 节。HotStuff（[Yin et al., arXiv v6, 2019-07-23](https://arxiv.org/abs/1803.05069v6)，[PODC 2019](https://doi.org/10.1145/3293611.3331591)）的模型是固定的 n = 3f+1 个副本，使用门限签名，所有副本共享一个公钥、各持不同的私钥。按论文的比较，一次决定之前若发生 O(n) 次视图变更，PBFT 共需传输 O(n⁴) 个认证子，HotStuff 在 GST 之后的最坏情况是 O(n²)；作者在 100 多个副本上测得吞吐与延迟和 BFT-SMaRt 相当。

CometBFT v1.0.1 的[介绍](https://github.com/cometbft/cometbft/blob/v1.0.1/docs/explanation/introduction/README.md)说，它在少于 1/3 的机器以任意方式失效时仍能工作，并把 ZooKeeper、etcd 与 Consul 归为只容忍崩溃的系统，“even a single Byzantine fault can jeopardize the whole system”。安全的前提是拜占庭验证者的投票权少于三分之一，此时不会在同一高度提交冲突的区块；[共识规范](https://github.com/cometbft/cometbft/blob/v1.0.1/spec/consensus/consensus.md)写明，任何占 1/3 以上的联盟都能靠不广播投票让链停止。验证者用各自的私钥签名投票；验证者集合由 ABCI 应用许可与管理，权益证明不是必需的，可以在应用里实现，用来量化违反“拜占庭投票权不足三分之一”这一假设的代价（[validators](https://github.com/cometbft/cometbft/blob/v1.0.1/docs/explanation/core/validators.md)）。

IPNS（[记录规范，2025-02-28](https://specs.ipfs.tech/ipns/ipns-record/)）的名字就是公钥的哈希，谁控制私钥谁就完全控制这个名字；记录由私钥签名后经路由系统分发，带 Sequence（版本号）、Validity（过期时间）与 TTL。解析方可能拿到同一记录的多个版本，按序号取最新的，再验证签名与有效期；规范没有规定持有同一私钥的多个发布者之间怎样互斥（未找到相关条文）。IPFS 的 [Kademlia DHT 规范（2025-11-20）](https://specs.ipfs.tech/routing/kad-dht/)承认不同 DHT 服务器可能存着不同版本的 IPNS 记录，建议收集 20 个中至少 16 个响应再挑最好的。DNSSEC（[RFC 4033](https://www.rfc-editor.org/rfc/rfc4033)，2005-03）给 DNS 加上数据来源认证与数据完整性，验证从带外取得的信任锚出发；它不提供机密性，也不防拒绝服务；签名有有效期，解析器还要考虑自己的时钟可能出错。推论：DNSSEC 证明的是数据出自哪个区，名字归谁仍由 RFC 1034 的委派关系决定。

Douceur 的 [The Sybil Attack（IPTPS 2002）](https://www.microsoft.com/en-us/research/publication/the-sybil-attack/)（[LNCS 2429](https://doi.org/10.1007/3-540-45748-8_24)）证明，没有逻辑上集中的权威时，除非假设各实体资源均等且彼此协调这种极端而不现实的条件，Sybil 攻击总是可能的；摘要提到的一种防范是由可信机构为身份背书。S/Kademlia（[Baumgart 与 Mies, ICPADS 2007](https://doi.org/10.1109/ICPADS.2007.4447808)，[作者所在研究所托管版](https://telematics.tm.kit.edu/publications/Files/267/SKademlia_2007.pdf)）据此写道，这种攻击只能阻碍、不能防止。它让节点 ID 取公钥的哈希，使别人无法冒用；没有可信权威时，用密码学难题限制随意挑选与大量生成节点 ID，网络刚启动时用证书机构签过的 supervised signature；查找经多条不相交的路径并行进行。

## 7. 分层边界：谁保证单一归属，谁管副本

结论：所看的分层系统里，传输与连接层都不负责“名字只有一个持有者”；gRPC 与 Envoy 把名字交给可插拔的解析器或控制面，把解析结果当作一组可按调用分摊的后端，单一归属由专门的协调层提供，这些层大多把权威做成了可替换的接口。

gRPC v1.83.2 的[命名文档](https://github.com/grpc/grpc/blob/v1.83.2/doc/naming.md)说，DNS 是默认的名字系统，客户端库按目标 URI 的 scheme 选择解析器插件；解析结果是一组地址和一份 service config，解析器可以持续推送更新。[负载均衡文档](https://github.com/grpc/grpc/blob/v1.83.2/doc/load-balancing.md)说负载均衡按调用而不是按连接进行，LB 策略同样可插拔，xDS 支持也通过 LB 策略接入。重试设计 [gRFC A6](https://github.com/grpc/proposal/blob/dc9fd4fe5b94b90b82fe2833ad1d80938e6a49c1/A6-client-retries.md) 只在 gRPC 能保证请求从未被服务端应用逻辑看到时才透明重试；其他重试按服务方配置的状态码进行，文档提醒不幂等的方法只有在状态码能保证原请求未被处理时才可重试。Envoy v1.40.2 从管理服务器经 xDS 取得监听器、路由、集群与端点，[xDS 协议文档](https://www.envoyproxy.io/docs/envoy/v1.40.2/api-docs/xds_protocol)写明这些 API 是最终一致的，更新期间流量可能短暂丢失或被黑洞，需要显式控制顺序的环境用聚合流 ADS。[stateful session 过滤器](https://www.envoyproxy.io/docs/envoy/v1.40.2/api-v3/extensions/filters/http/stateful_session/v3/stateful_session.proto)把会话绑定的上游地址存在 cookie 或头部里；`strict` 为 true 时，目标不在可用端点中就返回配置的状态码，目标不健康一律返回 503；默认 false，退回负载均衡另选上游。

Kubernetes 把稳定的名字与副本分开：[Service](https://kubernetes.io/docs/concepts/services-networking/service/) 为运行在一个或多个 Pod 上的应用提供入口，目标 Pod 通常由选择器决定；[Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) 滚动更新时默认最多同时存在期望数 125% 的 Pod，不提供单一实例；需要稳定身份的用 [StatefulSet](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/)，它对 Pod 的顺序与唯一性给出保证，边界见第 4 节。选主由 client-go 在 Lease 对象上完成，锁所用的资源由 `LeaderElectionConfig.Lock`（resourcelock 接口）提供，可以替换。

其余系统的出处在第 4 节。Orleans 把单一激活放在 grain 目录，成员判定放在 `IMembershipTable`，状态放在存储提供者，三者都可替换，状态写入由 ETag 把关。Akka 的集群成员服务只负责成员与可达性，谁被下线由 `downing-provider-class` 指定的 downing provider 决定（Split Brain Resolver 是其一），lease 实现经 `lease-class` 插入，供 Split Brain Resolver、单例与分片共用。Erlang 把唯一名字与锁放在 global（冲突时调用可替换的 Resolve 函数），一名多进程放在 pg。Dapr 的放置权威可以换成 Scheduler；Ray 的 GCS 持久化后端可选 Redis 或 RocksDB。

## 8. 与 C-Two 现状的对照

结论：C-Two 现在只在单个 relay 之内保证一个路由名至多一个活着的本地注册，替换时由该 relay 进程内的代次与纪元把关；没有 relay 时不同进程可以注册同一个路由名，relay 之间允许同名路由并存，解析返回按“本地优先、对端按 (registered_at, relay_id) 排序”排好的候选，对端消息不经认证。

按[契约与路由参考](../reference/contracts-and-routing.md)的 Registration, mesh resolution, and peer state 一节，另一个进程想注册某个 relay 上已有活着的本地持有者的路由名时，relay 返回 HTTP 409 与 `ResourceAlreadyRegistered`（703）（[router.rs](../../core/transport/c2-http/src/relay/router.rs) 的 `duplicate_route_response`，[c2-error](../../core/foundation/c2-error/src/lib.rs)）。替换之前 relay 先探测现有持有者；持有者已死或路由已不在时，候选要先通过 IPC 身份与路由契约核验，再由最后一次新的探测确认旧状态，提交时核对捕获的连接槽、owner generation、lease 纪元、可替换性与在途请求数，在途请求不为零就不可替换（[conn_pool.rs](../../core/transport/c2-http/src/relay/conn_pool.rs) 的 `validate_replaceable_owner_token`）。参考文档写明 lease 到期本身不放弃持有，持有者的新鲜度只留在所属 relay 之内、不经 gossip 传播；没有 relay 时，不同进程可以注册同一个路由名，同一进程内的重复在本地被拒绝。对照：这一把关与 Chubby 的 sequencer、Kleppmann 的 fencing token 同属“提交时比较单调的代次”，但比较发生在 relay 的内存里，而不在持有状态的资源一侧。

relay 对它所服务的每个上游 Host 实例保持一条控制连接，约每 50 ms 对其中每个路由重新核验一次（[upstream_control.rs](../../core/transport/c2-http/src/relay/upstream_control.rs) 的 `CONTROL_OBSERVE_INTERVAL`）。Host 报告路由不存在、已移除、已关闭或契约不符时，relay 撤下该路由并向对端广播撤销；同一地址回答的是另一个服务器身份时，撤下该实例的全部路由；传输错误不撤销任何东西，1 s 后重连。对照：“联系不上不等于已死”与 Orleans 成员表不可达时不判死的规则同类；这个核验确认的是路由是否还在，不是一个会到期的 lease。

relay 之间的路由表以 (name, relay_id) 为键（[route_table.rs](../../core/transport/c2-http/src/relay/route_table.rs) 的 `RouteTable`），不同 relay 可以同时公布同一个路由名。对端公布的路由通过格式、契约哈希与墓碑检查之后，只要发送者就是声称的 relay、该 relay 在本地记为存活、且不冒用本 relay 的 relay_id，就会被接受（[authority.rs](../../core/transport/c2-http/src/relay/authority.rs) 的 `announce_peer` 与 `trusted_peer_owner`），本地已有同名路由不构成拒绝的理由。按契约解析（`RouteTable::resolve_matching`）时先返回本地路由，再返回存活对端的路由，按 (registered_at, relay_id) 排序；registered_at 是每个 relay 自己的混合逻辑时间戳，取当前墙钟毫秒与上一个值加一中的较大者（`next_local_timestamp`），参考文档提醒时钟偏差会影响哪个对端排在前面。对端存活靠心跳：默认每 5 s 一次，距上次心跳超过 15 s（5 s 乘以 miss threshold 3）记为 Suspect，超过 30 s 记为 Dead 并删除该对端的全部路由，只有 Alive 的对端的路由参与解析（[background.rs](../../core/transport/c2-http/src/relay/background.rs) 的 `failure_detection_loop`，默认值在 [c2-config 的 relay.rs](../../core/foundation/c2-config/src/relay.rs)）；反熵每 60 s 与一个存活对端交换摘要，墓碑至少保留 600 s。参考文档写明，对端消息里的 `sender_relay_id` 只是声明，不是认证；部署方必须用自己的网络与节点身份手段保护内部的 `/_peer/*` 端点，单靠 IP 白名单不能识别 relay，协议没有 HMAC 对端认证。对照：这套网格状态是最终一致的注册表，同名的多个持有者可以并存，没有 Erlang global 那样的冲突解决函数，也没有法定人数或跨 relay 的 fencing；按第 1 节与第 6 节的分类，它属于崩溃故障模型，前提是对端由可信的运维方运行。

客户端一侧（参考文档的 Route bindings, lookup, and fallback 一节），绑定路由的客户端保留观察到的 `route_uid`、完整的期望契约与服务器身份；新的注册得到新的 route UID，已有客户端保持旧绑定直到关闭，绑定的 route UID 过时时得到 `RouteStale`。relay 感知的调用只发一次业务 POST：relay 答复路由过时时，调用以发送前的 `RouteStale` 失败，缓存的路由失效，下一次调用重新解析。C-Two 不保留输入副本用于重发，理由是过时的路由通常属于一个没有旧状态的新资源实例，由调用方决定是否恢复状态再调用；可能已分发之后的服务错误或连接丢失不会自动重放，因为 C-Two 没有调用去重身份（另见 [AGENTS.md](../../AGENTS.md) 的 Stateful RPC 一节）。对照：这与 Chubby 句柄绑定文件实例、Kubernetes 用 UID 区分同名对象相同，名字背后的那一次注册对客户端是可见的；与 Orleans grain 引用跨重启保持有效不同，持有者变化在 C-Two 里表现为一次发送前的失败。

[ADR 0002](../decisions/0002-remove-owner-subsystem.md)（2026-11-01 采用）删除了所有者子系统，包括恢复凭证与接管；它记下失去的能力是“控制方失联后自动停服，以及凭票据互斥接管同一个 Host”，并写明“以后真有使用者，在单一属主的连接模型上重新设计，不恢复旧协议”。toodle 是该 ADR 列出的已知下游之一，当时没有使用这一子系统。

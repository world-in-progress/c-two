# 显式关闭时的在途调用：gRPC、Ray 与其他框架的做法

日期：2026-11-02。起因：C-Two 要定下关闭 Runtime（`cc.shutdown()`，它同时关闭该 Runtime 的 IPC 客户端池）时，已发出、还没收到结果的调用（在途调用）怎么处理。0.10.1 与当前候选的做法是立即以 DispatchUncertain 失败；`cc.close(proxy)` 只释放该代理这一份引用，不取消传输，不在本题范围内。待选的是 (a) 立即失败，(b) 先拒绝新调用、在一个宽限预算内等在途调用完成、到期后中止剩下的，(c) 无限等、只如实报告"未完成"。另外 Python 解释器退出时会等待所有非守护线程，阻塞在调用里的线程可能让进程挂住。本文只讨论调用，不讨论共享内存缓冲的释放，后者见[共享内存借出调研](2026-11-01-shared-memory-lending-survey.md)第 5 节。状态：调研记录，只列做法、参数与代价，不给建议，没有改动代码。来源是官方文档、固定到版本标签或提交的源码、规范与 gRFC、维护者本人的提交说明；标"推论"的是本文据这些来源所做的推断；标"本机复现"的是 2026-11-02 在 macOS arm64 上自己运行得到的结果，脚本与输出没有放进仓库，没有标"本机复现"的内容只读了文档与源码，没有运行（grpc-go、grpc-java、Ray、Dask、Java、Go、tokio、Erlang、Cap'n Proto 都是这样）。所有查证都在 2026-11-02 做，版本：gRPC C core 与 Python v1.85.1（grpcio 1.85.1，2026-10-30 发布），grpc-go v1.85.0，grpc-java v1.85.1，Ray 2.59.0，CPython 3.15.2（复现用 3.14.5），JDK jdk-27-ga，Go 1.27.3，libzmq 4.3.5，pyzmq 27.2.0，Dask distributed 2026.8.0，tokio 1.54.1，Erlang/OTP 29.1.2，Cap'n Proto 1.5.0，RFC 9113，gRFC A6 与 A9（grpc/proposal 提交 89f34f2）。

## 1. gRPC

结论：服务端关闭都是"立刻停止接纳新连接与新调用，再处理在途调用"。客户端关闭则因 API 而异：Python 同步 `Channel.close()`、grpc-go `ClientConn.Close()`、grpc-java `shutdownNow()` 立即取消在途调用，没有宽限；Python aio `close(grace)` 与 Python `Server.stop(grace)` 内置宽限、到期取消；grpc-java 与 grpc-go 的宽限要调用方自己用两三个 API 拼出来。服务端宣告"已停止"的依据是 RPC 终止，不是 handler 返回：Python 同步与 aio 的 `stop()` 在 handler 仍在运行时就已完成（本机复现），与各自文档里"所有 handler 已终止"的写法不符，grpc-go 默认也不等 handler。被中止的 RPC 在调用方得到 `CANCELLED`（本方主动关闭）或 `UNAVAILABLE`（服务端或传输消失）；库内部区分"没离开客户端"、"服务端没见过"与其他情形，并据此做透明重试，公开的状态码不区分。

**Python 同步客户端。** `grpc.Channel.close()` 的文档：立即终止通道上所有活动 RPC，之后不能再发新 RPC，幂等，没有宽限参数（[__init__.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/__init__.py#L1112-L1120)）。实现是 `cygrpc.Channel.close(StatusCode.cancelled, "Channel closed!")`（[_channel.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_channel.py#L2220-L2225)）：把通道标为关闭，对每个活动调用执行 `grpc_call_cancel_with_status`，等托管调用与连接性监视收尾，再 `grpc_channel_destroy`；之后再发 RPC 抛 `ValueError("Cannot invoke RPC on closed channel!")`（[channel.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/channel.pyx.pxi#L447-L487)、[同文件](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/channel.pyx.pxi#L406-L410)）。阻塞的一元调用在调用者自己的线程里等 `call.next_event()`（[_channel.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_channel.py#L1152)）。本机复现（grpcio 1.85.1，服务端 handler 睡 2 s，两个线程阻塞在一元调用里）：`close()` 在 1 ms 内返回，两个线程立刻得到 `_InactiveRpcError`，状态 `CANCELLED`，details 为 `Channel closed!`；打开 `GRPC_TRACE=http` 可见客户端对每条流写出 RST_STREAM，服务端收到的原因码为 8（CANCEL）；服务端 handler 不受影响，约 1.5 s 后自己跑完，此时 `context.is_active()` 为 False；之后的新调用抛 `ValueError`。`Channel.__del__` 不关闭通道，源码注释的理由是要允许创建完 stub 就丢掉通道（[_channel.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_channel.py#L2243-L2258)）。

**Python aio 客户端。** `grpc.aio.Channel.close(grace=None)` 的文档：任何情况下都立即不再执行新 RPC；给了宽限就等活动 RPC 结束或宽限到期，未结束的被中止；`None` 则立即取消全部（[_base_channel.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/aio/_base_channel.py#L213-L226)）。v1.85.1 的实现：标记 closing，仅当 `grace` 为真值时才为每个未完成的调用起等待任务并 `asyncio.wait(..., timeout=grace)`，随后对所有调用 `call.cancel()`，最后销毁通道；负的宽限抛 `ValueError`，`grace=0` 与 `None` 一样不等，`async with` 退出时用 `None`（[aio/_channel.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/aio/_channel.py#L427-L476)）。新调用抛 `UsageError("Channel is closed.")`（[channel.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/channel.pyx.pxi#L80-L81)）。本机复现：`close(None)` 后正在 `await call` 的任务得到 `asyncio.CancelledError`，`call.code()` 为 `CANCELLED`、details 为 `Locally cancelled by application!`；`close(0.3)` 在 0.301 s 后返回并取消；调用只需 1 s 时 `close(5)` 在 0.603 s 返回、调用成功；宽限期内再发新调用抛 `UsageError`。

**Python 同步服务端。** `Server.stop(grace)` 的文档（[__init__.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/__init__.py#L1528-L1556)）：立即停止接受新 RPC；给了宽限就等活动 RPC 结束，到期中止剩下的；`None` 则立即中止全部，并阻塞到最后一个 handler 结束；幂等，后一次调用给更小的宽限会让服务端更早停，更大的无效（取最严）；返回的 `threading.Event` 在运行中的 RPC 完成或被中止、且所有 handler 已终止时置位。实现（[_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L1336-L1358)）：先 `_begin_shutdown_once`（核心层 shutdown，阶段变 `GRACE`），`None` 则 `cancel_all_calls()` 后等 Event；给了宽限则起一个线程（未设 daemon）等 `grace` 秒后 `cancel_all_calls()`，并立即返回 Event。Event 在 `_stop_serving` 里置位，条件是 `rpc_states` 与 `due` 都为空（[L1227-L1234](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L1227-L1234)）；一个 RPC 被取消且没有待完成的操作时就从 `rpc_states` 移除（[L223-L231](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L223-L231)、[L301-L311](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L301-L311)、[L852-L853](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L852-L853)），这条路径上没有等待用户 handler 线程的代码（推论）。本机复现（handler 里 `time.sleep(3)`，客户端 0.3 s 时调用 stop）：`stop(0.3)` 立刻返回，Event 在 0.3 s 后置位，客户端得到 `UNAVAILABLE`、details 为 `Cancelling all calls`，handler 要到 3.0 s 才返回，进程退出等到 3.1 s；`stop(None)` 同样立刻返回、Event 已置位（文档写的是阻塞到 handler 结束），handler 仍在跑；先 `stop(10)` 再 `stop(0.2)`，0.2 生效；handler 只要 0.5 s 时 `stop(5)` 在 handler 完成时置位 Event，客户端得到正常结果；`stop` 之后的新 RPC 立即得到 `UNAVAILABLE`（连接被拒，监听已关）。`Server.__del__` 只置一个标志，由服务线程在不超过 1 s 的轮询周期内开始 shutdown，不取消在途 RPC（[_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L1494-L1498)）。

**Python aio 服务端。** `stop(grace)` 的文档与同步版基本相同（[_base_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/aio/_base_server.py#L89-L111)）。实现是 READY、RUNNING、STOPPING、STOPPED 四态：先调核心的 `grpc_server_shutdown_and_notify` 并等接收新调用的主循环退出；`grace` 为 `None` 就立即 `grpc_server_cancel_all_calls` 再等核心的完成通知，否则 `wait_for(shield(完成通知), grace)`，超时则 `cancel_all_calls` 后无限期等通知（[server.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/server.pyx.pxi#L1189-L1244)）。包装类的 `__del__` 调度一次 `shutdown(None)`（[aio/_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/aio/_server.py#L212-L222)）。本机复现：`async` handler `await asyncio.sleep(3)`，`stop(0.3)` 在 0.303 s 返回，handler 此时收到 `CancelledError`，客户端得到 `UNAVAILABLE`、`Cancelling all calls`；handler 吞掉 `CancelledError` 后再做 2 s 善后，`stop()` 仍在 0.303 s 返回，善后在 2 s 后才结束；在线程池里 `time.sleep(3)` 的 handler 不受取消影响，`asyncio.run` 退出时为此多等到 3.0 s。

**C core、C++ 与服务端连接管理。** C 接口的注释：`grpc_server_shutdown_and_notify` 之后不再接纳新调用与新连接，已有调用允许完成，没有调用在服务时发出完成事件；`grpc_server_cancel_all_calls` 只能在 shutdown 之后用（[grpc.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpc/grpc.h#L473-L487)）。服务端关闭时向每条连接发 GOAWAY（NO_ERROR，文本 `Server shutdown`）（[server.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/server/server.cc#L989-L1003)）。本机用 `GRPC_TRACE=http` 看到的顺序：先发 last-stream-id 为 2^31-1 的 GOAWAY，收到 PING 回复后发 last-stream-id 为最后一条已接纳流（1）的 GOAWAY，在途的流做完后才关连接，与 RFC 9113 建议的两步优雅关闭一致；强制取消时客户端日志是 `Got goaway [2] ... Cancelling all calls`。C++ 的 `Server::Shutdown(deadline)`：到期后 `grpc_server_cancel_all_calls`，再无限期等，之后关闭同步 API 的线程管理器并等其线程退出（[server_cc.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/cpp/server/server_cc.cc#L1250-L1296)），与 Python 不同，等的是 handler 线程。服务端按连接年龄关闭时，`grpc.max_connection_age_grace_ms` 是 GOAWAY 之后留给在途 RPC 的宽限，默认 INT_MAX，即不设期限（[channel_arg_names.h](https://github.com/grpc/grpc/blob/v1.85.1/include/grpc/impl/channel_arg_names.h#L55-L61)、[gRFC A9](https://github.com/grpc/proposal/blob/89f34f2632b991776e206c97830ec3ac6f391988/A9-server-side-conn-mgt.md)）。

**核对一个说法：gRPC Python 有一套较复杂的关闭状态。** 说法的大意是（约一年前）先拒绝外部新请求，做完已接纳的请求，进入自旋式的优雅关闭状态，关不掉就强杀；没有说明是客户端还是服务端。最吻合的是 Python 的服务端同步栈，不是客户端。cygrpc 的 `Server` 有 `is_started`、`is_shutting_down`、`is_shutdown` 三个标志；`destroy()` 分三种情形：没调过 shutdown 就用备份队列自己发起并轮询等待，已在关闭中则释放 GIL 反复 `time.sleep(0)` 直到 `is_shutdown`，即自旋（[server.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/server.pyx.pxi#L233-L255)，`cancel_all_calls` 在 [L221-L228](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/server.pyx.pxi#L221-L228)）；Python 层 `_ServerStage` 有 STOPPED、STARTED、GRACE 三阶段（[_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L1124-L1127)），`_serve` 循环的注释提到 spinlock（[L1311-L1325](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L1311-L1325)），宽限线程到期后 `cancel_all_calls`。这些代码在 v1.76.0（2025-10-20 发布）与 v1.85.1 之间没有逻辑变化（本机对 shutdown、cancel、destroy 与 `_stop` 的相关段落做了 diff：`server.pyx.pxi` 的三个函数与 aio 服务端的 `shutdown` 逐字相同，cygrpc 通道的 `_close` 只差一处行尾空格，`_server.py` 只有写法调整），现在仍如此。客户端侧没有对应的多阶段状态：同步 `Channel` 只有一个 open 标志，aio 通道是 READY、CLOSING、DESTROYED 三态（[aio/channel.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/channel.pyx.pxi#L104-L112)）。客户端侧这一年里的实质变化只有 aio `Channel._close` 找出活动调用的办法：v1.76.0 遍历 `asyncio.all_tasks()` 并检查任务栈帧里的 `self`，再按宽限等待、取消（[v1.76.0](https://github.com/grpc/grpc/blob/v1.76.0/src/python/grpcio/grpc/aio/_channel.py#L383-L453)），v1.83.0（2026-07-22 发布）起改为通道自己维护 `_active_calls`（PR #42503，为适配 Python 3.14）。说法本身没有给出文件或版本，无法确定指的是哪一处，以上是吻合的两处。

**grpc-go。** `ClientConn.Close()` 的文档只有一句"拆除 ClientConn 与全部底层连接"；实现是先关 resolver、picker 与 balancer，再对每个 addrConn 调 `tearDown(ErrClientConnClosing)`（[clientconn.go](https://github.com/grpc/grpc-go/blob/v1.85.0/clientconn.go#L1188-L1243)），后者对传输层硬关闭 `curTr.Close(err)`，只有地址被移除（`errConnDrain`）才走 `GracefulClose`（[clientconn.go](https://github.com/grpc/grpc-go/blob/v1.85.0/clientconn.go#L1717-L1735)）。传输层 `Close` 先写 GOAWAY（NO_ERROR，文本 `client transport shutdown`，最多等 5 s），关连接，再对每条活动流 `closeStream`：流状态记为 `Unavailable`，读端收到的则是传入的 `err`（[http2_client.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_client.go#L1042-L1113)）。`ErrClientConnClosing` 是 `codes.Canceled`、文本 `grpc: the client connection is closing`（[clientconn.go](https://github.com/grpc/grpc-go/blob/v1.85.0/clientconn.go#L65-L70)）；流式 RPC 另有 goroutine 在 `cc.ctx` 结束时以它结束该 RPC（[stream.go](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L522-L536)），新 RPC 直接得到它（[stream.go](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L545-L547)）。一元调用最终是 `Canceled` 还是 `Unavailable`，我没有运行验证（本机 Go 1.24.1 低于 grpc-go 1.85.0 要求的 1.26，工具链下载在沙箱里因证书校验失败）；按代码读是 `Canceled`（推论）。服务端：`GracefulStop()` 停止接受新连接与新 RPC，阻塞到在途 RPC 全部结束；`Stop()` 立即关闭所有连接与监听，取消服务端的在途 RPC，对端因连接错误得知（[server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L1671-L1685)）。实现里 `GracefulStop` 先关监听，对每条传输 `Drain`（发 GOAWAY），等连接清空与 `handlersWG`，代码注释说中止一个太久的 `GracefulStop` 要靠并发调用 `Stop()`（[server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L1687-L1735)）；`Stop()` 默认不等 handler 返回，实验性选项 `WaitForHandlers(true)` 让它等（[server.go](https://github.com/grpc/grpc-go/blob/v1.85.0/server.go#L645-L658)）。

**grpc-java。** `ManagedChannel.shutdown()`：在途调用继续，新调用立即被取消；`shutdownNow()`：在途与新调用都取消，仍不是瞬时的，`isTerminated()` 很可能仍为 false；`awaitTermination(timeout, unit)` 返回是否已终止（[ManagedChannel.java](https://github.com/grpc/grpc-java/blob/v1.85.1/api/src/main/java/io/grpc/ManagedChannel.java#L27-L71)）。实现里 `shutdown()` 之后的新调用以 `UNAVAILABLE`、`Channel shutdown invoked` 关闭，`shutdownNow()` 让各子通道以 `UNAVAILABLE`、`Channel shutdownNow invoked` 关闭传输（[ManagedChannelImpl.java](https://github.com/grpc/grpc-java/blob/v1.85.1/core/src/main/java/io/grpc/internal/ManagedChannelImpl.java#L136-L141)、[L726-L775](https://github.com/grpc/grpc-java/blob/v1.85.1/core/src/main/java/io/grpc/internal/ManagedChannelImpl.java#L726-L775)、[L961-L994](https://github.com/grpc/grpc-java/blob/v1.85.1/core/src/main/java/io/grpc/internal/ManagedChannelImpl.java#L961-L994)）；Netty 强制关闭时对每条活动流报告该状态并发 RST_STREAM(CANCEL)，`RpcProgress` 取默认的 `PROCESSED`（[NettyClientHandler.java](https://github.com/grpc/grpc-java/blob/v1.85.1/netty/src/main/java/io/grpc/netty/NettyClientHandler.java#L942-L962)、[AbstractClientStream.java](https://github.com/grpc/grpc-java/blob/v1.85.1/core/src/main/java/io/grpc/internal/AbstractClientStream.java#L401-L403)）。服务端 `Server.shutdown()`：在途调用继续，新调用被拒，返回时监听 socket 已释放，不等在途调用，要靠 `awaitTermination`；`shutdownNow()` 在途与新调用都拒（[Server.java](https://github.com/grpc/grpc-java/blob/v1.85.1/api/src/main/java/io/grpc/Server.java#L112-L141)）。

**HTTP/2 的 GOAWAY 与 REFUSED_STREAM。** RFC 9113 §6.8：GOAWAY 的 last-stream-id 是发送方"可能处理过或还可能处理"的最大流号；对端发在更大流号上的流没有也不会被处理，可当作从未创建，在新连接上重试；不大于该号的流可能已被处理，其中没关完的不能重试（幂等操作除外），也可以继续做完；连接没发 GOAWAY 就断开，等于 last-stream-id 取最大；优雅关闭建议先发 last-stream-id 为 2^31-1 的 GOAWAY，等至少一个往返，再发带真实流号的 GOAWAY（[§6.8](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.8)）。§8.7：能保证"没被处理"的只有两个机制，GOAWAY 的 last-stream-id 与 RST_STREAM 的 REFUSED_STREAM，服务端只有在能保证时才可以使用它们（[§8.7](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.7)）。gRPC 的 HTTP/2 映射：REFUSED_STREAM 对应 `UNAVAILABLE`，表示没有处理发生、可以重试；GOAWAY 之后发起的流视为 `UNAVAILABLE`，已接受的流可继续做完（[PROTOCOL-HTTP2.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md#L231)、[L245-L248](https://github.com/grpc/grpc/blob/v1.85.1/doc/PROTOCOL-HTTP2.md#L245-L248)）。C core 的客户端收到 GOAWAY 时，把流号大于 last-stream-id 的流标为 `kNotSeenByServer` 并取消（[chttp2_transport.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L1407-L1421)），尚未开始的流标 `kNotSentOnWire`（[L1374-L1384](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/chttp2_transport.cc#L1374-L1384)）。grpc-go 对 REFUSED_STREAM 的 RST_STREAM 与流号超过 GOAWAY 的流都置 `unprocessed`（[http2_client.go](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_client.go#L1315-L1318)、[L1459-L1466](https://github.com/grpc/grpc-go/blob/v1.85.0/internal/transport/http2_client.go#L1459-L1466)）。grpc-java 的 `RpcProgress` 有 `PROCESSED`、`REFUSED`、`DROPPED`、`MISCARRIED`（流在离开客户端之前就关了）（[ClientStreamListener.java](https://github.com/grpc/grpc-java/blob/v1.85.1/core/src/main/java/io/grpc/internal/ClientStreamListener.java#L51-L72)），收到 REFUSED_STREAM 记 `REFUSED`（[NettyClientHandler.java](https://github.com/grpc/grpc-java/blob/v1.85.1/netty/src/main/java/io/grpc/netty/NettyClientHandler.java#L488-L498)）；GOAWAY 后超出 last-stream-id 的流，在错误码不是 NO_ERROR 时保守地记 `PROCESSED`，代码注释说这是为绕开 Netty 的一个已知问题（[同文件](https://github.com/grpc/grpc-java/blob/v1.85.1/netty/src/main/java/io/grpc/netty/NettyClientHandler.java#L1003-L1017)）。在 v1.85.1 的 C core 里，我只找到 GOAWAY 路径会设 `kNotSeenByServer`，没找到把收到的 RST_STREAM(REFUSED_STREAM) 标为 `kNotSeenByServer` 的代码，它只被映射成 `UNAVAILABLE`（[http2_status.h](https://github.com/grpc/grpc/blob/v1.85.1/src/core/ext/transport/chttp2/transport/http2_status.h#L68-L69)）；是否另有处理，未能核实。

**透明重试（gRFC A6）。** A6 把 RPC 失败分四处：负载均衡失败、没离开客户端、到了服务端库但应用逻辑没见过、应用逻辑见过后失败。中间两种由库自动重试，与服务配置的重试策略无关，因为请求没到应用逻辑，总是安全的：没离开客户端的可一直重试到成功或截止时间；服务端没见过的立刻重试一次，再失败才按配置的策略处理；透明重试不计入 `maxAttempts`，也不计入重试限流。HTTP/2 下，收到 REFUSED_STREAM 的 RST_STREAM，或连接以 last-stream-id 小于该流号的 GOAWAY 关闭，客户端就知道属于"服务端没见过"（[A6](https://github.com/grpc/proposal/blob/89f34f2632b991776e206c97830ec3ac6f391988/A6-client-retries.md#transparent-retries)）。C core 的实现与此一致：没写到线上的总是重试，写出但服务端没见过的只重试一次（[retry_filter_legacy_call_data.cc](https://github.com/grpc/grpc/blob/v1.85.1/src/core/client_channel/retry_filter_legacy_call_data.cc#L1107-L1122)）；grpc-go 只对首次尝试且 unprocessed 的流透明重试（[stream.go](https://github.com/grpc/grpc-go/blob/v1.85.0/stream.go#L806-L828)）。应用能不能区分：库内部区分（C core 的 `GrpcStreamNetworkState` 两个取值（[metadata_batch.h](https://github.com/grpc/grpc/blob/v1.85.1/src/core/call/metadata_batch.h#L602-L613)）、Java 内部包里的 `RpcProgress`、Go 内部传输层的 `Unprocessed()`），应用看到的只是状态码：文档把"数据已写出后连接断开"列为 `UNAVAILABLE`，并说 `UNAVAILABLE` 重试非幂等操作并不总是安全（[statuscodes.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/statuscodes.md#L22)、[L51](https://github.com/grpc/grpc/blob/v1.85.1/doc/statuscodes.md#L51)）。公开的状态类型里没有该区分的字段（Python `RpcError`、Go `status`、Java `Status` 我没有逐一核对，推论）。

**gRPC Python 的进程退出。** 没有为通道或服务端注册 atexit 关闭钩子：包内唯一的 `atexit.register` 在 call credentials 的元数据插件里，退出时最多累计等约 2.5 s（源码注释写约 2 s）让 C core 清理，超时只记一条错误日志（[credentials.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/credentials.pyx.pxi#L97-L120)）；gevent 路径另有一个（[grpc_gevent.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/grpc_gevent.pyx.pxi#L137)）。库自己的常驻线程都是守护线程（`stop(grace)` 临时起的宽限线程除外，见上）：通道的请求消费、自旋、投递、轮询线程（[_channel.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_channel.py#L349)、[L1736](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_channel.py#L1736)、[L1889](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_channel.py#L1889)、[L1955](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_channel.py#L1955)）、aio 的轮询线程（[completion_queue.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/completion_queue.pyx.pxi#L71)）、同步服务端的服务线程（[_server.py](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_server.py#L1373-L1375)）。会挂住进程的是用户拥有的线程：阻塞在同步调用里的调用线程，以及 `grpc.server(ThreadPoolExecutor)` 里还在跑的 handler 线程（见第 4 节）。aio 部分：2025-09-09 合入的 PR #40447（v1.76.0 起含，v1.75.x 不含）让 `shutdown_grpc_aio` 在解释器正在终结时直接跳过，理由是 3.14 起终结阶段 join 非守护线程会抛 `PythonFinalizationError`，且此时对象的销毁顺序不确定；提交说明还提到，此前有人手工调用 `init_grpc_aio` 让引用计数永不归零，借此躲开终结阶段的死锁（[grpc_aio.pyx.pxi](https://github.com/grpc/grpc/blob/v1.85.1/src/python/grpcio/grpc/_cython/_cygrpc/aio/grpc_aio.pyx.pxi#L105-L142)、[提交 9e2283db67](https://github.com/grpc/grpc/commit/9e2283db67)）。

## 2. Ray

结论：Ray 没有"关闭时统一处理在途调用"的 API，而是按终止方式分三档：`ray.kill` 立即失败，当前、排队与之后的调用都报 `RayActorError`；`__ray_terminate__` 与 `exit_actor()` 让已排在前面的任务先做完再退出，默认 30 s 内没退出就强杀；调用方（owner）消失时，它创建的非 detached actor 被强杀（命运共享）。`ray.shutdown()` 的文档没有写在途任务怎么办。Ray 明确写了"可能执行过也可能没有"的情形；actor 任务默认至多一次，`max_task_retries` 非零才变成至少一次。

**`ray.shutdown()`。** 文档字符串：断开 worker，终止由 `ray.init()` 启动的进程；连的是已有集群时只断开、不关集群；进程退出时由 atexit 自动调用（[worker.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/_private/worker.py#L2078-L2127)、[L2163](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/_private/worker.py#L2163)）。文档与文档字符串都没有写在途任务或 actor 调用的处理。驱动端的 C++ 实现：`Disconnect(INTENDED_USER_EXIT, "Shutdown by ray.shutdown().")`，再 `Shutdown()` 并等待完成（[core_worker_process.cc](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/core_worker/core_worker_process.cc#L1067-L1077)）；graceful 路径停 io 服务、断开 GCS，没有等待在途任务的步骤（[core_worker_shutdown_executor.cc](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/core_worker/core_worker_shutdown_executor.cc#L53-L127)，推论）。2.59.0 的 core worker 有四态关闭状态机 kRunning、kShuttingDown（排空已有工作、不接新工作）、kDisconnecting、kShutdown，强制路径跳过 kDisconnecting（[shutdown_coordinator.h](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/core_worker/shutdown_coordinator.h#L89-L105)）。驱动退出后它拥有的 actor：GCS 在 `OnWorkerDead` 里销毁该 worker 拥有的全部 actor，死因记为 OWNER_DIED，`DestroyActor` 的 `force_kill` 默认为 true（[gcs_actor_manager.cc](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/gcs/actor/gcs_actor_manager.cc#L1192-L1229)、[gcs_actor_manager.h](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/gcs/actor/gcs_actor_manager.h#L317-L321)）；文档同样写创建者进程死亡时 actor 被终止（[terminating-actors.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/actors/terminating-actors.rst#L7-L11)）。把 `ray.shutdown()` 与这条销毁链连起来是推论，没有运行验证。

**终止 actor 的三种方式。** `ray.kill(actor, no_restart=True)`：强制，中断正在跑的任务使其立即失败，不运行 atexit 与 `__ray_shutdown__`；文档页写当前、排队与之后的任务都以 `RayActorError` 失败；`no_restart=False` 且 `max_restarts` 非零才会重启（[worker.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/_private/worker.py#L3469-L3487)、[terminating-actors.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/actors/terminating-actors.rst#L64-L68)）。`actor.__ray_terminate__.remote()`：是一个排进队列的普通方法，内部调 `exit_actor()`（[actor.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/actor.py#L2905-L2906)）；文档说它等先前提交的任务做完再优雅退出，atexit 与 `__ray_shutdown__()` 会运行，后者在所有 actor 任务完成之后；默认等 30 s（`actor_graceful_shutdown_timeout_ms`，30000），超时强杀（[terminating-actors.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/actors/terminating-actors.rst#L156-L157)、[L238-L253](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/actors/terminating-actors.rst#L238-L253)、[ray_config_def.h](https://github.com/ray-project/ray/blob/ray-2.59.0/src/ray/common/ray_config_def.h#L349)）。`exit_actor()`：在任务里抛异常并安排 actor 退出，该任务的调用者看到的是 actor 之死而不是返回值；未开始的与排队的方法以 `RayActorError` 失败；并发与 async actor 里正在执行的任务会先跑完；atexit 会运行（[actor.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/actor.py#L2944-L2962)）。这个文档字符串与文档页"等先前提交的任务做完"的措辞不同，两者并存，未能从一手来源判断是否有出入。`ray.cancel`：排队中的 actor 任务被取消、不执行；执行中的，普通与线程 actor 只设取消标志，async actor 取消 asyncio 任务；`force=True` 对 actor 任务报 `ValueError`；被取消的任务不重试，`ray.get` 抛 `TaskCancelledError`（[worker.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/_private/worker.py#L3513-L3563)）。

**错误与"可能执行过"。** `RayActorError` 表示 actor 在完成任务前意外中断，下分 `ActorDiedError`（actor 进程在执行任务时死亡，或任务被提交给已死的 actor）与 `ActorUnavailableError`（暂时不可达，之后可能恢复）（[exceptions.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/exceptions.py#L417-L423)、[L456-L461](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/exceptions.py#L456-L461)、[L531-L543](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/exceptions.py#L531-L543)）。容错文档明确写：默认的至多一次语义下，`RayActorError` 即使任务其实已成功执行也可能抛出，例如 actor 在执行完后立刻死亡；`ActorUnavailableError` 不保证 actor 执行了任务与否，副作用可能可见也可能不可见，Ray 保证同一方法不会被执行两次，除非配置了重试；建议调用方收到后"隔离"该 actor，定期 ping 到出现 `ActorDiedError` 或成功为止（[fault_tolerance/actors.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/fault_tolerance/actors.rst#L29-L36)、[L141-L164](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/fault_tolerance/actors.rst#L141-L164)）。

**重试与命运共享。** 默认 `max_task_retries=0`，至多一次；`-1` 或大于 0 为至少一次：actor 不可达时自动重试，只有 `max_restarts` 或该任务的重试上限用尽才抛错；重试仍保证按最初提交顺序执行，失败任务之后提交的任务要等它重试成功才执行；`ActorUnavailableError` 同样按 `max_task_retries` 重试（[fault_tolerance/actors.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/fault_tolerance/actors.rst#L29-L62)、[L164](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/fault_tolerance/actors.rst#L164)）。非 detached actor 的 owner 是创建它的 worker，owner 死亡则 actor 随之死亡，即使 `max_restarts` 非零也不恢复；detached actor 没有 owner，仍由 Ray 重启（[fault_tolerance/actors.rst](https://github.com/ray-project/ray/blob/ray-2.59.0/doc/source/ray-core/fault_tolerance/actors.rst#L108-L121)）。

## 3. 其他框架

结论：这些框架里，"先拒绝新任务、再等、到期再强停"几乎都要调用方自己拼：Java 的 `shutdown`、`awaitTermination`、`shutdownNow`，Go 的 `Shutdown(ctx)` 加 `Close()`。自带时间预算的有 Dask 的 `close(timeout)`（超时抛错，不中止）、libzmq 的 `ZMQ_LINGER`（到期丢弃未发出的消息）、tokio 的 `shutdown_timeout`（超时后不中止，任务与线程泄漏）、asyncio 的默认执行器 join（300 s，超时放弃等待）、Erlang 监督者的 `shutdown`（超时后 kill）。默认无限等的有 Java `close()`、Python `Executor.shutdown(wait=True)`、`zmq_ctx_term`（LINGER 默认 -1）和 tokio 的 Drop。提供无限等的关闭 API 的库里，另有强行停下的有 grpc-go 的 `Stop`、Java 的 `shutdownNow`、Go 的 `Close`、ZeroMQ 的 LINGER=0，另有只放弃等待、不停下工作的有 tokio 的 `shutdown_timeout`；Python `concurrent.futures` 对运行中的 future 两者都没有，退出时还必须等。

**Go `net/http`。** `Server.Shutdown(ctx)`：先关全部监听，再关空闲连接，然后无限期等连接回到空闲；ctx 先到期就返回 ctx 的错误；`Serve` 等立即返回 `ErrServerClosed`，文档要求程序在 `Shutdown` 返回前别退出；不跟踪被劫持的连接（如 WebSocket），要调用方另行通知并等待，`RegisterOnShutdown` 可注册通知函数（[server.go](https://github.com/golang/go/blob/go1.27.3/src/net/http/server.go#L3252-L3311)）。`Close()`：立即关闭监听和处于 New、Active、Idle 状态的全部连接（[server.go](https://github.com/golang/go/blob/go1.27.3/src/net/http/server.go#L3213-L3231)）。代码里 ctx 到期时 `Shutdown` 直接 `return ctx.Err()`，不关剩下的连接（[L3306](https://github.com/golang/go/blob/go1.27.3/src/net/http/server.go#L3306)）；文档没写到期后的动作，要强停得另调 `Close()`（推论）。客户端的 `Transport.CloseIdleConnections` 只关空闲连接，不打断正在使用的（[transport.go](https://github.com/golang/go/blob/go1.27.3/src/net/http/transport.go#L945-L950)）。

**Java `ExecutorService`。** `shutdown()`：已提交的任务照常执行，不再接受新任务，不等待；`shutdownNow()`：尽力停止正在执行的任务，停止处理排队的任务，并返回从未开始的任务清单，同样不等待，除尽力而为外没有保证，典型实现靠 `Thread.interrupt`，不响应中断的任务可能永不结束（[ExecutorService.java](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/util/concurrent/ExecutorService.java#L154-L180)）。文档推荐的两阶段写法：`shutdown()`，`awaitTermination(60 s)`，超时则 `shutdownNow()`，再 `awaitTermination(60 s)`，仍未终止只打印一条提示；等待中被中断时也调 `shutdownNow()` 并恢复中断标志（[同文件](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/util/concurrent/ExecutorService.java#L116-L139)）。JDK 19 起的 `close()`：`shutdown()` 后无限期等；等待中被中断则 `shutdownNow()`，之后继续等到所有执行中的任务完成，并重新置位中断状态（[同文件](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/util/concurrent/ExecutorService.java#L370-L410)）。关闭后再提交，`ThreadPoolExecutor` 按拒绝策略处理，默认抛 `RejectedExecutionException`（[ThreadPoolExecutor.java](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/util/concurrent/ThreadPoolExecutor.java#L214)）。

**Python `concurrent.futures` 与 `asyncio.run`。** `Executor.shutdown(wait=True, *, cancel_futures=False)`：之后 `submit` 抛 `RuntimeError`；`wait=True` 等所有待处理的 future 完成并释放资源，`wait=False` 立即返回、资源待 future 完成后释放，无论 `wait` 取何值，整个程序在所有待处理 future 完成之前都不会退出；`cancel_futures=True` 取消尚未开始的 future，已完成或正在运行的不会被取消（3.9 起）（[concurrent.futures.rst](https://github.com/python/cpython/blob/v3.15.2/Doc/library/concurrent.futures.rst#L85-L122)）。`Future.cancel()` 对正在执行的调用返回 False（[同文件](https://github.com/python/cpython/blob/v3.15.2/Doc/library/concurrent.futures.rst#L525)）。`asyncio.run`（`Runner.close()`）：取消全部剩余任务，关异步生成器，然后 `shutdown_default_executor(300)`，最多等 300 s 让线程池线程 join，超时发 `RuntimeWarning` 并放弃等待（[runners.py](https://github.com/python/cpython/blob/v3.15.2/Lib/asyncio/runners.py#L66-L79)、[constants.py](https://github.com/python/cpython/blob/v3.15.2/Lib/asyncio/constants.py#L34)、[asyncio-eventloop.rst](https://github.com/python/cpython/blob/v3.15.2/Doc/library/asyncio-eventloop.rst#L193-L214)）。

**ZeroMQ 与 pyzmq。** `ZMQ_LINGER` 决定 `zmq_close`、`zmq_disconnect` 之后尚未发给对端的消息还在内存里留多久，并影响 `zmq_ctx_term`：-1 无限期保留，`zmq_ctx_term` 阻塞到全部发出；0 立即丢弃；正数是毫秒上限，到期丢弃；默认 -1（[zmq_setsockopt.txt](https://github.com/zeromq/libzmq/blob/v4.3.5/doc/zmq_setsockopt.txt#L484-L511)、[options.cpp](https://github.com/zeromq/libzmq/blob/v4.3.5/src/options.cpp#L184)；master 的文档与默认值没有变）。历史：LINGER 随 2.1.0 引入，NEWS 的说法是让 `zmq_close` 与 `zmq_term` 保证消息发完再终止（[NEWS](https://github.com/zeromq/libzmq/blob/v4.3.5/NEWS#L2183-L2186)）；4.2.2 的 NEWS 更正了手册：手册曾写成 30 秒，但任何已发布的版本里默认都不是 30 秒，只是短暂改过又改回，手册没有还原，默认值始终是 -1（[NEWS](https://github.com/zeromq/libzmq/blob/v4.3.5/NEWS#L896-L899)）。`zmq_ctx_term`：先让所有在途的阻塞操作立即返回 ETERM，其后的操作（`zmq_close` 除外）都失败；然后阻塞到所有 socket 都已关闭，且每个 socket 上应用发的消息要么已发到对端、要么 linger 到期（[zmq_ctx_term.txt](https://github.com/zeromq/libzmq/blob/v4.3.5/doc/zmq_ctx_term.txt#L19-L34)）；某个 socket 一直没 `zmq_close`，`zmq_ctx_term` 永远阻塞（[zmq_close.txt](https://github.com/zeromq/libzmq/blob/v4.3.5/doc/zmq_close.txt#L24-L30)）。`ZMQ_BLOCKY`（默认 true）设为 false 则新 socket 的 linger 为 0（[zmq_ctx_set.txt](https://github.com/zeromq/libzmq/blob/v4.3.5/doc/zmq_ctx_set.txt#L24-L36)）。pyzmq 14.3.0 起进程清理时不再调用 `Socket.close` 与 `Context.term`（[changelog](https://github.com/zeromq/pyzmq/blob/v27.2.0/docs/source/changelog.md#L859-L860)）；24 起把上下文管理器与未关闭就被回收的 `Context` 改为调用 `destroy()` 而非 `term()`，changelog 说几乎所有情形下这把原来的挂起变成警告，代价是 socket 仍在其他线程使用时不安全（[context.py](https://github.com/zeromq/pyzmq/blob/v27.2.0/zmq/sugar/context.py#L45-L56)、[L118-L124](https://github.com/zeromq/pyzmq/blob/v27.2.0/zmq/sugar/context.py#L118-L124)、[changelog](https://github.com/zeromq/pyzmq/blob/v27.2.0/docs/source/changelog.md#L315-L320)）。本机复现（pyzmq 27.2.0，libzmq 4.3.5）：PUSH 连到无人监听的地址并发一条消息，`close()` 后在线程里 `ctx.term()`：LINGER 读回 -1，2.5 s 后仍阻塞；LINGER=0 立即返回；LINGER=500 在 0.50 s 后返回；另有线程阻塞在 `recv()` 时，`ctx.term()` 让它立即抛 `zmq.ContextTerminated`（ETERM），`ctx.term()` 在该 socket 关闭后返回。

**Dask distributed。** `Client.close(timeout)`：文档只写超时后抛 `dask.distributed.TimeoutError`，以及 Python 会话结束时客户端会自动关闭；默认超时是客户端 `timeout` 的 2 倍，`distributed.comm.timeouts.connect` 默认 30 s，所以是 60 s（[client.py](https://github.com/dask/distributed/blob/2026.8.0/distributed/client.py#L1927-L1965)、[L1093-L1097](https://github.com/dask/distributed/blob/2026.8.0/distributed/client.py#L1093-L1097)、[distributed.yaml](https://github.com/dask/distributed/blob/2026.8.0/distributed/distributed.yaml#L238)）。同步客户端的实现是 `sync(self.loop, self._close, fast=True, callback_timeout=timeout)`；`_close` 向调度器发 `close-client`，把本地全部 future 置为已取消（之后 `result()` 抛 `FutureCancelledError`），并释放所有 key（[client.py](https://github.com/dask/distributed/blob/2026.8.0/distributed/client.py#L1862-L1925)、[L691-L695](https://github.com/dask/distributed/blob/2026.8.0/distributed/client.py#L691-L695)、[L1723-L1731](https://github.com/dask/distributed/blob/2026.8.0/distributed/client.py#L1723-L1731)）。调度器的 `remove_client` 释放该客户端要的全部 key（[scheduler.py](https://github.com/dask/distributed/blob/2026.8.0/distributed/scheduler.py#L5954-L5977)）；worker 上已在执行的任务不能被立即中断（文档给的理由是 Python 线程难以取消），任务继续跑完、结果被丢弃（[worker-state.rst](https://github.com/dask/distributed/blob/2026.8.0/docs/source/worker-state.rst#L211-L222)）。所以关闭客户端不会停下服务端正在执行的计算。退出时 atexit 注册的 `_close_global_client` 以 `timeout=3` 关全局客户端（[client.py](https://github.com/dask/distributed/blob/2026.8.0/distributed/client.py#L6166-L6187)）。

**tokio 运行时。** 关闭运行时靠 Drop、`shutdown_background` 或 `shutdown_timeout`：用 `spawn` 派生的任务运行到下一次 yield 就被丢弃，不保证跑完；`spawn_blocking` 的函数运行到返回；发起关闭的线程阻塞到所有已派生的工作停止，可能无限期，`Drop` 无限期等；`shutdown_timeout(d)` 最多等 d，到期后没停的工作与线程泄漏，继续跑到自然结束，但发起线程解除阻塞；`shutdown_background` 等于 `shutdown_timeout(0)`（[runtime.rs](https://github.com/tokio-rs/tokio/blob/tokio-1.54.1/tokio/src/runtime/runtime.rs#L30-L52)、[L457-L460](https://github.com/tokio-rs/tokio/blob/tokio-1.54.1/tokio/src/runtime/runtime.rs#L457-L460)、[L494-L496](https://github.com/tokio-rs/tokio/blob/tokio-1.54.1/tokio/src/runtime/runtime.rs#L494-L496)）。

**Erlang/OTP 与 Cap'n Proto。** `gen_server:call` 对调用方的失败表现为退出信号 `{Reason, {gen_server, call, Args}}`，Reason 可以是 `timeout`、`noproc`（进程不存在或已终止）、`{nodedown, Node}`、`shutdown`（被监督者停止）、`normal` 或 `{shutdown, Term}`（服务进程在未回复时返回 `{stop, ...}`）以及其他退出原因；OTP 24 起用进程别名，迟到的回复不会再进邮箱（[gen_server.erl](https://github.com/erlang/otp/blob/OTP-29.1.2/lib/stdlib/src/gen_server.erl#L1225-L1287)）。监督者子进程规格里的 `shutdown`：`brutal_kill` 立即 kill；整数毫秒则先发 `shutdown` 退出信号，超时再 `kill`；`infinity` 无限等；worker 默认 5000 ms，supervisor 默认 `infinity`（[supervisor.erl](https://github.com/erlang/otp/blob/OTP-29.1.2/lib/stdlib/src/supervisor.erl#L237-L262)、[L267](https://github.com/erlang/otp/blob/OTP-29.1.2/lib/stdlib/src/supervisor.erl#L267)）。Cap'n Proto：连接丢失后依赖该连接的调用以 `DISCONNECTED` 失败；协议文档说错误类型描述的是"调用方该怎样应对"，对 `disconnected` 的建议是释放相关能力并重建，重建中再遇到则按 `overloaded` 处理；文档没有区分请求是否已执行（[exception.h](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/kj/exception.h#L44-L62)、[rpc.capnp](https://github.com/capnproto/capnproto/blob/v1.5.0/c++/src/capnp/rpc.capnp#L1195-L1224)）。

## 4. 进程退出与阻塞的线程

结论：CPython 终结时先 join 所有非守护线程，再运行 atexit 回调，所以 atexit 里的关闭函数救不了一个阻塞在调用里的非守护线程；`concurrent.futures` 通过 `threading._register_atexit` 在 join 之前登记自己的退出函数，并等所有已提交的工作做完。所以在 Python 里，非守护线程中没有截止时间的阻塞调用会让进程挂到它返回（本机用 gRPC 与 ZeroMQ 复现）。各框架的规避办法：用守护线程（代价是线程被突然丢弃）、带超时的关闭（ZeroMQ 的 linger、Dask、tokio、asyncio 默认执行器）、进程语义本身不等（Go 的 `main` 返回）。

**CPython 的规定。** `Py_FinalizeEx` 的预终结阶段在一个循环里先 `wait_for_thread_shutdown`（即 `threading._shutdown`，等所有非守护线程），再处理挂起调用，再 `_PyAtExit_Call`（[pylifecycle.c](https://github.com/python/cpython/blob/v3.15.2/Python/pylifecycle.c#L2273-L2300)）。`threading._shutdown` 先按相反顺序执行用 `threading._register_atexit` 登记的函数（文档字符串写明它们在 join 线程之前调用），再等非守护线程结束（[threading.py](https://github.com/python/cpython/blob/v3.15.2/Lib/threading.py#L1672-L1685)、[L1696-L1721](https://github.com/python/cpython/blob/v3.15.2/Lib/threading.py#L1696-L1721)）。文档：只剩守护线程时整个程序才退出；守护线程在退出时被突然停止，资源可能不被释放，想让线程优雅停止就用非守护线程加 `Event` 之类的信号机制（[threading.rst](https://github.com/python/cpython/blob/v3.15.2/Doc/library/threading.rst#L489-L499)、[L705](https://github.com/python/cpython/blob/v3.15.2/Doc/library/threading.rst#L705)）；3.14 起终结后期 join 运行中的守护线程会抛 `PythonFinalizationError`（[同文件](https://github.com/python/cpython/blob/v3.15.2/Doc/library/threading.rst#L627-L629)）；程序被信号杀死、致命错误或 `os._exit` 时 atexit 回调不运行（[atexit.rst](https://github.com/python/cpython/blob/v3.15.2/Doc/library/atexit.rst#L34-L36)）。`concurrent.futures.thread` 用 `threading._register_atexit(_python_exit)`：置全局退出标志，给每个队列放 `None`，join 全部 worker 线程（[thread.py](https://github.com/python/cpython/blob/v3.15.2/Lib/concurrent/futures/thread.py#L23-L37)），排在队列前面的工作仍会被做完（文档写的是程序在所有待处理 future 完成前不退出，队列顺序是推论）。本机复现（grpcio 1.85.1，Python 3.14.5，服务端在另一个进程里，handler 睡 3 s）：线程阻塞在没有截止时间的同步一元调用里。非守护线程时，主脚本结束后 `atexit` 回调到 3.10 s 才运行（先等调用返回），进程 3.26 s 退出；守护线程时 `atexit` 回调在 0.40 s 就运行，进程 0.51 s 退出，调用线程被直接丢弃。

- **gRPC Python。** 见第 1 节末：库线程是守护线程，挂住进程的是调用线程与用户的线程池。同步服务端的 handler 在 `ThreadPoolExecutor` 里，退出时被 `concurrent.futures` join（本机复现：handler 睡 3 s，`stop()` 之后进程仍等到 3.1 s 才退出）；aio 里放在默认执行器里的阻塞调用，`asyncio.run` 退出时等它做完（本机复现 3.0 s）。
- **Ray。** `shutdown` 通过 atexit 自动运行（[worker.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/_private/worker.py#L2163)），按上面的顺序它在非守护线程 join 之后才运行（推论，未复现）。
- **Java。** 线程池默认用非守护线程（[Executors.java](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/util/concurrent/Executors.java#L371-L375)），JVM 的关闭序列在所有已启动的非守护线程结束后才开始（[Thread.java](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/lang/Thread.java#L92-L97)）；`ExecutorService.close()` 无限期等，文档给的规避办法是两阶段写法。
- **Go。** `main` 返回时程序退出，不等其他 goroutine（[go_spec.html](https://github.com/golang/go/blob/go1.27.3/doc/go_spec.html#L8438-L8443)）；`Server.Shutdown` 的文档要求程序自己等它返回，否则在途请求随进程消失。
- **ZeroMQ。** LINGER 为默认 -1 且有未发出的消息时，`zmq_ctx_term` 不返回；pyzmq 的规避是进程清理时不调 `term`（14.3）、`__del__` 里用 `destroy`（24）。本机复现：非守护线程里的 `ctx.term()` 让进程在脚本结束 5 s 后仍存活（由 5 s 看门狗强杀），放在守护线程里则脚本一结束进程就退出。
- **Dask、tokio、asyncio。** Dask 在 atexit 里以 `timeout=3` 关全局客户端；tokio 的 Drop 无限期等 `spawn_blocking` 的函数，规避办法是 `shutdown_timeout` 或 `shutdown_background`，代价是泄漏；`asyncio.run` 最多等默认执行器线程 300 s。

## 5. 结果怎样报告

结论：能让调用方区分"肯定没执行"与"可能执行了"的，在协议层只有 HTTP/2 的 GOAWAY last-stream-id 与 REFUSED_STREAM；在库层是 gRPC 内部的 `kNotSentOnWire`/`kNotSeenByServer`、Java 的 `RpcProgress`（都不对应用公开）、Ray 异常文字里的"可能执行也可能没有"，以及 Java `shutdownNow()` 返回的"从未开始"清单。其余框架给的是原因（取消、断开、超时、终止），不分执行与否。取消是否传到执行方也不一样：gRPC Python 与 Dask 的客户端关闭不会停下服务端已经在执行的 handler 或任务。

- **gRPC。** 本方主动关闭得到 `CANCELLED`（Python 同步 `Channel closed!`；aio 在等待的任务里抛 `asyncio.CancelledError`，`call.code()` 为 `CANCELLED`；grpc-go 的 `ErrClientConnClosing`，一元调用为推论）；服务端或传输消失得到 `UNAVAILABLE`（服务端强停 `Cancelling all calls`；grpc-java `shutdownNow` 为 `Channel shutdownNow invoked`，`shutdown` 之后的新调用为 `Channel shutdown invoked`）。状态码文档把"服务端正在关闭"与"数据写出后连接断开"都列为 `UNAVAILABLE`，不区分是否执行（[statuscodes.md](https://github.com/grpc/grpc/blob/v1.85.1/doc/statuscodes.md#L45-L51)）。
- **Ray。** `RayActorError` 下分 `ActorDiedError` 与 `ActorUnavailableError`；`ActorUnavailableError` 的异常文本写明任务可能执行过也可能没有（[exceptions.py](https://github.com/ray-project/ray/blob/ray-2.59.0/python/ray/exceptions.py#L531-L543)）；被 `ray.cancel` 取消的任务得到 `TaskCancelledError`。
- **Java。** `shutdownNow()` 返回从未开始的任务清单（`List<Runnable>`）；已开始的靠中断，不单独报告；`awaitTermination` 返回 boolean 表示是否已终止；关闭后提交抛 `RejectedExecutionException`。
- **Python 与 Dask。** `cancel_futures=True` 取消的 future 为已取消状态，已开始的不取消；关闭后 `submit` 抛 `RuntimeError`。Dask 关闭客户端后本地 future 抛 `FutureCancelledError`，worker 上已执行的部分不报告。
- **ZeroMQ。** 阻塞中的操作得到 ETERM（pyzmq 为 `ContextTerminated`）；已入队未发出的消息在 linger 到期后被丢弃，没有逐条通知。
- **Erlang、Cap'n Proto、Go。** `gen_server:call` 给退出原因元组，不分执行与否；Cap'n Proto 给 `DISCONNECTED`；Go 的 `Serve` 等返回 `ErrServerClosed`，`Shutdown` 到期返回 ctx 的错误，都没有逐请求的报告。

### 与 C-Two 三个选项的对应

只陈述各框架的行为落在哪一类，不作取舍。

- **(a) 立即失败。** gRPC Python 同步 `Channel.close()`、aio `close(None)`、grpc-go `ClientConn.Close()` 与 `Stop()`、grpc-java `shutdownNow()`、Python 服务端 `stop(None)`、`ray.kill`、Go `Server.Close()`、Dask `Client.close()` 对本地 future、ZeroMQ 对阻塞中的操作（ETERM）。这一类里的"立即"指取消 RPC 或 future，不等于停下执行方：gRPC Python 的 handler 与 Dask worker 上的任务都会继续跑完（前者本机复现，后者见文档）。
- **(b) 先拒绝新调用，宽限内等，到期中止。** 一个 API 内置的有：gRPC Python `Server.stop(grace)`、aio `Channel.close(grace)` 与 `Server.stop(grace)`，C++ `Server::Shutdown(deadline)`，Ray `__ray_terminate__` 的 30 s 加强杀，Erlang 监督者的 `shutdown` 毫秒数加 `kill`，libzmq 的有限 LINGER（到期丢弃未发出的消息）。到期后不中止、只放弃等待的有：tokio `shutdown_timeout`（工作泄漏）、asyncio 默认执行器 300 s（`RuntimeWarning`）、Dask `close(timeout)`（抛错）。要调用方用两三个 API 拼出来的有：Java（`shutdown`、`awaitTermination`、`shutdownNow`，文档给了写法）、grpc-go（`GracefulStop` 加 `Stop`）、Go（`Shutdown(ctx)` 加 `Close()`）、grpc-java 客户端。
- **(c) 无限等，只报告未完成。** grpc-go `GracefulStop()`、Java `close()`、Python `Executor.shutdown(wait=True)`、tokio 的 Drop、libzmq 默认 LINGER -1、Go 不带期限的 `Shutdown`。"报告未完成"的形式：Java 的 `awaitTermination` 返回 false 与 `isTerminated()`、grpc-java 的 `isTerminated()`、Python gRPC `stop` 的 Event 尚未置位、Dask 抛 `TimeoutError`；tokio 的 `shutdown_timeout` 到期没有任何报告。
- **同一个库里的组合。** 本文查到的库大多在同一个库里同时提供 (a) 与 (b) 或 (c) 的 API，由调用点选择：Python gRPC 的 `stop` 与 aio `close` 把 (a)(b) 放进同一个 `grace` 参数（`None` 即 (a)），Java 与 grpc-go 把它们分在不同的方法上；Python `concurrent.futures` 对运行中的工作只有等待一种，排队中的可以取消。

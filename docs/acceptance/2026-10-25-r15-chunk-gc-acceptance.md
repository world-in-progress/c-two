## 实现与实际增量

完整 `gc_sweep` 在原遍历中记录最早存活活动时间，以扫描开始时刻封顶，形成下一次可能过期的保守下界。原压力条件成立且当前时间严格早于该下界时，跳过确定无效的自动扫描；到达下界、没有证明或时间加法不可表示时，继续原扫描。每个 registry 仅增加一个私有 `Mutex<Option<Instant>>`，本机布局为 24 B；没有线程、timer、配置、公开接口或通用管理器。

缓存锁不跨 shard、pool、实际扫描或 context Drop。完整扫描仍先释放 backing/charge，再释放 context/permit，全部完成后才发布下界。feed 只向后刷新时间，晚到插入不早于扫描开始；各次完整证明独立安全，乱序发布最多增加扫描。`try_gc_sweep` 可能跳过忙对象，保持不发布证明。显式及周期 GC 始终完整执行，原压力触发条件、Duplicate → 几何 → Capacity 错误顺序、预算拒绝计数、身份与释放语义保持。

## 基线证据与针对性回归

生产保持基线逐字节不变时，先运行新覆盖：无 timer/预算矩阵与 context Drop 重入用例通过；持有无关 shard 锁的新鲜压力插入判据按预期失败，旧实现阻塞于不必要的全表扫描。失败路径先释放锁并 join worker，再断言，不遗留测试线程。候选同一判据通过，macOS `c2-wire` 全部 167 项通过；补强存活条目的精确下界断言后，该矩阵单独通过，最终源码随后冻结。

| 覆盖 | 验收边界 |
| --- | --- |
| count/字节压力，存量已过期 | 无 runtime、无 timer 时原 insert 同步回收并恢复准入，预算和拒绝计数正确。 |
| 新鲜存量、已满预算 | 仍返回 Capacity，原 owner 和计费保留；下界来自实际最早存活时间。 |
| 真实预算小于 registry 阈值 | 保持原拒绝，不借优化偷偷添加 GC 后重试。 |
| 不完整 `try_gc_sweep` | 忙 shard 被跳过后，后续 insert 仍能完整回收；不得发布假证明。 |
| 可重入、慢完整扫描 | context Drop 向已扫 shard 插入并 feed；嵌套扫描先发布，外层扫描跨过过期点后发布，后续准入仍回收。 |
| 锁序及释放 | 缓存锁在 context Drop 中可重入；backing/charge 先于 context；保留旧 contention、trim、共享预算、同代清理测试。 |
| 零 timeout / 不可表示下界 | 不得建立未来的跳过窗口；精确相等边界由生产 `>=` 条件静态核对，未宣称可确定性命中某个 Instant。 |

在独立源码副本分别引入三种错误：按扫描完成时间发布、忽略最早存活时间、从部分扫描发布证明。三种 mutant 均被对应行为测试拒绝，退出码 101；原候选未改变。没有放宽期限、断言或通过重复执行筛选结果。

Windows 11 x64 开发机实跑同一 `registry.rs` SHA-256，Rust 1.99.1，167 项通过、0 failed、0 ignored。原 PowerShell 包装在测试完成后的 `cargo clean` stderr 处理上中止，未保存测试命令退出码；独立读回原始测试日志、源码哈希、target 不存在及任务临时目录为空，补成带此限制的收据，没有重复测试。不能将包装失败写成整个脚本成功。

## 同环境性能

macOS 27.0.1 arm64、Apple M1 Max、Rust 1.91.0，相同 release/fat-LTO/codegen-units=1 参数。每个配置基线/候选各 9 次，按配对 AB/BA 交替顺序执行；108 组 registry、72 组真实 socket RPC，共 180 组全部保留，没有删除慢样本或重跑挑选。两版均使用原 `soft_limit=512`，没有以关闭压力扫描的配置代替基线。计时期间没有同时进行本机构建，未安装 tracing subscriber，因此不计日志 I/O 收益。[原始样本](evidence/2026-10-25-r15-benchmark.jsonl)与收据保留源码、编译器、二进制和两份临时测量程序哈希。

registry 测量直接链接真实生产库，保持 32/512/1024 个新鲜 assembly，每线程执行 8192 次 insert＋abort；四线程采用 barrier 同时开始。下表为 9 次中位数，四线程是总 wall time/操作数，不是单次请求延迟。

低于阈值时未进入新增缓存判断，32 条结果不计作算法收益。完整 GC 自身更贵：512/1024 条的单线程扫描由 1.713/4.039 µs 增至 2.227/5.215 µs，约慢 30.1%/29.1%；四线程 workload 结束后的扫描约慢 30%–32%。新增成本是遍历时收集下界及一次发布，收益来自避免后续重复全扫，不能宣称每次 GC 都更快。

RPC 测量复用现有测试 helper，在隔离源码中临时加入 harness；实际经过 `Server::run`、本批私有 Unix socket、IPC 13 握手、路由准入、两块请求重组、真实 callback 与响应。独立压力 route 保持 0/512 个未完成 assembly，echo route 先预热 64 次，再计时 1024 次调用并校验 RID、响应内容和调用次数。两版配置完全相同；不使用 SHM 引用传输，回复 inline；每个 workload 均在原 5 秒 GC timer 前结束并断言，因此没有周期扫描干扰。此结果只描述原生分片 RPC，不推导 Python/FastDB 应用吞吐或 Windows/Linux 性能。

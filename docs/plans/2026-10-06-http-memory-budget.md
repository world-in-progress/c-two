# HTTP 载荷内存预算与消费生命周期

状态：设计提案，尚未实施或验收。它接续 [relay 适配补齐](2026-10-06-relay-memory-followup.md)，扩展当前明确排除 HTTP 缓冲的 IPC 预算范围。[既有大载荷设计](../issues/relay-large-payload-transport-design.md) 的响应全量物化边界仍然成立。

## 目标状态

Rust 负责每个所有者域内的 HTTP 载荷准入、字节计费、背压和释放。SDK 继续负责领域序列化，relay 不解释 FastDB 内容。每个 relay 实例和每个客户端 Runtime 各有独立的远程传输预算上下文；同一所有者的连接、路由和重连共享它，观察统计不创建连接、不重置预算。IPC 的 SHM/file/reassembly 三项预算保持原有含义。

| 所有者 | 应计费内容 | 结束条件 |
| --- | --- | --- |
| 客户端 Runtime | C-Two 为 HTTP 请求创建的副本、响应/错误的接收缓冲 | 最后一个实际缓冲所有者释放；进入 held 后仍保留对应 reservation |
| relay | HTTP 请求暂存、响应发送窗口、错误响应缓冲 | Body 消费完成或被丢弃后释放；已送给网络层的共享切片按最后一个引用结束计费 |
| IPC 传输/资源进程 | 原有请求/响应 backing 和重组存储 | 既有真实 lease/carrier 生命周期；HTTP 转发不能提前退款 |

调用者原有 Python/FastDB 对象、对端映射、内核网络缓冲和第三方 HTTP 库内部空间不自动纳入此计费。统计必须列出这些边界，不将字节预算称为进程 RSS 上限。不能将同一所有者的 reservation 因分片、slice/clone 或重连重复创建或提前返还。

## 准入与进展

新增独立的 HTTP 载荷字节上限与在途调用数量上限，经 c2-config 解析和验证后冻结。零值拒绝相应正数准入。字节与调用数是不同资源；连接池的空闲连接数量不能替代它们。最终数值默认值需要用实际载荷和并发测量确定，不能从 IPC 默认值直接抄出。

在读取请求体、克隆调用者输入或接受响应分配前获取相应 reservation；未知长度输入逐块申请，持续检查单消息上限。等待队列和每个等待项都必须有限，不能先无限排队再限流。准入等待支持 deadline 和取消，关闭能唤醒等待者。保留独立且有界的控制面/错误响应容量，避免数据预算耗尽后连容量错误都无法返回。

请求和响应会同时推进，不能让所有预算被等待响应的请求副本占满。对需要保留以支持安全重试的请求副本，必须单独计费；响应至少保留能推进一个发送窗口的容量。无法在既定上限下保证进展的请求在发送前拒绝，不靠扩大缓存或忙等恢复。

## 传输与所有权

已知长度 HTTP 请求继续使用现有 IPC sized-stream 接口，复用 buddy、dedicated 和 checked chunk 选择；不在 relay 中直接操作 MemPool。HTTP 阶段按窗口拉取数据，在取得下游容量前不持续读取更多。低层写入背压与资源函数的增量输入是不同契约；本设计不改变资源仍在完整输入后执行的语义。

响应应由 c2-ipc 提供安全的、绑定实际存储所有者的读取接口。HTTP Body 持有该所有者和必要的上游 lease，以固定大小窗口复制并发送，不先构造完整响应 Vec。读取 guard 不能跨 await；SHM/文件视图必须被实际 owner 固定，禁止每次读取时重新查询可替换的当前连接池。旧连接关闭、idle 驱逐和新连接建立都不能令旧 Body 读到新的 backing。显式传输故障后的发送可以失败，不能重放已执行的业务。

Inline 和错误响应同样需要覆盖。若现有接收接口在上层准入前就分配完整 Vec，应先补可在长度校验后、分配前预留的原生接收边界；不能在构造 Body 后补记账并声称限制了分配。SDK 仍要求完整返回值的 API 可以继续全量接收，但必须先准入并保持 reservation，直至值/held 的实际所有者释放。

Body 完成、网络错误、超时、客户端断开和 Drop 都进入同一幂等释放路径。已投递给网络层的 Bytes 切片需要随 backing 携带 reservation；仅包装外层 Body 的 Drop 不足以证明缓冲已释放。需要异步收尾时，使用预先取得容量的有界清理机制；不能在 Drop 中创建无限后台任务，也不能因返回超时而伪造归零。普通 RPC 取消不等于资源方法已停止执行。

## 错误与观测

发送前准入失败可以标记 pre_dispatch。发送中、服务端可能已执行或响应接收中的失败必须保留 dispatch_uncertain 和禁止自动重放。单个调用容量不足不能自动撤销路由或关闭仍健康的共享连接。统计分别展示 live/peak/rejected bytes、在途调用与等待/清理数量，注明它们的计费范围。

## 实施次序与退出条件

1. 原生预算与配置：验证原子预留、溢出、零值、跨连接共享、取消等待和关闭唤醒。此阶段不声称响应已流式化。
2. 请求及客户端接收：用真实 HTTP server 验证长度不可信、未知长度、超限和错误 body，检查分配前准入与实际持有生命周期；反向测试移除 reservation 时必须失败。
3. relay 响应 owner Body：分别覆盖 inline、buddy、dedicated、文件 carrier；在慢读、断连、并发驱逐和旧 Body 跨重连情况下核验内容、owner、峰值和退款。禁止 raw pointer alias 安全的过度承诺。
4. 并发与平台：多个真实 upstream 同时发送大响应，慢客户端不应令窗口缓冲随完整载荷大小增长；容量耗尽时其他有额度调用及控制面继续推进。检查有限队列、超时、进程/文件/映射清理和 Windows 2022/2025。实际缓冲计数与 RSS 分开记录，并绑定所测源码及二进制。

各阶段应独立提交并由 Host 验收，再允许依赖其接口的后续实现。当前设计没有选择新 wire 协议、放宽失败检查、改变 SDK 业务接口或替换原有 IPC 回退体系。

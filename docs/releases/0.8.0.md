# C-Two 0.8.0

Python C-Two 0.8.0 pairs with c3 0.4.0 and FastDB 0.2.3. This release adds physical IPC connection observations, explicit owner recovery and structured local OS errors. It also consolidates allocation ownership, chunk admission and SHM response handling in the shared Rust runtime.

```bash
uv pip install --upgrade 'c-two==0.8.0'
# For FastDB Payload contracts:
uv pip install --upgrade 'c-two[fastdb]==0.8.0'
```

The base package still supports Python 3.10+ without Python runtime dependencies. The optional extra pins `fastdb4py==0.2.3`; ordinary imports, CRM definitions and calls do not load FastDB or NumPy. Rust/native source builds use the matching FastDB source and verified Core SDK.

## Connections and ownership

- Client observations and `cc.connection_events()` report physical IPC
  connection termination even when no business call is pending. They reuse native receive, heartbeat and close events on Unix sockets and Windows Named Pipes. A terminal connection does not prove process death or payload cleanup. Bounded server event streams report lag explicitly.
- `owner_control_pair()` returns `OwnerControl` and a one-use Rust
  `OwnerBootstrap` / Python `NativeOwnerBootstrap`. Trusted launchers transfer the bootstrap to the child before readiness. The previous owner interface is removed without aliases.
- The current owner can issue or revoke one recovery grant. Applications
  explicitly save exported tickets, prepare takeover, save the successor, then commit once. Commit requires `OwnerMissing` before the original grace deadline, consumes the old grant and advances the owner epoch. Old commands, tickets and EOF lose authority. Failed attempts cannot extend grace.
- Owner loss pauses native admission while preserving published route
  identity. A valid takeover restores the host gate without reopening closed routes or reviving old registration tokens. Late relay registration completion cannot reopen admission after owner loss or shutdown.
- `OwnerControl.close()` starts owner-missing grace; `request_shutdown()`
  requests drain and acknowledges initiation only. Ordinary IPC admin shutdown is refused for OwnerBound hosts. For Persistent hosts, it retries only before writing begins; lost confirmation does not replay shutdown.

See the [lifecycle guide](../reference/local-endpoint-lifecycle.md) for concrete observation and recovery APIs, ticket handling and indeterminate outcomes. There is no automatic ticket persistence, owner election or recovery retry.

## Rust migration and transport behavior

Recompile low-level Rust consumers and migrate removed APIs directly:

- Allocation handles are move-only owners bound to their actual pool.
  Received SHM carriers retain their pool; prepared carriers bind its identity. Raw memory access requires explicit unsafe contracts. Coordinate metadata is not ownership.
- `ChunkRegistry<C>` stores each assembly and its required context together.
  `take` / `take_id` replace `finish` / `abort_id`; `FinishedChunk`, `set_route_info` and assembler route fields are removed. GC returns the route permit with its assembly rather than through a later reconciliation sweep. Admission generations, budgets and release order remain enforced.
- `try_prepare_shm_response` returns `Result<Option<PreparedShmResponse>, String>`.
  Ordinary and preallocated SHM replies use the same sender. Ordinary reply release now uses existing `free_at` bookkeeping and shared diagnostics. Allocation failure may select inline/chunk transport before writing; writing failure never selects another transport or replays a response.
- `ServerLifecycleState::Failed` and `LifecycleError::Server` carry
  `ServerFailure`. Local bind/connect failures retain `LocalIoCause` through the Rust error chain and Python `CoreError.io_kind`, `raw_os_error` and `io_operation`. Non-I/O policy failures do not invent an OS cause.

IPC handshake 12, SHM format 3, C/FFI ABI 5, business frames and CRM hashes remain unchanged from 0.7.6. Owner control has a separate version 1; upgrade cooperating controllers and hosts together. No old owner protocol or API compatibility path is retained. Rust SDK package version 0.1.0 remains independent and source-only; this release does not publish a C-Two crate or npm package.

Response snapshots and cancellation boundaries remain unchanged. In particular, the existing cancellation-before-writer-lock behavior retains an unpublished allocation until its pool is destroyed; this response-path consolidation does not claim to repair that separate lifetime issue.

## Development dependencies and release scope

The development lock uses Pillow 13.0.0 and certifi 2026.10.19 to resolve the reported Dependabot advisories. Pillow belongs only to the `banner` group, which requires Python 3.11+; ordinary SDK and test environments retain Python 3.10 support. Run the tool with `uv run --python 3.11 --group banner tools/dev/generate_banner.py`.

The release matrix contains six CLI targets, 35 Python wheels and one sdist. Windows ARM64 adds native Python 3.11, 3.12, 3.13, 3.14 and 3.14t wheels and `c3-aarch64-pc-windows-msvc.exe`; the other five targets retain all six Python ABI rows from 3.10. Windows source validation includes Server 2022/2025 x64 and Windows 11 ARM64, with real Rust/Python/Node calls and standard-user package consumers. The ARM64 lane builds the locked PyArrow dependency from source for the grid examples. Python 3.10 syntax-only coverage uses an x64 interpreter on Windows; all ARM64 runtime gates use native interpreters. Windows services and a real Windows/Linux relay link remain outside this release's evidence.

Publication promotes the exact bytes from a successful same-source canonical Source Validation and Release Candidate run. The c3 release's `rc-manifest.json` and promotion receipts identify the source, dependencies, artifact hashes and validation runs. Historical endpoint directories are not migrated or cleaned during this release.

Published artifacts and validation are recorded in the [0.8.0 acceptance report](../acceptance/2026-10-23-r13-080-release-acceptance.md): [Python package](https://pypi.org/project/c-two/0.8.0/) and [c3 0.4.0](https://github.com/world-in-progress/c-two/releases/tag/c3-v0.4.0). The report distinguishes artifact source, later verifier/documentation commits, cross-platform results and cleanup.

# C-Two 0.10.1

Published on 2026-10-30: [C-Two 0.10.1](https://pypi.org/project/c-two/0.10.1/), from source `1a69b78a44f58ceaa671fcf6b0c892b0206f4c45`. All 35 wheels, including five Windows ARM64 wheels, and the sdist are published. See the [validation and cleanup record](../acceptance/2026-10-30-0101-release-acceptance.md). This patch keeps `cc.serve()` running when stdout cannot encode its messages, reported during adoption of 0.10.0, fixes an intermittent zero-timeout shutdown failure found while qualifying it, and makes the CRM template generator and the contract export write UTF-8 regardless of the platform code page. It continues to use FastDB 0.2.4 and the existing c3 0.6.0; no new CLI, Rust crate or npm package is published by this patch.

```bash
uv pip install --upgrade 'c-two==0.10.1'
# For FastDB Payload contracts:
uv pip install --upgrade 'c-two[fastdb]==0.10.1'
```

## `cc.serve()` output on non-UTF-8 stdout

Previously, the startup banner used box-drawing and bullet characters and the shutdown message an ellipsis, all written with `print()`. When stdout could not encode them, `cc.serve()` raised `UnicodeEncodeError` and the process exited with status 1. This happens on Windows when the server's output goes to a pipe or file and Python uses the system ANSI code page (for example cp1252 or GBK) instead of UTF-8 mode, and on POSIX under a non-UTF-8 locale. The shutdown message was written before `shutdown()`, so the error also skipped graceful shutdown.

The banner and the shutdown messages now use ASCII text and are written with stdout's own encoding: a route name that stdout cannot encode appears as `\uXXXX` escapes instead of raising. Each message is flushed, so a piped banner appears immediately. The wording is unchanged apart from the decoration characters (`-` rules and bullets, `...`).

## Zero-timeout shutdown right after completion

A shutdown with `timeout=0`, made right after an earlier shutdown had completed, could fail with `shutdown_wait_timeout` at stage `core_retirement_wait`. The Core shutdown driver woke its waiters while it still held the Runtime state lock, which a zero-deadline call must acquire without waiting; in the retirement path it also released its Host reference only after waking them. The driver now releases those locks and its retirement resources first and wakes waiters last, so a caller that has seen completion never contends with the driver. No API changes.

## Template and contract files on non-UTF-8 platforms

`generate_crm_template` read the CRM's source file and wrote the generated template with Python's default text encoding. On Windows that is the ANSI code page (for example cp1252 or GBK) unless UTF-8 mode is on, so a UTF-8 source with non-ASCII text, such as Chinese comments or docstrings, could fail to decode or produce garbled output. The source is now read with `tokenize.open`, which follows the file's encoding declaration and defaults to UTF-8, and the template is written as UTF-8.

`python -m c_two.cli.contract`, which the `c3 contract` subcommands run, wrote files with the default encoding and stdout through the stream's code page, while `c3` requires UTF-8 output. It now writes UTF-8 to files and to stdout.

## Compatibility

IPC handshake 14, Unix namespace format 3 and credential schema 4, C/FFI ABI 6, SHM 3, owner-control encoding 1, business frames and CRM hashes are unchanged, so 0.10.1 and 0.10.0 peers interoperate. Only the Python package changes.

The distribution matrix remains 35 wheels and one sdist. Windows ARM64 covers CPython 3.11, 3.12, 3.13, 3.14 and 3.14t; the other five platform targets retain Python 3.10 as well.

## Validation

The serve fix was accepted on `51cb141e`: the new tests fail on the 0.10.0 code under cp1252, GBK and ASCII stdout and pass with the fix, including a subprocess `cc.serve()` started without UTF-8 mode and, on Windows, under the default code page. The shutdown fix reorders only the driver's final publication in `c2-core`; with a 50 ms pause widening the old gap the original Python test failed 5/5 at `core_retirement_wait`, and with the same pause in the new order it passed 5/5. The SDK tests now treat any `EncodingWarning` raised from `c_two` as an error, and the test runner enables that warning on every platform: with the previous `template.py` the new template tests fail on it, and they pass with the fix. The Windows installed-wheel and standard-user smokes run the package without UTF-8 mode, as users do.

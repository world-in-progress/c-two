# C-Two 0.12.0 and c3 0.8.0

Published on 2026-11-23: [C-Two 0.12.0](https://pypi.org/project/c-two/0.12.0/) (35 wheels, including five Windows ARM64 wheels, plus 1 sdist) and [c3 0.8.0](https://github.com/world-in-progress/c-two/releases/tag/c3-v0.8.0) (6 platform binaries, 2 installers and provenance manifest), from canonical `main` commit `f388cc1405ccf36741239ddda6bdeb6ee2e1d408` (FastDB **0.3.0** / ABI-118, Rust **1.95+** for source builds). See the [0.12.0 release acceptance record](../acceptance/2026-11-23-0120-release-acceptance.md). Rust crate and npm package versions keep their independent 0.1.0 cadence.

This release delivers two major milestones on top of [C-Two 0.11.0 / c3 0.7.0](0.11.0.md) (`50be9a7966d6c8381715809440d69502c3cee5de`):

1. **Resource-owned publish/subscribe** ([ADR 0005](../decisions/0005-publish-subscribe.md)): a third connection primitive orthogonal to unary calls and server streams that broadcasts immutable frames from a stateful resource to many local and remote subscribers — sharing one sealed SHM 4 block across same-host subscribers and one upstream per hub across single-hop and two-tier `c3 relay` topologies, removing the `R×` write and cross-machine transfer amplification measured at `4×` for 32 MiB frames at `R = 1 → 4`.
2. **Unified `WritableSlab` direct-SHM channel + FastDB `0.3.0` zero-copy + KB-to-GB performance pass**: cuts the one-way SHM full-payload copy lower bound from **8 / 7 copies → 2 copies** (the [ADR 0001](../decisions/0001-single-owner-release.md) single-owner floor, **0** Python/FastDB glue copies) across unary, server stream, pub/sub topic, and client request paths; upgrades buddy pool geometry (`4 × 64 MiB` at `1 GiB` budget) with bounded warm `RecycledBytes` local buffer pooling; and trims KB-scale inline framing, timer, read-syscall, and Python bind overhead.

## Upgrade together

- **Protocols and ABIs:** IPC **17** (replaces 16 in 0.11.0), C/FFI ABI **9** (replaces 8 in 0.11.0), and FastDB **0.3.0** (`ABI-118`, replaces 0.2.4 / `ABI-117`). SHM **4**, relay mesh **7**, Unix namespace disk format **3**, Unix `EndpointCredential` schema **4**, and the `C2E1` v1 error wire are unchanged.
- **Clean cut, no compatibility path:** The permanent fixed 25-byte version preamble and its typed `ProtocolVersionMismatch` remain; an IPC 16 (0.11.0) peer and an IPC 17 (0.12.0) endpoint refuse each other through it, and ABI 8 loaders are rejected by the ABI 9 addon's version check rather than by a missing symbol. Stop running hosts and relays, upgrade the Python SDK, Rust SDK, `c3` and Node binding together (plus all relays communicating within one mesh), and regenerate generated Rust, Python and TypeScript contract clients.
- **Zero new configuration:** Publish/subscribe and warm local buffer recycling add no environment variables, CLI flags or slot settings. They operate strictly inside the existing per-role `(M, F, N)` domains ([memory policy](../reference/memory-policy.md)).

### Migration checklist (from 0.11.0 / c3 0.7.0)

1. **Coordinated package & binding upgrade:**
   - Upgrade Python to `c-two==0.12.0` (or `c-two[fastdb]==0.12.0`, pinning `fastdb4py==0.3.0`) and CLI to `c3 0.8.0`.
   - Rebuild the Rust SDK (`fastdb = "=0.3.0"` and the official FastDB `0.3.0` Core SDK), rebuild the Node addon (`C2_MEM_FFI_ABI_VERSION 9`), and regenerate all Rust, Python and TypeScript contract clients.
2. **Python `register()` return type:**
   - `cc.register(...)` and `Runtime.register(...)` now return a `Registration` handle (`name`, `publisher(topic)`, `is_closed`, `active_subscribers`) instead of a bare `str`. Code that ignored the return keeps working; code that stored or compared the returned string must read `registration.name`.
3. **Optional `BuildPlan` direct-SHM returns (FastDB `0.3.0`):**
   - Resource methods bound with `@cc.transfer(output=...)` may continue returning `Payload` or return a frozen `fastdb4py.payload.BuildPlan` (annotated as `BuildPlan`, `Payload | BuildPlan`, `Iterator[BuildPlan]`, or `Generator[BuildPlan, None, None]`) to execute direct-eligible plans straight into C-Two's `WritableSlab` SHM with zero intermediate staging copies.

## Resource-owned topics (ADR 0005)

- **Contract:** `c-two.contract.v2` gains an optional root-level `"topics"` array. A contract with no topics omits the key — an explicit empty array is rejected — so every existing unary and server-stream contract keeps `descriptor_sha256`, `abi_hash` and `signature_hash` byte for byte; old parsers reject topic-bearing descriptors as an unknown root key. Each topic declares `name`, `output` (fixed to `{"kind": "payload"}`) and a FastDB `binding`; topics sort by name ascending, reject duplicate and method-colliding names, count toward contract admission (at most 256 topics), and a topics-only contract is valid. Python-private pickle topics (a `@cc.topic` return annotation without `@cc.transfer(output=...)`) run only between Python peers and are refused by portable export. See [contracts and routing](../reference/contracts-and-routing.md#portable-contract-v2-and-artifact-composition).
- **Registration-scoped publishing:** Registering a route returns a `Registration` (Python `cc.register(...)` / Rust `Host::register(...)`) that the Runtime keeps alive; dropping the handle never unregisters. `registration.publisher(topic)` hands out a publisher bound to that one registration and its sequence space: after the registration ends it fails with `ResourceClosed` (707) and never writes to a later registration of the same name. Registration accepts an initial topic frame (`initial_topics` in Python, `initial_{topic}` builder methods in generated Rust) committed atomically with the same publish logic before the route opens — a codec or capacity failure rolls the whole registration back — and a per-topic history ring depth (`topic_capacity`, default `1`, at most 65,536).
- **History ring and lag policy:** Each topic keeps a monotonic `u64` sequence from `1` and a bounded history ring that always retains the latest published frame. `publish()` encodes the value exactly once and never blocks on a slow subscriber; when no in-budget storage exists for a new frame it fails immediately with `CallCapacityExceeded` (717), keeping the previous frame and consuming no `seq` — topic history never spills to disk implicitly. Subscriptions choose a start (`latest`: first delivery is the retained newest frame, or `max(h, 1)` at attach; `next`: wait for `head_seq + 1`) and a lag policy (`skip`, the default: jump to the newest available frame and report `dropped = s − n`; `error`: terminate the subscription with `SubscriptionLagged` (720) before sending successor frames — a frame already begun under `ITEM_BEGIN` is never swapped mid-flight).
- **Deliveries:** Every iteration yields an immutable `Delivery(value, seq, dropped)` (Rust `Delivery<T>` with `value()` / `seq()` / `dropped()`). `cc.hold(...)` selects `Delivery[HeldResult[T]]`, whose `.value` owns the retained local copy; closing a subscription does not invalidate already-delivered values. Same-process publishes take an immutable snapshot of mutable Python objects at `publish()` time, so one reader's release or the publisher's later mutation cannot affect other readers.

## IPC 17

The RPC protocol moves from 16 to 17, keeping the 25-byte fixed version preamble, the 16-byte frame envelope, SHM 4 descriptors and the request-ID high-water mark. IPC 16 compatibility is removed. See the [handshake specification](../reference/ipc-handshake.md).

- `CallMode` gains **Subscribe (2)**. A Subscribe OPEN carries the six route and contract identity fields, a bounded topic name and one packed options byte (bit 0 `start`: 0 `latest`, 1 `next`; bit 1 `on_lag`: 0 `skip`, 1 `error`; reserved bits must be zero). The handshake metadata gains no topic table.
- The server answers a Subscribe OPEN with **`READY(start_seq)`** (record kind 8, an 8-byte nonzero `u64`), confirming the subscription even on an empty topic; the client's `subscribe()` returns only after it.
- A subscription's **`ITEM_BEGIN`** (kind 2) carries the source `seq` followed by the item's `total_bytes` (16-byte body); `ITEM_DATA`, chunking and SHM descriptors are unchanged, and CREDIT keeps the stream discipline of at most one outstanding item and whole-item storage grants.
- **`SYNC` / `SYNC_ACK(head_seq)`** (kinds 9 and 10) let a relay confirm the source head on its one shared upstream subscription without transferring a payload, so a subscriber that joins an active hub gets a causally consistent `start=latest|next`. Waiters queued before a SYNC is written share its acknowledgement; later waiters require a new one.
- `CALL_END` keeps Success / Failed / NotExecuted, and a subscription terminal is always Failed or NotExecuted with a C2E1 error — Success is not valid for a subscription, which has no natural end; the Failed terminal carries the count of complete frames delivered. Terminal causes follow ADR 0005: unregistration, Host shutdown and relay shutdown seal publishing and new subscriptions atomically and end open subscriptions with `CallCancelled` (718) naming `route_unregistered` / `host_shutdown` / `relay_shutdown` after the frame selected last is delivered; a strict lag ends a subscription with `SubscriptionLagged` (720); an unknown topic on a matched contract is `ProtocolViolation` (713) — never `701`, which would trigger route re-acquisition.
- **Slots and concurrency:** A subscription holds one business slot of its role domain's `N` for its whole life and no new slot configuration exists. With `N ≥ 2`, long-lived subscriptions occupy at most `N − 1` slots, keeping at least one for ordinary control and unary calls; `N = 1` permits one total operation; `N = 0` refuses all. A relay's shared upstream keeps the last downstream's slot until upstream cleanup completes, so `N = 1` still admits a first subscription. Subscriptions take no route concurrency permit (`read_parallel` / `exclusive`), no execution worker and no method `max_pending` count; the registration's drain barrier waits for active subscriptions to finish their selected frame before terminating them.

## Same-host 1-to-N shared memory

Publish/subscribe keeps [ADR 0001](../decisions/0001-single-owner-release.md) single-owner release and the SHM 4 wire format; there is no cross-process overwrite ring, no timeout-based reclamation and no cross-process read-only zero-copy subscription view.

- `publish()` encodes once into one sealed immutable shared-memory block (buddy or dedicated, charged once to `server.M`); small frames, empty frames and the SHM-unavailable fallback carry the same sealed value inline or in chunks without re-running the business serializer.
- Each local subscriber that has demand and whose previous loan settled receives an independent `loan_id` on its own connection pointing at the same sealed block, maps it read-only through the existing `PeerMappingCache`, copies it into its own `client`-domain local copy and sends `RELEASE` immediately.
- A loan is settled only by that connection's lawful `RELEASE` or by the read side's peer end — never by connection-state destruction. The host reclaims a block only after its frame has left the history ring and every published loan has settled. See [memory policy](../reference/memory-policy.md#role-domain-budgets-and-call-slots).

## `c3 relay` topic fan-out

A relay serves topic subscriptions over HTTP and removes the per-subscriber upstream cost. See [contracts and routing](../reference/contracts-and-routing.md#relay-topic-forwarding).

- **Endpoint:** `POST /{route_name}/_topics/{topic_name}` with `Accept: application/vnd.c-two.topic-stream;version=1`, no request body, the `x-c2-topic-start` (`latest` / `next`) and `x-c2-topic-on-lag` (`skip` / `error`) headers, the route's `x-c2-expected-*` contract identity headers and the existing `x-c2-call-token` cancellation channel (`DELETE /_calls/{token}`). The response body is a sequence of records — `READY(start_seq)`, `ITEM_BEGIN(seq, total_bytes)`, `ITEM_DATA` parts, and one `TERMINAL` record with status, complete-item count and a `C2E1` error.
- **One upstream per hub:** For each active registration and topic the source relay opens exactly one upstream IPC subscription, driven internally with `skip` while retaining the source `seq`, and composes each frame once into a single `Arc<HubFrame>` charged once to the relay domain's `M` / `F`. Every downstream keeps an independent cursor that applies its own `skip` or `error` policy and computes its own `dropped`. Concurrent first subscribers merge into one upstream connection; the last downstream leaving tears the upstream down; a terminal arriving from a replaced upstream cleans only its own hub instance.
- **Late joiners and slow readers:** A subscriber joining an active hub gets its start sequence from a merged `SYNC` confirmation on the shared upstream (no payload transfer). Under relay budget pressure the hub first sheds disposable history, then skips frames that have not started, and only then terminates a stalled TCP downstream singly — maintaining record boundaries, never splicing half frames and never blocking fast readers.
- **Two-tier cross-relay fan-out (`Host → A → B → R`):** When a client subscribes through an anchor relay B whose mesh view resolves the route to a source relay A (`Connect::RelayAware` / `Connect::RelayAwareAt` route topics through the anchor rather than bypassing directly to A, and `Connect::ExplicitRelay` targeting B uses the same path), B opens exactly one cross-relay HTTP upstream subscription to A carrying the single-hop anti-loop header `x-c2-relay-origin-only: 1`. A admits `origin_only` requests only for its own local routes and never forwards onward; only that inter-relay `origin_only` response returns an opaque SHA-256 registration fingerprint over `(server_instance_id, route_uid)` in `x-c2-topic-registration` (ordinary client responses on A and B never emit it). Late joiners on an active remote hub on B share one merged lightweight `POST /{route_name}/_topics/{topic_name}/_confirm` request (zero payload bytes, carrying `x-c2-relay-origin-only: 1` and `x-c2-expected-registration`) to obtain the source `head_seq`; A refuses a replaced registration — including a same-Host re-registration whose `server_instance_id` is unchanged — with `718 CallCancelled` (`cause=route_unregistered`) and an absent route with `701 ResourceNotFound`, isolating B's stale hub immediately. Mesh gossip and full-sync formats are unchanged (mesh stays at 7) because topics already live in the contract identity.

## Unified `WritableSlab`, FastDB `0.3.0` zero-copy, and KB-to-GB performance

- **2-copy one-way SHM floor (down from 8 / 7 in 0.11.0):** All four IPC send paths (unary responses, server stream items, topic publications, and client requests) execute direct-build-eligible FastDB `BuildPlan` values straight into `WritableSlab` SHM (`0` staging copies) or copy published `Payload` bytes once via `Payload.memoryview()`. Both Rust and Python receive paths open local `RecycledBytes` zero-copy via `Payload.open_external` / `ExternalBytes` (automatically lifting FastDB's `OpenOptions.max_total_bytes` for `> 256 MiB` transport-admitted payloads), bringing Python/FastDB glue copies down to **0** while keeping ADR 0001 copy-then-release semantics intact.
- **Buddy geometry & warm local buffer recycling:** `PoolConfig::for_budget_share` targets 4 buddy segments up to the 64 MiB cap (yielding `4 × 64 MiB` at a `1 GiB` role budget so `32 MiB` frames stay inside warm buddy SHM instead of hitting per-call `Dedicated` `mmap`/page-faults). `DomainBudget` adds a bounded warm `RecycledBytes` local buffer pool (`>= 256 KiB`, up to 4 buffers, weak domain handle, `reserve_vec` warm-claim-before-evict, drained on shutdown) wired across unary IPC responses, server streams, topic deliveries, and server request copies, paired with `PeerRead::copy_into_vec` uninitialized-target writes.
- **KB-scale fixed-overhead trimming:** `c2-local` defers deadline timer construction on the immediate-ready fast path and uses `poll_write_vectored`; `c2-ipc` and `c2-server` use buffered reads and eliminate intermediate `Vec` copies on inline frames; Python `transfer_wrapper` and `stream` add an exact-positional bind fast path and hoist immutable binding hooks into closure constants.
- **Headless benchmark evidence (`1 KiB–1 GiB` + `4 GiB` streamed migration vs `Ray 2.56.0` on `562293c4`):** See [2026-11-22-kb-to-gb-slab-benchmark.md](../acceptance/2026-11-22-kb-to-gb-slab-benchmark.md):
  - `32 MiB published` stream: **2.50 ms (`12.52 GiB/s`, 5.2× faster than Ray)**; unary: **3.12 / 3.43 ms (`10.01 GiB/s`)**.
  - `32 MiB fresh` stream: **3.76 / 4.70 ms (`8.31 GiB/s`, 4.1×–5.0× lower server RSS vs 0.11.0)**; unary: **4.10 / 4.70 ms (`7.62 GiB/s`)**.
  - `256 MiB` single frame: C-Two stream & unary (`62–65 ms`) beat `ray-named-actor` (`76–93 ms`), while `ray-compiled-graph` fails `OutOfDiskError` on all `>= 256 MiB` frames.
  - `4 GiB` bounded-memory streamed migration (`128 × 32 MiB` inside strict `1 GiB` RAM budget): **13.80 GiB/s `published`** (`0.290 s`, `64 MiB` pools, **2.0× faster than Ray**) and **8.92 GiB/s `fresh`** (`0.448 s`, P95 `4.05 ms` vs Ray `5.21 ms`).
  - `32 MiB, R = 4` `@cc.topic`: **22.10 GiB/s** (`P95 8.44 ms`, flat `384 MiB` host pool; single-hop relay `7.68 GiB/s`, two-tier relay `6.17 GiB/s`); 1M-row Kostya: **14.21 ms** (**3.85× faster than Ray**, **10.2× faster than pickle**).

## SDK and codegen surfaces

- **Python:** `@cc.topic` declares a topic on a CRM contract (zero parameters, no access category, one published output; `@cc.transfer(output=...)` selects a portable FastDB binding, any other return annotation stays Python-private pickle). Clients subscribe through the natural member (`telemetry.state()`, `telemetry.heartbeat(start='next')`) or `proxy.subscribe(topic, start=..., on_lag=...)`; `cc.hold(...)` yields `Delivery[HeldResult[T]]`, and `cc.with_call_options(...)` views carry the subscription policy. `Subscription` exposes `start_seq`, `cancel()` and `close(timeout=...) -> TopicCloseReceipt`. `cc.error.SubscriptionLagged` projects code 720. Resource methods on `@cc.transfer(output=...)` may return and annotate `BuildPlan` directly. See [Python usage](../reference/python-usage.md#publish-subscribe-topics) and [pubsub.py](../../examples/python/pubsub.py).
- **Rust:** `c_two::{Publisher, Subscription, Delivery, SubscribeOptions, TopicStart, LagPolicy, TopicConfig, TopicCloseReceipt}`; `Registration::publisher(topic)` and `subscribe_local(topic, options)`; `Client::subscribe(topic, options)` over direct IPC and relay HTTP. `Connect::RelayAwareAt { anchor_url }` selects a relay-aware anchor per endpoint inside a shared Runtime budget domain, preserving local-IPC upgrade and HTTP fallback without mutating the Runtime's configured anchor. Portable receive adapters (`open_owned` / `open_held` / `open_borrowed`) decode received local vectors zero-copy via FastDB `0.3.0` `ExternalBytes`.
- **`c2-codegen`:** All three targets generate topic surfaces — Rust `subscribe_topic_{index}_{name}` plus the `TopicService` capacity/initial builders and `registration_topics(&Registration)` publishers; Python `subscribe_topic_{index}_{name}` / `hold_subscribe_topic_{index}_{name}`; TypeScript `subscribe_topic_{index}_{name}` / `hold_subscribe_topic_{index}_{name}` over `TopicSubscribeOptions` and `C2TopicSubscription<T>`. Topic outputs share digest-deduplicated payload composition with method bindings, topicless contracts generate no topic symbols in any target, and generated Rust/Python decoders adopt FastDB `0.3.0` (`ExternalBytes` in Rust; automatic `> 256 MiB` `OpenOptions` lift in Python).
- **Node (C/FFI ABI 9):** The addon and native library are rebuilt as ABI 9 (`C2_MEM_FFI_ABI_VERSION 9`). `c2_mem_ffi_subscription_open` / `_next` / `_cancel` / `_close` / `_check_deadline` / `_free` run subscriptions inside the Rust Core client, and `c2_mem_ffi_endpoint_context_new` accepts one address for both `ipc://` and `http(s)://` entries (HTTP mode `relay_aware`, the default, or `explicit_relay`), so Core executes direct-IPC, relay-local and anchor-relay HTTP subscriptions uniformly. TypeScript `endpoint.openSubscription(route, topic, options, timeoutMs)` exposes the READY sequence as `startSeq: bigint` and delivers owned local buffers. See the [C ABI reference](../reference/c-abi.md).

## Error surface

One new canonical code: **`720 SubscriptionLagged`**, carrying `topic`, `expected_seq`, `available_first_seq`, `available_last_seq` and `dropped`; Python raises `c_two.error.SubscriptionLagged` and generated TypeScript maps it in the transport error-code table. Unknown topics on a matched contract reuse `ProtocolViolation` (713) with `reason=unknown_topic`; topic capacity failures reuse `CallCapacityExceeded` (717); lifecycle termination reuses `CallCancelled` (718) with a `cause` detail. `704`, `706` and `711` stay retired. See [errors](../reference/errors.md#semantic-error-wire-and-sdk-projection).

## Stability and fixes

- Tightened `RuntimeSession` lock ordering and generation checks (releasing Python objects and projecting errors outside native locks), and added dynamic fork-route stress tests plus the [resident simulation example](../../examples/python/resident_simulation.py) ([PR #234](https://github.com/world-in-progress/c-two/pull/234)).
- Idle local topic subscriptions settle immediately on close and cancel instead of waiting for the drain barrier.
- Released binding-created caller input `Payload.memoryview()` pins immediately after copying into the request buffer (before awaiting replies), and closed borrowed-mode deferred `BuildPlan` handles before input invalidation on error paths to prevent traceback-frame pin retention.

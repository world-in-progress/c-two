# C-Two 0.7.1 / c3 0.3.1 release and upgrade notes

Python `c-two` 0.7.1 and CLI `c3` 0.3.1 are a **coordinated candidate pair that has
not been published yet**. Package manifests will identify Python 0.7.1 and c3 0.3.1;
Rust SDK/Core/TypeScript remain 0.1.0, with no C-Two crates.io or npm publication.
This page records the candidate scope and the validation evidence that actually
exists; formal release status is updated here only after the final same-source
gates and promotion complete.

## Scope

0.7.1 keeps the 0.7.0 defaults: the private native v2.2 Unix endpoint namespace,
current-logon-SID Windows Named Pipes, IPC wire version 11, existing call entry
points, `Persistent`/`OwnerBound` lifecycle policies, held/borrowed payload
release rules, and endpoint anti-deletion mechanisms. The pool-size validation
fix applies to existing configurations, and HTTP's inherited timeout now bounds
the whole logical call. Explicit per-call options and custom Unix roots are
optional.

FastDB stays pinned to published 0.2.1, with native source builds pinned to
`4f99f86a662b0e950a0dd29800c25a1c9fca4def`. Call deadlines are a caller-side
wait policy applied by the 0.7.1 client: the wire stays at version 11, no peer
upgrade is required for the caller's wait to end, and a deadline does not
represent server-side business cancellation. Custom Unix roots are a
coordinated local-domain configuration: the resource server and any relay
participating in that local domain must adopt the same root, while a relay
without namespace support answers custom-root routes over HTTP only, with full
contract and handshake validation unchanged. This candidate does not claim
separate interoperability testing against published 0.7.0 packages; adopt
custom roots on a communicating group configured for 0.7.1.

## Independent pool segment and message limits

`pool_segment_size` and `max_payload_size` are validated as independent
dimensions. The previous cross-check that required a pool segment to be no
larger than the single-message limit is removed, for buddy enabled and disabled
alike: one large segment holds many small messages, so segment capacity does
not need to be bounded by the per-message limit. Construction and wire-format
checks (positive sizes, representable indices, bounded segment counts, overflow
checks) still apply, and requests or responses that actually exceed
`max_payload_size` are still rejected.

`pool_enabled=False` continues to skip only the buddy layer; dedicated SHM,
inline frames, checked chunks and receiving-side file spill remain available,
so it is not a zero-shared-memory switch. Disabling the pool does not disable
the default segment size as a valid setting. See the
[memory policy](../memory-policy.md).

## Per-call deadlines for remote calls

Calls over direct IPC and HTTP relay accept an explicit per-call wait budget:

```python
short = cc.with_call_options(proxy, timeout=2.0)   # 2 s total budget per call
result = short.compute(data)

with cc.hold(short.compute)(data) as held:          # hold works on the view
    consume(held.value)

unlimited = cc.with_call_options(proxy, timeout=None)  # explicit unlimited
```

- The default values stay the same: direct IPC calls wait without limit; HTTP relay calls
  inherit `C2_RELAY_CALL_TIMEOUT` (300 s). In 0.7.1 that environment value is
  the total budget of **one logical call** — including in-call route
  reacquisition — rather than a per-HTTP-request timeout, and `0` means
  unlimited.
- `timeout=None` explicitly disables the deadline for that call; omitting the
  argument inherits the path default; `0` expires immediately and fails at
  `pre_dispatch` without dispatching anything. Negative, NaN and infinite
  values are rejected at entry.
- Each call made through the view carries its own independent deadline;
  concurrent views and concurrent calls do not share or reset each other's
  budgets. The view does not occupy CRM method parameters or mutate global
  configuration, and `cc.hold()` works on a view with the same held-result
  semantics.
- A finite deadline bounds **the caller's wait, not the resource method's
  execution**: after the caller returns, already-dispatched native work and
  payload leases continue to a real terminal state. Business cancellation is
  not claimed. Deadline-bounded continuations retain request inputs under
  finite admission defaults of 1,024 outstanding calls and 16 GiB retained
  input per runtime (`C2_CALL_MAX_OUTSTANDING`,
  `C2_CALL_RETAINED_INPUT_BUDGET_BYTES`). Setting the count to `0` rejects
  every new finite call, including zero-byte input; setting the byte budget
  to `0` rejects only calls that would retain non-zero input. These budgets
  apply to deadline-bounded continuations only; unlimited calls are
  not bounded by them.
- A deadline expiry raises `cc.CallDeadlineExceeded` with a `transport_phase`
  of `pre_dispatch` (the resource was not invoked; caller-side serialization
  may already have run) or
  `dispatch_uncertain` (the request may have executed; the runtime never
  replays uncertain business calls automatically). Expiry does not close
  healthy shared connections, evict relay routes, trigger OwnerBound shutdown,
  or invalidate held results already obtained within their deadline. A
  capacity-refused finite call raises `cc.CallCapacityExceeded` before
  dispatch and does not remove routes.
- Same-process synchronous proxies reject finite deadlines before execution
  with `cc.UnsupportedCallMode`; use IPC when remote wait semantics are
  needed. Inherited and unlimited views leave same-process direct calls
  unchanged. Serialization and OS scheduling are not hard real time.

No global resident daemon is required: deadlines are per-call caller-side
budgets enforced by the shared Rust core. Cross-machine hop-by-hop budget
propagation and cooperative resource cancellation remain future work and are
not claimed by 0.7.1.

## Unix local endpoint root override

Unix endpoints live in a private per-user directory under a configurable
absolute root. The default root stays `/tmp`, producing the unchanged
`/tmp/c2-<uidhex>/v2.2/<address-hash>.sock` layout. A custom root produces
`<root>/c2-<uidhex>/v2.2/<address-hash>.sock`:

```python
# Configure once, before the first local bind/connect attempt.
cc.set_local_endpoint(root='/run/user/1000/myapp')
```

```bash
# Environment or CLI equivalents (same Rust resolver):
C2_IPC_ROOT=/run/user/1000/myapp c3 relay --bind 127.0.0.1:8080
c3 endpoint inspect ipc://worker --ipc-root /run/user/1000/myapp
```

- Priority is explicit code/CLI > process environment > `.env` > default
  `/tmp`. `ipc://worker` remains a logical identity; SDKs never assemble
  socket paths themselves and the removed protocol selectors do not return.
- The container directory must be created by the deployment beforehand;
  C-Two creates only its own private per-UID directory and the version leaf
  inside it, and never sweeps or deletes other content in the container.
- The endpoint context freezes at the first local bind/connect attempt of a
  runtime — a failed attempt also freezes — and later changes to the root do
  not affect existing connections, listeners, credentials or sweeps. Pure
  configuration queries perform no filesystem I/O.
- The root moves local endpoint and coordination files only; SHM names and
  file-spill backing are not relocated.
- Credentials for default-root endpoints keep the historical schema 2 form;
  custom roots use schema 3, which adds the verified root namespace.
  `inspect`/`reap` operate strictly on the context captured with the
  credential, and a mismatched context is refused before touching the target.
- Relay discovery gains a local namespace hint: when a relay's local upstream
  context does not match the caller's — or the relay predates the namespace
  extension — custom-root routes answer over HTTP only, with full contract and
  handshake validation unchanged. The hint is a
  routing-domain signal, not an authentication credential.
- Windows is unchanged: endpoints remain current-logon-SID Named Pipes, and
  the Unix root option is rejected as not applicable there instead of being
  silently ignored.

`Persistent`/`OwnerBound` lifecycle, held-payload release ordering and scoped
maintenance behavior are unchanged. No protocol selector or SDK-side endpoint
watcher is reintroduced. See the
[lifecycle guide](../local-endpoint-lifecycle.md).

## Installation

> 0.7.1 is an unreleased candidate; availability statements on this page are
> not publication claims.

Python 0.7.1 installs with `uv pip install 'c-two==0.7.1'` (the project page is
<https://pypi.org/project/c-two/>); `fastdb4py==0.2.1` is installed
automatically. c3 0.3.1 will use the coordinated
[c3-v0.3.1 release entry](https://github.com/world-in-progress/c-two/releases/tag/c3-v0.3.1)
with per-target binaries, SHA-256 sidecars, installers and `rc-manifest.json`,
following the 0.3.0 layout; these target URLs do not assert that 0.3.1 is
published. Development wheels identify by source and hashes, not version
strings alone.

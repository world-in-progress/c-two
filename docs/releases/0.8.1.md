# C-Two 0.8.1

This patch fixes Python server startup configuration and startup error classification reported during adoption of 0.8.0. It continues to use FastDB 0.2.3 and the existing c3 0.4.0; no new CLI, Rust crate or npm package is published by this patch.

```bash
uv pip install --upgrade 'c-two==0.8.1'
# For FastDB Payload contracts:
uv pip install --upgrade 'c-two[fastdb]==0.8.1'
```

## Caller-controlled server startup

Previously, Python registration always used `HostOptions::default()` with a five-second wait and offered no override. Now configure it before registering resources:

```python
import c_two as cc

cc.set_server(startup_timeout=30.0)
```

The native RuntimeSession constructor and `set_server_options` expose the same seconds value. It must be finite, non-negative and representable by the native clock; zero expires immediately. `None` or omission retains the existing five-second default as a finite unattended-startup policy, not a promise about runner speed. Rust's explicit `HostOptions::with_startup_timeout` overrides the Runtime setting. Pre-use session replacement preserves the setting; the first Host start attempt freezes server configuration, including on failure. A completed `cc.shutdown()` provides a fresh session for reconfiguration.

The budget applies to native readiness and its direct IPC ping; owner startup fencing also uses the configured duration. Earlier configuration/contract validation and subsequent native cleanup are separate. Expiry does not bypass the existing shutdown barrier, so registration can take longer to return while cleanup completes. See the [configuration guide](../reference/configuration.md#server-startup-timeout).

## Structured failures

Previously, readiness expiry and failed startup were displayed as `config error`, even when the retained cause was a bind I/O failure. Startup expiry now has `CoreError.category == 'lifecycle'` and `CoreError.lifecycle_kind == 'startup_timeout'`, plus `startup_stage` (`readiness`, `responsiveness` or `owner_control`) and `timeout_seconds`. Applications can classify expiry without parsing text. Deadline errors have no fabricated OS cause.

Bind failures keep `io_operation='bind'`, their original `io_kind` and `raw_os_error`; their message no longer carries the incorrect configuration prefix. Real configuration validation remains distinct. The old classification has no alias or fallback.

## Rust surface and protocol boundaries

`RuntimeOptions` gains `server_startup_timeout`; `Runtime::set_server_options` takes that optional duration as its third argument and rejects mutation after the first Host start attempt. `ServerError` and `LifecycleError` expose `StartupTimeout`, with `ServerStartupTimeout`/`ServerStartupStage` metadata. `ServerFailure` preserves that metadata through lifecycle observations, and `Server::reject_start_attempt` accepts the structured failure instead of a string. Recompile low-level Rust consumers and update exhaustive matches and constructors directly.

IPC handshake 12, SHM 3, C/FFI ABI 5, owner-control protocol 1, business frames and CRM hashes are unchanged. Connection observations, owner recovery, identity validation and release ordering retain their existing mechanisms. Historical endpoint directories are not migrated or cleaned.

The existing distribution matrix remains 35 wheels and one sdist. Windows ARM64 covers CPython 3.11, 3.12, 3.13, 3.14 and 3.14t; the other five platform targets retain Python 3.10 as well. Publication is gated on exact-candidate cross-platform validation and installed-wheel checks; build completion alone is not publication evidence.

0.8.1 is now [published on PyPI](https://pypi.org/project/c-two/0.8.1/). All 36 file names, sizes and SHA-256 digests match the verified candidate, including the five Windows ARM64 wheels. Exact source, cross-platform gates, installed-package checks and cleanup are recorded in the [release acceptance report](../acceptance/2026-10-23-081-startup-release-acceptance.md).

# C-Two 0.7.0 / c3 0.3.0 release and upgrade notes

Python `c-two` 0.7.0 and CLI `c3` 0.3.0 provide a coordinated mechanism migration.
Package manifests identify Python
0.7.0 and c3 0.3.0; Rust SDK/Core/TypeScript remain 0.1.0, with no C-Two crates.io
or npm publication.

## Installation and source

Use [Python c-two 0.7.0](https://pypi.org/project/c-two/0.7.0/) together with
[c3 0.3.0](https://github.com/world-in-progress/c-two/releases/tag/c3-v0.3.0).
The Python distribution matrix has 30 wheels and one sdist; c3 targets Windows
x64 and Linux/macOS x86_64/aarch64. Current usage guides explicitly select
0.7.0 / 0.3.0, so a missing release fails instead of selecting the older stack.
Portable FastDB bindings and native Windows IPC already exist in the previous
[0.6.0 release](https://pypi.org/project/c-two/0.6.0/); that version does not
provide the mechanism changes below.

The canonical repository is [world-in-progress/c-two](https://github.com/world-in-progress/c-two).
For an exact release checkout, use the coordinated CLI tag. Its retained
`rc-manifest.json` identifies the actual C-Two and FastDB source inputs:

```bash
git clone --branch c3-v0.3.0 https://github.com/world-in-progress/c-two.git
cd c-two
FASTDB_PAYLOAD_LINK_MODE=source uv sync
FASTDB_PAYLOAD_LINK_MODE=source python tools/dev/c3_tool.py --build --link
```

See the [README development setup](../../README.md#development-checkout) or
[Windows setup](../windows-native-usage.md) for toolchains and interoperability
prerequisites. Use Python extension and c3 builds from the same source checkout.
Historical development artifacts may still report 0.6.0 / 0.2.0, so identify
them by source and hashes rather than version strings alone. FastDB 0.2.1 is officially
published; its immutable native source input is
`4f99f86a662b0e950a0dd29800c25a1c9fca4def`.

## Coordinated download availability

The 0.7 usage guides use Python `c-two==0.7.0` and the
[c3-v0.3.0 release entry](https://github.com/world-in-progress/c-two/releases/tag/c3-v0.3.0).
The release entry provides per-target binaries and SHA-256 sidecars, the Unix
and PowerShell installers, and `rc-manifest.json`. Windows x64 uses
`c3-x86_64-pc-windows-msvc.exe`, its `.sha256` sidecar and `c3-installer.ps1`.
Installers fetched from `latest` receive an explicit 0.3.0 version argument so
their default cannot select a different CLI version.

The published c3 0.2.0 release already provides
`c3-x86_64-pc-windows-msvc.exe` (10,488,320 bytes),
`c3-x86_64-pc-windows-msvc.exe.sha256` and `c3-installer.ps1`. Windows therefore
has a direct executable distribution path, like Linux/macOS. That historical
release is not the companion CLI for the 0.7 runtime. The 0.3.0 candidate
verifies its own bytes, checksums and installers; do not reuse the 0.2.0
size/hash as 0.3.0 evidence.

Canonical main is the development checkout convention. Use the release tag
and `rc-manifest.json` when reproducing published bytes.

## Main changes in the source

### One native local endpoint

Rust `LocalEndpoint::from_address` is the sole OS derivation. Unix automatically
uses `/tmp/c2-<uidhex>/v2.2/<sha>.sock` in a private managed directory, with nonce
gate/marker validation, the original gate inode pinned until listener lease
ownership ends, and retireable endpoint leases. Windows uses current-logon SID
Named Pipes plus a separate non-inheritable listener kernel lease.

The old Unix address mapping and permanent per-address lock paths are removed,
as are `endpoint_protocol`, `C2_IPC_ENDPOINT_PROTOCOL` and `with_protocol`
selectors. Credential `managed-v2` / `named-pipe` values are format metadata,
not configuration choices. SDKs, relay and CLI pass logical addresses to Rust.

### Persistent services and owner-bound children

Default `Persistent` services survive ordinary disconnects and relay idle
connection eviction/reconnect. `OwnerBound` is for a dedicated child whose
entire Runtime belongs to one controller. `cc.owner_control_pair()` and
`cc.spawn_owned_child()` transfer one private inherited receiver; the child
explicitly uses `cc.adopt_owner_stdin()` and
`cc.LifecycleConfig.owner_bound(owner_missing_grace_seconds=...)` before
registration/readiness. EOF stops admission, allows a finite grace period and
starts native drain; the channel cannot reconnect or be taken over.

`cc.shutdown(timeout=...)` observes completion of the native transaction.
`completed=false` preserves the same Session, bindings and pending hooks for
later observation. An IPC admin shutdown ACK only acknowledges initiation.
Listener closure, work drain and held/borrowed payload leases are independent;
closing an endpoint does not release payload leases. See the
[lifecycle integration guide](../local-endpoint-lifecycle.md).

### Exact, scoped maintenance

A runner saves `cc.inspect_endpoint(address)`'s credential after readiness.
After confirming actual child exit with an OS wait, it calls
`cc.reap_endpoint(address, credential)`; stale credentials cannot delete a new
incarnation. Inspection alone does not establish process liveness.

Use `cc.sweep_endpoints(addresses=[this_run_address], max_entries=64, max_ms=10)`
as a context manager, drive `next_batch()` and record completion only at
`round_complete`. Keep scope to addresses selected for this run; interruption
and namespace changes are separate outcomes. Unknown, damaged or partially
initialized objects are conservatively refused. No guarantee covers every
possible crash during registration. Windows cleanup is kernel-managed or
not-applicable. CLI `endpoint` commands project the same authority.

### Lazy pools and finite memory budgets

Buddy reuse/expansion, dedicated SHM and checked chunked IPC remain the transport
model; receiving-side storage can use file spill as its final fallback.
Chunking is byte transport, not a business streaming API, and file fallback is
not guaranteed for every path or resource.

Buddy pools are lazy by default, with no eager buddy mapping.
`pool_prewarm_segments`, `pool_min_retained_segments` and `pool_decay_seconds`
control explicit warmup and idle retention. `pool_enabled=False` skips buddy,
while dedicated SHM, inline/chunks and file fallback remain available; it does
not disable all SHM. Rust owns defaults and validation.

Three finite limits govern SHM backing, file backing and live reassembly:
`shm_backing_budget_bytes`, `file_backing_budget_bytes` and
`live_reassembly_budget_bytes`. Zero rejects positive reservations, rather than
meaning unlimited. Full reassembly capacity and backing stay charged until
actual release, including held owners after runtime shutdown. These units are
not additive process RSS measurements. See the [memory policy](../memory-policy.md).

The standalone `c3 relay` freezes its own upstream IPC policy; Python
`cc.set_client()` does not propagate to that process. Data-plane upstream
connections share its budgets, including across idle eviction/reconnect.
Buddy/budget flags and environment inputs are in the [CLI guide](../../cli/README.md).
Full contract and server/instance identity validation remain mandatory;
ambiguous data-plane failures are not automatically replayed.

### Native ABI and SDK boundary

`c2-mem-ffi` is ABI **3**. Build the Node addon/facade and native library as a
matching set; mismatches are rejected before pool/endpoint function calls.
See the [TypeScript binding guide](../../core/foundation/c2-mem-ffi/bindings/typescript/README.md).

SDKs remain facades over shared Rust Core. Portable values remain official
FastDB `Payload` owners. Held response and borrowed input release invalidate
FastDB owners/checked views before the transport lease. Hold is a lifetime
contract, not proof of zero-copy decoding. Unsafe raw NumPy/pointer aliases
cannot be mechanically revoked; materialize through FastDB before retaining
values beyond the lease.

## Upgrade from 0.6

1. Stop the communicating group deliberately and observe drain completion;
   materialize or release retained payloads as required by the application.
2. Upgrade clients, resource servers and c3 together from the same source or,
   the coordinated 0.7.0 / 0.3.0 releases. Rebuild external
   ABI consumers as matching ABI 3 sets and remove obsolete backend selectors.
3. Restart with logical `ipc://` addresses. Unix 0.6 endpoints under
   `/tmp/c_two_ipc` do not migrate to v2.2; 0.6/0.7 local paths cannot be assumed
   to interoperate. Do not mix an old published relay with new-source hosts.
4. Review finite budgets and lazy/idle settings for the actual workload,
   configuring each application direction and the independent relay process.
   Preserve `Persistent` unless the process is a controller's dedicated child.
5. Update runners to capture credentials after readiness, wait for real child
   exit and use exact reap or bounded sweeps scoped to their own logical addresses.

Historical `/tmp/c_two_ipc` data was **not deleted** by this implementation.
Never infer global cleanup permission from age, PID or failed connection.
Unknown historical objects need a separately scoped maintenance decision.

## Formal release evidence

The release pipeline validates the following gates at one canonical `main`
source commit before promoting its retained bytes:

- The complete **0.7 Python candidate matrix: 30 wheels plus one sdist**,
  with exact public FastDB dependency consumption and isolated installed
  consumers for every declared ABI/platform. The development CPython 3.12
  evidence does not replace this matrix.
- The complete **c3 0.3.0 five-target binary candidate matrix** and
  same-source Windows gates, binding hashes, manifests, installers and
  portable receipts to the actual candidate source and tested bytes.
- Byte-exact promotion to PyPI/GitHub without rebuilding the candidate.
  The CLI release retains the source manifest, hashes and links to the
  candidate and Windows runs; those records identify the formal release
  independently of the earlier development validation above.

Windows 11 desktop, Windows services and a real cross-OS two-machine relay
remain without evidence. Installed hey-my-buddy integration remains unproven.
Browser runtime, C++ SDK, compatibility ranges,
trust/signature/revocation, streaming and post-dispatch retry/deduplication
remain outside this release.

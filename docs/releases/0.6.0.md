# C-Two 0.6.0 / c3 0.2.0 release preparation

This change prepares Python `c-two==0.6.0` and CLI `c3 0.2.0` for the organization repository's `main` branch. A pull request and successful artifact builds do not establish publication. Rust SDK and internal Core crate versions remain `0.1.0`; this change does not introduce a crates.io or npm publishing workflow.

## Changes and migration

The release includes the language-neutral Rust runtime, portable FastDB payload contracts and generated Rust/Python/TypeScript adapters, explicit held/borrowed owner lifetimes, and native Windows IPC. Windows uses byte-mode Named Pipes and current-logon shared mappings; Unix keeps UDS behind the same `c2-local` boundary. Direct `ipc://` calls remain independent of relay discovery.

This is a 0.x clean cut. The portable contract is `c-two.contract.v2`; IPC handshake version 11 and generation-bearing memory handles replace the older wire layout. Upgrade communicating clients, hosts and relays together, and regenerate adapters. Do not mix old native memory bindings with the ABI 2 Node runtime. Legacy call-db and superseded transfer APIs are not supported.

Windows Server 2022/2025 x64 development acceptance is recorded in [the exact-source validation report](../reports/windows-native-final-validation.md). Its tested C-Two revision is `5cf96eafc4674f7961beb15b7a976cfee7f238d0`, before the release version changes. Release workflow execution must separately validate the new package bytes; the old receipts are not evidence for the new versions.

## Windows distribution prerequisite

FastDB 0.2.1 is officially published: `fastdb4py==0.2.1` wheels exist for the standard targets, and this checkout pins `fastdb4py==0.2.1` with Rust `fastdb = "=0.2.1"`. Linux aarch64 and macOS x86_64 have no published wheel; the release-candidate pipeline builds those rows from the exact published, SHA-256-verified sdist inside the row's own interpreter. Deployable application builds — the c3 CLI and the Python native extension — use `FASTDB_PAYLOAD_LINK_MODE=source` and statically link the same immutable FastDB 0.2.1 source; the Core/Rust SDK development contract is separate and links the extracted FastDB Core SDK in system mode via `.github/scripts/prepare_fastdb_sdk.py`. A relocated Python sdist is a packaged consumer: its isolated build repairs the wheel so `libfastdb` is bundled with an `$ORIGIN` runpath and no SDK paths, and the sdist proof records that standalone import and the installed-wheel lifecycle.

The C-Two dependency is exactly `fastdb4py==0.2.1`; publication requires the candidate's 30 ABI rows to prove compatible, non-yanked public-wheel consumption or a build from the verified official sdist for each advertised interpreter. Candidate FastDB wheels built from the verified sdist are retained as dependency proof, never published as C-Two packages. New complete release-candidate evidence for the 0.6.0/0.2.0 versions is still pending on the canonical repository; nothing here claims it has passed.

## Source and environment boundaries

C-Two source builds require the FastDB native payload Core. Application repository builds patch the raw Rust binding to the immutable official FastDB Git revision while the safe binding comes from crates.io. The sibling FastDB checkout supplies interoperability fixtures and TypeScript sources; it is not a package dependency override. A relocated Python sdist includes its Rust path dependencies, but FastDB's packaged binding requires `FASTDB_PAYLOAD_LINK_MODE=system` and an absolute `FASTDB_PAYLOAD_SYSTEM_LIB_DIR` pointing to a matching native Core SDK. A source archive must be tested outside both original checkouts before publication; containing Rust files alone is insufficient.

Native Windows acceptance currently covers CPython 3.12 x64. Windows 11 desktop, Windows services, ARM64, native Windows Python 3.10/free-threaded 3.14 and a real Windows/Linux two-machine relay remain separate targets. Minimum-Python syntax coverage does not establish native wheel coverage. Payload owners enforce checked-view invalidation; this release does not claim direct FastDB response-SHM construction or zero-copy decoding.

The configurable allocator fallback policy discussed separately is not part of this release preparation.

## Exact-tested-candidate promotion

The CLI Release and Python Package Release workflows no longer rebuild on `main`. Both are now promotion pipelines over the byte-exact artifacts retained by the Release Candidate workflow (schema `c-two.release-candidate.v1`: 5 CLI executables, 30 wheels, 1 sdist, separate FastDB proof inputs and source/version metadata). The shared preparer `.github/scripts/promote_release_candidate.py` downloads every candidate artifact ZIP through the authenticated GitHub Actions API, verifies the API SHA-256 digest, extracts through the reviewed safe-ZIP validators, re-hashes the `rc-manifest.json` inventory entry by entry, and re-validates the receipts that bind the tested bytes: the 30 executed ABI rows, 5 lifecycle smokes, 2 Windows standard-user receipts, the sdist inspection/proof, and the 18-row Rust/Python portable matrix plus the 12-row TypeScript real-call receipt from the Windows Native full-scope runs on both `windows-2022` and `windows-2025`.

Promotion triggers on the completion of either gate's `main`-push run and requires both same-source successful runs; the completion that arrives first defers (exit 75), and the late completion promotes. Manual dispatch accepts explicit `candidate_run_id`/`source_sha` inputs plus `dry_run`, and publishing authority exists only on `refs/heads/main` of the canonical repository; the preparer refuses any other ref or repository, and the prepare job always validates with the current `main` workflow code, never the candidate's input SHA. `dry_run` performs the identical read-only verification, including all remote release/registry comparisons, and publishes nothing.

The candidate receipt contract is the reviewed `release-candidate.yml`/`release_candidate.py` surface: ABI rows are `c-two.installed-wheel-smoke.v1` receipts carrying `source_commit_sha`, `row`, `wheel_abi` (interpreter `cp314` with ABI `cp314t` for the free-threaded row), and a FastDB decision bound to the verified published listing and the single retained sdist; lifecycle receipts must prove direct+relay checks, held-view invalidation, four borrowed inputs invalidated, orderly shutdown, and full temporary-directory cleanup. The Windows Native full-scope evidence must carry the complete gate inventory from the trusted runner source with every gate passed and no skipped steps, every internal artifact hash verified against the extracted bytes, the strict 18-row Rust/Python portable matrix and 12-row TypeScript receipts re-validated, and the ordinary and standard-user wheel receipts cross-bound to that gate's own debug `c3` build — which is deliberately never claimed byte-equal to the released candidate executables. Both source pins (the C-Two commit and the frozen FastDB revision `4f99f86a662b0e950a0dd29800c25a1c9fca4def`) must match exactly on both runner images.

Publication only ever uploads the verified staged bytes: the GitHub release keeps the `c3-v*` tag convention (created at the candidate source commit only when the plan says the release is missing, guarded with `--verify-tag` when the tag already exists, never moved), the canonical `c3-installer.sh` and `c3-installer.ps1` installer assets staged by the candidate, the FastDB upstream `fastdb-LICENSE`/`fastdb-THIRD_PARTY_NOTICES.txt` evidence, and `rc-manifest.json` for provenance; a partial existing release is completed with only its missing assets, never recreated or clobbered. PyPI keeps the `python-package-release.yml` filename, the `pypi` environment, and the OIDC trust identity; its staging directory holds exactly the registry-missing files after byte-exact resolution, so a rerun uploads only what is missing and differing bytes, versions, tag sources, or foreign assets fail closed. FastDB dependency-proof inputs are never published as C-Two packages.

Real-GitHub, non-publishing verification of both promotion workflows (event sequencing, deferral, authenticated artifact download, dry-run preparation, and the artifact upload/download staging roundtrip) remains pending until they run on the canonical repository; no live run was executed from this workspace.
